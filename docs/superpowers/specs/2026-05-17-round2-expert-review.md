## 专家 1：数据库/存储工程师 — "数据去哪了、怎么回来的"

### 视角

Agent 系统的所有状态——对话历史、session 元数据、memory 条目、配置快照——都存在某处。存储工程师关心：存在哪？什么格式？怎么迁移？怎么备份？

### 发现

#### 1A. Vector Database 完全空白（Critical）

全书提到 Memory（ch27）和 RAG（附录E/F），但从未讲**向量数据库的实际使用**。读者知道"把记忆转为向量存储"这个抽象概念，但不知道：

- Pinecone / Chroma / pgvector / Qdrant 的选型对比
- 嵌入模型（Embedding Model）的选择：text-embedding-3-small vs voyage vs bge
- 向量检索的 k-NN 参数调优（k 选多少？相似度阈值？）
- 向量存储的索引策略（HNSW、IVF）
- 增量更新 vs 全量重建

#### 1B. Session 持久化格式未讲（High）

ch27 讲了"跨越会话的记忆"但聚焦在 MEMORY.md 文件系统。没有讲：

- Session 本身如何序列化到磁盘
- JSON vs binary（MessagePack）的取舍
- 增量写入 vs 全量写入
- 损坏恢复：如果 session 写到一半断电了？

#### 1C. KV Store 未解释（Medium）

附录E 和 ch27 提到 Anthropic API 的 KV Store，但从未展开：
- KV Store 的 API 格式
- 与文件存储的取舍
- TTL 和过期策略

#### 1D. 数据迁移策略空白（Medium）

Agent 框架升级后，旧 session 格式可能不兼容：
- Schema 版本管理
- 迁移脚本的编写
- 灰度迁移（新旧格式共存期）

## 专家 2：分布式系统工程师 — "当 Agent 不止一个时"

### 视角

第一轮已补充了 CI/CD 和可观测性。但都假设**单实例** Agent。分布式工程师问：当 Agent 框架被部署到 Kubernetes，有 3 个 Pod 同时服务用户时怎么办？

### 发现

#### 2A. 无状态 vs 有状态 Agent 的架构选择（Critical）

全书把 Agent 当作单体应用。但没有讨论：
- Agent 是否应该是无状态的（请求间不共享任何东西）
- 如果需要状态（长对话），状态存在哪（Redis？DB？）
- Sticky Session 的路由策略
- 状态一致性的代价

#### 2B. 子 Agent 的跨进程调度（High）

ch26（Agent 的克隆与协作）聚焦在单进程内的 fork。分布式场景下：
- 子 Agent 运行在哪个节点？
- 消息队列（Redis Bull / SQS）作为 Agent 间的通信媒介
- 子 Agent 的超时和孤儿进程回收
- Work Stealing 负载均衡

#### 2C. 幂等性与 Exactly-Once（High）

工具调用不是幂等的。Bash("rm file.txt") 执行两次结果完全不同。分布式重试时：
- 哪些工具可以安全重试（Read、Grep）
- 哪些工具需要幂等键（Write、Bash、Edit）
- 幂等键的实现（UUID + 结果缓存）

#### 2D. 分布式 Tracing 跨 Agent 边界（Medium）

ch38 补充了单 Agent 的可观测性。分布式场景需要：
- 跨进程 Span 传播（W3C Trace Context）
- Agent-to-Agent 调用的延时归因
- 全链路追踪的可视化

#### 2E. 分布式锁与 Leader Election（Low）

- 定时任务（如 nightly eval）在多 Pod 下只跑一次
- Agent 批量任务的分片执行

## 专家 3：终端 UI / UX 工程师 — "屏幕上的东西用户真的能看懂吗"

### 视角

ch14（屏幕上的每一帧）和 ch19（React 在终端里奔跑）覆盖了渲染机制。但 UX 工程师关心的是**信息设计**，不是渲染管线。

### 发现

#### 3A. 流式输出的 UX 设计模式（High）

全书讲流式输出的"怎么实现"（SSE、AsyncGenerator），但没讲"怎么展示才不让人困惑"：

- 闪烁问题：快速更新的文本如何不抖动
- 部分内容撤回：模型改了主意，之前显示的文字如何优雅修正
- 长输出截断：100 行工具输出如何折叠为 "Show more..."
- 流式代码块：markdown 代码块在流式中的渲染（开始和结束不同步）

#### 3B. 终端无障碍（Medium）

- 屏幕阅读器（VoiceOver / JAWS）如何读取终端输出
- 色盲友好的色彩方案
- 高对比度模式
- 键盘导航的完整性（Tab、Arrow、Esc 的行为约定）

#### 3C. Progress 与等待体验（Medium）

Agent 在"思考"时可能 5-30 秒无输出：
- Spinner 动画的不同状态（thinking / executing / waiting for user）
- 预估剩余时间（基于历史平均值）
- 部分结果提前展示（"我已经找到了 3 个相关文件，正在分析..."）

#### 3D. 错误信息的人性化设计（Low）

- API 错误 → 用户能看懂的中文解释
- 权限错误 → 清晰的下一步操作指引
- 网络错误 → 自动重试的进度提示

## 专家 4：编程语言 / 类型系统专家 — "TypeScript 的保护伞哪里漏雨"

### 视角

ch41（为什么是 TypeScript）、附录A（TypeScript 速成）、附录B（Java 迁移）覆盖了 TS 基础。语言专家找类型系统的边界。

### 发现

#### 4A. Effect System 的缺失（High）

Agent 的核心操作——读文件、发网络请求、修改状态——都是**副作用（Effect）**。TypeScript 没有 Effect System（不像 Haskell 的 IO Monad 或 Rust 的 ownership），副作用是隐式的。

结果是：你无法从函数签名看出一个函数是否有副作用。`Tool.call()` 可能读文件，也可能不读。

如何弥补：
- 约定：所有副作用函数标注 `async`
- 架构约束：副作用集中在 Tool 层，AgentLoop 层不直接做 I/O
- 讨论 `Effect` 库（effect-ts）的可能性

#### 4B. 结构化类型的安全漏洞（Medium）

TypeScript 的结构化类型让"长得像"就等于"是"：

```typescript
type ApiKey = string & { __brand: "ApiKey" }
type UserId = string & { __brand: "UserId" }
// 编译时安全，运行时全是 string
```

这意味着运行时没有真正的类型安全。Zod 弥补了一部分（API 边界），但内部仍然依赖约定。

#### 4C. Recursive Type 的陷阱（Medium）

Agent 的消息结构是递归的（消息里有工具结果，工具结果里有消息）。TypeScript 的递归类型在某些深度下 infer 失败：

```typescript
type Message = {
  content: ContentBlock[]
}
type ContentBlock = TextBlock | ToolResultBlock
type ToolResultBlock = {
  content: string | ContentBlock[]  // 递归
}
```

实际遇到过的问题和解决策略。

#### 4D. 错误类型的穷举（Low）

Discriminated Union + `never` 检查确保错误类型被穷举处理。Agent 框架中应该在哪些地方使用这个模式。

### 滚雪球传递给专家 5

> "类型专家指出 Effect 是不可见的 → ML 研究员，模型本身的'黑箱效应'比代码的副作用更不可见。你们怎么处理不可见性？"

## 专家 5：ML/AI 研究员 — "模型内部不是魔法，但我们确实不完全理解它"

### 视角

全书以 Claude Code 的工程实现为中心。ML 研究员问：模型本身的特性如何影响工程决策？有哪些工程选择是被模型行为驱动的？

### 发现

#### 5A. Temperature 与 Agent 行为的系统性分析（Critical）

全书只在附录E 提了一句 temperature。但 temperature 对 Agent 的行为有巨大影响：

- temperature=0：确定性，适合评估和测试。但 Agent 可能陷入重复循环
- temperature=0.3-0.5：日常使用的最佳范围。有一定创造力但不会跑偏
- temperature=0.7-1.0：创意任务。Agent 可能产生意外行为（好或坏）

温度与工具调用的关系——高温度下，模型可能"不想"用工具，或者用了"奇怪"的参数。

#### 5B. 采样参数 (top_p / top_k) 从未展开（High）

全书没有解释这两个参数对 Agent 行为的影响：
- top_p=0.9 vs top_p=1.0 的工具选择差异
- top_k 与工具参数的多样性
- 不同任务类型的最佳采样配置

#### 5C. Hallucination 检测策略（High）

Agent 最大的失败模式之一是 hallucination——模型说有 bug 但其实没有，说改了但其实没改。全书没有系统讲：

- 幻觉检测：要求模型引用源码行号，然后验证
- 幻觉预防：在 system prompt 中嵌入"不确定时请说明"的指令
- 幻觉恢复：当工具结果与模型的断言矛盾时，如何纠正

#### 5D. 本地模型与 Ollama（Medium）

卷五构建的 Agent 框架假设调用 Anthropic API。但对于开源模型：
- Ollama / llama.cpp / vLLM 的接入方式
- OpenAI-compatible API 的适配
- 本地模型的局限（context window 更小、工具调用不稳定）
- 什么时候用本地模型、什么时候用云端

#### 5E. Embedding 与相似度（Medium）

与专家 1 的向量数据库空白呼应：
- 嵌入向量的语义：为什么 "bug" 和 "error" 在向量空间中接近
- 相似度度量的选择：cosine vs euclidean vs dot product
- Embedding 模型的对比和选择

#### 5F. Prompt Engineering 系统工程（Low）

全书各处散落了 prompt 片段，但没有成体系的 Prompt Engineering：
- Chain of Thought、Few-Shot、ReAct 等策略
- 如何迭代优化 system prompt（A/B 测试在附录H 有，但方法论没有）
- Prompt 长度与效果的 U 型曲线

## 专家 6：SRE / 平台工程师 — "凌晨 3 点谁被叫醒"

### 视角

全书在本地开发视角下写。SRE 问：Agent 跑在生产环境，凌晨 3 点出故障，谁处理？怎么处理？

### 发现

#### 6A. Graceful Shutdown 与状态保存（Critical）

Agent 在执行长任务时被 SIGTERM（K8s pod eviction），会发生什么？

- 当前 turn 的工具执行被中断
- 对话历史是否已持久化？
- 重启后能否从断点继续？

全书没有讲 graceful shutdown 的设计。Agent 框架需要：
- SIGTERM 信号处理
- 当前状态快照保存
- 恢复机制（重启后从快照继续 vs 放弃当前任务）

#### 6B. 健康检查与就绪探针（High）

Kubernetes 需要 `/health` 和 `/ready` 端点：
- `/health`：进程活着
- `/ready`：API key 有效、MCP Server 已连接、模型可访问
- Agent 特有健康指标：最近一次 API 调用是否成功

#### 6C. 熔断器模式（High）

当 API 连续失败时，不应该继续尝试——应该"熔断"：

```typescript
// 熔断器三态：CLOSED → OPEN → HALF_OPEN → CLOSED
//                   连续N次失败   等待X秒后尝试一个请求
```

#### 6D. 日志轮转与保留（Medium）

Agent 产生的日志量可能很大（每个 turn 多条日志）。需要：
- 日志轮转策略（按大小 / 按时间）
- 保留策略（调试日志 7 天、审计日志 90 天）
- PII（个人身份信息）在日志中的处理

#### 6E. 告警阈值与 Runbook（Medium）

附录 G 有指标，附录H 有 CI。但缺：
- 告警阈值具体数值（错误率 > 5%？还是 > 10%？）
- 告警升级策略（先通知谁、多久无响应后升级）
- Incident Runbook 模板

#### 6F. 灾难恢复演练（Low）

- 如果 Anthropic API 宕机 4 小时，Agent 怎么办？
- 如果 MCP Server 全部不可用，Agent 能降级到什么程度？
- 备份恢复的时间目标（RTO）和数据目标（RPO）

## 专家 7：产品经理 / 用户体验研究员 — "读者/用户到底需要什么"

### 视角

全书是技术书，以 "你" 为叙事视角。产品经理问：这本书的实际用户旅程是什么？有哪些痛点没有被覆盖？

### 发现

#### 7A. 各卷之间的"为什么升级"动机不足（High）

当前各卷边界有过渡句（"你现在从读者变成工匠"），但缺少**升级动机的具体说明**：

- 卷零→卷一：只是说"现在开始追踪"。应该给一个不能跳过的理由：如果你跳过卷一，后面你会看不懂 ch26 的 fork 机制
- 卷三→卷四：只是说"从怎么做变成为什么"。应该给一个案例：一个看似正确的设计在什么场景下会出问题，而卷四能让你预见这些问题

#### 7B. 缺少 "Debugging Story" 贯穿案例（High）

整本书没有一条贯穿的 "Bug 故事"。就像《网络是怎么连接的》有一个贯穿全书的"浏览器输入 URL"场景一样，本书应该有一个从 ch01 到 ch66 反复出现的具体例子，让读者在不同卷看到同一个问题的不同层次。

建议：选一个真实的 Claude Code bug（比如"Agent 在某个场景下会死循环"），在每一卷从不同的视角看这个 bug：
- 卷零：用户报告"Agent 好像卡住了"
- 卷一：追踪这个 bug 的请求流
- 卷二：深入死循环的 root cause（工具选择逻辑）
- 卷三：动手修复这个 bug
- 卷四：讨论为什么会设计成可能死循环（agentic loop 的退出条件设计权衡）
- 卷五：在你的框架中实现更好的退出检测

#### 7C. "技术全景图"在每卷开头缺失（Medium）

当前每卷开头没有一张本卷的知识全景图。读者不知道本卷会覆盖哪些概念、概念之间的依赖关系。
卷零有图（第 1 章的三组成部分），但后续各卷没有卷级全景图。

#### 7D. 常见错误的预防性提示不足（Medium）

每章有"常见错误"表，但都是**事后诊断**。缺少**事前预防**：
- "在修改 X 之前，先确保 Y 是正常的"
- "最容易浪费时间的 3 个方向是..."
- "如果你看到 Z，90% 的情况是 W 的问题，不是你的代码问题"

## 专家 8：教学 / 课程设计师 — "读者真的学会了吗"

### 视角

全书有"试试看"和"检查点"，但从教学设计角度看，这些练习的效果如何？知识留存率如何？

### 发现

#### 8A. 练习的层次只有两级（High）

当前"试试看"分"基础级"和"进阶级"两级。但实际读者群体更分散：

| 读者 | 需要什么 |
|------|---------|
| 只看不做的读者 | 能通过阅读理解概念 |
| 跟着敲的读者 | 有可复制粘贴的代码 |
| 想深入理解的读者 | 开放式问题，没有标准答案 |
| 想验证自己的读者 | 有标准答案的练习，可自评 |

建议加第三级：**挑战级**。没有步骤指引，只给目标。

#### 8B. "检查点"缺少自我评估机制（Medium）

当前检查点是 checklist 格式。但读者无法判断"我理解到哪个程度了"。

建议加：
- 每个检查点的自评等级（"我能解释给同事听" > "我能自己写出来" > "我读代码能看懂" > "我读描述能理解"）
- 少量选择题（每卷 5 题），测试概念理解

#### 8C. 概念密度曲线不平滑（Medium）

某些章的概念密度特别高（ch04 — 8 个新概念），某些章特别低。教学设计上应该更均匀地分布认知负荷。

#### 8D. 缺乏"间隔重复"机制（Low）

教学设计的一个基本原则是间隔重复——一个概念在不同时间点反复出现，每次都加深一层。

当前书是线性结构，一个概念出现一次就过去了。可以考虑：
- 在后续章节的"知识补全"中故意回顾前面学过的概念
- 每卷末尾有一个"本卷概念在后续卷中的出现预告"

### P0-2: Temperature/采样参数与Agent行为（ch52.6 或扩展 ch52.5）

```
## 第 N 节：采样参数 — Agent 行为的隐藏维度

### Temperature 的 Agent 行为影响
- 0.0: 确定性。工具选择稳定，但可能陷入重复模式
- 0.3: 最佳工具使用。足够创造力，不太会跑偏
- 0.7: 创意代码生成。工具参数可能"有创意"
- 1.0: 不可预测。Agent 可能拒绝用工具

### top_p 与工具选择多样性
- top_p=0.9 → 工具选择集中在高概率选项
- top_p=1.0 → 低概率工具也有机会被选

### 不同任务的推荐配置
| 任务 | temp | top_p | 原因 |
|------|------|-------|------|
| Bug 修复 | 0.1 | 0.9 | 需要精确 |
| 代码生成 | 0.3 | 0.95 | 需要创造力 |
| 安全审查 | 0.0 | 0.9 | 不能有幻觉 |
| 头脑风暴 | 0.7 | 1.0 | 需要多样性 |

### 评估中的采样固定
- 评估时 temperature=0（确保可复现）
- 但零温度下的表现 ≠ 实际使用的表现
```
