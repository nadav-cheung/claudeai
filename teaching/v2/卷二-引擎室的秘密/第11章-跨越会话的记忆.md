# 第11章：跨越会话的记忆

你今天下午跟 Claude Code 配合得天衣无缝。它知道你是个后端工程师，习惯用 Go，正在调试一个支付模块。你们一起修了三个 bug，重构了两处代码。

然后你关上电脑，回家吃晚饭。

第二天早上你打开终端，重新启动 Claude Code。它还记得你是谁吗？还记得你昨天在做什么吗？

答案是：**记得**，但不是靠魔法。靠的是一套精巧的文件系统——**跨会话记忆（cross-session memory）**。

这一章，我们打开 Claude Code 的记忆仓库，看看信息是怎么存进去、怎么被找到、怎么在新会话里发挥作用的。

---

## 这是什么

想象你在一家咖啡馆有个固定座位。你不是每次去都重新跟服务员自我介绍的——你有一张会员卡，上面记着你的名字、你的偏好、你上次点了什么。服务员看你来了，扫一眼会员卡，就知道该怎么服务你。

Claude Code 的记忆系统就是这张"会员卡"。

但跟简单的会员卡不同，Claude Code 的记忆分两个层次：

**第一层：会话记忆（Session Memory）**——只在**单次会话**内有效。你打开 Claude Code 开始对话，系统在后台悄悄记录你们的对话要点。当对话太长需要压缩时（还记得上一章的 compaction 吗？），这些记录就派上用场了。会话记忆存在 `~/.claude/projects/<项目路径>/<session-id>/session-memory/summary.md`，每个会话一份，对话结束就完成使命。

**第二层：持久记忆（Auto Memory）**——跨越会话边界，**永远存在**。你告诉 Claude Code "我是数据科学家"或者"别用 mock，直接测真实数据库"，这些信息被写成独立的 Markdown 文件，存在 `~/.claude/projects/<项目路径>/memory/` 目录下。下次你开新会话，Claude Code 自动加载这些文件，仿佛昨天的事从来没忘过。

两层记忆各司其职：会话记忆帮你应对超长对话，持久记忆帮你跨越会话鸿沟。两层叠加，Claude Code 就既能记住"刚才聊了什么"，又能记住"一直以来你是什么样的人"。

## 打开源码

记忆系统的代码分散在几个目录里，每个目录负责记忆生命周期的不同阶段：

```
src/memdir/                          -- 持久记忆的核心目录
  paths.ts                           -- 记忆文件路径计算（getAutoMemPath）
  memoryTypes.ts                     -- 四种记忆类型定义（user/feedback/project/reference）
  memoryScan.ts                      -- 扫描记忆文件、解析 frontmatter
  memoryAge.ts                       -- 记忆新鲜度计算（"3 days ago"）
  findRelevantMemories.ts            -- 根据用户查询找到相关记忆
  memdir.ts                          -- 构建记忆系统的提示词、加载 MEMORY.md

src/services/SessionMemory/          -- 会话记忆服务
  sessionMemory.ts                   -- 后台提取会话记忆的入口
  sessionMemoryUtils.ts              -- 提取阈值判断、配置管理
  prompts.ts                         -- 会话记忆的模板和更新提示词

src/services/extractMemories/        -- 后台记忆提取 Agent
  extractMemories.ts                 -- 对话结束时提取持久记忆
  prompts.ts                         -- 提取记忆的提示词模板
```

文件不少，但不用怕——我们按照记忆的**生命周期**来读：创建 -> 存储 -> 索引 -> 加载 -> 使用 -> 更新。

## 它怎么工作

### 第一步：记忆从哪里来

Claude Code 的持久记忆不是凭空产生的，它有三个来源：

**来源 A：主 Agent 直接写入。** 你在对话中说"我是个 Go 程序员，第一次碰 React"，Claude Code 的系统提示词里就有指导：遇到这种情况，写入一条 `user` 类型的记忆文件。主 Agent 在正常对话中直接调用 Write 工具保存。

**来源 B：后台提取 Agent。** 这是最主要的来源。每次对话结束（AI 生成最终回复、没有更多工具调用时），系统会悄悄启动一个后台 Agent——`extractMemories`。它像个小助手，读完整个对话记录，挑出值得记住的内容，写成记忆文件。

看 `src/services/extractMemories/extractMemories.ts`（约第 296-523 行）：

```typescript
// 初始化记忆提取系统
export function initExtractMemories(): void {
  // 每次提取后的游标位置
  let lastMemoryMessageUuid: string | undefined
  // 是否正在执行中（防止并发）
  let inProgress = false
  // 上一次提取后经过的轮次
  let turnsSinceLastExtraction = 0

  async function runExtraction({
    context,
    appendSystemMessage,
    isTrailingRun,
  }): Promise<void> {
    // 如果主 Agent 已经写了记忆，跳过这次提取
    if (hasMemoryWritesSince(messages, lastMemoryMessageUuid)) {
      return
    }

    // 扫描已有记忆文件，构建清单
    const existingMemories = formatMemoryManifest(
      await scanMemoryFiles(memoryDir, signal),
    )

    // 启动后台 Agent 执行提取
    const result = await runForkedAgent({
      promptMessages: [createUserMessage({ content: userPrompt })],
      cacheSafeParams,
      canUseTool,
      querySource: 'extract_memories',
      maxTurns: 5,  // 最多 5 轮，防止跑偏
    })
  }
}
```

后台 Agent 使用 `runForkedAgent`——这是我们在第 10 章见过的 fork 模式。它共享主 Agent 的提示缓存，但只能操作记忆目录里的文件（通过 `createAutoMemCanUseTool` 做权限隔离）。

**来源 C：用户手动写入。** 你可以运行 `/memory` 命令打开编辑器，直接创建或编辑记忆文件。

### 第二步：四种记忆类型

不是什么都值得记住。Claude Code 把记忆严格分为四类，定义在 `src/memdir/memoryTypes.ts`（约第 14-19 行）：

```typescript
export const MEMORY_TYPES = [
  'user',       // 用户画像
  'feedback',   // 行为反馈
  'project',    // 项目状态
  'reference',  // 外部参考
] as const
```

每种类型都有明确的使用场景：

| 类型 | 存什么 | 例子 |
|------|--------|------|
| `user` | 用户的角色、偏好、知识背景 | "用户是数据科学家，正在调查日志系统" |
| `feedback` | 用户纠正 AI 的行为方式 | "不要 mock 数据库——上次被 mock 坑惨了" |
| `project` | 项目当前的工作状态、截止日期 | "周四后冻结合并，移动团队在切发布分支" |
| `reference` | 外部系统的指针 | "pipeline bug 在 Linear 的 INGEST 项目里追踪" |

关键设计决策：**代码模式、架构、文件路径这些能从代码直接读到的信息，不应该存为记忆。** 记忆只保存那些无法从当前项目状态推导出来的信息。这样避免了记忆和代码的重复，也减少了过期记忆带来的问题。

每条记忆文件都使用 YAML frontmatter 格式：

```markdown
---
name: user-role
description: 用户是数据科学家，关注可观测性
type: user
---

用户是数据科学家，目前正在调查项目中已有的日志和监控系统。
对 Python 数据分析工具链非常熟悉，但对前端代码不太了解。
```

### 第三步：MEMORY.md 索引系统

记忆文件越来越多，怎么快速找到相关的？Claude Code 用了一个简单但有效的方案——**索引文件 `MEMORY.md`**。

`MEMORY.md` 不是记忆内容本身，而是一个**目录索引**。每条记忆写入时，都会在 `MEMORY.md` 里添加一行指针：

```markdown
- [用户角色](user_role.md) — 数据科学家，关注可观测性
- [测试策略](feedback_testing.md) — 必须用真实数据库，禁止 mock
- [移动端发布冻结](project_merge_freeze.md) — 2026-03-05 后冻结非关键合并
```

这个索引文件在会话启动时被完整加载到系统提示词中（最多 200 行、25KB），所以 Claude Code 一"睁眼"就能看到所有记忆的标题和摘要。需要深入某个记忆时，再按指针去读完整文件。

索引的大小有严格限制。看 `src/memdir/memdir.ts`（约第 35-38 行）：

```typescript
export const MAX_ENTRYPOINT_LINES = 200
export const MAX_ENTRYPOINT_BYTES = 25_000
```

超出了？截断，并附上警告：

```typescript
// src/memdir/memdir.ts，约第 57-103 行
```

### 第四步：按需召回——findRelevantMemories

光有索引还不够。用户提出一个新问题时，Claude Code 怎么知道哪些记忆跟当前问题相关？

答案在 `src/memdir/findRelevantMemories.ts`（约第 39-75 行）。它用了一个聪明的两步策略：

```typescript
export async function findRelevantMemories(
  query: string,        // 用户当前的问题
  memoryDir: string,    // 记忆目录路径
  signal: AbortSignal,
): Promise<RelevantMemory[]> {
  // 第一步：扫描所有记忆文件的 frontmatter
  const memories = await scanMemoryFiles(memoryDir, signal)

  // 第二步：让 AI 从所有记忆中选出最相关的 5 条
  const selectedFilenames = await selectRelevantMemories(
    query, memories, signal,
  )

  return selected  // 最多返回 5 条相关记忆
}
```

`selectRelevantMemories` 调用了一次轻量级的 AI 请求（用 Sonnet 模型），把用户的查询和所有记忆的清单交给 AI，让它选出最相关的 5 条。这个选择过程用的是 `sideQuery`——一种不污染主对话的旁路查询。

### 第五步：记忆的新鲜度

记忆不是永恒的真理。一个月前存的项目状态，可能早就过时了。

`src/memdir/memoryAge.ts`（约第 6-20 行）处理了这个问题：

```typescript
export function memoryAgeDays(mtimeMs: number): number {
  return Math.max(0, Math.floor((Date.now() - mtimeMs) / 86_400_000))
}

export function memoryAge(mtimeMs: number): string {
  const d = memoryAgeDays(mtimeMs)
  if (d === 0) return 'today'
  if (d === 1) return 'yesterday'
  return `${d} days ago`
}
```

超过一天的记忆会自动附上新鲜度警告（约第 33-42 行）：

```typescript
export function memoryFreshnessText(mtimeMs: number): string {
  const d = memoryAgeDays(mtimeMs)
  if (d <= 1) return ''
  return `This memory is ${d} days old. ` +
    `Memories are point-in-time observations, not live state — ` +
    `claims about code behavior or file:line citations may be outdated.`
}
```

这不是把记忆删掉，而是给主 Agent 加了个提醒："这条记忆可能过时了，用之前先验证。"

### 第六步：会话记忆——单次对话的笔记

除了跨会话的持久记忆，Claude Code 还有一个**会话记忆**系统，专门服务于单次对话内的 compaction（我们在上一章详细讲过）。

会话记忆的核心在 `src/services/SessionMemory/sessionMemory.ts`。它的工作方式很巧妙——在后台悄悄运行一个 forked Agent，实时提取对话要点，写入 `summary.md`。

触发条件在 `sessionMemory.ts`（约第 134-181 行）：

```typescript
export function shouldExtractMemory(messages: Message[]): boolean {
  const currentTokenCount = tokenCountWithEstimation(messages)

  // 还没初始化过？检查是否达到了最低 token 阈值
  if (!isSessionMemoryInitialized()) {
    if (!hasMetInitializationThreshold(currentTokenCount)) {
      return false
    }
    markSessionMemoryInitialized()
  }

  // 检查 token 增长是否达到更新阈值
  const hasMetTokenThreshold = hasMetUpdateThreshold(currentTokenCount)

  // 检查工具调用次数是否达到阈值
  const hasMetToolCallThreshold =
    toolCallsSinceLastUpdate >= getToolCallsBetweenUpdates()

  // 两个条件满足其一即可触发
  // 或者：最后一个 assistant 消息没有工具调用（自然对话间隙）
  const shouldExtract =
    (hasMetTokenThreshold && hasMetToolCallThreshold) ||
    (hasMetTokenThreshold && !hasToolCallsInLastTurn)

  return shouldExtract
}
```

会话记忆的内容有固定的模板结构（`src/services/SessionMemory/prompts.ts`，约第 11-41 行）：

```markdown
# Session Title
# Current State          <-- 最重要：当前正在做什么
# Task specification
# Files and Functions
# Workflow
# Errors & Corrections
# Codebase and System Documentation
# Learnings
# Key results
# Worklog
```

每个章节有 2000 token 的上限，总文件不超过 12000 token。超出就截断——保留最重要的部分。

### 完整的生命周期

把上面的步骤串起来，一条记忆的完整生命周期是：

```
用户说话 → 主 Agent 判断是否值得记住
                    ↓ 是
          写入记忆文件（frontmatter + 内容）
                    ↓
          更新 MEMORY.md 索引
                    ↓
    对话结束 → 后台 Agent 扫描遗漏
                    ↓
    下次会话启动 → 加载 MEMORY.md 索引
                    ↓
    用户提问 → findRelevantMemories 选出相关记忆
                    ↓
    注入主 Agent 的上下文 → AI 参考记忆回答问题
                    ↓
    记忆过期 → 自动标注新鲜度警告
```

## 深入机制：CLAUDE.md 加载流程

记忆系统的核心入口是 `getUserContext()`，它负责把所有 CLAUDE.md 文件的内容加载、拼接、注入到 AI 的系统提示词中。整个过程分六步：

```
getUserContext()
  │
  ├── 1. 收集所有 CLAUDE.md 路径
  │     ├── getManagedClaudeRulesDir() → Managed 级别
  │     ├── getUserClaudeRulesDir()    → User 级别
  │     └── 从 CWD 向上遍历到根目录：
  │         ├── CLAUDE.md
  │         ├── .claude/CLAUDE.md
  │         └── .claude/rules/*.md
  │
  ├── 2. 解析每个文件
  │     ├── 读取文件内容
  │     ├── 解析 frontmatter（如有）
  │     │     ├── 检测 agent 类型（仅对特定 agent 可见）
  │     │     ├── 检测 MCP 服务器定义
  │     │     └── 检测 hooks 定义
  │     ├── 处理 @include 指令
  │     └── 防止循环引用（已处理文件追踪）
  │
  ├── 3. 按优先级排序
  │     └── 近 CWD 的文件排在后面 → 模型更关注
  │
  ├── 4. 检查文件大小
  │     └── MAX_MEMORY_CHARACTER_COUNT = 40,000 字符
  │         └── 超出时截断并警告
  │
  ├── 5. 触发 InstructionsLoaded hooks
  │     └── executeInstructionsLoadedHooks()
  │
  └── 6. 返回 { claudeMd: "所有文件内容拼接" }
```

六步走完，所有指令文本被拼接成一个字符串，作为系统提示词的一部分注入到每次 API 调用中。

### @include 指令支持

CLAUDE.md 文件里可以用 `@` 语法包含外部文件，规则如下：

| 语法 | 含义 | 例子 |
|------|------|------|
| `@path` | 相对路径 | `@docs/coding-style.md` |
| `@./path` | 相对路径（显式） | `@./team/conventions.md` |
| `@~/path` | 用户 Home 目录 | `@~/.config/shared-rules.md` |
| `@/path` | 绝对路径 | `@/etc/claude-code/defaults.md` |

三条约束：
- `@include` 只在**叶文本节点**生效，不在代码块内工作
- 已处理的文件会被追踪，**防止循环引用**
- 引用的文件如果不存在，**静默忽略**（不报错）

支持加载的文件扩展名包括 `.md`、`.txt`、`.json`、`.yaml`、`.yml`、`.toml`、`.js`、`.ts`、`.py`、`.sh` 等文本格式——不会意外加载二进制文件。

### Session Memory 完整模板

会话记忆的模板定义在 `src/services/SessionMemory/prompts.ts` 中，一共九个固定章节：

```markdown
# Session Title
_A short and distinctive 5-10 word descriptive title for the session._

# Current State
_What is actively being worked on right now? Pending tasks not yet completed._

# Task specification
_What did the user ask to build? Any design decisions or other explanatory context._

# Files and Functions
_What are the important files? In short, what do they contain and why are they relevant?_

# Workflow
_What bash commands are usually run and in what order? How to interpret their output?_

# Errors & Corrections
_Errors encountered and how they were fixed. What approaches failed and should not be tried again?_

# Codebase and System Documentation
_What are the important system components? How do they work/fit together?_

# Learnings
_What has worked well? What has not? What to avoid?_

# Key results
_If the user asked a specific output such as an answer to a question, a table, or other document, repeat the exact result here._
```

**Current State** 是最关键的章节——compaction 之后 AI 恢复对话时，首先看的就是这里。模板的总大小限制为 12000 token，每个章节上限 2000 token，超出就截断。

## 对比Java

如果你熟悉 Java，你可能会想：这跟 Java 的持久化有什么区别？

**Java 的方案：序列化 + 数据库**

在 Java 世界里，"跨会话记忆"通常意味着以下几种技术：

```java
// 方案一：Java 序列化
public class UserPreferences implements Serializable {
    private String role;
    private List<String> preferences;
}
// 用 ObjectOutputStream 写入文件，用 ObjectInputStream 读回来
```

```java
// 方案二：Properties 文件
// config.properties
user.role=data-scientist
feedback.no-mock=true
```

```java
// 方案三：数据库
// JDBC → INSERT INTO memories (type, content) VALUES (?, ?)
// 或者用 JPA/Hibernate 做 ORM 映射
```

**Claude Code 的方案：纯 Markdown 文件**

Claude Code 完全不使用数据库或二进制序列化。它用 Markdown + YAML frontmatter 存储一切。

为什么？因为这个系统的"读者"不是程序，而是 **AI 模型**。AI 天生就理解 Markdown。不需要 ORM 映射，不需要 SQL 查询，不需要反序列化——直接读文本就行。

| 维度 | Java 序列化/数据库 | Claude Code 记忆 |
|------|-------------------|-----------------|
| 存储格式 | 二进制 / SQL 行 | Markdown 文本 |
| 读取方式 | ObjectInputStream / SQL 查询 | AI 直接阅读 |
| 查询方式 | 精确 SQL WHERE | AI 语义匹配 |
| Schema | 预定义表结构 | 自由文本 + frontmatter |
| 索引 | 数据库索引 | MEMORY.md 人工索引 |
| 过期处理 | 手动 DELETE | 新鲜度标注 + AI 自行判断 |

最大的区别在**查询**。Java 用精确的条件查询（`SELECT * FROM memories WHERE type = 'feedback'`），而 Claude Code 用 AI 做语义匹配——它"理解"你的问题，然后选出最相关的记忆。这意味着即使你提问的方式和记忆的描述不完全匹配，AI 也能建立关联。

另一个有趣的对比是**Schema 灵活性**。Java 的数据库需要预先定义好表结构（alter table 加字段是个大工程），而 Claude Code 的记忆文件完全是自由文本。你可以在 frontmatter 里加任何字段，不影响已有记忆的读取。

当然，代价也是有的：没有严格的类型检查，没有事务保证，查询效率取决于 AI 的判断力。但对于"给 AI 编程助手做记忆"这个场景，简单和灵活远比严谨和高效重要。

## 你能改什么

理解了记忆系统的工作原理，你可以做这些定制：

### 1. 手动管理记忆

运行 `/memory` 命令会打开一个文件选择器，让你直接创建、编辑或删除记忆文件。如果你想确保某条信息被记住，这是最直接的方式。

### 2. 自定义会话记忆模板

会话记忆的模板支持自定义。把你的模板放在 `~/.claude/session-memory/config/template.md`。如果你发现默认的章节结构不符合你的工作流，可以改成自己的风格——比如加一个 "Design Decisions" 章节，或者去掉你不需要的 "Workflow" 章节。

同样，更新提示词也可以自定义，放在 `~/.claude/session-memory/config/prompt.md`。支持 `{{currentNotes}}` 和 `{{notesPath}}` 变量替换。

### 3. 控制记忆存储位置

默认情况下，记忆存在 `~/.claude/projects/<项目路径>/memory/`。你可以通过设置修改这个路径：

```json
// 在 settings.json 中
{
  "autoMemoryDirectory": "~/my-custom-memory-dir"
}
```

或者通过环境变量覆盖（通常由 SDK 调用方使用）：

```bash
export CLAUDE_COWORK_MEMORY_PATH_OVERRIDE=/path/to/custom/memory
```

### 4. 完全关闭记忆

如果你不想要自动记忆功能，可以关闭：

```json
// settings.json
{
  "autoMemoryEnabled": false
}
```

或者用环境变量：

```bash
export CLAUDE_CODE_DISABLE_AUTO_MEMORY=1
```

### 5. 添加新的记忆类型

如果你深入研究 `memoryTypes.ts`，你会发现四种记忆类型是通过常量数组定义的。虽然直接修改源码添加新类型需要重新构建，但你可以通过在 frontmatter 中省略 `type` 字段来创建"无类型"记忆——系统对缺失的 type 字段有优雅降级处理。

### 6. 搜索历史会话

记忆目录和会话记录（JSONL 格式）都存在 `~/.claude/projects/` 下。你可以用 grep 直接搜索所有历史对话和记忆：

```bash
# 搜索所有记忆文件中的关键词
grep -rn "支付模块" ~/.claude/projects/*/memory/ --include="*.md"

# 搜索历史会话记录
grep -rn "支付模块" ~/.claude/projects/ --include="*.jsonl"
```

系统提示词里也内置了这段指导，让 Claude Code 自己能在需要时搜索过去的对话记录。
