# 第07章：安全门卫

上一章你看到了工具执行引擎——AI 说"执行这个命令"，引擎就调用 BashTool，命令就跑了。但你有没有注意到，有时候命令直接就执行了，有时候终端底部却弹出一个提示："Claude 想要运行 `npm install`，是否允许？"

是谁在拦住那些命令？是谁在说"这个可以放行"或者"这个必须问一下用户"？

这个角色叫做**权限系统**。它就像一栋大楼的门卫——每天有无数人（工具调用）要进出，门卫得快速判断：这个人有通行证吗？是老熟人可以直接放行？还是得请示一下上级（用户）？又或者这个人根本不该出现在这里？

这一章，我们走进门卫室，看看它是怎么做决定的。

---

## 这是什么

想象你在一家科技公司上班。公司里有一个安全门卫系统，规则是这样的：

1. **黑名单上的人**——直接拒绝，不用多说。
2. **白名单上的人**——直接放行，一路绿灯。
3. **既不在黑名单也不在白名单**——请示上级，让领导决定。

Claude Code 的权限系统就是这样一个三层决策机制。每当 AI 要执行一个工具——不管是读文件、写文件还是跑命令——系统都会先问一句话："这个操作有权限吗？"

答案有三种：

- **`allow`**（允许）——直接执行，不打扰用户。
- **`deny`**（拒绝）——直接拦下，告诉 AI "不行"。
- **`ask`（询问）——弹出一个提示，让用户来拍板。

这三种行为定义在 `src/types/permissions.ts`（约第 44 行）：

```typescript
// 文件：src/types/permissions.ts，约第44行
export type PermissionBehavior = 'allow' | 'deny' | 'ask'
```

就这么简单。三个单词，撑起了整个安全体系。

## 打开源码

权限系统的核心代码在 `src/utils/permissions/` 目录下。这个目录有 20 多个文件，看起来吓人，但核心逻辑集中在一个函数上：**`hasPermissionsToUseTool`**。

这个函数定义在 `src/utils/permissions/permissions.ts`（约第 473 行）：

```typescript
// 文件：src/utils/permissions/permissions.ts，约第473行
export const hasPermissionsToUseTool: CanUseToolFn = async (
  tool,
  input,
  context,
  assistantMessage,
  toolUseID,
): Promise<PermissionDecision> => {
  const result = await hasPermissionsToUseToolInner(tool, input, context)
  // ... 后续处理各种模式 ...
}
```

每个工具执行之前，都会先调用这个函数。它返回一个 `PermissionDecision`——要么放行、要么拒绝、要么交给用户。

除了这个主函数，目录里还有几个重要的帮手：

| 文件 | 作用 |
|---|---|
| `permissions.ts` | 主函数 `hasPermissionsToUseTool`，决策的总调度 |
| `PermissionRule.ts` | 权限规则的类型定义 |
| `permissionRuleParser.ts` | 解析规则字符串，如 `"Bash(npm install)"` |
| `PermissionMode.ts` | 权限模式（default、plan、bypassPermissions 等） |
| `permissionsLoader.ts` | 从磁盘加载权限规则 |
| `bashClassifier.ts` | Bash 命令的 AI 分类器（实验功能） |
| `dangerousPatterns.ts` | 危险命令模式列表 |
| `shellRuleMatching.ts` | Shell 命令的规则匹配逻辑 |
| `filesystem.ts` | 文件路径的安全检查 |
| `denialTracking.ts` | 拒绝次数追踪 |
| `permissionExplainer.ts` | 用 AI 解释命令的风险等级 |

文件虽多，但它们都在为 `hasPermissionsToUseTool` 这一个决策服务。让我们走进这个函数的内部。

## 它怎么工作

### 决策流程：六步安检

`hasPermissionsToUseToolInner`（约第 1158 行）是一个安检流程，每个工具调用都要依次经过六道检查。就像机场安检一样，任何一道检查发现问题，你就被拦下了：

**第 1a 步：黑名单检查**

```typescript
// 文件：src/utils/permissions/permissions.ts，约第1171行
const denyRule = getDenyRuleForTool(appState.toolPermissionContext, tool)
if (denyRule) {
  return {
    behavior: 'deny',
    decisionReason: { type: 'rule', rule: denyRule },
    message: `Permission to use ${tool.name} has been denied.`,
  }
}
```

最先检查的是：这个工具是不是被明确禁止了？如果用户的配置里写了 `"deny": ["Bash"]`，那所有 Bash 命令都会被直接拒绝。没有任何商量余地。

**第 1b 步：强制询问检查**

```typescript
// 文件：src/utils/permissions/permissions.ts，约第1184行
const askRule = getAskRuleForTool(appState.toolPermissionContext, tool)
if (askRule) {
  return {
    behavior: 'ask',
    decisionReason: { type: 'rule', rule: askRule },
    message: createPermissionRequestMessage(tool.name),
  }
}
```

如果用户配置了 `"ask": ["Bash"]`，意思就是"只要用到 Bash，就必须问我"。这比 deny 宽松一点——不直接拒绝，而是每次都要请示。

**第 1c 步：工具自己的权限检查**

每类工具还可以定义自己的权限逻辑。系统会调用 `tool.checkPermissions()`，让工具自己判断：

```typescript
// 文件：src/utils/permissions/permissions.ts，约第1216行
toolPermissionResult = await tool.checkPermissions(parsedInput, context)
```

这一步是权限系统最精妙的地方。比如 BashTool 不会对所有命令一视同仁——`ls` 和 `rm -rf /` 的待遇显然不一样。BashTool 的 `checkPermissions` 会分析命令内容，做更细粒度的判断。

**第 1d 步：工具实现拒绝**

如果 `checkPermissions` 返回 `deny`，那就拒绝。

**第 1e-1g 步：特殊情况处理**

- **1e**：某些工具即使用户选了"跳过所有权限"模式，也必须让用户确认（比如涉及交互的工具）。
- **1f**：内容级别的 ask 规则（比如 `Bash(npm publish:*)` 这种专门针对特定命令的规则）。
- **1g**：安全路径检查——`.git/`、`.claude/`、`.vscode/`、`.bashrc` 这些敏感路径，即使在"跳过权限"模式下也必须提示。

```typescript
// 文件：src/utils/permissions/permissions.ts，约第1255行
if (
  toolPermissionResult?.behavior === 'ask' &&
  toolPermissionResult.decisionReason?.type === 'safetyCheck'
) {
  return toolPermissionResult
}
```

**第 2a 步：权限模式检查**

如果你开启了 `bypassPermissions` 模式（相当于"全部放行"），前面没被拦截的操作就直接允许：

```typescript
// 文件：src/utils/permissions/permissions.ts，约第1268行
const shouldBypassPermissions =
  appState.toolPermissionContext.mode === 'bypassPermissions'
if (shouldBypassPermissions) {
  return { behavior: 'allow', decisionReason: { type: 'mode', mode: 'bypassPermissions' } }
}
```

**第 2b 步：白名单检查**

最后，如果工具被加入了 `"allow"` 列表，直接放行：

```typescript
// 文件：src/utils/permissions/permissions.ts，约第1284行
const alwaysAllowedRule = toolAlwaysAllowedRule(
  appState.toolPermissionContext,
  tool,
)
if (alwaysAllowedRule) {
  return { behavior: 'allow', decisionReason: { type: 'rule', rule: alwaysAllowedRule } }
}
```

**第 3 步：兜底——转为"询问"**

如果前面所有检查都没给出明确答案，默认行为是"问用户"：

```typescript
// 文件：src/utils/permissions/permissions.ts，约第1300行
const result: PermissionDecision =
  toolPermissionResult.behavior === 'passthrough'
    ? { ...toolPermissionResult, behavior: 'ask' }
    : toolPermissionResult
```

`passthrough` 是一个特殊的中间状态，意思是"我没什么意见，交给上级决定"。它会被转换为 `ask`，弹窗让用户来拍板。

### 权限模式：五种状态

系统支持五种权限模式，定义在 `src/types/permissions.ts`（约第 16-22 行）：

```typescript
// 文件：src/types/permissions.ts，约第16行
export const EXTERNAL_PERMISSION_MODES = [
  'acceptEdits',      // 自动接受文件编辑
  'bypassPermissions', // 跳过所有权限检查
  'default',          // 默认模式——该问就问
  'dontAsk',          // 不弹窗——该问的直接拒绝
  'plan',             // 规划模式——只规划不执行
] as const
```

每种模式的策略不同：

| 模式 | 行为 |
|---|---|
| `default` | 正常流程，该问就问 |
| `plan` | 只做规划，不实际执行 |
| `acceptEdits` | 自动接受文件编辑类的操作 |
| `bypassPermissions` | 跳过所有权限检查（但 1d/1e/1f/1g 的安全检查不跳过） |
| `dontAsk` | 不弹窗——需要询问的操作直接拒绝 |

这些模式在 `PermissionMode.ts`（约第 42-91 行）里有对应的配置，包括标题、图标和颜色。

### 权限规则：字符串里的天地

权限规则以字符串形式存储在配置文件里，格式是 `ToolName(content)`。比如：

- `"Bash"` —— 匹配所有 Bash 命令
- `"Bash(npm install)"` —— 精确匹配 `npm install`
- `"Bash(npm:*)"` —— 匹配所有 `npm` 开头的命令（前缀匹配）
- `"Bash(git *)"` —— 匹配所有 `git` 后面带参数的命令（通配符匹配）

这些字符串由 `permissionRuleParser.ts` 负责解析。核心是 `permissionRuleValueFromString` 函数（约第 93 行）：

```typescript
// 文件：src/utils/permissions/permissionRuleParser.ts，约第93行
export function permissionRuleValueFromString(
  ruleString: string,
): PermissionRuleValue {
  const openParenIndex = findFirstUnescapedChar(ruleString, '(')
  if (openParenIndex === -1) {
    return { toolName: normalizeLegacyToolName(ruleString) }
  }
  // 找到 ToolName(content) 的结构，分别提取
  const toolName = ruleString.substring(0, openParenIndex)
  const rawContent = ruleString.substring(openParenIndex + 1, closeParenIndex)
  return { toolName: normalizeLegacyToolName(toolName), ruleContent }
}
```

它把字符串拆成 `{ toolName, ruleContent }` 两部分。如果字符串里没有括号，就是整工具级别的规则。括号内的内容可以包含转义的括号（`\(` 和 `\)`），解析器会正确处理。

### Bash 命令怎么分类

BashTool 的权限检查是最复杂的。因为 Bash 命令千变万化——`ls` 是安全的，`rm -rf /` 是危险的，`curl https://example.com | bash` 是灾难性的。

`dangerousPatterns.ts`（约第 18-43 行）列出了一组危险模式：

```typescript
// 文件：src/utils/permissions/dangerousPatterns.ts，约第18行
export const CROSS_PLATFORM_CODE_EXEC = [
  'python', 'python3', 'node', 'deno', 'tsx',
  'ruby', 'perl', 'php', 'lua',
  'npx', 'bunx', 'npm run', 'yarn run',
  'bash', 'sh', 'ssh',
] as const
```

这些都是可以执行任意代码的命令。如果权限规则是 `"Bash(node:*)"`——意思是"允许所有 node 命令"——在自动模式下会被视为危险规则而被剥离，因为 `node` 可以执行任意 JavaScript 代码。

`shellRuleMatching.ts`（约第 159-184 行）处理三种匹配模式：

```typescript
// 文件：src/utils/permissions/shellRuleMatching.ts，约第159行
export function parsePermissionRule(
  permissionRule: string,
): ShellPermissionRule {
  const prefix = permissionRuleExtractPrefix(permissionRule)
  if (prefix !== null) {
    return { type: 'prefix', prefix }         // "npm:*" → 前缀匹配
  }
  if (hasWildcards(permissionRule)) {
    return { type: 'wildcard', pattern: permissionRule }  // "git *" → 通配符匹配
  }
  return { type: 'exact', command: permissionRule }       // "npm install" → 精确匹配
}
```

三种模式各有用途：精确匹配最安全但最死板；前缀匹配（`:*` 语法）兼容老版本；通配符匹配最灵活但需要小心。

### 决策的理由

每次权限决策都会附带一个 `decisionReason`，解释"为什么做了这个决定"。这个理由有多种类型，定义在 `src/types/permissions.ts`（约第 271 行）：

```typescript
// 文件：src/types/permissions.ts，约第271行
export type PermissionDecisionReason =
  | { type: 'rule', rule: PermissionRule }        // 匹配了某条规则
  | { type: 'mode', mode: PermissionMode }        // 当前模式决定
  | { type: 'hook', hookName: string }            // Hook 拦截
  | { type: 'classifier', classifier: string }    // AI 分类器决定
  | { type: 'safetyCheck', reason: string }        // 安全检查触发
  | { type: 'subcommandResults', reasons: Map<...> }  // 子命令结果
  // ... 等等
```

这个设计很重要。当用户看到权限提示时，系统能告诉他"为什么"——是因为匹配了某条规则？还是因为当前是 plan 模式？还是因为触发了安全检查？信息透明让用户更容易做出判断。

### 拒绝追踪：连续被拦就退让

在自动模式（auto mode）下，系统用 AI 分类器来判断命令是否安全。但分类器可能会误判。`denialTracking.ts` 实现了一个保险机制：

```typescript
// 文件：src/utils/permissions/denialTracking.ts，约第12行
export const DENIAL_LIMITS = {
  maxConsecutive: 3,   // 连续拒绝3次
  maxTotal: 20,        // 总共拒绝20次
} as const
```

如果 AI 分类器连续拒绝了 3 次，或者总共拒绝了 20 次，系统会说："算了，AI 你可能判断有误，还是让用户来决定吧。" 于是停止自动模式，回退到正常的用户提示。这是一个很好的安全阀设计——即使 AI 分类器出了问题，用户仍然有最终决定权。

### 权限提示如何呈现

当决策是 `ask` 时，权限系统会生成一条人类可读的提示信息。`createPermissionRequestMessage` 函数（约第 137 行）根据不同的 `decisionReason` 生成不同的消息：

```typescript
// 文件：src/utils/permissions/permissions.ts，约第137行
export function createPermissionRequestMessage(
  toolName: string,
  decisionReason?: PermissionDecisionReason,
): string {
  if (decisionReason?.type === 'rule') {
    return `Permission rule '${ruleString}' from ${sourceString} requires approval...`
  }
  if (decisionReason?.type === 'mode') {
    return `Current permission mode (${modeTitle}) requires approval...`
  }
  // 默认消息
  return `Claude requested permissions to use ${toolName}...`
}
```

用户看到提示后，可以选择"允许"或者"拒绝"。如果选了"总是允许"，系统会把这条规则写入配置，下次就不用再问了。

## 对比 Java

如果你学过 Java，可能会觉得这套权限系统有点眼熟。Java 世界里也有类似的门卫。

### Java SecurityManager（已废弃）

Java 曾经有一个 `SecurityManager`，它的工作原理和 Claude Code 的权限系统很像——代码执行前先检查权限。区别在于：

- Java 的 `SecurityManager` 是**全局的、一次性的**——要么启用，要么不启用。它在 Java 17 中被废弃了。
- Claude Code 的权限系统是**细粒度的**——每个工具、每条命令都可以单独配置规则。

### Spring Security

更接近的类比是 Spring Security 的权限控制。Spring Security 用 `@PreAuthorize` 注解来保护方法：

```java
// Spring Security 的方式
@PreAuthorize("hasRole('ADMIN')")
public void deleteUser(String userId) { ... }
```

Claude Code 用的是规则列表而不是注解，但思路一样：**在执行之前插入一个检查点**。

| 对比维度 | Claude Code | Spring Security |
|---|---|---|
| 检查时机 | 工具执行前 | 方法调用前 |
| 规则存储 | JSON 配置文件 | 注解 + 配置类 |
| 决策结果 | allow / deny / ask | granted / denied |
| 动态性 | 用户可以在运行时修改规则 | 通常需要重启 |
| 默认策略 | 未经允许的默认询问 | 默认拒绝 |

最大的区别在于 **`ask`（询问）这个行为**。Spring Security 只有"允许"和"拒绝"两种结果，而 Claude Code 多了一个"请示用户"的选项。这是因为 Claude Code 是一个交互式工具——它可以直接问坐在终端前的用户。而 Spring Security 通常运行在后台服务里，没有用户可以问。

## 你能改什么

理解了权限系统，你能做这些定制：

### 1. 添加自定义权限规则

最简单的定制方式是修改配置文件。Claude Code 的权限规则存储在 `.claude/settings.json` 或 `.claude/settings.local.json` 里：

```json
{
  "permissions": {
    "allow": [
      "Bash(git status)",
      "Bash(npm test:*)",
      "Read",
      "Grep"
    ],
    "deny": [
      "Bash(rm -rf:*)",
      "Bash(curl * | bash)"
    ],
    "ask": [
      "Bash(npm publish:*)"
    ]
  }
}
```

- `allow`：自动放行，不再询问。
- `deny`：直接拒绝，不给机会。
- `ask`：每次都问。

规则的语法支持三种匹配方式：
- **精确匹配**：`Bash(npm install)` 只匹配 `npm install` 本身。
- **前缀匹配**：`Bash(npm:*)` 匹配所有 `npm` 开头的命令。
- **通配符匹配**：`Bash(git *)` 匹配 `git` 后面带任意参数的命令。

### 2. 添加新的危险模式

如果你发现某个命令在你的环境中特别危险，可以在 `dangerousPatterns.ts` 里的 `DANGEROUS_BASH_PATTERNS` 数组中添加。比如你不想让 AI 在自动模式下使用 `docker`：

```typescript
// 文件：src/utils/permissions/dangerousPatterns.ts
export const DANGEROUS_BASH_PATTERNS: readonly string[] = [
  ...CROSS_PLATFORM_CODE_EXEC,
  'docker',     // 你加的！
  // ...
]
```

添加后，`Bash(docker:*)` 这样的规则在自动模式下会被自动剥离。

### 3. 自定义工具的权限逻辑

如果你想给某个工具添加自定义的权限检查，可以在工具类中实现 `checkPermissions` 方法。这个方法接收解析后的输入和上下文，返回 `PermissionResult`：

```typescript
// 你可以给任何工具添加自定义的 checkPermissions
async checkPermissions(input, context): Promise<PermissionResult> {
  // 你的自定义逻辑
  if (isMySpecialCase(input)) {
    return {
      behavior: 'ask',
      message: '这个操作需要你确认一下',
      decisionReason: { type: 'other', reason: '自定义安全检查' },
    }
  }
  return { behavior: 'allow' }
}
```

### 4. 调整拒绝阈值

如果你觉得自动模式的拒绝阈值太严格或太宽松，可以修改 `denialTracking.ts` 里的常量：

```typescript
// 文件：src/utils/permissions/denialTracking.ts，约第12行
export const DENIAL_LIMITS = {
  maxConsecutive: 3,   // 调大 → 更信任 AI，调小 → 更早回退到用户
  maxTotal: 20,        // 同上
} as const
```

## 小结

权限系统是 Claude Code 的安全防线，它像一个尽职的门卫，在每次工具执行前做一次快速检查。你学到了：

1. **三种决策**：`allow`（放行）、`deny`（拒绝）、`ask`（请示用户）构成权限系统的基石。
2. **六步安检**：从黑名单到白名单，从工具自身检查到安全路径保护，每一步都有明确的职责。
3. **规则语法**：`ToolName(content)` 的字符串格式，支持精确匹配、前缀匹配和通配符匹配三种模式。
4. **分层安全**：即使用户选了"跳过权限"，安全检查（`.git/`、`.bashrc` 等）和 ask 规则仍然生效——系统在最关键的环节留了后手。
5. **拒绝追踪**：当 AI 分类器连续误判时，系统自动退让，把决定权交还给用户。

门卫保护了大楼的安全，但它不负责记住每个访客的来访记录。谁来记住对话的上下文、AI 之前说过什么、用户之前做过什么？那是下一章的主题——对话的记忆术。
