# 第06章：工具执行引擎

上一章我们看了 30 多个工具的故事——它们怎么被注册、怎么被找到。但你有没有想过，当 AI 说"我要读一个文件"的时候，从这句话到文件内容真正出现在你面前，中间到底发生了什么？

你可能以为过程很简单：AI 发请求，工具执行，返回结果。但实际上，这中间有一条精心设计的流水线。就像快递一样，你以为只是"下单→收货"，但背后有订单验证、仓库拣货、安检扫描、物流配送、签收确认。每一步都有它的理由。

这条流水线就是**工具执行引擎**。它的核心是一个叫 `runToolUse` 的函数。这一章，我们打开引擎盖，看看里面的齿轮是怎么咬合的。

---

## 这是什么

想象你是一个工厂的生产调度员。每天你收到几十张工单，每张工单写着"做某件事"——焊接、喷涂、质检、包装。你的工作不是亲自去做每一件事，而是确保每张工单按正确流程走完：

1. **核对工单**——工单填得对不对？材料齐不齐？
2. **查安全许可**——这个操作有危险吗？需要特别授权吗？
3. **通知前置工位**——告诉上下游，"我要开始做这件事了"。
4. **执行**——让对应的工位开工。
5. **通知后置工位**——做完了，让后续流程接手。
6. **交还结果**——把成品交给下一环节。

`runToolUse` 就是这个调度员。AI 发来一个工具调用请求，`runToolUse` 不关心具体做什么，它关心的是**流程**——确保每一步在正确的时机以正确的顺序执行。

为什么需要这样一个调度员？因为如果让每个工具自己管自己的流程，很快就会乱套。有的工具忘了做权限检查，有的工具忘了跑钩子，有的工具错误处理不一致。集中的执行引擎保证了一致性：不管哪个工具，流程都一样。

## 打开源码

工具执行引擎的核心代码在 `src/services/tools/toolExecution.ts` 文件中。这个文件大约 1745 行，是整个工具系统最重要的文件之一。

让我们先看入口函数 `runToolUse`：

```typescript
// 文件：src/services/tools/toolExecution.ts，约第337行
export async function* runToolUse(
  toolUse: ToolUseBlock,
  assistantMessage: AssistantMessage,
  canUseTool: CanUseToolFn,
  toolUseContext: ToolUseContext,
): AsyncGenerator<MessageUpdateLazy, void> {
```

先别急着看函数体，注意几个关键的设计决策。

**第一，它是一个 `AsyncGenerator`。** 不是返回一个 `Promise<Message>`，而是用 `yield` 持续产出消息。为什么？因为工具执行是一个**过程**，不是一个瞬间。从开始执行到返回结果，中间可能有进度更新、权限确认、钩子消息。用生成器可以让调用方实时收到每一步的更新，而不是干等最后的结果。

**第二，参数精简但信息丰富。** 四个参数各司其职：`toolUse` 是 AI 发来的原始请求（工具名 + 参数），`canUseTool` 是权限检查函数，`toolUseContext` 包含了执行所需的所有上下文信息。

函数体的第一件工作是**找到工具**：

```typescript
// 文件：src/services/tools/toolExecution.ts，约第344-356行
let tool = findToolByName(toolUseContext.options.tools, toolName)
if (!tool) {
  const fallbackTool = findToolByName(getAllBaseTools(), toolName)
  if (fallbackTool && fallbackTool.aliases?.includes(toolName)) {
    tool = fallbackTool
  }
}
```

先在当前会话可用的工具列表里找。找不到？再去全局工具列表里找——但只接受通过别名匹配的（比如旧版 transcript 里用了工具的旧名字）。如果还是找不到，直接返回错误消息：

```typescript
// 文件：src/services/tools/toolExecution.ts，约第396-410行
yield {
  message: createUserMessage({
    content: [{
      type: 'tool_result',
      content: `<tool_use_error>Error: No such tool available: ${toolName}</tool_use_error>`,
      is_error: true,
      tool_use_id: toolUse.id,
    }],
    toolUseResult: `Error: No such tool available: ${toolName}`,
    sourceToolAssistantUUID: assistantMessage.uuid,
  }),
}
return
```

注意：错误也是通过 `yield` 返回的，不是抛异常。这保证了调用方用统一的方式处理所有结果。

## 它怎么工作

找到了工具之后，真正的工作开始了。`runToolUse` 把实际执行委托给了 `checkPermissionsAndCallTool` 函数（约第599行），但为了支持进度报告，中间有一层 `streamedCheckPermissionsAndCallTool` 的包装（约第492行）。这一层把 Promise 转成 AsyncIterable，让进度事件和最终结果走同一个管道。

执行引擎的完整生命周期是这样的：

```
验证输入 → 运行前置钩子 → 检查权限 → 执行工具 → 运行后置钩子 → 返回结果
```

每一步都可能中断流程。让我们跟着代码一步步走。

### 第一步：验证输入

AI 并不总是靠谱的。它可能传了一个字符串给你期望数字的字段，可能忘了必填参数，可能塞了多余的东西。所以第一步是用 Zod 做输入验证：

```typescript
// 文件：src/services/tools/toolExecution.ts，约第615行
const parsedInput = tool.inputSchema.safeParse(input)
if (!parsedInput.success) {
  let errorContent = formatZodValidationError(tool.name, parsedInput.error)
  // ... 返回错误消息
}
```

`safeParse` 不会抛异常——它返回一个 `{ success: boolean, error?: ... }` 对象。如果验证失败，错误消息被格式化后返回给 AI，让它知道哪里传错了。

接着还有一层自定义验证：

```typescript
// 文件：src/services/tools/toolExecution.ts，约第683行
const isValidCall = await tool.validateInput?.(parsedInput.data, toolUseContext)
if (isValidCall?.result === false) {
  // ... 返回工具特定的验证错误
}
```

`validateInput` 是可选的——不是所有工具都需要额外的验证。但有些工具（比如 BashTool）会在这里做更深层的检查。

### 第二步：运行前置钩子（PreToolUse Hooks）

验证通过后，引擎会运行所有注册的 PreToolUse 钩子：

```typescript
// 文件：src/services/tools/toolExecution.ts，约第800行
for await (const result of runPreToolUseHooks(
  toolUseContext, tool, processedInput, toolUseID,
  assistantMessage.message.id, requestId, mcpServerType, mcpServerBaseUrl,
)) {
  switch (result.type) {
    case 'message':          // 钩子产生的消息
    case 'hookPermissionResult': // 钩子做出的权限决定
    case 'hookUpdatedInput': // 钩子修改了输入参数
    case 'preventContinuation': // 钩子要求停止执行
    case 'stopReason':       // 停止原因
    case 'additionalContext': // 钩子提供的额外上下文
    case 'stop':             // 立即停止
  }
}
```

钩子是什么？你可以把它理解为一组"旁观者脚本"。每当工具要执行时，这些脚本会被通知，它们可以：

- **批准或拒绝**执行——钩子返回 `{ decision: 'approve' }` 或 `{ decision: 'block' }`。
- **修改输入参数**——钩子返回 `{ updatedInput: {...} }`，工具实际收到的参数会被替换。
- **添加额外上下文**——钩子返回 `{ additionalContext: "..." }`，这些信息会传给 AI。
- **阻止继续执行**——钩子返回 `{ continue: false, stopReason: "..." }`，整个工具调用被中止。

钩子系统是怎么执行的？在 `src/utils/hooks.ts` 里，`executePreToolHooks` 函数会查找当前会话中所有为 `PreToolUse` 事件注册的钩子，然后逐个执行：

```typescript
// 文件：src/utils/hooks.ts，约第3418行
const hookInput: PreToolUseHookInput = {
  ...createBaseHookInput(permissionMode, undefined, toolUseContext),
  hook_event_name: 'PreToolUse',
  tool_name: toolName,
  tool_input: toolInput,
  tool_use_id: toolUseID,
}
yield* executeHooks({ hookInput, toolUseID, matchQuery: toolName, signal, ... })
```

钩子可以是 shell 命令，也可以是 JavaScript 回调。它们通过标准输入接收 JSON 格式的钩子输入，通过标准输出返回 JSON 格式的钩子结果。这种设计让钩子可以用任何语言编写，只要能读写 JSON 就行。

### 第三步：检查权限

前置钩子跑完后，引擎进入权限检查阶段：

```typescript
// 文件：src/services/tools/toolExecution.ts，约第921行
const resolved = await resolveHookPermissionDecision(
  hookPermissionResult, tool, processedInput, toolUseContext,
  canUseTool, assistantMessage, toolUseID,
)
const permissionDecision = resolved.decision
```

`resolveHookPermissionDecision`（定义在 `src/services/tools/toolHooks.ts`，约第332行）是一个关键的决策函数。它合并两个信息来源：

1. **钩子的决定**——如果前置钩子已经批准或拒绝了，这个决定会被优先考虑，但不完全采信。
2. **规则系统的决定**——即使钩子说"批准"，如果 `settings.json` 里有 deny 规则，deny 仍然生效。

这是一个重要的安全设计：**钩子不能绕过安全规则**。钩子可以说"我同意"，但如果管理员配置了"这个工具永远不能用"，那管理员的话算数。

如果权限检查的结果不是 `allow`，执行到此终止，错误消息被返回。

### 第四步：执行工具

权限通过后，终于到了真正执行工具的时刻：

```typescript
// 文件：src/services/tools/toolExecution.ts，约第1207行
const result = await tool.call(
  callInput,
  { ...toolUseContext, toolUseId: toolUseID, userModified: permissionDecision.userModified ?? false },
  canUseTool,
  assistantMessage,
  progress => { onToolProgress({ toolUseID: progress.toolUseID, data: progress.data }) },
)
```

`tool.call()` 是我们在上一章见过的那个核心方法。每个工具有自己的实现——BashTool 执行 shell 命令，FileReadTool 读取文件，FileEditTool 编辑文件。引擎不关心内部细节，它只关心结果。

### 第五步：运行后置钩子（PostToolUse Hooks）

工具执行成功后，引擎会运行 PostToolUse 钩子：

```typescript
// 文件：src/services/tools/toolExecution.ts，约第1483行
for await (const hookResult of runPostToolUseHooks(
  toolUseContext, tool, toolUseID, assistantMessage.message.id,
  processedInput, toolOutput, requestId, mcpServerType, mcpServerBaseUrl,
)) {
  // 处理钩子结果...
}
```

后置钩子能做什么？比如：

- **记录审计日志**——每次文件被修改时写一条日志。
- **自动格式化**——代码写完后自动跑一遍 linter。
- **修改 MCP 工具的输出**——`updatedMCPToolOutput` 让钩子可以拦截和修改工具的返回值。
- **阻止继续**——即使工具执行成功了，后置钩子也可以决定停止后续流程。

如果工具执行**失败**了，引擎会运行另一组钩子——`PostToolUseFailure`：

```typescript
// 文件：src/services/tools/toolExecution.ts，约第1700行
for await (const hookResult of runPostToolUseFailureHooks(
  toolUseContext, tool, toolUseID, messageId,
  processedInput, content, isInterrupt, ...
)) {
  hookMessages.push(hookResult)
}
```

这让钩子有机会在失败时做清理工作，或者给 AI 提供修复建议。

### 第六步：返回结果

所有步骤完成后，引擎把收集到的消息打包返回。这些消息会被发送回 AI，让它知道工具调用的结果，然后决定下一步做什么。

### 一个完整的例子：AI 调用 FileReadTool

让我们用一个具体的例子把整个流程串起来。假设 AI 想读取文件 `/tmp/hello.txt`：

**1. AI 发出请求。** AI 返回一个工具调用块，里面写着工具名 `Read` 和参数 `{ file_path: "/tmp/hello.txt" }`。

**2. runToolUse 找到工具。** `findToolByName("Read", ...)` 在可用工具列表里找到了 FileReadTool。

**3. 验证输入。** Zod 检查：`file_path` 是字符串吗？是。必填字段都有吗？有。验证通过。

**4. 运行 PreToolUse 钩子。** 假设你配置了一个钩子，在每次读文件前打印一条日志。钩子收到输入 `{ tool_name: "Read", tool_input: { file_path: "/tmp/hello.txt" } }`，打印日志后返回 `{ continue: true }`——允许继续。

**5. 检查权限。** `resolveHookPermissionDecision` 检查规则——没有 deny 规则，Read 是只读工具，默认放行。

**6. 执行 FileReadTool.call()。** 工具读取 `/tmp/hello.txt` 的内容，返回 `{ content: "Hello, World!" }`。

**7. 运行 PostToolUse 钩子。** 假设没有配置后置钩子，这一步直接跳过。

**8. 返回结果。** 引擎把文件内容包装成标准消息格式，发送回 AI。AI 看到 "Hello, World!"，然后继续和你的对话。

整个过程不到一秒钟，但背后走了六个步骤。这就是为什么你的文件内容能安全、可靠地出现在 AI 的视野里。

## 对比：如果用 Java

如果你做过 Java Web 开发，工具执行引擎的模式你应该很熟悉——它和 **Servlet Filter Chain** 或 **Spring Interceptor** 是同一个思路。

在 Spring 里，一个 HTTP 请求的处理流程是：

```
Filter.doFilter() → HandlerInterceptor.preHandle() → Controller处理请求 → HandlerInterceptor.postHandle() → 渲染视图 → afterCompletion()
```

在 Claude Code 里，一个工具调用的处理流程是：

```
PreToolUse Hooks → 权限检查 → tool.call() → PostToolUse Hooks → 返回结果
```

对应关系很明确：

| Java/Spring | Claude Code | 作用 |
|---|---|---|
| `Filter.doFilter()` | PreToolUse Hooks | 前置拦截，可以修改请求或拒绝 |
| `Interceptor.preHandle()` | `resolveHookPermissionDecision()` | 权限检查 |
| `Controller.method()` | `tool.call()` | 执行实际业务逻辑 |
| `Interceptor.postHandle()` | PostToolUse Hooks | 后置处理，可以修改结果 |
| `Interceptor.afterCompletion()` | PostToolUseFailure Hooks | 异常处理和清理 |

但有一个关键区别。Spring 的拦截器是通过**类继承和接口实现**来扩展的——你写一个类实现 `HandlerInterceptor` 接口，然后在配置类里注册它。Claude Code 的钩子是通过**外部脚本**来扩展的——你写一个 shell 命令，在 `.claude/settings.json` 里配置它。

这意味着什么？Spring 的拦截器在同一个 JVM 进程里运行，能直接访问 Java 对象。Claude Code 的钩子在**独立进程**里运行，通过 JSON 标准输入/输出通信。这个设计牺牲了一点性能（进程间通信比函数调用慢），但换来了巨大的灵活性——钩子可以用 Python、Bash、Go、任何语言写，甚至可以调用远程 API。

另一个区别是**权限优先级**的设计。在 Spring 里，Filter 和 Interceptor 的顺序由注册顺序决定——先注册的先执行，如果第一个 Filter 拒绝了请求，后面的 Filter 和 Controller 都不会执行。在 Claude Code 里，引擎做了一个更精巧的设计：钩子的"批准"决定**不能绕过**规则系统的"拒绝"决定。这就像公司里的审批流程——部门经理可以批准你的请假，但如果 HR 系统显示你没剩假期了，批准也无效。这种分层安全设计在 Java 应用中不常见，但在安全敏感的系统中非常有价值。

## 你能改什么

### 入门级：理解钩子系统

**阅读钩子配置。** 打开你项目里的 `.claude/settings.json` 文件，看看 `hooks` 部分。如果你还没配置过钩子，它可能是空的。试着理解钩子的配置格式——每个钩子有一个事件名（如 `PreToolUse`）、一个匹配模式（如工具名），和一个 shell 命令。

**追踪一次工具执行的完整流程。** 在 `runToolUse` 函数的开头（约第343行）和 `checkPermissionsAndCallTool` 的关键节点打 `console.log`，然后触发一次简单的工具调用（比如让 AI 读一个文件），观察日志输出的顺序。这能帮你建立对执行流程的直觉。

### 中级：添加自定义钩子

**添加一个 PreToolUse 钩子。** 在 `.claude/settings.json` 的 `hooks.PreToolUse` 里添加一个钩子。比如，每次写文件前自动创建备份：

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Write",
        "hooks": [
          {
            "type": "command",
            "command": "cp \"$TOOL_INPUT_FILE_PATH\" \"$TOOL_INPUT_FILE_PATH.bak\" 2>/dev/null || true"
          }
        ]
      }
    ]
  }
}
```

当然，实际的钩子输入是通过 stdin 的 JSON 传递的，你需要用 `jq` 之类的工具来解析它。但这个示例展示了钩子的配置思路。

**添加一个审计钩子。** 在 PostToolUse 里记录每次工具调用的结果到日志文件。这在调试和安全审计中很有用。

### 高级：修改执行引擎

**添加新的执行阶段。** 如果你需要在工具执行前后做更复杂的事情（比如缓存、重试、限流），可以在 `checkPermissionsAndCallTool` 函数里添加新的阶段。但要注意：这个函数已经很长了（从第599行到第1745行，超过1100行），修改时需要非常小心。

**修改权限决策逻辑。** `resolveHookPermissionDecision`（在 `src/services/tools/toolHooks.ts` 约第332行）是权限决策的核心。如果你想改变钩子和规则系统之间的优先级关系，这是你要改的地方。但请三思——当前的"钩子不能绕过规则"设计是有安全原因的。

### 危险区域

**修改 runToolUse 的消息协议。** `runToolUse` 是一个 `AsyncGenerator<MessageUpdateLazy>`——它产出的消息类型被整个系统依赖。改变消息格式会导致上游消费者（查询引擎、消息存储）出问题。

**修改钩子执行的超时机制。** 钩子执行有超时保护（`TOOL_HOOK_EXECUTION_TIMEOUT_MS`），防止一个卡死的钩子阻塞整个工具执行。移除或增大这个超时可能导致系统对无响应钩子失去防御能力。

**修改 Stream 包装层。** `streamedCheckPermissionsAndCallTool`（约第492行）把 Promise 转成 AsyncIterable，让进度事件和最终结果走同一个管道。这个包装看起来"有点 hack"（代码注释也这么说的），但它解决了一个真实的问题。如果你要重构这部分，确保进度事件不会丢失或乱序。

## 回顾

这一章，我们跟着 `runToolUse` 走完了工具执行的完整生命周期：

1. **找到工具**——按名字查找，支持旧名别名回退。
2. **验证输入**——先用 Zod 做 schema 验证，再用工具自定义逻辑做深度验证。
3. **运行前置钩子**——让外部脚本在工具执行前介入，可以修改参数、批准/拒绝执行、添加上下文。
4. **检查权限**——合并钩子决定和规则系统的决定，确保安全规则不可绕过。
5. **执行工具**——调用 `tool.call()`，让工具做它该做的事。
6. **运行后置钩子**——让外部脚本在工具执行后介入，可以修改结果、记录日志、做清理。
7. **返回结果**——把所有消息打包，发送回 AI。

整个过程用 `AsyncGenerator` 串联，让进度更新和最终结果走同一个管道。钩子系统通过 JSON 标准输入/输出通信，用任何语言都能写。

你看到了工具执行的流水线。但有一个关键问题我们还没深入：**权限系统到底是怎么工作的？** 钩子的决定、规则系统的决定、用户的交互确认，它们之间到底是什么关系？下一章，我们走进安全门卫的岗亭。
