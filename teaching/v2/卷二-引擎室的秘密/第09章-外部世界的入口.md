# 第09章：外部世界的入口

你用 Claude Code 读文件、执行命令、搜索代码——这些都是内置工具，我们在前面几章已经拆解过了。但你可能还见过一些更酷的操作：让 AI 直接操作浏览器、查询数据库、调用 Slack API。这些不是内置的，它们来自外部世界，通过一扇名为 **MCP** 的大门进入。

MCP 全称 Model Context Protocol（模型上下文协议），它定义了一套标准化的通信规则，让 Claude Code 能跟任何支持这套规则的外部服务器对话。你不需要为每个外部工具写专门的集成代码，只要它说 MCP 的语言，Claude Code 就能听懂。

这一章，我们打开这扇门，看看门后面是什么。

---

## 这是什么

先打个比方。你家的路由器有很多网口——有的插电脑，有的插电视，有的插手机充电器。设备千差万别，但网口是统一的。路由器不关心对面插的是什么，只要接头对得上，数据就能流通。

MCP 就是 Claude Code 的网口。它是一个协议——一套约定好的消息格式和交互规则。任何实现了这套规则的服务器（我们叫它 MCP Server），都可以被 Claude Code 发现、连接、使用。

一个 MCP Server 可以提供三种东西：

- **工具（Tools）**——让 AI 调用的函数。比如一个数据库 MCP Server 提供 `query` 工具，AI 就能发 SQL 查询。
- **资源（Resources）**——让 AI 读取的数据。比如一个文件系统 MCP Server 暴露配置文件内容。
- **提示（Prompts）**——预定义的提示模板，可以注册为斜杠命令。

而 Claude Code 在这头扮演的角色叫 **MCP Client**。它的职责是：找到服务器、建立连接、询问"你有什么工具"、把工具注册到自己的工具表里，最后在 AI 需要的时候转发调用请求。

## 打开源码

MCP 相关的代码全部住在 `src/services/mcp/` 目录下。打开这个目录，你会看到大约 20 个文件。核心文件不多，我们先挑最重要的几个看看各自的角色：

| 文件 | 角色 |
|------|------|
| `types.ts` | 所有 MCP 相关的类型定义——服务器配置、连接状态、工具序列化格式 |
| `config.ts` | 配置管理——从 `.mcp.json`、全局设置、企业策略等来源加载服务器配置 |
| `client.ts` | 核心客户端——建立连接、发现工具、调用工具、管理连接缓存 |
| `useManageMCPConnections.ts` | React Hook——管理连接生命周期、自动重连、状态同步到 UI |
| `normalization.ts` | 名称规范化——把服务器名转换成合法的工具名前缀 |
| `mcpStringUtils.ts` | 字符串工具——解析 `mcp__server__tool` 格式的名字 |
| `envExpansion.ts` | 环境变量展开——处理配置中的 `${VAR}` 和 `${VAR:-default}` |
| `utils.ts` | 辅助函数——按服务器过滤工具、检测过期客户端、哈希比较配置变更 |
| `auth.ts` | 认证处理——OAuth 流程、token 管理 |

这些文件形成了一条清晰的数据流：**配置决定连接哪些服务器，连接发现哪些工具，工具合并到工具表，工具表交给 AI 使用**。

## 它怎么工作

### 第一步：配置——告诉 Claude Code 该连接谁

MCP 服务器不是凭空出现的，它们需要被配置。配置可以来自好几个地方，定义在 `config.ts` 里（约第 1071 行的 `getClaudeCodeMcpConfigs` 函数）：

1. **项目配置**（`scope: 'project'`）——来自项目根目录的 `.mcp.json` 文件。团队共享。
2. **用户配置**（`scope: 'user'`）——来自全局 `settings.json`。个人专用，跨项目生效。
3. **本地配置**（`scope: 'local'`）——来自项目本地的 `settings.local.json`。私有，不提交到版本控制。
4. **插件配置**（`scope: 'dynamic'`）——来自已安装的插件。自动注册。
5. **企业配置**（`scope: 'enterprise'`）——来自管理员分发的受管文件。优先级最高。
6. **claude.ai 配置**（`scope: 'claudeai'`）——从 claude.ai 网站同步的服务器配置。

最常见的是项目配置。你在项目根目录放一个 `.mcp.json`，长这样：

```json
{
  "mcpServers": {
    "my-database": {
      "command": "npx",
      "args": ["-y", "@my-org/mcp-database"],
      "env": {
        "DB_URL": "${DB_URL}"
      }
    },
    "my-api": {
      "type": "http",
      "url": "https://api.example.com/mcp"
    }
  }
}
```

注意两种不同的配置模式。`my-database` 没有写 `type`，默认是 `stdio`——Claude Code 会启动一个子进程，通过标准输入输出通信。`my-api` 写了 `type: "http"`，走的是 HTTP 网络连接。

`types.ts`（约第 28 行起）定义了所有支持的传输类型的 Schema。除了 `stdio` 和 `http`，还有 `sse`（Server-Sent Events）、`ws`（WebSocket）、`sse-ide`（IDE 扩展专用）等。每种类型有自己需要的参数——`stdio` 需要 `command` 和 `args`，而网络类型需要 `url`。

配置加载后，环境变量会被展开。`envExpansion.ts` 支持 `${VAR}` 和带默认值的 `${VAR:-default}` 语法，这样你可以在配置中引用环境变量而不用硬编码密钥。

### 第二步：连接——跟服务器握手

配置加载完毕后，`useManageMCPConnections` 这个 React Hook 开始工作（约第 143 行）。它启动一个两阶段加载流程：

- **Phase 1**：快速加载本地配置（文件读取，不走网络），立即开始连接。
- **Phase 2**：等待 claude.ai 的远程配置下载完成（可能较慢），然后连接这些远程服务器。

实际的连接逻辑在 `client.ts` 的 `connectToServer` 函数里（约第 595 行）。这个函数被 `memoize` 包裹——同一个服务器不会重复连接。连接过程根据传输类型分叉：

```typescript
// 文件：src/services/mcp/client.ts，约第595行
export const connectToServer = memoize(
  async (name, serverRef, serverStats) => {
    let transport

    if (serverRef.type === 'sse') {
      // SSE 传输：创建 SSEClientTransport
      transport = new SSEClientTransport(new URL(serverRef.url), options)
    } else if (serverRef.type === 'http') {
      // HTTP 传输：创建 StreamableHTTPClientTransport
      transport = new StreamableHTTPClientTransport(new URL(serverRef.url), options)
    } else if (serverRef.type === 'stdio' || !serverRef.type) {
      // Stdio 传输：启动子进程
      transport = new StdioClientTransport({
        command: serverRef.command,
        args: serverRef.args,
        env: { ...subprocessEnv(), ...serverRef.env },
        stderr: 'pipe',
      })
    }
    // ... 其他类型 ...

    const client = new Client(
      { name: 'claude-code', version: MACRO.VERSION },
      { capabilities: { roots: {}, elicitation: {} } }
    )
    await client.connect(transport)
    // ... 返回连接结果 ...
  }
)
```

关键点：不管哪种传输方式，最终都创建一个 MCP SDK 的 `Client` 对象，然后调用 `client.connect(transport)` 完成握手。底层用的是 JSON-RPC 2.0 协议——客户端发一个 `initialize` 请求，服务器回复它的能力和信息。

连接的结果有五种状态，定义在 `types.ts`（约第 180 行）：

```typescript
// 文件：src/services/mcp/types.ts，约第180行
type MCPServerConnection =
  | ConnectedMCPServer    // 连接成功
  | FailedMCPServer       // 连接失败
  | NeedsAuthMCPServer    // 需要认证
  | PendingMCPServer      // 等待连接
  | DisabledMCPServer     // 已禁用
```

这个状态机驱动整个 UI 展示。你在 `/mcp` 命令里看到的每个服务器状态，就是这几个值。

### 第三步：发现——服务器你有什么工具

连接成功后，下一步是问服务器："你有什么工具？"

这个工作由 `fetchToolsForClient` 完成（`client.ts` 约第 1743 行）。它向服务器发送一个 `tools/list` 的 JSON-RPC 请求，然后拿到工具列表：

```typescript
// 文件：src/services/mcp/client.ts，约第1743行
export const fetchToolsForClient = memoizeWithLRU(
  async (client) => {
    if (client.type !== 'connected') return []
    if (!client.capabilities?.tools) return []

    const result = await client.client.request(
      { method: 'tools/list' },
      ListToolsResultSchema,
    )

    return result.tools.map((tool) => {
      const fullyQualifiedName = buildMcpToolName(client.name, tool.name)
      return {
        ...MCPTool,
        name: fullyQualifiedName,
        mcpInfo: { serverName: client.name, toolName: tool.name },
        // ... 其他属性 ...
      }
    })
  }
)
```

注意一个关键细节：**工具名被重命名了**。假设你的服务器叫 `my-database`，它提供了一个 `query` 工具，Claude Code 会把它重命名为 `mcp__my_database__query`。

为什么？因为不同服务器可能提供同名工具。两个数据库服务器都有 `query` 工具，没有前缀就冲突了。`mcp__服务器名__工具名` 的三段式命名保证了全局唯一。

名称规范化的逻辑在 `normalization.ts`（约第 17 行）：把非字母数字的字符替换成下划线，确保名字合法。

### 第四步：注册——合并到工具表

发现的工具怎么进入 AI 能看到的工具表？这步在 `useManageMCPConnections.ts` 的 `flushPendingUpdates` 函数里完成（约第 216 行）。

它用一个 **批处理机制**：多个服务器几乎同时连接完成，每个都带着自己发现的工具列表。与其每个都触发一次 UI 刷新，不如攒在一起，16 毫秒后统一更新一次。

```typescript
// 文件：src/services/mcp/useManageMCPConnections.ts，约第216行
const flushPendingUpdates = useCallback(() => {
  setAppState(prevState => {
    let mcp = prevState.mcp
    for (const update of updates) {
      const { tools, commands, resources, ...client } = update
      // 移除这个服务器旧的工具，加入新的
      const updatedTools = [
        ...reject(mcp.tools, t => t.name?.startsWith(prefix)),
        ...tools
      ]
      mcp = { ...mcp, tools: updatedTools, clients: updatedClients, ... }
    }
    return { ...prevState, mcp }
  })
}, [setAppState])
```

这里的关键策略是 **替换而非追加**。每个 MCP 服务器有一组工具，以 `mcp__服务器名__` 为前缀。更新时，先删掉这个前缀的所有旧工具，再加入新发现的。这样即使工具列表变了（服务器升级了），也不会出现重复或过时的工具。

MCP 工具跟内置工具放在同一个 `mcp.tools` 数组里，对 AI 来说没有区别——它们共享同一个 `Tool` 类型（第04章讲的 DNA）。AI 只看到一个扁平的工具列表，不知道哪些是内置的、哪些是 MCP 外来的。

### 第五步：使用——转发 AI 的调用请求

当 AI 决定调用一个 MCP 工具时（比如 `mcp__my_database__query`），执行路径经过 `MCPTool.call` 方法（`client.ts` 约第 1833 行）。它把参数打包成 JSON-RPC 请求，发给对应的 MCP 服务器：

```typescript
// 文件：src/services/mcp/client.ts，约第1862行（简化）
const connectedClient = await ensureConnectedClient(client)
const result = await connectedClient.client.request(
  {
    method: 'tools/call',
    params: {
      name: tool.name,          // 原始工具名，如 "query"
      arguments: args,           // AI 传入的参数
    },
  },
  CallToolResultSchema,
)
```

注意 `ensureConnectedClient`——它会检查连接是否还活着。如果会话过期了（HTTP 404 + JSON-RPC 错误码 -32001），会自动重新连接。这是 `client.ts` 约第 193 行定义的 `isMcpSessionExpiredError` 检测到的。

结果返回后，还需要一步处理：MCP 服务器可能返回图片、文件等二进制内容。`transformMCPResult` 函数（约第 2662 行）负责把这些内容转成 AI 能理解的格式——图片会被缩小和压缩，大文本会被截断。

### 第六步：清理——断开连接

当 MCP 服务器断开连接（网络波动、服务器重启），`client.ts` 里设置的 `onclose` 回调会被触发。对于远程传输（SSE、HTTP、WebSocket），Claude Code 会尝试自动重连。

重连策略是 **指数退避**：第 1 次等 1 秒，第 2 次等 2 秒，第 3 次等 4 秒……最多重试 5 次，最长间隔 30 秒。定义在 `useManageMCPConnections.ts` 约第 88 行：

```typescript
// 文件：src/services/mcp/useManageMCPConnections.ts，约第88行
const MAX_RECONNECT_ATTEMPTS = 5
const INITIAL_BACKOFF_MS = 1000
const MAX_BACKOFF_MS = 30000
```

如果 5 次都失败了，服务器状态变成 `failed`，工具被清空。用户可以在 `/mcp` 面板里手动重连。

对于 stdio 类型的服务器（本地子进程），断开通常意味着进程崩溃了，不会自动重连——因为进程死了，重连也没意义。

还有一个动态清理场景：当你运行 `/reload-plugins` 时，`excludeStalePluginClients` 函数（`utils.ts` 约第 185 行）会比较当前配置和已有连接的哈希值。配置变了的服务器会被标记为过期，断开旧连接，建立新连接。

### 一个完整的生命周期图

把上面六步串起来：

```
配置加载 → pending 状态
  ↓
connectToServer → stdio/http/sse/ws 分支
  ↓
client.connect(transport) → JSON-RPC 握手
  ↓
成功 → connected / 失败 → failed / 要认证 → needs-auth
  ↓
fetchToolsForClient → tools/list 请求
  ↓
工具重命名 → mcp__server__tool 格式
  ↓
flushPendingUpdates → 合并到 AppState.mcp.tools
  ↓
AI 看到工具 → 调用 → MCPTool.call → tools/call 请求
  ↓
服务器断开 → onclose → 自动重连（远程）或 failed（本地）
```

从配置到可用，一个 MCP 工具需要走过完整的六步。每一步都有对应的源码文件和函数。整个流程是事件驱动的——连接结果、工具列表变更、服务器断开，都通过回调或通知触发状态更新。

## 对比 Java

如果你学过 Java，MCP 的架构会让你想起两个东西。

**第一个是 JDBC**。JDBC 定义了一套统一的数据库访问接口——`Connection`、`Statement`、`ResultSet`。不管底层是 MySQL、PostgreSQL 还是 Oracle，只要提供了 JDBC 驱动，Java 程序就能用同一套代码访问。MCP 的角色类似：它定义了统一的工具发现和调用接口，不管底层是文件系统、数据库还是浏览器，只要实现了 MCP 协议，Claude Code 就能用同一套代码调用。

```
JDBC 世界：
  Java 程序 → JDBC 接口 → MySQL 驱动 → MySQL 数据库
  Java 程序 → JDBC 接口 → PG 驱动   → PostgreSQL 数据库

MCP 世界：
  Claude Code → MCP 协议 → 文件系统服务器 → 操作系统文件
  Claude Code → MCP 协议 → 数据库服务器   → MySQL/PostgreSQL
  Claude Code → MCP 协议 → 浏览器服务器   → Chrome DevTools
```

**第二个是 OSGi 插件系统**。OSGi 允许 Java 应用在运行时动态发现、加载、卸载插件（它叫 Bundle）。每个 Bundle 声明自己提供的服务，框架自动匹配和注册。MCP 的服务器也有类似的动态性——运行时发现、注册工具，服务器可以随时上线或下线，工具列表通过 `listChanged` 通知动态更新。

不过 MCP 比 JDBC 和 OSGi 更进一步：它把 **传输层也标准化了**。JDBC 驱动是 Java 类，得放在 classpath 里。MCP 服务器可以是本地子进程（stdio），可以是远程 HTTP 服务，可以是 WebSocket 连接——传输方式不同，但协议层完全一样。这让 MCP 天然支持分布式部署。

## 你能改什么

### 添加一个新的 MCP 服务器

最简单的方式是创建或编辑项目根目录的 `.mcp.json` 文件：

```json
{
  "mcpServers": {
    "weather": {
      "command": "npx",
      "args": ["-y", "@anthropic/mcp-weather"],
      "env": {
        "API_KEY": "${WEATHER_API_KEY}"
      }
    }
  }
}
```

或者用命令行：

```bash
claude mcp add weather -s project -- npx -y @anthropic/mcp-weather
```

这个命令最终调用的是 `config.ts` 里的 `addMcpConfig` 函数（约第 625 行），它会验证名字合法性（只允许字母、数字、连字符、下划线）、检查企业策略是否允许、防止重名，然后写入 `.mcp.json`。

### 构建一个自定义 MCP 工具服务器

如果你想自己写一个 MCP 服务器，MCP 官方提供了 TypeScript SDK。最小例子：

```typescript
import { McpServer } from '@modelcontextprotocol/sdk/server/mcp.js'
import { StdioServerTransport } from '@modelcontextprotocol/sdk/server/stdio.js'
import { z } from 'zod'

const server = new McpServer({ name: 'my-tools', version: '1.0.0' })

server.tool(
  'hello',                          // 工具名
  '向指定的人问好',                    // 描述（AI 靠这个决定何时调用）
  { name: z.string().describe('名字') }, // 输入 Schema
  async ({ name }) => ({             // 处理函数
    content: [{ type: 'text', text: `你好，${name}！` }]
  })
)

const transport = new StdioServerTransport()
await server.connect(transport)
```

然后在 `.mcp.json` 里配置：

```json
{
  "mcpServers": {
    "my-tools": {
      "command": "node",
      "args": ["./my-mcp-server.js"]
    }
  }
}
```

Claude Code 启动时会自动连接这个服务器，发现 `hello` 工具，注册为 `mcp__my_tools__hello`。AI 就能调用它了。

### 理解工具注解

MCP 工具可以声明注解（Annotations），Claude Code 会尊重这些声明。在 `client.ts` 约 第 1796 行，你能看到：

- `readOnlyHint`——标记为只读工具，不修改任何状态，可以安全并发。
- `destructiveHint`——标记为破坏性工具（如删除文件），系统会特别提示。
- `openWorldHint`——标记工具访问外部世界（如发 HTTP 请求），影响权限判断。

你的自定义工具可以通过这些注解跟 Claude Code 的权限和安全系统协作。

### 调试 MCP 连接问题

如果 MCP 服务器连不上，可以设置环境变量获取详细日志：

```bash
export MCP_DEBUG=1
claude
```

这会启用 `logMCPDebug` 输出，你能看到完整的连接过程：传输层创建、握手请求、工具发现、错误详情。所有调试日志都来自 `src/services/mcp/client.ts` 中的 `logMCPDebug` 和 `logMCPError` 调用。

还可以设置 `MCP_TIMEOUT` 环境变量调整连接超时（默认 30 秒），设置 `MCP_TOOL_TIMEOUT` 调整工具调用超时。

## 小结

这一章我们从配置文件走到工具调用，跟踪了 MCP 的完整生命周期：

1. **配置**来自多个来源（`.mcp.json`、全局设置、企业策略、claude.ai），按优先级合并。
2. **连接**根据传输类型分叉——stdio 启子进程，HTTP/SSE 走网络。底层统一用 JSON-RPC 2.0。
3. **发现**通过 `tools/list` 请求获取工具列表，重命名为 `mcp__server__tool` 格式防止冲突。
4. **注册**通过批处理机制合并到 AppState，跟内置工具放在一起，对 AI 透明。
5. **使用**时通过 `tools/call` 转发请求，自动处理会话过期和重连。
6. **清理**时远程服务器自动重连（指数退避），本地进程直接标记失败。

MCP 把 Claude Code 从一个封闭的工具箱变成了一个开放的平台。只要有人写了 MCP 服务器，AI 的能力就能无限扩展。下一章，我们看另一种扩展方式——Agent 的克隆和协作。
