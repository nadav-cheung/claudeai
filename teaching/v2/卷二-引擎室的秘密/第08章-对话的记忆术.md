# 第08章：对话的记忆术

你正在和 Claude Code 进行一场深入的对话。你让它读文件、改代码、跑测试、修 bug，来回几十轮。每一条消息——你的输入、AI 的回复、工具的执行结果——都堆在上下文窗口里，像越叠越高的积木塔。

突然有一天，积木塔碰到了天花板。

这个天花板叫**上下文窗口（context window）**。AI 模型一次能"看到"的文本是有限的，通常在 128K 到 200K 个 token 之间。你的对话一旦超出这个限制，AI 就看不到最早的消息了。但 Claude Code 不能简单地砍掉老消息——那些老消息里可能包含关键的代码片段、重要的用户需求、刚修完的 bug 记录。

怎么办？Claude Code 的答案是一套精密的"记忆术"：在不丢失关键信息的前提下，把长对话压缩成精简版本。这个过程叫 **compaction（压缩）**，它不只是删，更是**总结**——让 AI 用更少的 token 记住更多的事。

这一章，我们打开引擎室的记忆系统，看看 Claude Code 怎么决定什么时候压缩、压缩什么、保留什么。

---

## 这是什么

想象你在读一本 1000 页的小说，突然有人要求你用 50 页复述整个故事。你会怎么做？

你不会逐字抄写——那没有节省任何东西。你会**总结**：主线剧情保留，人物关系保留，关键对话保留，但那些冗长的风景描写、重复的铺垫、已经解决的支线，都被压缩成几句话。

Claude Code 的 compaction 做的是同样的事。当对话越来越长，接近上下文窗口的极限时，系统会启动压缩流程：

1. 把历史对话交给 AI
2. 让 AI 生成一份详细的摘要——包括用户的请求、代码改动、错误修复、待办任务
3. 用这份摘要替换掉原来的历史消息
4. 保留最近几轮对话的原样

压缩之后，AI 的上下文从"1000 页原文"变成"50 页摘要 + 最近几页原文"。关键信息没有丢失，但 token 消耗大幅下降。

Claude Code 其实不只有一种压缩方式。它有三套不同力度的记忆术，按"轻量"到"重量"排列：

- **Micro-compact（微压缩）**：不生成摘要，只是把旧工具的执行结果清空或标记为已删除。最轻量，几乎无感。
- **Session memory compaction（会话记忆压缩）**：利用预提取的会话记忆文件作为摘要，保留最近的对话尾部。中等力度，不需要额外的 API 调用。
- **Full compaction（全量压缩）**：调用 AI 生成完整对话摘要，替换所有历史消息。最重量，压缩效果最好。

让我们一个个打开看。

## 它怎么工作

### 第一道防线：微压缩（Micro-compact）

微压缩是 Claude Code 最安静的记忆术。你可能用了很久 Claude Code 都不知道它的存在——因为它不会生成摘要，不会重启对话，只是悄悄地把旧工具的执行结果"清空"。

为什么要清空工具结果？想一想：你让 AI 读了一个 500 行的文件，这个文件内容就作为"工具执行结果"留在上下文里。几轮对话之后，AI 不再需要看到那个文件的完整内容了——它已经知道文件里有什么。但那些 token 还占着位置。

微压缩做的事情就是：找到那些"老"的工具结果，把它们替换成一个简短的标记 `[Old tool result content cleared]`。

在 `src/services/compact/microCompact.ts` 约第 36 行，定义了这个替换文本：

```typescript
// 文件：src/services/compact/microCompact.ts，约第36行
export const TIME_BASED_MC_CLEARED_MESSAGE = '[Old tool result content cleared]'
```

但不是所有工具结果都会被清除。约第 41-50 行定义了一个白名单：

```typescript
// 文件：src/services/compact/microCompact.ts，约第41-50行
const COMPACTABLE_TOOLS = new Set<string>([
  FILE_READ_TOOL_NAME,   // 读文件
  ...SHELL_TOOL_NAMES,   // Shell命令
  GREP_TOOL_NAME,        // 搜索
  GLOB_TOOL_NAME,        // 文件匹配
  WEB_SEARCH_TOOL_NAME,  // 网页搜索
  WEB_FETCH_TOOL_NAME,   // 网页抓取
  FILE_EDIT_TOOL_NAME,   // 文件编辑
  FILE_WRITE_TOOL_NAME,  // 文件写入
])
```

只有这些工具的结果才会被清除。为什么？因为这些工具的输出通常很长（一个文件可能有几千行），但信息在后续对话中往往已经"被消化"了。而其他类型的工具结果可能包含关键的交互状态，不应该被自动清除。

微压缩有两种触发方式。第一种是**基于时间**的触发。在 `src/services/compact/timeBasedMCConfig.ts` 里，默认配置是：当距离上一次 AI 回复超过 60 分钟时，清除旧工具结果。为什么是 60 分钟？因为服务端的 prompt cache（提示缓存）的 TTL（存活时间）大约是 1 小时。缓存已经过期了，下次 API 调用会重写全部前缀——既然要重写，不如先瘦身再重写，省点 token。

第二种是**缓存编辑**（cache editing）方式——这是更高级的技术。它不修改本地消息内容，而是通过 API 的 `cache_edits` 功能告诉服务端："这几条工具结果你帮我删掉，但不要让缓存失效。"这样既省了 token，又保住了缓存命中率。

### 第二道防线：会话记忆压缩（Session Memory Compaction）

如果微压缩不够用，Claude Code 会尝试一种更智能的方式：利用**会话记忆（session memory）**文件来做压缩。

会话记忆是什么？简单来说，Claude Code 在对话过程中会持续提取关键信息，写入一个独立的文件。这个文件包含了对话的结构化摘要——用户的需求、技术决策、代码改动记录等等。

在 `src/services/compact/sessionMemoryCompact.ts` 的 `trySessionMemoryCompaction` 函数（约第 514 行）中，这个流程是：

1. 检查是否有会话记忆文件存在
2. 如果存在，计算要保留最近多少条消息
3. 用会话记忆作为摘要，替换被保留之前的所有历史
4. 保留最近的消息不动

它的优势是**不需要额外的 API 调用**——不需要让 AI 现场生成摘要，因为摘要已经在会话记忆里准备好了。这既省钱又省时间。

保留最近多少条消息？在约第 324-397 行的 `calculateMessagesToKeepIndex` 函数里，有三个关键参数：

```typescript
// 文件：src/services/compact/sessionMemoryCompact.ts，约第57-61行
export const DEFAULT_SM_COMPACT_CONFIG: SessionMemoryCompactConfig = {
  minTokens: 10_000,          // 至少保留1万个token的最近消息
  minTextBlockMessages: 5,    // 至少保留5条有文本内容的消息
  maxTokens: 40_000,          // 最多保留4万个token（硬上限）
}
```

系统从最后一条被摘要覆盖的消息开始向前扫描，一直扩展到满足"至少 1 万 token"和"至少 5 条文本消息"这两个最低要求。但也设了 4 万 token 的上限，防止保留太多。

还有一个精妙的细节：`adjustIndexToPreserveAPIInvariants` 函数（约第 232 行）确保保留的消息不会在中间切断 `tool_use` 和 `tool_result` 的配对关系。如果你只保留了 `tool_result` 但丢掉了对应的 `tool_use`，API 会报错——因为每个工具执行结果都必须有一个对应的工具调用请求。

### 第三道防线：全量压缩（Full Compaction）

当微压缩和会话记忆压缩都不够用时，Claude Code 会祭出最后的手段：**全量压缩**。

全量压缩的核心函数是 `src/services/compact/compact.ts` 里的 `compactConversation`，从约第 387 行开始。它的工作流程是：

**第一步：执行前置钩子。** 在压缩开始前，运行用户或插件注册的 `pre_compact` 钩子，这些钩子可以注入额外的压缩指令。

**第二步：构建压缩提示词。** 在 `src/services/compact/prompt.ts` 里，有一个精心设计的提示词模板。这个模板告诉 AI 怎么写摘要：

```typescript
// 文件：src/services/compact/prompt.ts，约第61-77行
// （提示词的一部分，定义了摘要必须包含的9个部分）
1. Primary Request and Intent        -- 用户的主要请求
2. Key Technical Concepts            -- 关键技术概念
3. Files and Code Sections           -- 涉及的文件和代码
4. Errors and fixes                  -- 遇到的错误和修复方式
5. Problem Solving                   -- 问题解决过程
6. All user messages                 -- 所有用户消息（非工具结果）
7. Pending Tasks                     -- 待办任务
8. Current Work                      -- 当前正在做的工作
9. Optional Next Step                -- 下一步计划
```

注意第 6 条——要求列出**所有用户消息**。这是因为用户说的话比工具结果重要得多。工具结果可以重新获取（再读一遍文件就行了），但用户说过什么、改过什么主意，一旦丢失就无法恢复。

**第三步：调用 AI 生成摘要。** 这里有一个巧妙的设计——系统会尝试利用**缓存共享**（cache sharing）。在约第 1179 行，它先尝试通过 `runForkedAgent` 发起一个"分叉"请求，复用主对话的缓存前缀。如果缓存共享失败，才退回到普通的流式请求。

**第四步：恢复关键附件。** 压缩之后，上下文里那些"刚刚读过哪些文件"的信息会被清空。但 AI 可能还需要这些文件。所以在约第 1415 行的 `createPostCompactFileAttachments` 函数里，系统会自动重新读取最近访问过的文件（最多 5 个，每个不超过 5000 token），作为附件注入到压缩后的上下文里：

```typescript
// 文件：src/services/compact/compact.ts，约第122-130行
export const POST_COMPACT_MAX_FILES_TO_RESTORE = 5
export const POST_COMPACT_TOKEN_BUDGET = 50_000
export const POST_COMPACT_MAX_TOKENS_PER_FILE = 5_000
export const POST_COMPACT_MAX_TOKENS_PER_SKILL = 5_000
export const POST_COMPACT_SKILLS_TOKEN_BUDGET = 25_000
```

这些常量控制着压缩后的"恢复预算"——最多花 5 万 token 恢复文件内容，花 2.5 万 token 恢复技能（skill）内容。

**第五步：创建边界标记。** 在约第 598 行，系统创建一个 `compactBoundary` 消息，标记压缩发生的位置。这个标记记录了压缩的类型（自动还是手动）、压缩前的 token 数量。它就像书签，告诉系统"从这里开始是摘要，之前的内容已经被压缩了"。

### 压缩的触发时机

那么，Claude Code 怎么知道什么时候该压缩？

答案在 `src/services/compact/autoCompact.ts` 里。约第 72-91 行的 `getAutoCompactThreshold` 函数计算了触发阈值：

```typescript
// 文件：src/services/compact/autoCompact.ts，约第72-91行
export function getAutoCompactThreshold(model: string): number {
  const effectiveContextWindow = getEffectiveContextWindowSize(model)
  const autocompactThreshold =
    effectiveContextWindow - AUTOCOMPACT_BUFFER_TOKENS  // 减去1.3万token的缓冲
  return autocompactThreshold
}
```

缓冲区大小是 13000 token（约第 62 行的 `AUTOCOMPACT_BUFFER_TOKENS`）。也就是说，当上下文使用量达到"有效窗口 - 13000"时，自动压缩就会触发。这个缓冲区确保压缩有足够的空间完成——压缩本身也需要消耗 token（生成摘要、处理附件等）。

系统还设计了多层警告（约第 93-145 行的 `calculateTokenWarningState` 函数）：

- **警告阈值**：距离自动压缩还有 20000 token 时，显示警告。
- **错误阈值**：距离自动压缩还有 20000 token 时（与警告重叠，但用途不同）。
- **阻塞阈值**：上下文几乎满了，必须手动压缩才能继续。

还有一个贴心的**熔断器**（circuit breaker）机制。约第 70 行定义了最大连续失败次数：

```typescript
// 文件：src/services/compact/autoCompact.ts，约第70行
const MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3
```

如果自动压缩连续失败 3 次，系统就不再尝试了。这是一个自我保护机制——避免在上下文已经爆炸的情况下，反复发起注定失败的 API 调用，白白浪费资源。

### 部分压缩（Partial Compact）

除了全量压缩，Claude Code 还支持一种"精确制导"的压缩方式——**部分压缩**。在 `compact.ts` 的 `partialCompactConversation` 函数（约第 772 行）中，用户可以选择只压缩对话的某一截：

- **`from` 方向**：从指定消息往后压缩，保留前面的部分。前面部分的 prompt cache 不受影响。
- **`up_to` 方向**：从指定消息往前压缩，保留后面的部分。后面的部分保持原样。

这种设计让用户可以精细控制哪些对话被压缩。比如你可以说"保留最近讨论架构的部分，但之前调试 bug 的过程可以压缩掉"。

### 压缩后的清理

压缩完成后，不能就这么算了。系统里还有大量缓存和状态需要重置。`src/services/compact/postCompactCleanup.ts` 的 `runPostCompactCleanup` 函数（约第 31 行）负责这项工作：

```typescript
// 文件：src/services/compact/postCompactCleanup.ts，约第31行
export function runPostCompactCleanup(querySource?: QuerySource): void {
  resetMicrocompactState()        // 重置微压缩状态
  clearSystemPromptSections()     // 清空系统提示缓存
  clearClassifierApprovals()      // 清空分类器审批缓存
  clearSpeculativeChecks()        // 清空推测性权限检查
  clearSessionMessagesCache()     // 清空会话消息缓存
  // ... 还有更多清理操作
}
```

注意，代码注释特别指出**不清除已调用的技能（skill）内容**——技能内容必须跨多次压缩存活下来，这样后续压缩时才能把技能文本包含在附件里。

## 对比 Java

如果你学过 Java，Claude Code 的压缩机制会让你想起两个经典概念。

### 对比一：垃圾回收（Garbage Collection）

Java 的垃圾回收器（GC）负责自动回收不再使用的内存。它有几个关键特征和 Claude Code 的压缩很像：

- **分代回收**：Java GC 把堆内存分为新生代和老生代，新对象在新生代分配，存活够久的对象晋升到老生代。Claude Code 的三道防线也有类似的"分代"思路——微压缩是最轻量的"新生代回收"，只清理工具结果；会话记忆压缩是中等力度的回收；全量压缩是"全堆回收"，处理整个对话历史。

- **触发阈值**：Java GC 不是等到内存完全满了才回收，而是在达到某个水位线（比如堆使用率 75%）时触发。Claude Code 也一样，在上下文使用量达到"有效窗口 - 13000 token"时就启动自动压缩，留出缓冲空间。

- **安全点（Safepoint）**：Java GC 需要找到安全点才能开始回收，不能在任意时刻暂停应用。Claude Code 的压缩也需要"安全点"——`groupMessagesByApiRound`（在 `src/services/compact/grouping.ts` 里）按 API 轮次对消息分组，确保不会在 `tool_use` 和 `tool_result` 中间切断。这就像 GC 不能在一个对象还在被引用的时候回收它。

但有一个关键区别：Java GC 是完全自动的，开发者几乎不需要干预。而 Claude Code 的压缩提供了手动控制——用户可以随时执行 `/compact` 命令手动触发，甚至可以传入自定义指令（"压缩时重点保留测试相关的内容"）。这更像 Java 的 `System.gc()`——只是 Claude Code 的版本更有用。

### 对比二：缓存淘汰策略（Cache Eviction）

Java 的缓存框架（如 Guava Cache、Caffeine）需要决定什么时候淘汰旧数据。常见的策略有 LU（最近最少使用）、LFU（最不经常使用）等。

Claude Code 的微压缩本质上也是一种缓存淘汰。它保留最近 N 条工具结果（`keepRecent` 参数），淘汰更早的。这和 LRU 策略的思路一致——最近用过的数据，接下来被再次用到的概率更高。

但微压缩比 LRU 多了一个维度：**时间感知**。在 `src/services/compact/timeBasedMCConfig.ts` 里，如果距离上一次 AI 回复超过 60 分钟，说明 prompt cache 已经过期了——不管那些工具结果"最近"有没有被用到，全部清除。这更像是 Java 缓存框架的 **TTL（Time To Live）** 策略——缓存条目有保质期，过期就淘汰。

## 你能改什么

### 入门级：理解和使用

**手动触发压缩。** 在对话过程中输入 `/compact` 可以随时手动触发压缩。你还可以附加自定义指令：`/compact 请重点保留关于数据库迁移的所有讨论`。这些指令会被注入到压缩提示词的 "Additional Instructions" 部分，引导 AI 在摘要中保留你关心的内容。

**理解压缩警告。** 当你看到 Claude Code 显示 "Context left until auto-compact" 的警告时，意味着上下文使用量已经接近阈值。这是系统在提醒你：对话即将自动压缩，如果你想让 AI 记住某些重要信息，最好现在就确认它们是否已经被 AI 充分理解。

**查看压缩后的摘要。** 压缩完成后，摘要被保存在会话的 transcript 文件里。摘要里包含了用户消息、代码改动、错误修复等关键信息。如果你觉得摘要遗漏了重要内容，可以在下次压缩时通过自定义指令提醒 AI。

### 中级：调整压缩参数

**调整自动压缩阈值。** 通过环境变量 `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` 可以控制自动压缩在上下文使用率达到多少百分比时触发。比如设置为 80 表示在上下文使用率达到 80% 时就压缩（比默认的更早触发）：

```bash
export CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=80
```

**调整上下文窗口大小。** 环境变量 `CLAUDE_CODE_AUTO_COMPACT_WINDOW` 可以手动设置上下文窗口的上限（单位是 token 数），让压缩更早或更晚触发。

**禁用自动压缩。** 如果你不想让系统自动压缩（比如你在做长时间的自动化任务），可以设置：

```bash
export DISABLE_AUTO_COMPACT=true
```

这会禁用自动压缩，但手动 `/compact` 命令仍然可用。如果你连手动压缩也想禁用（不推荐），可以设置 `DISABLE_COMPACT=true`。

**关闭用户配置中的自动压缩。** Claude Code 的全局配置里有一个 `autoCompactEnabled` 选项。在 `src/services/compact/autoCompact.ts` 约第 147-158 行的 `isAutoCompactEnabled` 函数中，系统会检查这个配置。你可以通过 Claude Code 的设置界面或配置文件来切换。

### 高级：自定义压缩行为

**利用 Pre-compact 钩子。** Claude Code 支持 `PreCompact` 和 `PostCompact` 类型的钩子。你可以在 `.claude/hooks/` 目录下配置脚本，在压缩前注入自定义指令，或在压缩后执行清理操作。比如你可以在每次压缩前提醒 AI "保留所有与安全漏洞相关的讨论"。

**理解 PTL 重试机制。** 偶尔压缩请求本身也会因为太长而失败（"压缩也需要上下文"这个悖论）。在 `compact.ts` 约第 243-291 行的 `truncateHeadForPTLRetry` 函数里，系统会把最老的消息分组砍掉，只保留较新的部分重新尝试压缩。最多重试 3 次（`MAX_PTL_RETRIES`）。如果你遇到"Compaction interrupted"的错误，通常是这个重试机制也失败了——可能需要手动缩短对话。

### 危险区域

**修改压缩提示词。** `src/services/compact/prompt.ts` 里的提示词模板直接影响摘要的质量。如果你修改了摘要必须包含的部分（比如去掉"Errors and fixes"这个要求），AI 就不再在摘要里保留错误修复记录——这可能让压缩后的对话丢失关键信息。

**修改保留预算。** `POST_COMPACT_MAX_FILES_TO_RESTORE`、`POST_COMPACT_TOKEN_BUDGET` 等常量控制压缩后恢复多少文件内容。如果你大幅降低这些值，AI 压缩后可能忘记它正在编辑的文件内容，需要重新读取，降低效率。如果你大幅增加这些值，压缩可能省不了多少 token，失去意义。

**修改微压缩的工具白名单。** `COMPACTABLE_TOOLS` 集合决定哪些工具的结果可以被自动清除。如果你往里加了不该加的工具（比如某个返回关键状态的工具），可能会在 AI 还需要这些信息的时候把它们清空。

## 回顾

这一章，我们跟着 Claude Code 的记忆系统走了一遍：

1. **三道防线**层层递进：微压缩清除旧工具结果（最轻量）、会话记忆压缩利用预提取的摘要（中等力度）、全量压缩调用 AI 生成完整摘要（最彻底）。
2. **触发时机**由 token 阈值控制，留出 13000 token 的缓冲区确保压缩有空间完成。熔断器防止连续失败时浪费 API 调用。
3. **保留策略**精心设计：压缩后自动恢复最近访问的文件、保留技能内容、维持 tool_use/tool_result 的配对关系。
4. **对比 Java**：压缩机制像垃圾回收（分代回收、触发阈值、安全点），也像缓存淘汰（LRU + TTL 的时间感知策略）。
5. **用户可控**：从手动 `/compact` 带自定义指令，到环境变量调整阈值，再到钩子系统自定义压缩行为。

对话被压缩了，但记忆没有丢失。下一章，我们走出对话的边界，看看 Claude Code 如何连接外部世界——工具怎么发现、MCP 服务器怎么注册、插件怎么加载。
