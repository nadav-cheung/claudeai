# 第06章：AI说要执行一条命令

AI 的回答不是普通的文字。在流式数据中，出现了一个特殊的标记：`tool_use`。AI 想执行一条命令。

上一章里，我们看着 AI 的回答一个字一个字地流回来——"你"、"好"、","、"这"、"是"——像水龙头一样，一滴一滴。我们学会了怎么用 `AsyncGenerator` 接住这些水滴，学会了流式传输的基本原理。

但你有没有想过一个问题：如果 AI 只会"说话"，它怎么帮你修 bug？

它能告诉你"你的代码第三行有个拼写错误"，但你还是得自己去改。它能告诉你"试试运行 `npm test`"，但你还是得自己动手敲命令。

这不像一个真正的助手。真正的助手会说："让我来看看"，然后自己去翻代码；会说："我来帮你运行一下测试"，然后自己去敲命令。

Claude Code 里的 AI 就是这样的助手。它不只是说话——它会"动手"。

但"动手"这件事，在代码世界里怎么表达？一条流式传输的数据流里，怎么区分"AI 在说话"和"AI 要做事"？

答案就藏在一个小小的标记里：`tool_use`。

---

## 一条消息，两种内容

先回忆一下上一章看到的画面。AI 的回答像一条河流一样流回来。这条河里流的不是普通的水，而是一个一个"内容块"（content block）。

有些内容块是文字——AI 在跟你说话。比如：

```json
{
  "type": "text",
  "text": "让我先看看你的代码，找找 bug 在哪里。"
}
```

但有些内容块不是文字。它们是另一种东西——"工具使用请求"：

```json
{
  "type": "tool_use",
  "id": "toolu_01A09q90qw90lq917835lq9",
  "name": "Bash",
  "input": {
    "command": "cd /Users/nadav/my-project && npm test"
  }
}
```

看到区别了吗？同样是内容块，但 `type` 字段不一样。一个是 `"text"`，一个是 `"tool_use"`。

这就像你收到一个快递。快递有两种：一种是信件，里面是别人写给你的话；一种是包裹，里面是别人寄给你的东西。外表看起来差不多，但打开方式完全不同。

在 TypeScript 的世界里，这种"一个值可以是 A 也可以是 B"的概念，叫做**联合类型**（union type）。

---

## 联合类型：快递可以是信件或包裹

联合类型的写法很简单，用 `|` 符号连接：

```typescript
type ContentBlock = TextBlock | ToolUseBlock
```

这行代码的意思是：一个 `ContentBlock`，要么是 `TextBlock`，要么是 `ToolUseBlock`。就像说"今天的快递，要么是信件，要么是包裹"。

`TextBlock` 长这样：

```typescript
type TextBlock = {
  type: "text"
  text: string
}
```

`ToolUseBlock` 长这样（简化版）：

```typescript
type ToolUseBlock = {
  type: "tool_use"
  id: string
  name: string
  input: object
}
```

两个类型都有一个 `type` 字段，但值不一样。一个是 `"text"`，一个是 `"tool_use"`。

你可能会好奇：为什么不用两个完全独立的类型？为什么非要共享一个 `type` 字段？

因为 Claude Code 的代码需要处理一条消息里的所有内容块。有时候一条消息里有三个文字块加两个工具请求块，它们混在一起。代码需要一个统一的方式来遍历它们，然后在遇到每一个的时候判断："这个是文字，还是工具请求？"

而判断的方法，就是看 `type` 字段。

---

## 类型守卫：看一眼快递标签

当你手里拿着一个快递，你怎么知道它是信件还是包裹？你会看标签。

在 TypeScript 里，"看标签"这个动作叫做**类型守卫**（type guard）。

Claude Code 的源码里充满了这种类型守卫。在 `src/query.ts` 第 829-831 行，你会看到这样的代码：

```typescript
const msgToolUseBlocks = message.message.content.filter(
  content => content.type === 'tool_use',
) as ToolUseBlock[]
```

这段代码做的事情用大白话说就是：从消息的所有内容块里，把 `type` 是 `"tool_use"` 的挑出来。

`content => content.type === 'tool_use'` 这个箭头函数就是一个类型守卫。它检查每个内容块的 `type` 字段：如果是 `"tool_use"`，保留；否则，丢弃。

这种模式在 Claude Code 里反复出现。几乎每个需要处理 AI 回复的地方，第一件事就是把内容块按类型分开——文字块走文字块的逻辑，工具请求块走工具请求块的逻辑。

`as ToolUseBlock[]` 是 TypeScript 的**类型断言**，意思是："我确认过滤出来的这些东西都是 `ToolUseBlock` 类型，请编译器按照这个类型来处理。"就好像你把挑出来的包裹放到一个专门的架子上，上面挂个牌子写着"包裹区"。

你可能注意到一个细节：`"tool_use"` 这个字符串被用在了判断条件里。为什么不用数字，比如 1 表示文字、2 表示工具请求？

因为字符串有语义。当你读代码的时候，看到 `content.type === 'tool_use'`，你立刻就知道这是在找工具请求。但如果看到 `content.type === 2`，你得去查文档才知道 2 代表什么。

而且，TypeScript 有一种更强大的写法来约束这些字符串值。

---

## 字符串字面量类型：不是随便什么字符串

在普通的 TypeScript 里，`string` 类型表示"随便什么字符串"——`"hello"` 可以，`"tool_use"` 可以，`"随便什么"` 也可以。

但有时候你不想让字符串"随便"。你希望这个字段的值只能是某几个特定的字符串之一。

这就是**字符串字面量类型**（string literal type）。看看 `TextBlock` 和 `ToolUseBlock` 的 `type` 字段：

```typescript
type TextBlock = {
  type: "text"       // 不是 string，而是 "text" 这个具体的字符串
  text: string
}

type ToolUseBlock = {
  type: "tool_use"   // 不是 string，而是 "tool_use" 这个具体的字符串
  id: string
  name: string
  input: object
}
```

`type: "text"` 不是在说"这个字段的类型是字符串"。它是在说"这个字段的值必须恰好是 `"text"` 这四个字母，不能是别的"。

类比一下：`string` 类型像一张空白名片——你可以在上面写任何名字。字符串字面量类型 `"text"` 像一张印好的名片——上面已经印好了 "text" 这个名字，你不能改。

这种精确性有什么好处？

好处在于：当你写 `content.type === 'tool_use'` 的时候，TypeScript 编译器会检查——如果 `content` 的 `type` 字段只能是 `"text"` 或 `"tool_use"` 之一，那你写 `'tool_use'` 就是合法的判断条件。但如果你手误写成了 `'tool_ue'`，编译器会报错，因为它知道没有这个选项。

这种编译器帮你检查的能力，在大项目里特别有用。Claude Code 有几十万行代码，如果 `type` 字段可以用任何字符串，那你永远不知道自己是不是拼错了。字符串字面量类型让编译器变成了一双额外的眼睛。

## tool_use 块里装了什么

现在我们知道了 `tool_use` 是一种特殊的内容块。但它的内部结构是什么样的？让我们把它的三个关键字段拆开来看。

回到前面的例子：

```json
{
  "type": "tool_use",
  "id": "toolu_01A09q90qw90lq917835lq9",
  "name": "Bash",
  "input": {
    "command": "cd /Users/nadav/my-project && npm test"
  }
}
```

**`name`：工具的名字。** 这个字段告诉 Claude Code："AI 想用哪个工具？" 在这个例子里，名字是 `"Bash"`，意思是 AI 想执行一条 Bash 命令。Claude Code 内置了很多工具——`Read` 用来读文件，`Write` 用来写文件，`Edit` 用来编辑文件，`Bash` 用来执行命令，等等。每个工具都有自己的名字。

**`input`：工具的参数。** 这个字段告诉 Claude Code："AI 想怎么用这个工具？" 在这个例子里，`input` 是一个对象，里面有一个 `command` 字段，值是 AI 想执行的 Bash 命令字符串。不同的工具，`input` 的结构不一样。`Read` 工具的 input 里会有 `file_path` 字段；`Bash` 工具的 input 里有 `command` 字段。

**`id`：这次工具调用的唯一标识。** 这个字段看起来像一串随机字符。它的作用是给这次工具调用一个身份证号。为什么需要身份证号？因为 AI 的一次回答可能触发多个工具调用，每个调用都会产生一个结果。这些结果需要跟对应的调用匹配上——就像快递要有快递单号一样，这样你才知道哪个结果是哪个请求的回复。

这三个字段组成了一个完整的"行动指令"：**谁来做**（name）、**怎么做**（input）、**这是哪一单**（id）。

## 大脑和手：AI 与工具的关系

在深入看代码之前，让我们先建立一个大图景的理解。

AI 模型——Claude——就像一个大脑。它能思考、能分析、能做决策。但它没有手。它不能自己打开文件、不能自己执行命令、不能自己修改代码。

工具就是 AI 的手。

Claude Code 给 AI 准备了一整套"手"：

- **Bash** —— 可以执行终端命令的手
- **Read** —— 可以阅读文件的手
- **Write** —— 可以创建文件的手
- **Edit** —— 可以修改文件的手
- **Glob** —— 可以搜索文件的手
- **Grep** —— 可以搜索文件内容的手

每一只"手"都有自己的能力范围。Bash 手能做几乎所有终端能做的事。Read 手只能看，不能改。Write 手能创建新文件，但只能从头写。

当 AI 遇到一个问题时，它会思考"我需要做什么"，然后决定"我应该用哪只手"。这就是 `tool_use` 块的来源——AI 在它的思考过程中决定"我需要执行一条 Bash 命令来运行测试"，于是在回答里插入了一个 `tool_use` 块，`name` 设为 `"Bash"`，`input` 里写上命令。

但 AI 只能"请求"使用工具。它不能真的"使用"。真正执行命令、读取文件、修改代码的，是 Claude Code 这个程序。

所以整个流程是这样的：

1. AI 思考："我需要运行测试"。
2. AI 在回答里插入一个 `tool_use` 块：`name: "Bash"`，`input: { command: "npm test" }`。
3. Claude Code 从流式数据中识别出这个 `tool_use` 块。
4. Claude Code 找到名叫 `"Bash"` 的工具。
5. Claude Code 把 `input` 里的参数传给这个工具。
6. 工具执行命令，返回结果。
7. 结果被送回给 AI，AI 看到结果后继续思考。

步骤 3-4 就是我们这一章要讲的重点。步骤 5-6 是下一章的内容。

## 从流中识别 tool_use

让我们回到代码层面。当 AI 的回答通过流式传输一个块一个块地到来时，Claude Code 需要识别出哪些块是 `tool_use`。

在 `src/query.ts` 中，当一条完整的助手消息（assistant message）到达后，代码会扫描它的所有内容块：

```typescript
const msgToolUseBlocks = message.message.content.filter(
  content => content.type === 'tool_use',
) as ToolUseBlock[]
```

这行代码做的事情我们已经讨论过了——用类型守卫过滤出 `tool_use` 块。

但这里有一个值得注意的细节：`filter` 是在整条消息上操作的。也就是说，AI 的回答可能长这样：

```
[文字] "让我先看看你的代码。"
[文字] "我来运行一下测试。"
[工具请求] name: "Bash", input: { command: "npm test" }
```

一条消息里混合了文字和工具请求。`filter` 把它们分开——文字块去显示给用户看，工具请求块去执行。

如果一条消息里有多个工具请求，它们全部都会被收集起来：

```typescript
if (msgToolUseBlocks.length > 0) {
  toolUseBlocks.push(...msgToolUseBlocks)
  needsFollowUp = true
}
```

注意 `needsFollowUp = true` 这个标记。它的意思是"AI 还没说完——它提出了行动请求，我们需要执行这些请求，然后把结果送回给 AI，让 AI 继续思考"。这就像你问朋友"这道题怎么做"，朋友说"让我查一下资料"——对话还没结束，等查完资料会继续。

---

## 找到正确的工具

识别出 `tool_use` 块之后，下一步是什么？是找到 AI 要用的那个工具。

`tool_use` 块里的 `name` 字段告诉 Claude Code："我要用名叫 `Bash` 的工具。" 但 Claude Code 内部有很多工具，怎么根据名字找到正确的那一个？

这就要提到一个叫 `findToolByName` 的函数了。它定义在 `src/Tool.ts` 第 358-360 行：

```typescript
export function findToolByName(tools: Tools, name: string): Tool | undefined {
  return tools.find(t => toolMatchesName(t, name))
}
```

这个函数做的事情非常直白：在一组工具列表里，找到名字匹配的那一个。

`tools.find(...)` 是 JavaScript 数组的原生方法——遍历数组，找到第一个满足条件的元素。`toolMatchesName` 是辅助函数，它检查工具的名字是否匹配：

```typescript
export function toolMatchesName(
  tool: { name: string; aliases?: string[] },
  name: string,
): boolean {
  return tool.name === name || (tool.aliases?.includes(name) ?? false)
}
```

这段代码翻译成大白话：一个工具匹配这个名字，要么它的正式名字就是这个名字，要么这个名字是它的别名之一。

为什么需要别名？因为工具有时候会改名。比如一个工具原来叫 `KillShell`，后来改名叫 `TaskStop`。但旧的对话记录里可能还在用旧名字。有了别名机制，即使用旧名字也能找到正确的工具——就像你改了手机号，但朋友还能通过你的旧号码找到你，因为你做了呼叫转移。

`findToolByName` 的返回类型是 `Tool | undefined`。`| undefined` 的意思是"可能找不到"。如果 AI 请求了一个不存在的工具，函数会返回 `undefined`——就像你在通讯录里搜一个不存在的人名，结果是空的。

## 工具是什么：一个完整的定义

说了这么多"找工具"，工具到底长什么样？

在 `src/Tool.ts` 第 362 行开始，你会看到一个巨大的类型定义。它定义了一个工具的完整面貌。让我们挑最关键的几个字段来看：

```typescript
export type Tool<
  Input extends AnyObject = AnyObject,
  Output = unknown,
  P extends ToolProgressData = ToolProgressData,
> = {
  readonly name: string
  readonly inputSchema: Input
  call(
    args: z.infer<Input>,
    context: ToolUseContext,
    canUseTool: CanUseToolFn,
    parentMessage: AssistantMessage,
    onProgress?: ToolCallProgress<P>,
  ): Promise<ToolResult<Output>>
  // ... 更多字段
}
```

**`name`：工具的名字。** 比如 `"Bash"`、`"Read"`、`"Write"`。这就是 `tool_use` 块里的 `name` 字段要匹配的值。

**`inputSchema`：输入的规则。** 这个字段定义了工具接受的参数长什么样。比如 Bash 工具的 inputSchema 会规定"必须有一个 `command` 字段，类型是字符串"。这个规则用来验证 AI 传过来的参数对不对。

**`call`：执行函数。** 这是最重要的字段——它就是"工具真正干活"的代码。当 AI 说"执行 Bash 命令"时，Claude Code 会调用 Bash 工具的 `call` 函数，把 AI 传过来的命令参数交给它。这个函数会启动一个子进程，执行命令，收集输出，然后返回结果。

除了这三个，一个 `Tool` 还有其他能力：

- `isEnabled()` —— 这个工具当前是否可用
- `isReadOnly()` —— 这个工具是不是只读的（不会修改任何东西）
- `isDestructive()` —— 这个工具是否会做不可逆的操作
- `checkPermissions()` —— 检查当前是否允许执行这个操作
- `aliases` —— 别名列表，支持旧名字兼容

每一个工具都是这个 `Tool` 类型的一个具体实现。Bash 工具实现了 `call` 函数来执行命令；Read 工具实现了 `call` 函数来读取文件；Write 工具实现了 `call` 函数来写入文件。它们的骨架都一样，但"手"的动作各不相同。

而 `Tools` 类型——注意有 s——就是一组工具的集合：

```typescript
export type Tools = readonly Tool[]
```

一个只读数组，里面装着一堆工具。Claude Code 启动时会把所有可用工具装进这个数组。当 AI 发出工具请求时，代码就在这个数组里查找。

## 当工具不存在时

让我们看一个有趣的边界情况：如果 AI 请求了一个不存在的工具怎么办？

在 `src/services/tools/toolExecution.ts` 的 `runToolUse` 函数里（第 337 行开始），处理了这种情况：

```typescript
export async function* runToolUse(
  toolUse: ToolUseBlock,
  assistantMessage: AssistantMessage,
  canUseTool: CanUseToolFn,
  toolUseContext: ToolUseContext,
): AsyncGenerator<MessageUpdateLazy, void> {
  const toolName = toolUse.name
  let tool = findToolByName(toolUseContext.options.tools, toolName)

  // ... 别名查找逻辑 ...

  if (!tool) {
    // 工具不存在！
    yield {
      message: createUserMessage({
        content: [{
          type: 'tool_result',
          content: `<tool_use_error>Error: No such tool available: ${toolName}</tool_use_error>`,
          is_error: true,
          tool_use_id: toolUse.id,
        }],
        // ...
      }),
    }
    return
  }
  // ... 继续执行工具 ...
}
```

注意这段代码的结构：先找工具，再检查是否找到，没找到就报错返回。

这种模式叫"提前返回"（early return）。它让代码的逻辑更清晰：如果前提条件不满足（工具不存在），立刻处理异常情况并返回，不让后续的正常逻辑被异常处理的代码污染。

当工具不存在时，Claude Code 会创建一条错误消息，类型是 `tool_result`，里面包含错误信息。这条消息会被送回给 AI，告诉它"你要用的工具不存在"。AI 看到这个错误后，可以换一种方式来实现它的目标。

注意 `tool_use_id` 字段。它被设为 `toolUse.id`——就是前面说的"身份证号"。这样 AI 就知道这条错误消息是对应哪次工具调用的。就像快递单号一样，确保错误信息不会送错门。

## 流式工具执行：不等 AI 话说完就开始动手

还有一个值得一提的设计。

如果你回顾一下上一章的内容，AI 的回答是流式的——一个块一个块地到来。这意味着 `tool_use` 块可能在 AI 还没"说完"的时候就出现了。

Claude Code 没有等 AI 把所有内容都输出完再开始处理工具。它有一种叫做**流式工具执行**（streaming tool execution）的机制。

在 `src/services/tools/StreamingToolExecutor.ts` 里，有一个类专门负责这件事。每当从流中识别出一个新的 `tool_use` 块，这个类就把它加入执行队列：

```typescript
addTool(block: ToolUseBlock, assistantMessage: AssistantMessage): void {
  const toolDefinition = findToolByName(this.toolDefinitions, block.name)
  // ... 立即开始执行，不等流结束 ...
}
```

`addTool` 方法在识别到工具请求的瞬间就被调用（在 `src/query.ts` 第 841-843 行）：

```typescript
for (const toolBlock of msgToolUseBlocks) {
  streamingToolExecutor.addTool(toolBlock, message)
}
```

这意味着 AI 还在说话的时候，它请求的工具已经开始在执行了。文字和行动并行推进。这就像你跟一个高效的同事合作——你说"帮我把那份报告拿来"，话还没说完，他已经起身去拿了。

如果多个工具请求同时到达，StreamingToolExecutor 还会判断哪些工具可以同时执行（`isConcurrencySafe`），哪些必须排队。比如两个读文件的操作可以同时进行，但两个写文件的操作需要排队执行，以免互相覆盖。

---

## 路标：从识别到执行

让我们把这一章走过的路整理一下：

1. AI 的回答不是纯文字，而是由多种"内容块"组成的。其中一种叫 `tool_use`。
2. `tool_use` 块包含三个关键信息：工具名字（name）、参数（input）、身份证号（id）。
3. 代码用**类型守卫** `content.type === 'tool_use'` 从流中识别出工具请求。
4. 识别出来后，用 `findToolByName` 在工具列表里找到对应的工具。
5. 每个工具都是一个 `Tool` 类型的对象，里面有名字、输入规则、执行函数等。
6. 如果找不到工具，返回错误消息给 AI。
7. 如果找到了，工具就可以开始执行了。

类型系统在这个过程中扮演了关键角色。联合类型让一个内容块可以是文字也可以是工具请求；字符串字面量类型让 `type` 字段只能是特定的几个值；类型守卫让代码能够在运行时区分这两种情况。

这些不是抽象的概念练习。它们是让代码安全、可读、可维护的实用工具。当你看到 `content.type === 'tool_use'` 时，你立刻知道这是在做什么；当你把类型写错时，编译器会告诉你。在一个有几十万行代码的项目里，这种保障是无价的。
