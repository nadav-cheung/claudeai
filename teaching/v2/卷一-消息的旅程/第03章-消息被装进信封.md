# 第03章：消息被装进信封

你的消息"帮我修个 bug"现在是一串文字。但它不能就这样被扔给 AI——它需要被装进一个标准信封。

---

## 为什么不能直接发字符串

你可能会想：我有一句话，AI 是一个语言模型，语言模型处理的就是文字。那直接把"帮我修个 bug"这串字符扔给 AI 不就好了吗？

不行。原因有两层。

第一层：AI 不只是处理你这一句话。它需要知道这句话是**谁说的**。是你说的？还是 AI 自己之前说的？还是某个工具执行后返回的结果？如果 AI 不知道"谁说的"，它就不知道该以什么身份去理解这段文字。想象一下，你收到一张纸条写着"明天不用来"，但你不知道是老板写的还是同事开玩笑写的——同一句话，理解完全不同。

第二层：你和 AI 之间的对话不是只有一条消息。你们可能已经聊了十个来回。AI 需要看到**完整的对话历史**才能给出连贯的回答。如果只发你最后说的这一句话，AI 就像一个失忆的人，完全不知道你们之前聊过什么。

所以，你的消息不能是一个赤裸裸的字符串。它需要被装进一个**标准化的容器**——一个标注了"谁说的、什么时候说的、内容是什么"的容器。这个容器，我们叫它**信封**。

---

## 信封长什么样

在 Claude Code 的世界里，信封是一个**对象**。对象是编程里的一个基本概念，你暂时可以把它理解为一张家谱表或者一张简历——上面有好几个字段，每个字段填了不同的信息。

你那条"帮我修个 bug"被装进信封之后，看起来像这样：

```
{
  role: 'user',
  content: '帮我修个 bug'
}
```

就这么简单。两个字段：

- **role**（角色）：`'user'`，意思是"这是用户说的"。
- **content**（内容）：`'帮我修个 bug'`，就是你输入的那句话。

整个信封用一对花括号 `{}` 包起来，里面用逗号分隔不同的字段。每个字段有一个名字（`role`、`content`），后面跟一个冒号，再跟上具体的值。这种格式叫做 **JSON**。

**JSON 是什么？** JSON 的全称是 JavaScript Object Notation（JavaScript 对象表示法）。虽然名字里有 JavaScript，但它实际上是一种通用的数据格式，几乎所有编程语言都能读懂它。你可以把它想象成一种**国际通用的快递单**——不管包裹从哪个国家寄出、寄到哪个国家，快递单上的格式是一样的：寄件人、收件人、物品描述、重量。JSON 就是程序世界里的快递单。

JSON 的规则很简单：对象用 `{}` 包起来，列表用 `[]` 包起来，文字用引号，数字直接写，真假用 `true` 和 `false`。每个字段是 `"名字": 值` 的格式。就这么几种基本元素，组合起来就能表达任何复杂的数据。

每个信封必须有一个 `role` 和一个 `content`，缺一不可。

---

## 三种角色：user、assistant、tool

信封上的 `role` 字段只能填几个固定的值。在 Claude Code 和 AI 的对话中，最核心的角色有三种：

**user（用户）。** 这是你说的每一句话。你输入"帮我修个 bug"，它的 role 就是 `'user'`。你输入"不对，那个文件不要改"，它的 role 也是 `'user'`。所有从你的键盘出发的消息，都是 user 角色。

**assistant（助手）。** 这是 AI 回复的每一句话。当 AI 说"好的，我来看看你的代码"，这句话被装进一个 role 为 `'assistant'` 的信封。当 AI 说"我找到了问题，在第三行……"，这也是 assistant 角色。

**tool（工具）。** 当 AI 让程序去执行某个操作（比如读一个文件），操作的结果也会被装进信封送回给 AI。这些信封的 role 也是 `'user'`——从 AI 的视角看，工具返回的结果和用户输入一样，都是"进来"的信息。但内容里会标注这是一个工具执行的结果。这一点我们后面讲到工具调用的时候会详细展开。

为什么要区分角色？回到刚才那个比喻：如果你在看一份聊天记录，你一定需要知道每一句话是谁说的。如果所有的话都挤在一起，没有标注发言者，你根本看不懂对话的脉络。角色标注就是发言者的名字。

---

## 整个对话是一个信封数组

你的一条消息是一个信封。但你和 AI 之间的完整对话，是很多个信封排成一列。

```
[
  { role: 'user',      content: '帮我看看这个项目有什么问题' },
  { role: 'assistant',  content: '我来看一下项目结构...' },
  { role: 'user',      content: '帮我修个 bug' },
]
```

这个列表——用方括号 `[]` 包起来的有序序列——叫做**数组**。数组就是一排按顺序排列的东西。就像一叠信件，最底下是最早的，最上面是最新的。AI 看到这叠信件，就能还原出你们对话的完整过程。

每次你发送一条新消息，Claude Code 做的事情就是：把你的新消息装进信封，放到信件叠的最上面，然后把整叠信件一起寄给 AI。

为什么要把所有历史都寄过去？因为 AI 模型是"无状态"的——它不会在内部记住你们上一次聊了什么。每次你跟它说话，它都像是第一次见面。唯一的办法就是把之前的所有对话都给它看一遍。就像你每次跟客服打电话，如果客服换人了，新客服需要你把之前的故事从头讲一遍。

Claude Code 把完整的对话历史打包成消息数组，每次请求都带上。AI 读一遍这个数组，就"想起来"了你们之前聊的所有内容。

---

## 系统提示词：AI 的员工手册

除了你的消息和 AI 的回复之外，还有一样东西会被寄给 AI。它不在消息数组里，而是单独放在一个特殊的位置。这个东西叫做**系统提示词**（System Prompt）。

系统提示词是什么？想象你是一个新入职的员工，入职第一天，HR 递给你一本手册。手册里写着：你的职位是什么、你的职责范围是什么、你被允许做什么、你不被允许做什么、公司的工作流程是什么样的、遇到特定情况该怎么处理。这本手册不是某个同事跟你说的某句话——它是**你的角色定义**，是在你开始工作之前就被定好的框架。

系统提示词就是 AI 的员工手册。

在 Claude Code 里，系统提示词包含了大量信息。比如：

- AI 的身份和职责："你是一个终端助手，帮助用户完成编程任务。"
- 当前的工作环境：你在哪个目录下、项目里有哪些文件、用了什么技术栈。
- AI 被允许使用的工具：它可以读文件、编辑代码、执行命令——但具体的工具列表是在系统提示词里定义的。
- 各种行为规范：怎么组织回复、什么时候该用工具、什么时候该问用户。

这些信息被组装成一个文本块数组，通过 API 的 `system` 参数传递——注意，它不在消息数组里，而是作为一个独立的参数。这样做是有意为之的：系统提示词是"背景设定"，消息数组是"对话内容"。两者在 API 层面是分开的。

在源码里，系统提示词的构建发生在 `src/services/api/claude.ts` 的 `buildSystemPromptBlocks` 函数中：

```typescript
// 文件：src/services/api/claude.ts，第3213-3237行
export function buildSystemPromptBlocks(
  systemPrompt: SystemPrompt,
  enablePromptCaching: boolean,
  options?: {
    skipGlobalCacheForSystemPrompt?: boolean
    querySource?: QuerySource
  },
): TextBlockParam[] {
  // 把系统提示词拆分成多个文本块
  return splitSysPromptPrefix(systemPrompt, {
    skipGlobalCacheForSystemPrompt: options?.skipGlobalCacheForSystemPrompt,
  }).map(block => {
    return {
      type: 'text' as const,
      text: block.text,
      // 如果启用了提示缓存，给这个块加上缓存控制标记
      ...(enablePromptCaching &&
        block.cacheScope !== null && {
          cache_control: getCacheControl({
            scope: block.cacheScope,
            querySource: options?.querySource,
          }),
        }),
    }
  })
}
```

这个函数做的事情很直观：它把系统提示词拆分成一个一个的文本块（`TextBlockParam`），每个块有 `type` 和 `text` 两个字段。如果有缓存需要，还会加上 `cache_control` 字段。

你暂时不需要理解缓存机制——那是后面的故事。现在只需要记住：系统提示词是一份独立的文档，告诉 AI "你是谁、你能做什么"，它在消息数组之外，单独传递。

---

## 你的消息被装进信封

现在回到你的消息。在上一章里，你的"帮我修个 bug"被 `onSubmit` 函数接住，变成了一个字符串变量。接下来，这个字符串要被装进信封。

装信封的动作是由一个函数完成的。这个函数叫 `createUserMessage`，住在 `src/utils/messages.ts` 里。

```typescript
// 文件：src/utils/messages.ts，第460行
export function createUserMessage({
  content,
  isMeta,
  isVisibleInTranscriptOnly,
  isVirtual,
  // ... 其他参数 ...
}: {
  content: string | ContentBlockParam[]
  isMeta?: true
  // ... 其他参数的类型定义 ...
}): UserMessage {
  const m: UserMessage = {
    type: 'user',
    message: {
      role: 'user',
      content: content || NO_CONTENT_MESSAGE,
    },
    // ... 其他元数据 ...
    uuid: (uuid as UUID | undefined) || randomUUID(),
    timestamp: timestamp ?? new Date().toISOString(),
  }
  return m
}
```

这个函数接收一堆参数，但最核心的是 `content`——你输入的那段文字。它把你的文字包进一个对象，设好 `type` 和 `role`，还附上了一些元数据：一个唯一的 ID（`uuid`）和一个时间戳（`timestamp`）。

注意返回值的类型：`UserMessage`。这是一个 **类型**。

---

## 类型：信封的模板

这里我们需要引入一个重要的 TypeScript 概念：**类型**。

什么是类型？类型就是数据的模板。想象你是一个信封厂的设计师。你画了一张信封的模板图，上面标注了：这个信封必须有一个"寄件人"栏、一个"收件人"栏、一个"内容"栏。任何不符合这个模板的信封，都不允许出厂。

类型在程序里起的就是这个作用。它定义了数据应该长什么样——有哪些字段、每个字段应该是什么类型的值。然后 TypeScript 会检查你代码里所有的数据，看看它们是否符合模板。如果某个地方把一个应该填数字的字段填成了文字，TypeScript 就会报错，让你在程序运行之前就发现这个问题。

`UserMessage` 就是一个类型。它规定了：一个用户消息对象必须有哪些字段。比如它必须有 `type: 'user'`，必须有 `message` 字段且 `message.role` 必须是 `'user'`，必须有 `uuid`，必须有 `timestamp`。

类型的好处是**安全**。没有类型检查，你可能在某个地方不小心忘了给消息设 role，然后这个没有 role 的消息被寄给了 AI，AI 的服务器收到一个格式不对的请求，返回一个错误。有了类型检查，这种错误在你写代码的时候就会被发现——TypeScript 会说："嘿，你忘了一个字段。"

---

## 接口：一份契约

TypeScript 里定义类型的常用方式有两种：`type` 和 `interface`。

**type**（类型别名）像是一张便签："UserMessage 就是这种形状的东西。" 简单直接。

**interface**（接口）更像是一份正式的**契约**。接口这个词来自现实世界：USB 接口承诺提供电源和数据传输，不管你插的是鼠标还是键盘，只要符合规格就能用。在 TypeScript 里，接口也是同样的意思："我承诺这个对象会有这些字段。"

两者在实践中经常可以互换，选择哪个更多是团队习惯。你只需要知道：它们都是用来定义数据模板的工具，确保数据不会长错形状。

---

## 从内部格式到 API 格式

`createUserMessage` 创建的是 Claude Code **内部**的消息格式。这个格式比 AI API 要求的格式更丰富——它包含了 `uuid`、`timestamp`、`isMeta` 等内部用的字段。这些额外信息是给 Claude Code 自己用的，AI 不需要知道。

所以，在把消息真正发给 AI 之前，还需要一步：把内部格式转换成 API 格式。这个转换由 `userMessageToMessageParam` 函数完成，它住在 `src/services/api/claude.ts` 里。

```typescript
// 文件：src/services/api/claude.ts，第588行
export function userMessageToMessageParam(
  message: UserMessage,        // 内部格式的用户消息
  addCache = false,            // 是否添加缓存标记
  enablePromptCaching: boolean,
  querySource?: QuerySource,
): MessageParam {              // 返回 API 格式的消息
  // 简化路径：不需要缓存的时候，直接构造信封
  return {
    role: 'user',
    content: Array.isArray(message.message.content)
      ? [...message.message.content]   // 如果内容是数组，复制一份
      : message.message.content,        // 如果内容是字符串，直接用
  }
}
```

这个函数做的事情很清楚：它接收一个内部格式的 `UserMessage`，提取出其中的核心信息（role 和 content），扔掉那些 AI 不需要的内部字段（uuid、timestamp 等），构造一个干净的 API 信封（`MessageParam`）。

注意返回类型的名字：`MessageParam`。这个名字来自 Anthropic 的官方 SDK。`Param` 是 parameter（参数）的缩写，意思是"传给 API 的参数"。`MessageParam` 就是"传给 API 的消息参数"——一个标准化的信封。

如果你看完整版代码（包括缓存逻辑），会发现这个函数还有一个更复杂的分支：当 `addCache` 为 `true` 时，content 会从简单的字符串变成一个包含多个文本块的对象数组，每个文本块可以附带缓存控制标记。这个缓存机制能让重复的系统提示词和长对话历史不需要每次都重新传输，节省大量时间和费用。但我们现在先不管这个——你只需要知道，最简单的情况下，信封就是 `{ role: 'user', content: '...' }`。

---

## 所有信封被排成一列

在发送请求之前，Claude Code 会把对话中的所有消息都转换成 API 格式，排成一个数组。这个过程发生在 `src/services/api/claude.ts` 的主查询流程中：

```typescript
// 文件：src/services/api/claude.ts，约第3090行
const result = messages.map((msg, index) => {
  const addCache = index === markerIndex  // 只给最后一条消息加缓存标记
  if (msg.type === 'user') {
    return userMessageToMessageParam(msg, addCache, ...)
  }
  return assistantMessageToMessageParam(msg, addCache, ...)
})
```

这段代码做的事很朴素：遍历所有消息（`messages.map`），对每一条消息判断它是 user 类型还是 assistant 类型，然后调用对应的转换函数。结果就是一个纯 API 格式的消息数组——一叠整齐的信封，随时可以寄出。

对应的，assistant 消息也有自己的转换函数 `assistantMessageToMessageParam`，逻辑几乎一样，只是 role 换成了 `'assistant'`。

至此，所有东西都准备好了：

- **消息数组**：一个 `MessageParam` 对象的数组，包含完整的对话历史。
- **系统提示词**：一组文本块，定义了 AI 的角色和行为规范。
- **工具定义**：一份可选的工具列表，告诉 AI 它可以使用哪些工具。

这三样东西加在一起，就是一个完整的 API 请求。你的"帮我修个 bug"已经从一个裸字符串，变成了一封信，被放进了一叠信件中，旁边还放了一本员工手册。它们被捆成一包，等着被寄出去。

---

## 回顾：从字符串到信封

让我们回顾一下这一章走过的路：

1. 你的消息"帮我修个 bug"在上一步还是一个字符串，存在一个变量里。
2. 它不能直接发给 AI，因为 AI 需要知道"谁说的"（role），需要看到完整的对话历史（消息数组），需要一份角色手册（系统提示词）。
3. 你的消息被 `createUserMessage` 函数装进了 Claude Code 内部的信封格式（`UserMessage`），附带了唯一 ID 和时间戳。
4. 在真正发给 AI 之前，`userMessageToMessageParam` 把内部格式转换成了 API 格式（`MessageParam`），只保留 AI 需要的信息。
5. 所有消息——你的、AI 的、工具结果的——都被转换成同样的 API 格式，排成一个数组。
6. 系统提示词被单独组装成文本块数组。
7. 三样东西（消息数组、系统提示词、工具定义）捆在一起，就是一个完整的 API 请求。

这个过程中，我们遇到了几个 TypeScript 的概念：

- **类型（type）**：数据的模板，确保数据不会长错形状。
- **接口（interface）**：一份契约，承诺对象会有哪些字段。
- **JSON**：一种通用的数据格式，程序世界的国际快递单。
- **对象**：用花括号包起来的键值对集合，比如 `{ role: 'user', content: '...' }`。
- **数组**：用方括号包起来的有序列表，比如 `[{ ... }, { ... }, { ... }]`。

你的消息现在已经准备好了。它被装进了标准信封，和整叠历史信件捆在一起，旁边是一本员工手册。但这一切都还发生在你的电脑里。信封装好了。现在它需要被寄出去——穿越网络，到达 Anthropic 的服务器。
