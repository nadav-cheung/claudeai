# 第07章：命令真的被执行了

AI 决定要执行 `git status`。这不是一个模拟——这条命令会在你的电脑上真实地运行。

上一章结束时，AI 完成了思考，输出了一段结构化的 JSON：工具名是 `Bash`，参数是 `{ command: "git status" }`。现在这个 JSON 躺在消息流里，等待被执行。

但"执行"到底是什么意思？你的终端里明明只有一个 Claude Code 程序在运行，它又不是操作系统，怎么能让另一条命令跑起来？

这就要说到 Claude Code 的"手"了。

---

## 工具箱里的扳手：BashTool

你可能已经注意到，Claude Code 不只是一个聊天机器人。它能读文件、写文件、搜索代码，还能执行命令。每一种能力背后，都对应着一个"工具"。

如果说 Claude Code 是一个工具箱，那 BashTool 就是其中那把最基础、最常用的扳手。它的职责很简单：接收一条命令字符串，在你的电脑上执行它，把结果带回来。

在源码里，BashTool 的定义长这样：

```typescript
// src/tools/BashTool/BashTool.tsx, 第 420 行
export const BashTool = buildTool({
  name: BASH_TOOL_NAME,
  searchHint: 'execute shell commands',
  maxResultSizeChars: 30_000,
  strict: true,
  async description({ description }) {
    return description || 'Run shell command'
  },
  // ...还有几十行其他配置
```

`buildTool` 是 Claude Code 里所有工具的"模具"。不管你是读文件的 FileReadTool、写文件的 FileWriteTool，还是执行命令的 BashTool，都通过同一个 `buildTool` 函数创建。它的作用是把一堆配置项组装成一个标准化的工具对象——就像工厂里的流水线，不管造的是扳手还是螺丝刀，都走同一条生产线。

这里有一个有趣的 TypeScript 概念：**泛型**。

你看 `buildTool` 的类型签名，它长这样：

```typescript
// src/Tool.ts, 第 721 行
export type ToolDef<
  Input extends AnyObject = AnyObject,
  Output = unknown,
  P extends ToolProgressData = ToolProgressData,
> = ...
```

`<Input, Output, P>` 这组尖括号里的东西叫"类型参数"。你可以把它理解成一个模具：模具的形状是固定的，但你可以往里面灌不同的材料。BashTool 灌进去的是 `{ command: string }` 作为输入、`{ stdout: string, stderr: string }` 作为输出；FileReadTool 灌进去的是 `{ file_path: string }` 作为输入、文件内容作为输出。

模具不变，材料在变。这就是泛型的意义。

## 输入格式：谁来检查命令合不合法

AI 返回的工具调用是 JSON 格式的。但 JSON 可以装任何东西——一个字符串、一个数字、甚至一个嵌套了五层的对象。程序怎么知道这个 JSON 是不是 BashTool 能接受的格式？

答案是 **Zod**。

Zod 是一个 TypeScript 的数据验证库。它的工作方式很直观：你先定义一个"蓝图"，告诉它"我期望的数据长什么样"，然后它帮你检查实际收到的数据是否符合这个蓝图。

BashTool 的输入蓝图是这样画的：

```typescript
// src/tools/BashTool/BashTool.tsx, 第 227 行
const fullInputSchema = lazySchema(() => z.strictObject({
  command: z.string().describe('The command to execute'),
  timeout: semanticNumber(z.number().optional())
    .describe(`Optional timeout in milliseconds (max ${getMaxTimeoutMs()})`),
  description: z.string().optional()
    .describe('Clear, concise description of what this command does...'),
  run_in_background: semanticBoolean(z.boolean().optional())
    .describe('Set to true to run this command in the background.'),
  dangerouslyDisableSandbox: semanticBoolean(z.boolean().optional())
    .describe('Set this to true to dangerously override sandbox mode...'),
}))
```

逐行翻译成白话：

- `command`：一个字符串，必填。这就是要执行的命令，比如 `"git status"`。
- `timeout`：一个数字，选填。如果这条命令跑太久，多久之后强制停掉。
- `description`：一个字符串，选填。AI 给这条命令的简短描述，比如 `"Show working tree status"`。
- `run_in_background`：一个布尔值，选填。是否在后台运行。
- `dangerouslyDisableSandbox`：一个布尔值，选填。是否关闭沙箱保护。注意这个名字里就有"dangerously"——程序在用命名警告你，这不是一个好主意。

当 AI 返回 `{ command: "git status", description: "Show working tree status" }` 时，Zod 会逐个字段检查：`command` 是字符串吗？是。`description` 有吗？有，也是字符串。`timeout` 没填？没关系，它是 optional 的。全部通过，数据合法，放行。

如果 AI 返回了 `{ command: 123 }`——`command` 是个数字而不是字符串——Zod 会立刻拦住，告诉程序"这个输入不对劲，别往下走了"。

这就像机场的安检：不管你带的是什么，都得过一遍扫描仪。格式对了放行，格式不对挡住。

## 子进程：让另一个程序替你跑腿

输入验证通过了。现在到了最关键的一步：怎么在你的电脑上执行 `git status`？

你的 Claude Code 是一个正在运行的程序——一个 Node.js 进程。它自己没法直接运行 `git status`，因为 `git` 是另一个完全独立的程序。这就像你在办公室里坐着，想让楼下打印店帮你打印一份文件——你得把文件送下去，等打印完再拿回来。

在编程的世界里，这叫"子进程"（child process）。

Node.js 提供了一个叫 `child_process` 的模块。它的功能就是让你的程序去启动另一个程序。你告诉它"帮我跑这条命令"，它就帮你启动一个新的进程来执行，等执行完了把结果还给你。

在 Claude Code 的源码里，真正干这件事的代码在 `src/utils/Shell.ts`：

```typescript
// src/utils/Shell.ts, 第 316 行
const childProcess = spawn(spawnBinary, shellArgs, {
  env: {
    ...subprocessEnv(),
    SHELL: shellType === 'bash' ? binShell : undefined,
    GIT_EDITOR: 'true',
    CLAUDECODE: '1',
    ...envOverrides,
  },
  cwd,
  stdio: usePipeMode
    ? ['pipe', 'pipe', 'pipe']
    : ['pipe', outputHandle?.fd, outputHandle?.fd],
  detached: provider.detached,
  windowsHide: true,
})
```

这段代码做了几件事：

**第一，选择用什么 shell 来执行命令。** `spawnBinary` 是 shell 的路径，通常是 `/bin/zsh` 或 `/bin/bash`。Claude Code 会自动检测你系统上安装了哪个 shell，优先用你自己配置的那个。如果你在环境变量里设置了 `SHELL=/bin/zsh`，它就用 zsh。

**第二，设置环境变量。** 注意 `CLAUDECODE: '1'` 这一行——Claude Code 在子进程的环境里加了一个标记，让其他程序知道"我是被 Claude Code 启动的"。同时 `GIT_EDITOR: 'true'` 是个巧妙的小设置：它防止 git 尝试打开文本编辑器（因为 Claude Code 运行在终端里，没有交互式编辑器可用）。

**第三，设置工作目录。** `cwd` 是 "current working directory" 的缩写。子进程会在你的项目目录下执行命令——这样 `git status` 才能正确地找到你的 `.git` 文件夹。

**第四，配置输入输出。** `stdio` 参数控制子进程的输入输出管道。这里 `['pipe', ...]` 表示子进程的输入被"接管"了，Claude Code 可以通过管道向它发送数据或读取它的输出。

`spawn` 函数一执行，操作系统就会创建一个新的进程。这个新进程独立于 Claude Code 运行，执行你请求的命令，然后退出。

从你的视角来看，就好像你自己在终端里敲了 `git status` 一样。只不过这次，是 AI 替你敲的。

## 输出：命令的"嘴"和"错误喇叭"

命令跑完了，结果得拿回来。但一个命令的输出其实分两路：正常的输出和错误的输出。

在 Unix/Linux 的世界里，这叫 **stdout**（标准输出）和 **stderr**（标准错误）。每个进程都有这两条管道：

- **stdout** 是命令的"嘴"——它用来说正常的、预期的内容。`git status` 把仓库状态打印到 stdout。
- **stderr** 是命令的"错误喇叭"——它用来喊出错了、警告、或者一些辅助信息。比如 `git status` 遇到一个不认识的参数，它会通过 stderr 喊 "unknown option"。

这两条管道是分开的，这样程序就能区分"正常的结果"和"出了问题"。

在 BashTool 的输出定义里，你可以清楚地看到这种区分：

```typescript
// src/tools/BashTool/BashTool.tsx, 第 279 行
const outputSchema = lazySchema(() => z.object({
  stdout: z.string().describe('The standard output of the command'),
  stderr: z.string().describe('The standard error output of the command'),
  interrupted: z.boolean().describe('Whether the command was interrupted'),
  // ...还有更多字段
}))
```

但有一个有趣的细节。在 Claude Code 的实际实现里，stdout 和 stderr 被合并到了同一个文件里：

```typescript
// src/utils/Shell.ts, 第 330 行
stdio: usePipeMode
  ? ['pipe', 'pipe', 'pipe']
  : ['pipe', outputHandle?.fd, outputHandle?.fd],
```

看最后两个元素：`outputHandle?.fd` 重复出现了两次。第一个是 stdout 的去向，第二个是 stderr 的去向。它们被指向了同一个文件描述符。代码注释解释了原因：在 POSIX 系统上，`O_APPEND` 标志保证每次写入都是原子的（先跳到文件末尾，再写入），所以 stdout 和 stderr 会按时间顺序交替出现，不会互相打断。

这就像两个人同时对着一台录音机说话，但录音机保证每个人的每句话都是完整的，不会你半句话还没说完就被另一个人打断。

输出被收集起来后，流回到 BashTool 的 `call` 方法。在那里，`stdout` 和 `stderr` 被打包成一个结构化的结果对象，最终送回到消息流里，告诉 AI "这是命令的执行结果"。

## 超时和中断：命令跑太久了怎么办

不是所有命令都能在几秒内完成。有些命令可能会跑很久——比如 `npm install` 在网络不好的时候可能要跑几分钟，或者一个失控的脚本可能永远不会停下来。

Claude Code 为此设计了超时机制。

每个 BashTool 调用都有一个默认的超时时间——30 分钟（`DEFAULT_TIMEOUT = 30 * 60 * 1000`，在 `Shell.ts` 第 44 行定义）。如果 AI 觉得某条命令不需要这么久，可以在输入里指定一个更短的 `timeout`。

当超时到了，或者用户按下了 Ctrl+C 想中断命令，会发生什么？

Claude Code 使用了 `AbortController`——这是 JavaScript 的一个标准机制，专门用来发出"停！"的信号。在 BashTool 的 `call` 方法里，你可以看到它是怎么被使用的：

```typescript
// src/tools/BashTool/BashTool.tsx, 第 624 行
async call(input: BashToolInput, toolUseContext, ...) {
  const { abortController, ... } = toolUseContext;
  // ...
  const commandGenerator = runShellCommand({
    input,
    abortController,
    // ...
  });
```

`abortController` 就像是一个遥控器上的"停止"按钮。当超时到了或者用户主动中断时，程序按下这个按钮。信号沿着管道传到子进程，子进程收到信号后停止执行。

如果命令被中断了，结果里会标记 `interrupted: true`，AI 会看到一条信息：`"Command was aborted before completion"`。这样 AI 就知道命令没跑完，可以根据情况决定是重试、换一种方式、还是告诉你出了什么问题。

还有一个更精细的机制：有些长命令不应该被无情杀掉，而应该被移到后台继续跑。比如你在跑一个 `npm run build`，它需要 5 分钟，但你不想干等着。Claude Code 支持 `run_in_background` 选项——设置之后，命令在后台执行，AI 可以继续和你对话。等命令跑完了，系统会发一个通知告诉 AI "你之前跑的那个命令，结果出来了"。

## BashTool 的使用说明

在结束这一章之前，还有一点值得看：Claude Code 怎么告诉 AI "这个工具怎么用"。

每个工具都有一个 `prompt` 方法，返回一段说明文字。这段文字会被放进系统提示词里，告诉 AI 使用这个工具的规则和注意事项。BashTool 的使用说明里有这么几条：

```
File search: Use Glob (NOT find or ls)
Content search: Use Grep (NOT grep or rg)
Read files: Use Read (NOT cat/head/tail)
Edit files: Use Edit (NOT sed/awk)
Write files: Use Write (NOT echo >/cat <<EOF)
Communication: Output text directly (NOT echo/printf)
```

这些规则的存在是因为 BashTool 是一个"万能"工具——理论上 AI 可以用 `cat filename` 来读文件、用 `echo > filename` 来写文件。但 Claude Code 为这些操作提供了更专门化的工具（FileReadTool、FileWriteTool 等），它们更安全、更高效。所以 prompt 里明确告诉 AI：别用 Bash 做这些事，用专门的工具。

这就像一家餐厅的厨房里有万能烤箱、切菜机、搅拌机。你当然可以用万能烤箱做所有事，但用专门的工具效率更高、效果更好。

## 一条命令的一生

让我们把 `git status` 的完整旅程串一遍：

1. AI 在思考后决定使用 BashTool，输出工具调用：`{ name: "Bash", input: { command: "git status" } }`。
2. 程序找到 BashTool 的定义，把输入交给 Zod 验证：`command` 是字符串，格式正确。
3. BashTool 的 `call` 方法被调用。它准备好 `AbortController`、输出累加器，然后调用 `runShellCommand`。
4. `runShellCommand` 最终调用 `Shell.ts` 里的 `exec` 函数，`exec` 用 `spawn` 创建一个子进程。
5. 子进程在你的项目目录下执行 `git status`，输出通过管道被捕获。
6. 命令完成，输出被打包成 `{ stdout: "...", stderr: "", interrupted: false }`，送回给 AI。
7. AI 看到输出，理解了你的仓库状态，继续决定下一步该做什么。

从 AI 做出决定，到命令真正在你的电脑上执行，中间经过了输入验证、子进程创建、输出捕获、超时保护好几道工序。每一步都有检查、有保护、有预案。

这不是魔法。这是一个精心设计的系统。
