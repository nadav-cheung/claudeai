# 第08章：你确定吗

AI 要在你的电脑上执行命令。但程序停了下来，问你："你确定吗？"这个停顿不是多余的——它是你的安全网。

上一章结束时，`git status` 已经通过了输入验证，子进程的管道已经准备好，一切就绪。但在那个 `spawn` 被调用之前，还有一道关卡。程序拦住了这条命令，转头问你："Claude 想要使用 Bash，你还没有授权。"

你按下回车，命令才开始执行。

这个"按下回车"的动作看似简单，背后是一整套权限系统在工作。今天我们就来拆解它。

---

## 为什么需要权限系统？

想象一下：你在公司上班，门口有一个保安。员工刷卡进来，保安看一眼工牌，放行。访客来了，保安拦住，打电话确认，才让进。陌生人想闯进来，保安直接挡住。

这个保安不是摆设。他存在的意义是：**不是所有人都能随便进出**。

Claude Code 面对的情况类似。AI 是一个强大的助手，它可以读取你的文件、执行命令、修改代码。这些操作一旦失控，后果可能很严重——删掉重要文件、执行危险命令、把代码搞乱。

所以 Claude Code 在设计上有一个基本原则：**AI 的每一个动作，都需要经过许可**。

许可不是一刀切的。有些操作你已经提前允许了，它们可以静默通过。有些操作你明确拒绝了，它们连尝试的机会都没有。还有些操作需要你当场拍板——程序会暂停，等你点头。

三种状态，三种命运。这就是权限系统的核心。

---

## 三种状态：allow、deny、ask

在 Claude Code 的源码里，权限有三种行为（behavior），用一个简单的联合字符串类型来定义：

```typescript
// src/utils/permissions/PermissionRule.ts, 第 25-27 行
export const permissionBehaviorSchema = lazySchema(() =>
  z.enum(['allow', 'deny', 'ask']),
)
```

`z.enum` 是 Zod 验证库提供的方法。它创建一个枚举验证器，限定值只能是 `'allow'`、`'deny'` 或 `'ask'` 中的某一个。传别的字符串进来？验证失败，直接报错。

这个设计在 TypeScript 的语境里有一个对应的类型概念：**联合字符串类型**（union string type）。你可以这样理解：

```typescript
type PermissionBehavior = 'allow' | 'deny' | 'ask'
```

变量 `PermissionBehavior` 只能是这三个字符串中的一个。不是布尔值（太简单了，只有两种状态），不是数字（谁能记住 1、2、3 分别代表什么），而是有意义的文字。你读到 `'allow'`，立刻知道这是"放行"。你读到 `'deny'`，立刻知道这是"拒绝"。代码自己解释了自己。

> **TypeScript 小课堂：联合字符串类型**
>
> TypeScript 的联合类型（union type）用 `|` 连接多个选项，表示"这些值中的某一个"。
>
> ```typescript
> type TrafficLight = 'red' | 'yellow' | 'green'
> ```
>
> 这比用数字或布尔值更安全。编译器会在你拼错单词时报错，IDE 会自动补全所有选项。这是一种用类型系统代替注释的实践——类型本身就是文档。
>
> Zod 的 `z.enum()` 把这个概念带到了运行时：不仅编译时检查，运行时也验证。如果有人通过网络请求发来了 `'maybe'`，Zod 会直接拦截。

三种行为各自意味着什么？回到保安的比喻：

- **`'allow'`**——保安认识你，看过你的工牌了，直接放行。命令静默执行，不打扰你。
- **`'deny'`**——保安把你拦住了。不管什么情况，这条命令绝对不能执行。程序直接返回拒绝，AI 连尝试的机会都没有。
- **`'ask'`**——保安不确定，需要你亲自确认。程序暂停，在终端里显示一条消息，等你按下回车或输入指令。

这三种状态不是凭空产生的。每一条命令进来，系统都会走一遍检查流程，最终决定用哪种行为来对待它。

## 权限检查的入口：hasPermissionsToUseTool

当 AI 决定使用某个工具（比如 BashTool 执行 `git status`），程序不会直接调用这个工具。它会先问一个函数："这条工具调用有权限吗？"

这个函数叫 `hasPermissionsToUseTool`。它是权限检查的入口，也是整个安全系统的总调度。

```typescript
// src/utils/permissions/permissions.ts, 第 473-501 行
export const hasPermissionsToUseTool: CanUseToolFn = async (
  tool,
  input,
  context,
  assistantMessage,
  toolUseID,
): Promise<PermissionDecision> => {
  const result = await hasPermissionsToUseToolInner(tool, input, context)

  // 如果结果是 allow，重置连续拒绝计数器
  if (result.behavior === 'allow') {
    // ... 处理计数器重置逻辑
    return result
  }

  // 如果结果是 ask，还需要进一步检查当前的模式
  if (result.behavior === 'ask') {
    const appState = context.getAppState()

    // dontAsk 模式：把 ask 变成 deny
    if (appState.toolPermissionContext.mode === 'dontAsk') {
      return {
        behavior: 'deny',
        decisionReason: { type: 'mode', mode: 'dontAsk' },
        message: DONT_ASK_REJECT_MESSAGE(tool.name),
      }
    }
    // ... 还有更多模式判断
  }
```

注意看这个函数的结构。它先调用 `hasPermissionsToUseToolInner` 拿到一个初步结果，然后根据结果的 `behavior` 字段做不同的处理。

这就是 TypeScript 里的**模式匹配**（pattern matching）。虽然 TypeScript 不像 Rust 或 Haskell 那样有专门的 `match` 语法，但用 `if` 和 `switch` 检查联合类型的不同分支，本质上是同一回事。

> **TypeScript 小课堂：模式匹配**
>
> 当你有一个联合类型 `PermissionDecision`，它的值可能是三种情况之一：`PermissionAllowDecision`、`PermissionAskDecision` 或 `PermissionDenyDecision`。你怎么知道拿到的是哪一种？
>
> 答案是：检查 `behavior` 字段。
>
> ```typescript
> if (result.behavior === 'allow') {
>   // 这里 TypeScript 知道 result 是 PermissionAllowDecision
> } else if (result.behavior === 'ask') {
>   // 这里 TypeScript 知道 result 是 PermissionAskDecision
> }
> ```
>
> TypeScript 的类型系统会根据你的 `if` 判断自动缩窄类型（type narrowing）。在 `behavior === 'allow'` 的分支里，你可以安全地访问 `PermissionAllowDecision` 独有的字段，不用担心类型错误。
>
> 这种"根据类型标签走不同分支"的编程模式，在函数式编程里叫 discriminated union（可辨识联合），在实际开发里大家都叫它"模式匹配"。

函数的返回类型是 `Promise<PermissionDecision>`。`PermissionDecision` 本身也是一个联合类型：

```typescript
// src/types/permissions.ts, 第 241-246 行
export type PermissionDecision<
  Input extends { [key: string]: unknown } = { [key: string]: unknown },
> =
  | PermissionAllowDecision<Input>
  | PermissionAskDecision<Input>
  | PermissionDenyDecision
```

三种可能，对应三种命运。函数返回的是一个"决定"（Decision），而不是一个简单的"是"或"否"。

## 权限规则：命令是怎么被分类的？

你可能会问：系统怎么知道一条命令应该被 allow、deny 还是 ask？

答案是：**规则**。

Claude Code 维护了三套规则列表，分别对应三种行为：

- **alwaysAllowRules**——始终允许的规则列表。比如你在配置里写了允许 `Bash(git status)`，那每次 AI 想执行 `git status`，系统都会直接放行。
- **alwaysDenyRules**——始终拒绝的规则列表。比如你明确禁止了 `Bash(rm -rf)`，那这条命令永远不会被执行。
- **alwaysAskRules**——始终询问的规则列表。即使你处于自动模式，这些命令也会被拦下来问你。

每条规则的格式是 `工具名(内容)`。比如：

- `Bash`——匹配所有 Bash 工具调用
- `Bash(git *)`——匹配以 `git` 开头的 Bash 命令
- `Read`——匹配所有文件读取操作
- `Write`——匹配所有文件写入操作

系统在检查权限时，会遍历这些规则列表。先检查 deny 列表（如果被拒绝了，后面的都不用看了），再检查 allow 列表，最后检查 ask 列表。如果三个列表都没匹配到，就走默认行为——问你。

回到保安的比喻：

- deny 规则 = 黑名单。名字在上面？不让进。
- allow 规则 = 白名单。名字在上面？直接放行。
- ask 规则 = 特别关注名单。名字在上面？需要额外确认。

这些规则从哪里来？有好几个来源：你在 `.claude/settings.json` 里手动配置的、命令行参数指定的、当前会话中临时添加的。规则来源不同，但检查逻辑一样。

在源码里，获取规则的函数长这样：

```typescript
// src/utils/permissions/permissions.ts, 第 122-132 行
export function getAllowRules(
  context: ToolPermissionContext,
): PermissionRule[] {
  return PERMISSION_RULE_SOURCES.flatMap(source =>
    (context.alwaysAllowRules[source] || []).map(ruleString => ({
      source,
      ruleBehavior: 'allow',
      ruleValue: permissionRuleValueFromString(ruleString),
    })),
  )
}
```

`PERMISSION_RULE_SOURCES` 是一个数组，包含所有规则来源（设置文件、命令行、会话等）。`flatMap` 遍历每个来源，把对应的规则字符串解析成 `PermissionRule` 对象，最后合并成一个大数组。

`deny` 和 `ask` 的获取方式完全一样，只是换了个字段名。

## 权限模式：你选择哪种"保安策略"？

除了细粒度的规则，Claude Code 还提供了一个更高层次的控制：**权限模式**（Permission Mode）。模式决定了整体的"保安策略"——你的门口是站一个严格的保安，还是一个宽松的保安。

在源码里，权限模式被定义成一组有限的字符串常量：

```typescript
// src/types/permissions.ts, 第 16-22 行
export const EXTERNAL_PERMISSION_MODES = [
  'acceptEdits',
  'bypassPermissions',
  'default',
  'dontAsk',
  'plan',
] as const
```

`as const` 是 TypeScript 的一个语法，它告诉编译器："这个数组里的每一个值，请当作常量类型来对待。" 这意味着 `EXTERNAL_PERMISSION_MODES` 不仅是一个数组，还是一个类型元组。TypeScript 可以从中推导出精确的联合类型。

> **TypeScript 小课堂：`as const` 和字面量类型**
>
> 普通的 `const` 声明只能让变量本身不可重新赋值。但 `as const` 更进一步——它让值里的每一个元素都变成"字面量类型"。
>
> ```typescript
> const colors = ['red', 'green'] as const
> // colors 的类型是 readonly ['red', 'green']
> // 而不是 string[]
> ```
>
> 然后你就可以用类型推导来创建联合类型：
>
> ```typescript
> type Color = (typeof colors)[number]
> // 等价于 type Color = 'red' | 'green'
> ```
>
> 这样做的妙处是：如果你在数组里新增了一个值 `'blue'`，联合类型会自动包含 `'blue'`，不需要手动维护两份列表。

每一种模式代表不同的安全级别。让我们看看源码里的配置：

```typescript
// src/utils/permissions/PermissionMode.ts, 第 42-91 行
const PERMISSION_MODE_CONFIG: Partial<
  Record<PermissionMode, PermissionModeConfig>
> = {
  default: {
    title: 'Default',
    shortTitle: 'Default',
    symbol: '',
    color: 'text',
    external: 'default',
  },
  plan: {
    title: 'Plan Mode',
    shortTitle: 'Plan',
    symbol: PAUSE_ICON,
    color: 'planMode',
    external: 'plan',
  },
  acceptEdits: {
    title: 'Accept edits',
    shortTitle: 'Accept',
    symbol: '⏵⏵',
    color: 'autoAccept',
    external: 'acceptEdits',
  },
  bypassPermissions: {
    title: 'Bypass Permissions',
    shortTitle: 'Bypass',
    symbol: '⏵⏵',
    color: 'error',
    external: 'bypassPermissions',
  },
  dontAsk: {
    title: "Don't Ask",
    shortTitle: 'DontAsk',
    symbol: '⏵⏵',
    color: 'error',
    external: 'dontAsk',
  },
}
```

注意这个类型：`Partial<Record<PermissionMode, PermissionModeConfig>>`。`Record` 创建一个从 `PermissionMode` 到 `PermissionModeConfig` 的映射，`Partial` 表示不是每种模式都有配置。这是一种常见的 TypeScript 模式——用 `Record` 保证键的类型安全，用 `Partial` 允许部分缺失。

让我们用保安的比喻来理解每种模式：

**`default`**——标准保安。大部分操作需要你确认，但已经加入白名单的操作可以自动通过。这是默认模式，平衡了安全和效率。

**`plan`**——严格的保安队长。在这个模式下，AI 只能做计划和读取操作，不能执行任何修改命令。就像你告诉保安："今天只让看文件的进，改文件的一个都不让进。"适合你只想让 AI 分析问题、不改代码的场景。

**`acceptEdits`**——宽松的保安。文件编辑操作自动通过，只有执行命令才需要确认。相当于保安被告知："编辑文件的人不用查了，放行。"

**`dontAsk`**——沉默的保安。所有需要询问的操作都变成拒绝。这个模式听起来奇怪，但在自动化场景中很有用——如果你不想被打断，又不想让 AI 为所欲为，那"宁可拒绝也不问"是一个合理的选择。

回到 `hasPermissionsToUseTool` 的代码，你可以看到 `dontAsk` 模式的作用：

```typescript
// src/utils/permissions/permissions.ts, 第 505-517 行
if (result.behavior === 'ask') {
  if (appState.toolPermissionContext.mode === 'dontAsk') {
    return {
      behavior: 'deny',
      decisionReason: { type: 'mode', mode: 'dontAsk' },
      message: DONT_ASK_REJECT_MESSAGE(tool.name),
    }
  }
```

当模式是 `dontAsk` 时，所有本该询问的操作都被转换为拒绝。这是一种"宁可错杀，不可放过"的策略。

而 `bypassPermissions` 则是另一极端——跳过所有权限检查。源码里它被标记为 `color: 'error'`，用红色显示，暗示这是危险操作。

## 被拦下来时，你看到了什么？

当一条命令被判定为 `'ask'`，程序需要暂停执行，在终端里显示一条消息，等待你的回应。

这条消息不是随便写的。它会告诉你为什么要问你、哪条规则触发了这次询问。生成这条消息的函数叫 `createPermissionRequestMessage`：

```typescript
// src/utils/permissions/permissions.ts, 第 137-200 行
export function createPermissionRequestMessage(
  toolName: string,
  decisionReason?: PermissionDecisionReason,
): string {
  if (decisionReason) {
    if (decisionReason.type === 'classifier') {
      return `Classifier '${decisionReason.classifier}' requires approval for this ${toolName} command: ${decisionReason.reason}`
    }
    switch (decisionReason.type) {
      case 'hook': {
        const hookMessage = decisionReason.reason
          ? `Hook '${decisionReason.hookName}' blocked this action: ${decisionReason.reason}`
          : `Hook '${decisionReason.hookName}' requires approval for this ${toolName} command`
        return hookMessage
      }
      case 'rule': {
        const ruleString = permissionRuleValueToString(
          decisionReason.rule.ruleValue,
        )
        const sourceString = permissionRuleSourceDisplayString(
          decisionReason.rule.source,
        )
        return `Permission rule '${ruleString}' from ${sourceString} requires approval for this ${toolName} command`
      }
      case 'mode': {
        const modeTitle = permissionModeTitle(decisionReason.mode)
        return `Current permission mode (${modeTitle}) requires approval for this ${toolName} command`
      }
      // ... 更多 case
    }
  }
  // 默认消息
  return `Claude requested permissions to use ${toolName}, but you haven't granted it yet.`
}
```

注意这个函数的结构：它接收一个 `decisionReason` 参数，这个参数的类型是 `PermissionDecisionReason`——又是一个联合类型。然后函数用 `switch` 语句根据 `type` 字段走不同的分支，为每种原因生成不同的提示消息。

- **`'hook'`**——一个钩子脚本（hook）拦截了这条命令。消息会告诉你哪个钩子、为什么。
- **`'rule'`**——一条权限规则匹配了。消息会告诉你规则内容和来源。
- **`'mode'`**——当前模式要求询问。消息会告诉你模式名称。
- **`'subcommandResults'`**——这条命令包含多个子命令，其中部分需要确认。消息会列出哪些子命令需要你点头。
- **`'safetyCheck'`**——安全检查触发了。比如命令中包含可疑的文件路径或操作。

这就是为什么你在终端里看到的权限提示总是这么详细——它不是一句干巴巴的"你确定吗？"而是告诉你"为什么我要问你"。

## 一条命令的权限旅程

让我们用 `git status` 这个例子，把权限检查的完整流程串一遍：

1. AI 决定使用 BashTool，输出工具调用 `{ name: "Bash", input: { command: "git status" } }`。
2. 程序调用 `hasPermissionsToUseTool`，传入工具名、输入参数和上下文。
3. `hasPermissionsToUseToolInner` 开始检查：先看 deny 规则列表——`git status` 不在黑名单里。再看 allow 规则列表——如果你之前配置过允许 Bash 命令，它可能在这里被放行。最后看 ask 规则列表——如果没有匹配，走默认行为。
4. 如果初步结果是 `'ask'`，函数还会检查当前的权限模式。如果是 `default` 模式，保持 `'ask'`。如果是 `dontAsk`，转为 `'deny'`。如果是 `auto`，可能交给 AI 分类器自动判断。
5. 最终结果返回给调用者。如果是 `'allow'`，命令静默执行。如果是 `'deny'`，命令被拒绝，AI 会收到一条拒绝消息。如果是 `'ask'`，程序在终端显示权限提示，等你回应。
6. 你按下回车（允许）或者输入拒绝指令。程序根据你的选择更新权限状态，然后继续或中止。

这就是为什么你会在终端里看到那个提示，然后按下回车，命令才真正开始执行。这中间发生的事情，比你想象的要多得多。

## 安全不是麻烦

你可能会觉得：每次都要确认，太烦了吧？为什么不能让 AI 自由发挥？

答案是：**安全不是麻烦，安全是信任的边界**。

想象你雇了一个助手帮你管理文件。你会希望他能自主处理日常事务，但涉及到删除文件、执行系统命令这种大事，你一定会想先知道一声。不是因为你信不过他，而是因为有些操作一旦做了就收不回来。

Claude Code 的权限系统就是这条边界。它不是在阻碍 AI 的工作，而是在确保你始终拥有控制权。`allow` 让信任的操作快速通过，`deny` 把危险操作挡在门外，`ask` 在不确定的时候把决定权交给你。

三种状态，三条路径，一个目的：**让你安心**。
