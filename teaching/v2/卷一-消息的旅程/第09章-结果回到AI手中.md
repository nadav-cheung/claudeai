# 第09章：结果回到AI手中

命令执行完了。结果——可能是一段输出，也可能是报错——现在需要被送回给 AI。

上一章你看到权限检查通过了。Claude Code 拿到了你的许可，BashTool 开始执行 `git status`。命令跑完了，终端吐出了一串文字。但这段文字现在还躺在工具函数的返回值里，AI 看不到它。

要让 AI 看到结果，Claude Code 需要做三件事：把结果包装成特定格式，把它放进对话流，然后把整个对话重新发送给 AI。

这一章讲的就是这个过程。

---

## 第一站：结果长什么样

当 `git status` 执行完毕，BashTool 返回的不只是一段纯文本。它返回的是一个结构化的对象，里面有 stdout（正常输出）、stderr（错误输出）、exit code（退出码），还有执行耗时等信息。

但 AI 不需要看到所有这些细节。AI 需要的是一个清晰、简洁的结果，告诉它命令是否成功，输出了什么。

所以在结果被送回给 AI 之前，有一个"翻译"步骤。源码里这个函数叫 `mapToolResultToToolResultBlockParam`。每个工具都有自己的实现——BashTool 会把 stdout 和 stderr 拼起来，FileReadTool 会返回文件内容，FileEditTool 会返回 diff 信息。

翻译完之后，结果变成了一个固定格式的对象：

```typescript
{
  type: 'tool_result',
  content: "On branch cmbt\nChanges not staged for commit...",
  is_error: false,
  tool_use_id: "toolu_01ABC123"
}
```

四个字段，各有各的意义：

- `type: 'tool_result'`——告诉 API "这是一个工具执行结果"
- `content`——实际的内容，通常是一段文字
- `is_error`——标记这次执行是否出了错
- `tool_use_id`——和之前 AI 发出的工具调用配对的 ID

最后那个 `tool_use_id` 是关键。还记得第 06 章里 AI 说"我要执行一条命令"时，每个工具调用都带了一个唯一的 ID 吗？现在结果里也带着同样的 ID。这样 API 就知道：这个结果是那条命令的回答。

就像写信要有收信人一样，结果必须精确地匹配到对应的请求。一个对话里 AI 可能同时调用好几个工具，每个结果都得回到正确的"信封"里。

## 第二站：包装进消息

光有结果还不够。Claude Code 的消息系统里，一条 `tool_result` 不是独立存在的。它必须被放进一条"用户消息"里。

这听起来有点奇怪——明明是工具执行的结果，为什么变成了"用户消息"？

因为从 API 的角度来看，对话只有两个角色：`assistant`（AI）和 `user`（你）。AI 发出工具调用，那是一个 `assistant` 消息的一部分。工具执行的结果，必须以 `user` 消息的形式回来。API 不认识第三个角色。

源码里，这个包装过程在 `toolExecution.ts` 的 `checkPermissionsAndCallTool` 函数中。当工具成功执行后，结果被这样处理：

```typescript
// src/services/tools/toolExecution.ts, 第 1403-1473 行
async function addToolResult(
  toolUseResult: unknown,
  preMappedBlock?: ToolResultBlockParam,
) {
  const toolResultBlock = preMappedBlock
    ? await processPreMappedToolResultBlock(
        preMappedBlock,
        tool.name,
        tool.maxResultSizeChars,
      )
    : await processToolResultBlock(tool, toolUseResult, toolUseID)

  const contentBlocks: ContentBlockParam[] = [toolResultBlock]
  // 如果用户在批准权限时附加了反馈，也一并加入
  if (
    'acceptFeedback' in permissionDecision &&
    permissionDecision.acceptFeedback
  ) {
    contentBlocks.push({
      type: 'text',
      text: permissionDecision.acceptFeedback,
    })
  }

  resultingMessages.push({
    message: createUserMessage({
      content: contentBlocks,
      toolUseResult: toolUseResult,
      sourceToolAssistantUUID: assistantMessage.uuid,
    }),
  })
}
```

注意看 `resultingMessages.push(...)` 这一行。这里用到了一个 TypeScript 基础操作：**Array 的 push 方法**。

`resultingMessages` 是一个数组（Array）。在 TypeScript 里，数组就像一个可以不断添加东西的列表。`push` 的意思是"把一个新元素加到列表末尾"。如果你有一个购物清单，`push` 就相当于在最后加一行。

```typescript
// 简单的 push 例子
const shoppingList = ["牛奶", "面包"]
shoppingList.push("鸡蛋")
// 现在 shoppingList = ["牛奶", "面包", "鸡蛋"]
```

在 Claude Code 的场景里，`resultingMessages` 就是这个"购物清单"。每执行完一个工具，结果就被 `push` 进去。如果 AI 一次调用了三个工具，这个数组就会 `push` 三次，收集所有结果。

还有一个有趣的细节：如果你在批准权限时顺便写了点什么（比如"记得加上 --verbose"），这段话也会被当作 `text` 块塞进同一个消息里。这样 AI 不仅能看到命令的结果，还能看到你的额外要求。

## 出错了怎么办

不是每次执行都一帆风顺。命令可能报错，参数可能不对，甚至工具本身可能出了 bug。

错误和成功走的路径几乎一样，只有一个关键区别：`is_error` 被设为 `true`。

比如当工具的输入参数验证失败时（AI 给出了一个不合法的命令格式），源码会这样组装结果：

```typescript
// src/services/tools/toolExecution.ts, 第 664-679 行
return [
  {
    message: createUserMessage({
      content: [
        {
          type: 'tool_result',
          content: `<tool_use_error>InputValidationError: ${errorContent}</tool_use_error>`,
          is_error: true,
          tool_use_id: toolUseID,
        },
      ],
      toolUseResult: `InputValidationError: ${parsedInput.error.message}`,
      sourceToolAssistantUUID: assistantMessage.uuid,
    }),
  },
]
```

错误内容被 `<tool_use_error>` 标签包裹。这不是为了好看，而是给 AI 一个明确的信号：这不是正常输出，这是错误。AI 看到这个标签，就知道需要换一种方式重试或者告诉你出了什么问题。

还有一类特殊的"错误"：权限被拒绝。上一章你选择了"拒绝"，那么结果消息的 `content` 就是拒绝的原因，`is_error` 同样是 `true`。AI 会理解"用户不同意执行这条命令"，然后换一个方案。

## 第三站：对话循环

结果准备好了。现在到了最关键的一步：把结果送回给 AI。

但这不是简单地发一条消息。Claude Code 会把整个对话历史重新发送给 API——你的原始问题、AI 的第一次回答、AI 请求执行的工具、工具执行的结果，全部打包。

为什么要这样？因为 API 是"无状态"的。它不记得你们之前聊过什么。每次你调用 API，都得把完整的对话历史告诉它。就像给一个健忘的朋友写信——你每次都得把之前的来往信件全部附上，他才能理解上下文。

在源码里，这个循环在 `query.ts` 中，看起来像这样：

```typescript
// src/query.ts, 第 307 行
while (true) {
  // 准备消息历史
  // 调用 API
  // 收到 AI 的回复
  // 如果 AI 请求了工具：
  //   执行工具
  //   把结果加入消息历史
  //   回到循环开头，重新发送给 API
  // 如果 AI 没有请求工具：
  //   跳出循环，结束
}
```

`while (true)` 是 TypeScript 里的一个 **while 循环**。`while` 的意思是"当...的时候"，括号里的 `true` 意味着"条件永远成立"。所以这个循环会一直跑，直到遇到 `break` 或 `return` 才停下来。

这就像你和朋友下棋：你走一步，他走一步，直到有人赢或者平局。Claude Code 的对话循环也是这样——你发消息，AI 回复，AI 可能要执行工具，工具结果回来，AI 再回复，可能又要执行工具......如此往复。

在每一轮循环中，源码会检查 AI 的回复里是否包含工具调用。如果包含，就标记 `needsFollowUp = true`，然后执行工具、收集结果，准备下一轮。如果没有工具调用，说明 AI 认为对话可以结束了，循环跳出。

```typescript
// src/query.ts, 第 829-834 行
const msgToolUseBlocks = message.message.content.filter(
  content => content.type === 'tool_use',
) as ToolUseBlock[]
if (msgToolUseBlocks.length > 0) {
  toolUseBlocks.push(...msgToolUseBlocks)
  needsFollowUp = true
}
```

注意这里又出现了一个类似 `push` 的操作：`toolUseBlocks.push(...msgToolUseBlocks)`。`...` 是"展开运算符"——它把一个数组里的所有元素一个一个取出来，然后 `push` 进去。好比把一盒鸡蛋逐个放进冰箱，而不是连盒子一起塞进去。

当一轮工具执行全部完成，所有结果都收集完毕后，这些结果被加入消息历史，然后循环继续：

```typescript
// src/query.ts, 第 1715-1716 行
const next: State = {
  messages: [...messagesForQuery, ...assistantMessages, ...toolResults],
  // ...
}
state = next
```

又是 `...` 展开运算符。旧的消息、AI 的回复、工具的结果，全部拼在一起，变成新的一轮对话的起点。`state = next` 把这个新的对话状态赋给 `state`，然后 `while (true)` 把你带回循环的开头，开始下一轮。

## 生活中的回信

把整个流程翻译成日常生活的场景，大概是这样：

你给一个远方的专家寄了一封信（用户消息），说"帮我看看这段代码有什么 bug"。专家回信了（AI 回复），但他说"我需要看一下这个文件的内容，请帮我查一下"。你在信的背面附上了文件内容（工具结果），然后把整封信——包括你最初的问题、专家的回复、以及你查到的文件内容——重新寄给专家。

专家看了文件，又回信说"我还需要看一下另一个文件"。于是你又去查，又把结果附上，连同所有之前的来往信件一起寄过去。

这就是对话循环。每次寄信，你都附上完整的历史记录。专家每次回信，可能需要更多信息，也可能直接给你答案。当他终于给出最终答案时，循环结束。

这个"你寄信、专家回信、你附上信息、再寄"的过程可能重复很多次。在你的 `git status` 场景里，AI 看到了命令的输出，理解了当前的代码状态，然后决定下一步该做什么——可能是查看某个文件，可能是运行 `git diff`，也可能是直接告诉你修复方案。

## 多轮工具调用：一次不够

实际上，解决一个 bug 很少只需要一条命令。

AI 看了 `git status` 的结果，发现有两个文件被修改了。它想看看具体改了什么，于是又发出了一条工具调用：`git diff`。等 `git diff` 的结果回来，它发现改动涉及一个它不了解的函数，于是又调用了 FileReadTool 去读那个文件。

每一轮工具调用都经历同样的流程：AI 请求 -> 权限检查 -> 执行 -> 结果包装 -> 追加到对话历史 -> 重新发送给 API。

`while (true)` 循环保证了这个过程可以一直持续下去，直到 AI 认为问题已经解决。在源码里，这个终止条件是 AI 的回复里不再包含工具调用——也就是说，AI 直接给出了文字回复，而不是又要求执行某个工具。

当然，循环不是无限期的。Claude Code 有一个最大轮次限制（`maxTurns`），防止 AI 陷入无限循环：

```typescript
// src/query.ts, 第 1704-1711 行
if (maxTurns && nextTurnCount > maxTurns) {
  yield createAttachmentMessage({
    type: 'max_turns_reached',
    maxTurns,
    turnCount: nextTurnCount,
  })
  return { reason: 'max_turns', turnCount: nextTurnCount }
}
```

就像棋局有步数限制一样，对话也有轮次上限。如果 AI 在限定的轮次内还没解决问题，循环会强制终止。

## 结果的旅途，一图以蔽之

让我们回顾一下，从命令执行完毕到 AI 看到结果，整个过程只有四步：

1. **工具执行完毕**，返回结果对象
2. **结果被翻译**成 `tool_result` 格式（`mapToolResultToToolResultBlockParam`）
3. **结果被包装**进一条用户消息（`createUserMessage`），然后 `push` 到消息数组
4. **整个对话历史**被重新发送给 API，AI 看到结果，继续回复

如果 AI 的回复又包含了工具调用，就回到第 1 步。如此循环。

这就是 Claude Code 的心跳：提问、执行、反馈、再提问。每一次循环都让 AI 离答案更近一步。

---

## 对话在继续

你的 `git status` 结果已经回到了 AI 手中。AI 看到了输出，理解了当前的状况，正在思考下一步该做什么。

它可能需要查看更多文件，可能需要运行更多命令，也可能已经准备好告诉你该怎么修这个 bug 了。不管怎样，对话还在继续。AI 的回复会出现在你的终端上，你看到了，也许会再输入什么，也许会直接让 AI 继续。

每一次交互，消息数组都在增长。你的问题、AI 的回答、工具调用、工具结果、AI 的追问、更多的工具调用......全都被忠实地记录在这个数组里。

但有一个问题。

对话在继续。但随着工具调用越来越多，对话变得很长。AI 的记忆力是有限的......
