# 第10章：对话越来越长

你的对话已经很长了。用户消息、AI 回答、工具调用、工具结果……加起来可能有好几万字。但 AI 的"记忆"是有限的。

回到上一章：AI 读到了工具执行的结果——`git status` 的输出——它根据这些结果继续思考，可能又决定执行下一条命令、读另一个文件、再做一次搜索。就这样一轮接一轮，消息数组越来越长。

一切看起来运转正常。但在平静的水面下，一个危机正在酝酿。

---

## 白板满了

想象你站在一块白板前。这块白板就是你每次和 AI 对话时，AI 能"看到"的全部内容。你打出的每一个字、AI 的每一句回答、每一次工具调用和结果，都被写在这块白板上。

白板很大，但它不是无限大的。

在 Claude Code 的世界里，这块白板叫做 **context window**（上下文窗口）。它的容量用 **token** 来衡量——你可以把 token 想象成一个"字"或"半个词"。一块典型的白板大约能容纳 200,000 个 token。

200,000 听起来很多。但一次典型的调试会话会消耗多少呢？

你的初始消息："帮我修个 bug"——几十个 token。AI 的第一轮回答——几百个 token。然后 AI 决定读文件，文件内容被加进来——可能几千个 token。接着搜索代码，搜索结果又加进来——又是几千个 token。再来一轮工具调用和结果……

一轮对话下来，可能就用了几千个 token。聊上十轮、二十轮，加上文件内容、命令输出，token 数量很快就会逼近白板的边缘。

白板满了会怎样？新内容写不进去了。AI 看不到你的新消息，对话就断了。

所以在白板写满之前，必须做一件事：擦掉一些旧内容，腾出空间来。

但不是随便擦。你不能把用户的核心需求擦掉，不能把刚找到的 bug 线索擦掉。你需要一种聪明的方式来"总结"旧内容，用一行话代替十行话，用一段摘要代替整页笔记。

这个过程，在 Claude Code 里叫做 **compact**（压缩）。

---

## 什么时候该压缩？

不能每条消息都压缩，那太频繁了，会影响对话的连贯性。也不能等到白板全满才压缩，那时候已经来不及了。

Claude Code 需要一种机制来判断："是时候压缩了。"

你可能会想：这不就是一个简单的比较吗？看看当前用了多少 token，看看阈值是多少，超过了就压缩。

没错，大体思路确实如此。但在实现层面，有几个细节值得细看。

首先，"白板多大"这件事并不是一个固定数字。它取决于你用的 AI 模型——不同的模型有不同的上下文窗口大小。而且，这个窗口还得预留一些空间给 AI 的输出——毕竟 AI 回答你的问题也需要 token。

在源码里，"实际可用的白板大小"是这样计算的：

```typescript
// src/services/compact/autoCompact.ts, 第 33-49 行
export function getEffectiveContextWindowSize(model: string): number {
  const reservedTokensForSummary = Math.min(
    getMaxOutputTokensForModel(model),
    MAX_OUTPUT_TOKENS_FOR_SUMMARY, // 20,000
  )
  let contextWindow = getContextWindowForModel(model, getSdkBetas())
  // ...环境变量覆盖...
  return contextWindow - reservedTokensForSummary
}
```

注意这里的一个关键概念：**effective** context window（有效上下文窗口）。总窗口减去必须留给输出的 token，剩下的才是你真正能用来放对话内容的空间。就像一块白板，你得在角落留出一块空白，以备随时需要写新的东西。

有了"白板多大"这个数字，下一步就是设定一个阈值——当对话占用的 token 达到这个阈值时，触发压缩。但这个阈值不能等于白板的大小，必须留一个缓冲区：

```typescript
// src/services/compact/autoCompact.ts, 第 62 行
export const AUTOCOMPACT_BUFFER_TOKENS = 13_000

// src/services/compact/autoCompact.ts, 第 72-91 行
export function getAutoCompactThreshold(model: string): number {
  const effectiveContextWindow = getEffectiveContextWindowSize(model)
  const autocompactThreshold =
    effectiveContextWindow - AUTOCOMPACT_BUFFER_TOKENS
  // ...环境变量覆盖...
  return autocompactThreshold
}
```

为什么需要 13,000 token 的缓冲区？因为压缩本身需要时间。从判断"该压缩了"到真正完成压缩，用户可能又发了一条消息，AI 可能又开始了一轮工具调用。这 13,000 token 就是给这段"空档期"留的余量。

好，现在有了白板大小，有了阈值。接下来就是核心判断：**要不要压缩？**

这个判断由 `shouldAutoCompact` 函数完成。它的逻辑可以用一个简单的条件来概括：如果当前对话的 token 数 >= 阈值，就压缩。但在实际代码中，还有更多的边界检查：

```typescript
// src/services/compact/autoCompact.ts, 第 160-238 行
export async function shouldAutoCompact(
  messages: Message[],
  model: string,
  querySource?: QuerySource,
  snipTokensFreed = 0,
): Promise<boolean> {
  // 递归保护：压缩内部的 AI 调用不能再触发压缩
  if (querySource === 'session_memory' || querySource === 'compact') {
    return false
  }

  if (!isAutoCompactEnabled()) {
    return false
  }

  // ...功能开关检查...

  const tokenCount = tokenCountWithEstimation(messages) - snipTokensFreed
  const threshold = getAutoCompactThreshold(model)

  const { isAboveAutoCompactThreshold } = calculateTokenWarningState(
    tokenCount,
    model,
  )

  return isAboveAutoCompactThreshold
}
```

这里有几个值得注意的设计决策：

**递归保护。** 压缩本身就是一次 AI 调用（让 AI 来总结对话）。如果这次 AI 调用又触发了压缩检查，就会陷入死循环。所以代码明确排除了 `compact` 和 `session_memory` 这两种来源。

**Token 估算。** `tokenCountWithEstimation` 这个函数名里的"estimation"（估算）值得玩味。精确计算 token 需要调用专门的分词器，很慢。所以在日常判断中，Claude Code 用的是估算值——够用就行，不一定精确到个位。

**Snip 机制。** 参数 `snipTokensFreed` 来自另一个叫 "snip" 的优化——系统会提前裁剪掉一些冗长的工具输出（比如超大的文件搜索结果），`snipTokensFreed` 就是裁剪释放的 token 数。在计算当前占用量时需要扣除这部分，否则会高估。

整个过程可以简化为一个 TypeScipt 风格的伪代码：

```typescript
if (querySource === 'compact') return false  // 别递归
if (!autoCompactEnabled) return false         // 用户关了
if (tokenCount >= threshold) return true      // 超了，压缩
return false                                  // 没超，不用管
```

这就是条件逻辑的力量——用一系列 `if` 判断来决定程序的行为。在编程中，这种模式无处不在：满足条件就做 A，否则做 B（或者什么都不做）。

## 压缩：把一本书变成一段话

当 `shouldAutoCompact` 返回 `true`，真正的压缩过程开始了。

压缩的核心思路，说白了就是：让 AI 自己读一遍整个对话，然后写一段摘要。之后，旧的对话被丢弃，只保留这段摘要。

你可以想象成这样：你在一个会议上记了十页笔记。会议快结束了，你需要把十页笔记浓缩成一段话，写在新的一页上。然后你把旧的十页笔记扔掉，只留这一页。

但"浓缩"不是随便缩写。Claude Code 给 AI 的压缩指令非常具体，要求摘要必须包含以下几个部分：

1. 用户的核心请求是什么
2. 涉及哪些技术概念
3. 操作了哪些文件，改了什么代码
4. 遇到了什么错误，怎么修的
5. 解决了什么问题，还有什么没解决
6. 所有用户发送过的消息（不是工具结果的消息）

压缩入口函数 `compactConversation` 是这样开始的：

```typescript
// src/services/compact/compact.ts, 第 387-450 行
export async function compactConversation(
  messages: Message[],
  context: ToolUseContext,
  cacheSafeParams: CacheSafeParams,
  suppressFollowUpQuestions: boolean,
  customInstructions?: string,
  isAutoCompact: boolean = false,
  recompactionInfo?: RecompactionInfo,
): Promise<CompactionResult> {
  // 空消息？报错
  if (messages.length === 0) {
    throw new Error(ERROR_MESSAGE_NOT_ENOUGH_MESSAGES)
  }

  const preCompactTokenCount = tokenCountWithEstimation(messages)

  // ...执行 PreCompact 钩子...

  // 构造压缩提示词
  const compactPrompt = getCompactPrompt(customInstructions)
  const summaryRequest = createUserMessage({
    content: compactPrompt,
  })

  // 循环生成摘要
  for (;;) {
    summaryResponse = await streamCompactSummary({
      messages: messagesToSummarize,
      summaryRequest,
      // ...
    })
    // ...
  }
```

注意那个 `for (;;)`——这是一个无限循环。为什么？因为生成摘要本身也是一次 AI 调用，如果对话太长，连"压缩"这个请求本身都可能超出白板大小。这时候代码会截断一部分最旧的消息，再试一次。如果还是太长，再截断，再试。最多重试三次。

还有一个巧妙的细节：压缩指令里明确写了"不要使用任何工具"：

```
CRITICAL: Respond with TEXT ONLY. Do NOT call any tools.
- Do NOT use Read, Bash, Grep, Glob, Edit, Write, or ANY other tool.
- Tool calls will be REJECTED and will waste your only turn.
```

为什么要强调这一点？因为 AI 在总结对话时可能会"顺手"想去读个文件或执行个命令来确认什么。但压缩的目的是节省 token，如果 AI 在压缩过程中又去调工具，就完全本末倒置了。所以必须用最强烈的语气告诉它：只输出纯文本，别的都不要做。

## 压缩之后：消息数组变短了

AI 生成了摘要。接下来，旧的对话消息被丢弃，取而代之的是一组全新的、更短的消息。

新的消息数组由 `buildPostCompactMessages` 函数构建：

```typescript
// src/services/compact/compact.ts, 第 330-338 行
export function buildPostCompactMessages(result: CompactionResult): Message[] {
  return [
    result.boundaryMarker,        // 压缩边界标记
    ...result.summaryMessages,    // 摘要消息
    ...(result.messagesToKeep ?? []), // 保留的最近消息
    ...result.attachments,        // 附件信息
    ...result.hookResults,        // 钩子结果
  ]
}
```

这段代码用了一个我们还没见过的语法：**展开运算符** `...`。

它做的事情很简单：把一个数组"拆开"，把里面的元素一个一个放进新数组里。就像你把一个盒子里的东西倒出来，摆到桌上。

`result.summaryMessages` 是一个数组，假设里面有两个元素 A 和 B。那么 `[...result.summaryMessages, ...result.attachments]` 就相当于 `[A, B, ...attachments]`。

新消息数组的结构是这样的：

- **boundaryMarker**：一个特殊的系统消息，标记"这里发生了一次压缩"。它不是给 AI 看的，而是给系统自己看的——方便以后追踪对话历史。
- **summaryMessages**：摘要内容。就是 AI 写的那段"把十页笔记浓缩成一段话"的结果。
- **messagesToKeep**：最近几轮的原始消息。压缩不会丢弃所有旧消息——最近几轮的对话通常最有价值，所以会保留。
- **attachments**：一些附加上下文信息。比如压缩前 AI 已经读取过的文件列表、已加载的工具信息等。这些信息不能因为压缩就丢了。
- **hookResults**：钩子系统的输出。可以暂时忽略它。

压缩前后，消息数组的变化可能看起来像这样：

```
压缩前（50 条消息，180,000 token）:
  [系统消息, 用户消息, AI回复, 工具调用, 工具结果, AI回复, 用户消息, ...]

压缩后（8 条消息，40,000 token）:
  [压缩边界标记, 摘要消息, 最近的用户消息, 最近的AI回复, 附件信息]
```

从 180,000 降到 40,000，腾出了大量空间。对话可以继续了。

## 数组长度和阈值：编程中的"够了没有"

回顾这一章的核心逻辑，你会发现它反复出现一种模式：**拿一个值和另一个值比较，根据结果决定做什么。**

- 当前 token 数 vs. 阈值：超过就压缩，没超过就不管。
- 消息数组长度 vs. 零：长度为零就报错，不为零就继续。
- 重试次数 vs. 最大重试次数：超了就放弃，没超就再试。

这种模式在编程里叫做 **条件逻辑**（conditional logic），是几乎所有程序的基础构建块。在 TypeScript 里，它通常长这样：

```typescript
if (currentValue >= threshold) {
  // 执行动作 A
} else {
  // 执行动作 B（或者什么都不做）
}
```

Claude Code 的压缩判断把条件逻辑用得很精细。它不是简单的一个 `if`，而是多层嵌套的条件：先检查来源是否合法，再检查功能是否开启，再检查 token 是否超限，每一步都可能提前返回 `false`，跳过后续所有逻辑。

这种"层层把关"的设计叫做 **guard clause**（守卫子句）——在函数开头就排除掉所有不该进入的情况，而不是把所有逻辑塞进一个巨大的 `if-else` 里。它让代码读起来像一张检查清单：不符合条件？走人。符合？继续下一项检查。

## 白板永远不会满

现在，让我们把整个压缩流程串一遍：

1. 你发送了一条新消息，或者 AI 完成了新一轮回复。
2. 系统调用 `shouldAutoCompact`，计算当前对话的 token 数。
3. 如果 token 数没超过阈值，什么都不做，对话继续。
4. 如果超过了，`compactConversation` 被调用。
5. 系统构造一段压缩提示词，告诉 AI："请总结这段对话。"
6. AI 读完全部旧消息，输出一段摘要。
7. 旧的对话消息被替换为：边界标记 + 摘要 + 最近几轮消息 + 附件。
8. 消息数组变短了，token 数大幅下降，对话可以继续。

这个过程对你是透明的。你可能注意到屏幕上闪过一行 "Compacting conversation..."，但除此之外，一切如常。AI 依然记得你的核心需求，依然知道之前改了哪些文件，只是它"记住"的方式从"逐字复述"变成了"概括总结"。

就像一个学生在考试前复习：他不可能把整本教材背下来，但通过做笔记、画思维导图，他可以把几百页的内容浓缩成几页关键知识点。压缩后的 AI 就像一个拿着精简笔记的学生——细节可能丢了一些，但大局还在。

白板永远不会满。因为每次快要满的时候，就会有人来擦掉旧内容，写上一段简洁的摘要，腾出空间来写新的东西。
