# 第05章：文字一个字一个字地回来

你盯着屏幕，AI 的回答开始一个字一个字地出现。像有人在屏幕上打字。

这不是魔法——这是"流式响应"。

---

## 为什么不一口气说完

先想一个场景：你让一个朋友帮你写一篇文章。有两种模式。

第一种模式：朋友说"你等着"，然后关上门埋头苦写。三个小时后，门开了，朋友递给你一篇一万字的文章。你在这三个小时里什么都看不到，只能干等。你不知道他写到哪了，不知道他是不是跑了，甚至不知道他还在不在房间里。

第二种模式：朋友写一句，就从门缝里递出来一张纸条。你拿到第一张纸条就知道他在写了。拿到第十张纸条，你已经能看出文章的大致方向。你不用等他全部写完，就可以开始阅读已经递出来的部分。

你选哪个？

当然是第二种。这就是流式响应（streaming）存在的原因。

对于 AI 来说，一次完整的回答可能很长——几百字、几千字，甚至需要"思考"很久。如果服务器等整个回答全部生成完毕再一次性返回，你可能要盯着一个空白的屏幕等上十几秒甚至几十秒。这段等待时间在用户体验上是灾难性的——你不知道 AI 在不在工作，不知道它是不是卡死了，不知道还要等多久。

流式响应解决了这个问题。AI 每生成一小段文字，就立刻发送给你。你的终端几乎在发出请求的同时就开始显示文字。你看到第一个字出现，就知道 AI 在工作了。文字一个字一个字地出现，你能跟着它的思路走，像看有人在实时打字。

在 Claude Code 的源码里，负责流式响应的核心函数叫 `queryModelWithStreaming`。它的声明是这样的：

```typescript
// src/services/api/claude.ts:752-769

export async function* queryModelWithStreaming({
  messages,
  systemPrompt,
  thinkingConfig,
  tools,
  signal,
  options,
}: {
  messages: Message[]
  systemPrompt: SystemPrompt
  thinkingConfig: ThinkingConfig
  tools: Tools
  signal: AbortSignal
  options: Options
}): AsyncGenerator<
  StreamEvent | AssistantMessage | SystemAPIErrorMessage,
  void
> {
  return yield* withStreamingVCR(messages, async function* () {
    yield* queryModel(
      messages,
      systemPrompt,
      thinkingConfig,
      tools,
      signal,
      options,
    )
  })
}
```

这段代码看起来很短，但信息量很大。不过先别急——在我们逐行理解它之前，你需要先知道几个底层概念。

## 水管和桶：两种传输方式

想象你需要从楼下的水站把水弄到你家。

方式一：你拎一个桶下楼，把水装满，拎回来。这一桶水就是一次完整的数据。你得等桶装满才能往回走。如果水站很大，你可能要等很久。

方式二：你接一根水管，从水站连到你家。水一滴一滴地流过来。你不需要等所有的水都到位——第一滴水到你家的时候，你就能用了。水管一直在输送，你一直在接收，两边同时工作。

第一种方式叫"一次性返回"（one-shot）。你发一个请求，服务器处理完，把完整的响应一次性丢给你。HTTP 请求的传统模式就是这样的——你发一个请求，等响应，拿到完整的响应体。

第二种方式叫"流式传输"（streaming）。你发一个请求，服务器开始处理，处理的过程中不断把中间结果推送给你。你这边一边接收一边处理，不需要等服务器全部完成。

Claude Code 用的是第二种——水管模式。

---

## 水管的名字叫 SSE

那这根"水管"在技术上是怎么实现的呢？

答案是一个叫 SSE（Server-Sent Events，服务器推送事件）的协议。它是 HTTP 协议的一个扩展，专门用于服务器向客户端单向推送数据。

普通的 HTTP 请求是这样的：你发一个请求，服务器返回一个响应，连接关闭。一问一答，结束。

SSE 不一样。你发一个请求，服务器返回一个**不关闭的连接**。然后服务器可以在这个连接上持续发送数据。每次发送的数据叫一个"事件"（event）。事件是一小段格式化的文本，通常以 `data:` 开头，以两个换行符结尾。

打个比方：普通 HTTP 是发一封邮件——你写好，发送，对方收到一封完整的信。SSE 更像是打开了一个聊天窗口——对方打一个字，你就看到一个字。

在 Claude Code 的场景里，Anthropic 的服务器在生成 AI 回答时，每生成一小段内容，就通过 SSE 推送一个事件。你的终端接收到这个事件，把内容显示在屏幕上。然后下一个事件到来，再追加显示。一直持续到服务器说"我回答完了"。

这就是为什么你看到 AI 的文字是一个字一个字地出现的——每个"字"都是服务器推送过来的一个事件。

不过，这里说的"字"并不完全准确。每个事件里携带的单位，不一定是人类意义上的一个字。

---

## Token：AI 眼中的"字"

AI 不像人一样一个字一个字地思考。它用一种特殊的单位，叫 token（词元）。

什么是 token？简单说，token 是 AI 处理文字的基本单位。一个 token 可能是一个完整的词，可能是一个词的一部分，也可能是一个标点符号。在英文里，"hello"可能是一个 token，"hamburger"可能是两个 token（"ham" + "burger"）。在中文里，一个汉字通常是一个 token，有时候两个汉字组成一个 token。

你可以把 token 理解为 AI 世界的"音节"。就像人类说话时以音节为基本节奏单位一样，AI 生成文字时以 token 为基本单位。

为什么这很重要？因为流式响应里，服务器推送的每个事件里包含的就是一个或几个 token。AI 不会一次生成一个完整的句子——它一次生成一个 token，然后立刻推送给你。

所以你看到的"一个字一个字地出现"，在技术层面上，是 AI 一次生成一个 token，服务器通过 SSE 推送过来，你的终端接收到之后渲染在屏幕上。

整个过程是一个持续流动的数据管道：AI 生成 token，服务器推送事件，终端接收并显示。三件事同时进行，没有谁在等谁。

---

## 能暂停的函数：Generator

现在我们回到代码。理解了流式传输的原理，你就能看懂 `queryModelWithStreaming` 的声明了。

关键在于函数声明里的那个星号：`async function*`。

在 TypeScript（和 JavaScript）里，普通函数是这样的：

```typescript
function cookDinner() {
  // 做三道菜
  // 全部做好后一起端上桌
  return [soup, mainCourse, dessert]
}
```

你调用 `cookDinner()`，它执行完毕后返回一个完整的结果。这就是"桶模式"——你得等所有菜做好才能吃到。

带星号的函数叫**生成器函数**（generator function）。它不一样：

```typescript
function* cookDinner() {
  // 做好汤，先端上来
  yield soup
  // 做好主菜，再端上来
  yield mainCourse
  // 做好甜点，最后端上来
  yield dessert
}
```

`yield` 这个词在英文里是"让出、产出"的意思。生成器函数执行到 `yield` 的时候，会**暂停**，把 `yield` 后面的值交出来。等外部代码说"继续"的时候，它才从暂停的地方接着往下执行。

这就是"水管模式"——生成器函数就像一根水管，数据从里面一段一段地流出来。每次 `yield`，就是水管里流出一段数据。

如果在生成器前面再加一个 `async`，变成 `async function*`，那就是**异步生成器**（async generator）。它能做异步操作——比如等待网络请求——然后 `yield` 结果。这正是流式响应需要的：等待服务器推送一个事件，然后 `yield` 出来。

Claude Code 的 `queryModelWithStreaming` 就是一个异步生成器。它的返回类型是 `AsyncGenerator<StreamEvent | AssistantMessage | SystemAPIErrorMessage, void>`——意思是这个生成器会不断地产出（yield）三种类型的值：流式事件（StreamEvent）、助手消息（AssistantMessage）、或者系统错误消息（SystemAPIErrorMessage）。

---

## 接住水管里的水：for await...of

生成器函数负责"产出"数据。那谁来"消费"这些数据呢？

答案是 `for await...of` 循环。这是一个专门用来遍历异步数据流的语法。

普通循环你肯定见过：

```typescript
for (const item of array) {
  // 处理每个 item
}
```

`for await...of` 是它的异步版本：

```typescript
for await (const message of stream) {
  // 每当 stream 产出一个值，就执行一次
}
```

它的工作方式是：向 `stream` 请求下一个值。如果 `stream` 还没有产出值，就**等**着。等 `stream` 通过 `yield` 产出了一个值，拿过来，执行循环体。然后再请求下一个值。一直持续到 `stream` 说"我产出了所有值了"（生成器函数执行完毕或者 `return`）。

你看到它和流式响应的对应关系了吗？`for await...of` 就是"接水"的那个动作——水管里每流出一滴水，它就接住一滴。

在 Claude Code 的源码里，处理流式数据的核心循环是这样的：

```typescript
// src/services/api/claude.ts:1940

for await (const part of stream) {
  // 每当服务器推送一个事件，这段代码就执行一次
  // part 就是服务器推送过来的一个事件
  switch (part.type) {
    case 'message_start':
      // 消息开始了，初始化状态
      break
    case 'content_block_start':
      // 一个新的内容块开始了（可能是一段文字、一个工具调用等）
      break
    case 'content_block_delta':
      // 内容块有了新增量——一个 token 来了
      break
    case 'content_block_stop':
      // 这个内容块结束了，把它组装成一条完整的消息
      break
    case 'message_delta':
      // 消息级别的更新（比如 token 用量、停止原因）
      break
    case 'message_stop':
      // 整条消息结束了
      break
  }
}
```

这个 `for await (const part of stream)` 就是整个流式处理的骨架。服务器推送的事件就像水滴一样，一滴一滴地流进来。每流进来一滴，`switch` 语句就判断它是哪种类型的事件，然后做相应的处理。

## 一滴水的一生

让我们跟着一滴水——也就是一个事件——走过它的完整旅程。

AI 开始生成回答。服务器通过 SSE 推送了第一个事件，类型是 `message_start`。这个事件包含消息的基本信息——模型版本、初始的 token 用量等。代码接住它，记录下首字节时间（TTFB，Time To First Byte）——从发出请求到收到第一个字节用了多久。

```typescript
// src/services/api/claude.ts:1980-1993

case 'message_start': {
  partialMessage = part.message
  ttftMs = Date.now() - start
  usage = updateUsage(usage, part.message?.usage)
  break
}
```

`ttftMs` 是一个很关键的性能指标。它告诉你服务器用了多长时间才返回第一个数据。如果这个数字很大，说明要么网络延迟高，要么服务器排队久。

接下来，服务器推送 `content_block_start` 事件。这表示一个新的"内容块"开始了。内容块可能是文字（text）、思考过程（thinking）、或者工具调用（tool_use）。代码根据内容块的类型初始化一个空的容器：

```typescript
// src/services/api/claude.ts:2019-2038

case 'text':
  contentBlocks[part.index] = {
    ...part.content_block,
    text: '',  // 初始化为空字符串，等待后续的增量填充
  }
  break
case 'thinking':
  contentBlocks[part.index] = {
    ...part.content_block,
    thinking: '',  // 思考内容也是空的，等待填充
    signature: '',
  }
  break
```

注意一个细节：不管是文字还是思考，初始化时内容都是空字符串。因为内容会在后续的事件里一点一点地到来。

然后，重头戏来了。服务器开始推送 `content_block_delta` 事件。每个 delta（增量）就是一个 token 的内容。对于文字类型的内容块，处理方式非常直接——把新的增量追加到已有内容后面：

```typescript
// src/services/api/claude.ts:2113-2126

case 'text_delta':
  if (contentBlock.type !== 'text') {
    throw new Error('Content block is not a text block')
  }
  contentBlock.text += delta.text
  break
```

`contentBlock.text += delta.text`——就这么一行。每一次增量到来，就追加到文字的末尾。你在屏幕上看到 AI 的文字一个字一个字地增长，背后就是这行代码在反复执行。

思考内容（thinking）的处理方式完全一样：

```typescript
case 'thinking_delta':
  contentBlock.thinking += delta.thinking
  break
```

而工具调用（tool_use）的增量处理稍有不同——工具的输入是 JSON 格式的，所以增量是 JSON 片段：

```typescript
case 'input_json_delta':
  contentBlock.input += delta.partial_json
  break
```

每到一个 JSON 片段，就拼接到已有的片段后面。等所有片段到齐，完整的 JSON 就组装好了。

当一个内容块的所有增量都到齐后，服务器推送 `content_block_stop` 事件。这时候代码把这个内容块组装成一条完整的助手消息，然后 `yield` 出去：

```typescript
// src/services/api/claude.ts:2192-2211

const m: AssistantMessage = {
  message: {
    ...partialMessage,
    content: normalizeContentFromAPI(
      [contentBlock],
      tools,
      options.agentId,
    ),
  },
  requestId: streamRequestId ?? undefined,
  type: 'assistant',
  uuid: randomUUID(),
  timestamp: new Date().toISOString(),
}
newMessages.push(m)
yield m
break
```

注意最后的 `yield m`。这就是生成器函数"交出"数据的关键动作。每完成一个内容块，就 `yield` 一条完整的消息。外层的 `for await...of` 循环会接住这个 `yield` 出来的消息，然后更新终端的显示。

## 水管的清洁工

流式传输有一个容易被忽略但非常重要的问题：**清理**。

水管用完了要关水龙头。如果不管它，水会一直流——在程序里，这意味着网络连接不会被释放，内存不会被回收。长时间运行下来，就会造成资源泄漏。

在 Claude Code 的源码里，有一个专门的函数负责清理流式连接：

```typescript
// src/services/api/claude.ts:2898-2912

export function cleanupStream(
  stream: Stream<BetaRawMessageStreamEvent> | undefined,
): void {
  if (!stream) {
    return
  }
  try {
    // 如果流还没有被中止，就中止它
    if (!stream.controller.signal.aborted) {
      stream.controller.abort()
    }
  } catch {
    // 忽略错误——流可能已经关闭了
  }
}
```

逻辑很简单：如果流还在，就中止它。如果已经关了，什么都不做。`try...catch` 包了一圈，是因为中止操作本身可能抛异常——比如流已经在另一个地方被关闭了。对于清理操作来说，报不报错无所谓，重要的是资源被释放了。

在生成器函数内部，清理操作被封装在一个叫 `releaseStreamResources` 的本地函数里：

```typescript
// src/services/api/claude.ts:1519-1526

function releaseStreamResources(): void {
  cleanupStream(stream)
  stream = undefined
  if (streamResponse) {
    streamResponse.body?.cancel().catch(() => {})
    streamResponse = undefined
  }
}
```

它做了两件事：中止流（通过 `cleanupStream`），取消底层的 HTTP 响应体（`streamResponse.body?.cancel()`）。两者都需要清理，因为流对象和 HTTP 响应是两个独立的资源，各自持有网络连接和内存缓冲区。

这个清理函数会在多种场景下被调用：正常结束时、出错时、用户主动取消时。不管哪种情况，水管都会被妥善关掉。

## 记账：Token 用量统计

流式传输还有一件重要的事情要做：记录 token 的使用量。

为什么要记录？因为 AI 的每一次调用都是要花钱的。输入多少 token、输出多少 token、缓存命中了多少 token——这些数据直接关系到你的账单。

在流式传输中，token 用量不是一次性告诉你的。它在不同的事件里分批到来。`message_start` 事件告诉你输入 token 的数量（因为输入在你发请求的时候就已经确定了）。后续的 `message_delta` 事件会告诉你累计的输出 token 数量。

关键词是"累计"。服务器不会告诉你"这一段新增了 5 个 token"——它告诉你的是"到目前为止，总共输出了 37 个 token"。这是一种更简单也更可靠的设计。

Claude Code 用一个叫 `updateUsage` 的函数来处理这个逻辑：

```typescript
// src/services/api/claude.ts:2924-2946

export function updateUsage(
  usage: Readonly<NonNullableUsage>,
  partUsage: BetaMessageDeltaUsage | undefined,
): NonNullableUsage {
  if (!partUsage) {
    return { ...usage }
  }
  return {
    input_tokens:
      partUsage.input_tokens !== null && partUsage.input_tokens > 0
        ? partUsage.input_tokens
        : usage.input_tokens,
    cache_creation_input_tokens:
      partUsage.cache_creation_input_tokens !== null &&
      partUsage.cache_creation_input_tokens > 0
        ? partUsage.cache_creation_input_tokens
        : usage.cache_creation_input_tokens,
    cache_read_input_tokens:
      partUsage.cache_read_input_tokens !== null &&
      partUsage.cache_read_input_tokens > 0
        ? partUsage.cache_read_input_tokens
        : usage.cache_read_input_tokens,
    output_tokens: partUsage.output_tokens ?? usage.output_tokens,
    // ... 还有更多字段
  }
}
```

这段代码的精髓在于：对于输入相关的 token（input_tokens、cache_creation_input_tokens、cache_read_input_tokens），只有当新值是非零的时候才更新。为什么？因为 `message_delta` 事件有时候会把这些字段设为 0——但 0 不代表"用了 0 个 token"，而是代表"这一段没有更新这些字段"。如果直接用 0 覆盖之前的值，你就会丢失真实的输入 token 数。

这是一个很典型的"累计统计"模式：只接受有意义的新值，忽略无意义的零值更新。

## 整条水管的全貌

现在，让我们把所有东西串起来，看看从你的终端发出请求到文字出现在屏幕上，整条水管长什么样。

第一步，`queryModelWithStreaming` 被调用。它是一个异步生成器，内部调用了 `queryModel`——另一个异步生成器。

第二步，`queryModel` 通过 Anthropic SDK 向服务器发送 HTTP 请求，请求里带了 `stream: true`，告诉服务器"我要流式响应"。

第三步，服务器开始处理，通过 SSE 连接推送事件。第一个事件是 `message_start`，然后是 `content_block_start`，接着是一系列的 `content_block_delta`（每个包含一个 token），然后是 `content_block_stop`。

第四步，`for await (const part of stream)` 循环接住每一个事件。对于 `content_block_delta` 事件，代码把增量追加到对应的内容块上。对于 `content_block_stop` 事件，代码把内容块组装成一条助手消息，然后 `yield` 出去。

第五步，`queryModelWithStreaming` 里的 `yield*` 把 `queryModel` yield 出来的消息原封不动地传递给外层。外层的代码通过 `for await...of` 接住这条消息，更新终端显示。

第六步，当服务器推送 `message_stop` 事件，流结束。`for await` 循环退出，清理函数释放网络连接和内存。

你在终端里看到的就是：一个字，又一个字，又又一个字——直到 AI 说完了它想说的话。

每个字背后，都是一个 token 从服务器通过 SSE 连接流过来，被 `for await...of` 接住，被 `+=` 追加到已有文字后面，然后被渲染到你的屏幕上。

水管模式，从头到尾。

---

## yield*：水管的转接头

你可能注意到 `queryModelWithStreaming` 里有一行奇怪的代码：

```typescript
return yield* withStreamingVCR(messages, async function* () {
  yield* queryModel(...)
})
```

这里出现了 `yield*`（带星号的 yield）。它和普通的 `yield` 有什么区别？

普通 `yield` 产出一个值，然后暂停。`yield*` 则是把另一个生成器的所有产出值**全部转发**出来。你可以把它理解为一个水管转接头——把另一根水管接上来，让水直接流过去，不用你一个一个地接。

在 Claude Code 的架构里，`queryModelWithStreaming` 本身不做实际的流式处理。它是一个包装层，把 `queryModel` 的输出通过 `yield*` 透传给外层，同时加了一层 VCR（Video Cassette Recorder，录像机）的功能——这是用来记录和回放 API 响应的测试机制。`withStreamingVCR` 会在生成器的外面包一层，把所有 yield 出来的值记录下来，方便后续的测试和调试。

```typescript
// src/services/vcr.ts:349-380

export async function* withStreamingVCR(
  messages: Message[],
  f: () => AsyncGenerator<
    StreamEvent | AssistantMessage | SystemAPIErrorMessage,
    void
  >,
): AsyncGenerator<
  StreamEvent | AssistantMessage | SystemAPIErrorMessage,
  void
> {
  if (!shouldUseVCR()) {
    return yield* f()   // 不需要录像，直接转发
  }

  // 需要录像：先收集所有产出值
  const buffer: (StreamEvent | AssistantMessage | SystemAPIErrorMessage)[] = []
  const cachedBuffer = await withVCR(messages, async () => {
    for await (const message of f()) {
      buffer.push(message)
    }
    return buffer
  })

  yield* cachedBuffer   // 把收集到的值全部转发出去
}
```

这就是 `yield*` 的妙用——不管内层生成器 yield 了多少次，外层只需要一行 `yield*` 就能全部转发。不需要手动写一个 `for await` 循环去逐个接住再逐个 yield。

## 回到你的屏幕

让我们回到你正在盯着的那块屏幕。

你输入了"帮我修个 bug"，按下回车。消息被打包成信封，通过网络发到 Anthropic 的服务器。服务器开始处理，通过 SSE 连接推送流式事件。你的终端里，`for await (const part of stream)` 循环正在忠实地接住每一个事件。

第一个事件来了——`message_start`。终端记录下首字节时间。

然后，`content_block_start`——一段文字要开始了。

接着，`content_block_delta`——第一个 token。"好"字出现在你的屏幕上。

又一个 delta——"的"。

又一个 delta——"，"。

又一个 delta——"我"。

你的屏幕上，文字一行一行地生长。每到一个 token，就追加一个字。你跟着 AI 的思路走，看它一句一句地把回答组织起来。

有时候 AI 会突然停顿——这不是卡了，而是它在"思考"（thinking）。思考过程也是通过流式推送的，只是你看不到。你只看到文字输出的停顿，然后继续流动。

直到服务器推送 `message_stop`，循环退出。AI 说完了。

但有时候，AI 不只是说话。

你看完它的回答，可能看到了这样一行：

```
> Execute: git log --oneline -5
```

AI 不只是给你回了文字——它说要执行一条命令。
