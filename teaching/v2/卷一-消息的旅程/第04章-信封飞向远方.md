# 第04章：信封飞向远方

你的消息被装进了信封。现在，这个信封要穿越互联网，飞到数千公里外的服务器。

上一章里，我们看着"帮我修个 bug"这几个字被包装成了一个精心构造的请求体——包含了对话历史、系统提示词、工具定义、思考配置。信封已经封好了口，上面写好了收件地址。

但信封自己不会飞。它需要一个投递系统。

---

## 餐厅窗口：什么是 API

在讲投递之前，我们先聊一个更基本的问题：你的终端和 Anthropic 的服务器之间，是怎么"说话"的？

想象你去一家餐厅。你坐在座位上，看菜单，决定了要吃什么。然后你怎么办？你不会自己冲进厨房跟厨师喊话——你会填一张点餐单，交给服务员，服务员送到厨房窗口。过了一会儿，厨房窗口那头递出来一盘做好的菜。

这个"厨房窗口"就是 API（Application Programming Interface，应用程序编程接口）。

API 的本质很简单：**你递进去一个请求，它返回给你一个结果。** 你不需要知道厨房里在干什么——厨师怎么切菜、火候怎么控制、调料放多少——你只需要知道：我把点餐单递进去，过一会儿菜会从窗口出来。

在 Claude Code 的场景里，"厨房"就是 Anthropic 的服务器，上面运行着 Claude 大语言模型。"点餐单"就是上一章装好的那个信封——包含你的消息、历史对话、工具定义的请求体。"菜"就是 Claude 生成的回答。

你可能会问：为什么不直接跟模型对话，要搞一个"窗口"？

因为模型不是跑在你电脑上的。你电脑上跑的是 Claude Code 这个客户端程序，它负责跟远方的服务器通信。API 就是客户端和服务器之间的协议——双方约定好了：请求长什么样、回答长什么样、出了问题怎么办。

这种"请求-响应"的模式在计算机世界里无处不在。你打开一个网页，浏览器向服务器发请求，服务器返回页面——这也是 API。你用手机查天气，天气 App 向气象服务发请求，返回温度湿度——这也是 API。

## HTTP：信封是怎么被送到的

知道了"厨房窗口"的概念，下一个问题：你的信封具体是怎么被投递的？

答案是一个你大概率听过的词：HTTP（HyperText Transfer Protocol，超文本传输协议）。别被名字吓到——HTTP 就是一套寄信的规则。

寄一封信，你需要几个东西：

**信封上的地址。** HTTP 把这个叫 URL（Uniform Resource Locator）。对于 Anthropic 的 API，地址大概长这样：

```
https://api.anthropic.com/v1/messages
```

你不需要记住这个地址。Claude Code 会自己搞定。

**寄信的方式。** HTTP 定义了好几种"寄信方式"，最常用的是 GET 和 POST。GET 是"我想看东西"——浏览器打开网页就是 GET。POST 是"我有些东西要交给你处理"——你往服务器提交数据，服务器处理后返回结果。Claude Code 给 Anthropic 发消息用的是 POST，因为它要把那一大包请求体提交过去，让服务器处理。

**信封上的标签。** HTTP 里叫 headers（请求头）。想象信封上除了地址，还有一些备注标签："寄件人是张三"、"这是加急件"、"请用中文回复"。HTTP 的 headers 做的就是这件事。比如有一个 header 叫 `Content-Type`，告诉服务器"我寄过去的东西是 JSON 格式的"；还有一个 header 叫 `Authorization`，我们待会儿会重点讲。

**信封里的东西。** HTTP 里叫 body（请求体）。这就是上一章我们辛辛苦苦组装好的那个 JSON 对象——包含 messages、system、tools 等字段的那个大家伙。

整个流程拼起来：Claude Code 构造一个 HTTP POST 请求，地址写成 Anthropic 的 API 地址，headers 里写上格式和认证信息，body 里塞进那个大 JSON，然后把这个请求扔到互联网上。

互联网的路由器、光缆、交换机负责把请求送到 Anthropic 的服务器。服务器收到后，调用 Claude 模型生成回答，把回答打包成 HTTP 响应送回来。

整个过程大概几百毫秒到几秒。对于你来说，就是按下回车后等了一会儿。

## SDK：一个专业的快递员

你可能会想：构造 HTTP 请求听起来很麻烦。要拼 URL，要设 headers，要把 JSON 序列化，还要处理响应……

没错。所以 Anthropic 提供了一个叫 SDK（Software Development Kit，软件开发工具包）的东西。它就像一个专业的快递员——你把信封交给他，他说"放心，交给我"，然后帮你把所有寄信的细节都处理好。

在 Claude Code 的源码里，这个快递员来自一个 npm 包：`@anthropic-ai/sdk`。我们看看它是怎么被请进来的：

```typescript
// 文件：src/services/api/client.ts，第1行
import Anthropic, { type ClientOptions } from '@anthropic-ai/sdk'
```

第一行代码就引入了 SDK。`Anthropic` 是这个快递员的"名字"——准确地说，是一个类。你通过创建它的实例来获得一个可以发请求的客户端。

那这个客户端是怎么创建的呢？我们看源码里的关键片段：

```typescript
// 文件：src/services/api/client.ts，第300-315行
// 根据认证方式创建 Anthropic 客户端
const clientConfig: ConstructorParameters<typeof Anthropic>[0] = {
  // API 密钥：非订阅用户使用 API Key
  apiKey: isClaudeAISubscriber() ? null : apiKey || getAnthropicApiKey(),
  // 认证令牌：订阅用户使用 OAuth 访问令牌
  authToken: isClaudeAISubscriber()
    ? getClaudeAIOAuthTokens()?.accessToken
    : undefined,
  ...ARGS,
}
return new Anthropic(clientConfig)
```

这段代码干了一件事：根据你是哪类用户，选择不同的认证方式来创建客户端。`new Anthropic(clientConfig)` 就是在说："快递员同志，这是你的工作证件和投递路线，请上岗。"

有了客户端之后，发送请求就很简单了。不需要手写 HTTP 请求，不需要拼 URL，不需要设 headers。在源码里，真正的 API 调用长这样：

```typescript
// 文件：src/services/api/claude.ts，第1822-1831行
const result = await anthropic.beta.messages
  .create(
    { ...params, stream: true },
    {
      signal,
      ...(clientRequestId && {
        headers: { [CLIENT_REQUEST_ID_HEADER]: clientRequestId },
      }),
    },
  )
  .withResponse()
```

看到了吗？`anthropic.beta.messages.create(...)`——就这么一行。你把参数传给它，它帮你发 HTTP 请求，帮你处理响应，把结果交给你。

你不需要知道底层用的是 POST 还是 GET，不需要知道 URL 是什么。SDK 把这些细节全封装了。你把信封递给快递员，说一句"帮我送到 Anthropic"，剩下的事他全包了。

不过注意那个 `stream: true`——这说明请求的不是一次性返回全部回答，而是让回答"流"回来。这个我们下一章会细讲。

## 会员卡：身份认证

快递员拿着你的信封去投递，但 Anthropic 的服务器不会随便接收谁的信。它需要确认：你是谁？你有权限用这个服务吗？

这就是认证（Authentication）。

想象你走进一家会员制超市。门口的保安拦住你："请出示会员卡。"你掏出会员卡，保安扫了一下，门开了。

在 API 的世界里，"会员卡"就是一个字符串，叫做 API Key（API 密钥）。它通常长这样：

```
sk-ant-api03-xxxxxxxxxxxxxxxxxxxxx
```

（这不是一个真的 key，只是展示一下格式。）

这个 key 是你在 Anthropic 注册账号后获得的。它唯一标识你的身份。每次 Claude Code 发请求时，都会在 HTTP headers 里带上这个 key，就像在信封上贴上你的会员卡：

```
x-api-key: sk-ant-api03-xxxxxxxxxxxxxxxxxxxxx
```

Anthropic 的服务器收到请求后，第一步就是检查这个 key。如果 key 有效，请求继续处理；如果 key 无效或过期，服务器直接拒绝，返回一个 401 状态码（意思是"未授权"）。

不过，如果你是 Claude 的订阅用户（比如用了 Claude Pro 或 Max），认证方式稍有不同。源码里区分了两种情况：

```typescript
// 文件：src/services/api/client.ts，第302-305行
apiKey: isClaudeAISubscriber() ? null : apiKey || getAnthropicApiKey(),
authToken: isClaudeAISubscriber()
  ? getClaudeAIOAuthTokens()?.accessToken
  : undefined,
```

如果你是订阅用户，用的是 OAuth 访问令牌（`authToken`）而不是 API Key。OAuth 是一种更安全的认证方式——你不需要手动管理密钥，系统会自动帮你刷新令牌。但对于 Claude Code 的使用者来说，这两种方式在体验上没有区别，你只需要登录一次就行。

如果你用的是 AWS Bedrock 或 Google Vertex 这种云平台来访问 Claude，认证方式又不一样了——会使用云平台自己的身份认证系统。源码里也有对应的处理（`AnthropicBedrock`、`AnthropicVertex`），但原理一样：证明你是谁，证明你有权限。

认证这件事，在源码里被处理得相当仔细。比如当令牌过期时，系统会自动刷新：

```typescript
// 文件：src/services/api/withRetry.ts，第243-249行
// 令牌过期时，自动刷新
if (
  (lastError instanceof APIError && lastError.status === 401) ||
  isOAuthTokenRevokedError(lastError)
) {
  const failedAccessToken = getClaudeAIOAuthTokens()?.accessToken
  if (failedAccessToken) {
    await handleOAuth401Error(failedAccessToken)
  }
  client = await getClient()  // 用新令牌重新创建客户端
}
```

这段代码的意思是：如果上一次请求因为认证失败（401）而被拒绝，那就刷新令牌，重新创建客户端，再试一次。你作为用户完全感知不到这个过程。

## Promise：我稍后给你结果

在继续往下走之前，我们需要认识一个 TypeScript 的概念。因为接下来你会在源码里反复看到它。

这个概念叫 Promise。

想象你去了一个人很多的餐厅。服务员没法马上给你上菜，所以给你一个取餐号码牌："您的号码是 42，一会儿叫到您的时候来取。"

你不需要站在出餐口干等。你可以回到座位上刷手机、跟朋友聊天。等菜好了，广播会叫你的号。当然，菜也有可能做不了了——比如厨房食材用完了，服务员会来告诉你"抱歉，今天做不了了"。

**Promise 就是这个号码牌。**

在代码里，很多操作不是立刻就能完成的。网络请求需要时间，文件读取需要时间，数据库查询需要时间。如果每做一个操作都要干等到它完成，那程序就卡死了。

Promise 的意思是："这件事我正在做，做完了我会把结果给你。做不了我也会告诉你。"

看一个具体的例子。前面我们提到的 API 调用：

```typescript
// 文件：src/services/api/claude.ts，第1822行
const result = await anthropic.beta.messages.create(...)
```

注意那个 `await` 关键字。它的意思是"等一下"——等 Promise 完成，拿到结果，再继续往下走。就像你拿着号码牌站在出餐口等菜——但跟现实世界不同的是，在代码里用 `await` 的时候，程序会真的停在这一行，直到结果回来。

这也是为什么 Claude Code 在等你按回车后会"卡住"一小会儿——因为它在 `await` 网络请求的返回。当网络请求的结果回来后，`result` 变量就被赋值了，程序继续往下走。

你可能会问：那如果我不想等呢？如果我想先做别的事，等结果回来再说？

TypeScript 也支持这种写法，不过需要用回调或者 `.then()` 的方式。在 Claude Code 的源码里，绝大多数地方用的是 `await`，因为逻辑是线性的——发出请求，等结果，处理结果。这种方式更直观，更容易理解。

在函数签名上，如果一个函数内部使用了 `await`，它的声明前面要加上 `async`。所以你会看到：

```typescript
// 文件：src/services/api/claude.ts，第709行
export async function queryModelWithoutStreaming({
  messages,
  systemPrompt,
  thinkingConfig,
  tools,
  signal,
  options,
}: { ... }): Promise<AssistantMessage> {
```

这个函数的返回类型是 `Promise<AssistantMessage>`——意思是"我承诺稍后给你一个 AssistantMessage"。调用这个函数的人可以选择 `await` 它，也可以选择拿到 Promise 先放着。

在源码中你会频繁看到 `async` 和 `await` 这对搭档。记住：`async` 标记一个函数是"异步的"（会返回 Promise），`await` 标记"我在这里等结果"。就这么简单。

## try/catch：万一出了问题

网络请求有一个讨厌的特点：它可能失败。

你的网可能断了。Anthropic 的服务器可能正在维护。你的 API Key 可能过期了。请求可能因为超时而丢失。任何一种情况都可能导致你的请求收不到回应。

如果代码不处理这些异常，程序就会崩溃——终端里弹出一堆红色错误信息，然后 Claude Code 直接退出。这不是好的用户体验。

所以代码需要一种机制来"捕获"错误，优雅地处理它。这就是 `try/catch`。

想象你在餐厅点了餐。正常情况下，菜会被端上来（`try` 块里的代码正常执行）。但如果厨房出了问题——食材用完了、厨师生病了、煤气停了——你需要有一个应对方案（`catch` 块里的代码）。也许换个菜，也许等一会儿再点，至少不能在座位上干坐着不知所措。

在 Claude Code 的源码里，错误处理无处不在。最典型的地方是重试机制（retry）。我们看看源码中 `withRetry` 函数的骨架：

```typescript
// 文件：src/services/api/withRetry.ts，第170-178行
export async function* withRetry<T>(
  getClient: () => Promise<Anthropic>,
  operation: (
    client: Anthropic,
    attempt: number,
    context: RetryContext,
  ) => Promise<T>,
  options: RetryOptions,
): AsyncGenerator<SystemAPIErrorMessage, T> {
```

`withRetry` 是一个"带重试的执行器"。你把要执行的操作（`operation`）交给它，它帮你执行。如果执行失败了，它不会直接崩溃——它会判断错误类型，决定要不要重试，要等多久再重试。

它的核心逻辑是一个 `try/catch` 循环。简化来看，大概是这个意思：

```
for 每次尝试（最多 maxRetries 次）：
  try：
    执行操作
    如果成功，返回结果
  catch 出错了：
    判断错误类型
    如果可以重试，等一会儿，继续下一轮循环
    如果不能重试，抛出错误，告诉调用方"我尽力了"
```

这个设计非常实用。网络请求偶尔失败是正常的——就像你打电话偶尔会占线一样。重试机制让 Claude Code 在面对网络抖动、服务器过载等临时问题时，不会直接放弃，而是自动重试，直到成功或者确认是真的出问题了。

## 重试的艺术：不是所有错误都值得重试

不过，重试不是瞎重试。

如果你打错了一个电话号码，重试一百次也还是打不通。只有那些"临时性问题"才值得重试——比如占线（服务器忙）、信号不好（网络抖动）。

源码里的 `shouldRetry` 函数负责做这个判断。它检查错误的类型和状态码，决定哪些值得重试：

```typescript
// 文件：src/services/api/withRetry.ts，第696行
function shouldRetry(error: APIError): boolean {
  // 模拟错误不重试（内部测试用）
  if (isMockRateLimitError(error)) {
    return false
  }

  // 408 请求超时 -- 重试
  if (error.status === 408) return true

  // 429 速率限制 -- 特定条件下重试
  if (error.status === 429) {
    return !isClaudeAISubscriber() || isEnterpriseSubscriber()
  }

  // 401 未授权 -- 刷新密钥后重试
  if (error.status === 401) {
    clearApiKeyHelperCache()
    return true
  }

  // 500+ 服务器错误 -- 重试
  if (error.status && error.status >= 500) return true

  return false
}
```

这段代码的逻辑很清晰：

- **429（请求太频繁）**：如果你被限流了，系统会在部分条件下重试。但对于订阅用户，可能会选择不重试，因为限流通常意味着"你用得太多了，需要等一段时间"。
- **401（认证失败）**：可能是令牌过期了，刷新后重试。
- **500 以上（服务器错误）**：服务端出了问题，值得重试——可能过一会儿就好了。

还有一类特别的情况：**529（服务过载）**。这是 Anthropic 专门定义的状态码，意思是"我们太忙了，现在处理不了你的请求"。源码里对 529 有专门的处理逻辑——包括重试次数限制、模型降级（换一个不那么忙的模型来处理）等。

重试之间还有一个重要的细节：**等待时间**。你不能一失败就立刻重试，那样只会给已经过载的服务器雪上加霜。源码使用了一种叫"指数退避"（Exponential Backoff）的策略：

```typescript
// 文件：src/services/api/withRetry.ts，第530-548行
export function getRetryDelay(
  attempt: number,
  retryAfterHeader?: string | null,
  maxDelayMs = 32000,
): number {
  // 如果服务器告诉我们要等多久，听它的
  if (retryAfterHeader) {
    const seconds = parseInt(retryAfterHeader, 10)
    if (!isNaN(seconds)) {
      return seconds * 1000
    }
  }

  // 否则用指数退避：500ms, 1000ms, 2000ms, 4000ms, ...
  const baseDelay = Math.min(
    BASE_DELAY_MS * Math.pow(2, attempt - 1),
    maxDelayMs,
  )
  // 加一点随机抖动，防止所有客户端同时重试
  const jitter = Math.random() * 0.25 * baseDelay
  return baseDelay + jitter
}
```

第一次重试等 500 毫秒，第二次等 1000 毫秒，第三次等 2000 毫秒……每次翻倍，但最多不超过 32 秒。这就叫指数退避——等的时间越来越长，给服务器恢复的机会。

还有一个细节很有意思：`jitter`（抖动）。在计算出等待时间后，会加上一点随机量。为什么？想象一下：如果一百个客户端同时失败，它们都会在 500 毫秒后同时重试，服务器会再次被冲击。加上随机抖动，大家的重试时间就错开了——有人在 500 毫秒后重试，有人在 600 毫秒后，有人在 550 毫秒后。这样服务器的压力就分散了。

这是分布式系统里一个非常经典的设计技巧。

默认情况下，最多重试 10 次（`DEFAULT_MAX_RETRIES = 10`）。对于绝大多数网络问题，10 次重试加上指数退避已经足够了。

## 请求在飞

让我们把整条线串起来。

你的消息"帮我修个 bug"经过上一章的打包，变成了一个包含 messages、system、tools 等字段的请求体。这个请求体被交给 Anthropic SDK，SDK 把它封装成一个 HTTP POST 请求，在请求头里附上你的认证信息，然后通过互联网发送到 `api.anthropic.com`。

如果一切顺利，几秒钟后，Anthropic 的服务器会返回结果。

如果不顺利——网络断了、服务器忙、认证过期——`withRetry` 会接住错误，判断能不能重试，等一段时间后自动再发一次。你可能在终端里会看到一行小字："正在重试……"或者完全不会注意到，因为重试在后台悄悄完成了。

请求已经发出了。但 AI 不会一口气说完——它的回答会一个字一个字地流回来。
