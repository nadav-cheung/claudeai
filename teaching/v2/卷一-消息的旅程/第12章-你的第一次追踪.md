# 第12章：你的第一次追踪

你读完了消息的旅程。现在，你要亲手追踪一次。

---

## 打开源码

如果你还没有 Claude Code 的源码，现在是时候把它拿出来了。两种方式任选：

**方式一：直接打开本地目录。** 如果你已经在使用 Claude Code 的开发版本，源码就在你手上。

**方式二：从 GitHub 克隆。** 打开终端，运行：

```bash
git clone https://github.com/anthropics/claude-code.git
cd claude-code
```

用你喜欢的编辑器打开这个目录。VS Code、WebStorm、Vim——都行。唯一的要求是你能方便地在文件之间跳转、搜索关键词。

准备好了吗？我们来追踪一条消息。

---

## 设定场景

假设你是 Claude Code 团队的新成员。有用户报告了一个问题："我明明装了那个工具，但 AI 说找不到。为什么这个工具没有被加载？"

你不知道答案。但你知道消息是怎么走的——你刚刚花了十一章学完了整条链路。现在该用上了。

你的追踪策略：从入口开始，沿着消息的路径，在每个关键检查点停下来看看。

---

## 第一站：入口

打开 `src/main.tsx`，跳到第 585 行：

```typescript
export async function main() {
```

这是整个程序的入口。当你在终端里输入 `claude` 并按下回车，操作系统加载 Node.js，Node.js 执行这个文件，控制权就到了 `main()` 函数手里。

在 `main()` 函数内部，你会看到它做了一大堆初始化工作：解析命令行参数、加载配置文件、设置日志、初始化权限系统。然后，它启动了 REPL——那个你跟 AI 对话的界面。

我们先不在入口处停留太久。入口只是起点，消息的故事从这里才刚开始。

但为了让你知道程序"正在经过这里"，你可以加一行 `console.log`：

```typescript
export async function main() {
  console.log("[TRACE] main() entered")
  // ... 原有代码
}
```

这不是调试器的断点，但效果类似——当这行文字出现在终端里时，你就知道程序确实走到了这一步。这是最朴素的追踪手段：在代码里留个记号，看它有没有被触达。

---

## 第二站：REPL

消息的旅程从用户输入开始，而用户输入发生在 REPL 里。

打开 `src/screens/REPL.tsx`，跳到第 572 行：

```typescript
export function REPL({
```

这是 REPL 组件的定义。REPL 是 Read-Eval-Print Loop 的缩写——读入你的输入，处理它，打印结果，然后等待下一次输入。

在 REPL 组件里，你需要关注的是用户消息的提交逻辑。当你在终端里输入"帮我修个 bug"并按下回车，这条消息就在这里被捕获，然后被打包成一个内部对象，准备送入下一道工序。

如果你想追踪消息是如何从键盘进入系统的，在 REPL 的提交处理函数附近加一行日志：

```typescript
console.log("[TRACE] REPL received user message:", userMessage)
```

现在，每次你输入一条消息，终端都会打印出消息的内容和结构。你开始看到消息的"内脏"了。

---

## 第三站：消息封装

你的文字被 REPL 捕获了。但它不能以原始文字的形式被发送给 AI——它需要被"装进信封"。

打开 `src/services/api/claude.ts`，跳到第 588 行：

```typescript
export function userMessageToMessageParam(
```

这个函数负责把用户消息转换成 AI 能理解的格式。如果你回顾第三章的内容，这就是那个"装信封"的过程。你的文字被包进一个结构化的对象里，附带上时间戳、附件信息、引用的文件内容等。

这是追踪的好位置。在这个函数里加一行日志：

```typescript
console.log("[TRACE] Message param built:", JSON.stringify(param, null, 2))
```

你会看到你的"帮我修个 bug"变成了一个带着 `role: "user"`、`content: [...]` 结构的 JSON 对象。从这一刻起，它不再是一行纯文字，而是一个"信封"——一个结构化的、可以被 API 处理的消息。

---

## 第四站：API 调用

信封封装好了。现在它要被寄出去。

同一个文件里，往下翻到第 752 行：

```typescript
export async function* queryModelWithStreaming({
```

这是真正把消息发送给 AI 的地方。注意函数名里的 `Streaming`——这意味着数据不是一次性返回的，而是像水龙头一样一个字一个字地流回来。

在这个函数的开头加一行：

```typescript
console.log("[TRACE] API call started, model:", model)
```

当你运行程序、发送一条消息时，你会看到这行日志在几毫秒内被触发。然后程序会"暂停"——不是真的暂停，而是在等待网络响应。几秒后，AI 的回答开始流回来。

如果你在这个函数的内部也加了日志，你会看到流式数据一个块一个块地到达：先是 `text` 块（AI 的文字回答），然后可能是一个或多个 `tool_use` 块（AI 请求执行工具）。

---

## 第五站：工具分发

我们的场景是"为什么工具没有被加载"。所以工具分发这一站是关键。

打开 `src/services/tools/toolExecution.ts`，跳到第 337 行：

```typescript
export async function* runToolUse(
```

这个函数是工具执行的入口。每当 AI 发出一个 `tool_use` 请求，代码就会来到这里。函数的第一件事就是根据工具名字找到对应的工具对象：

```typescript
let tool = findToolByName(toolUseContext.options.tools, toolName)
```

如果 `tool` 是 `undefined`——找不到——就会返回一条错误消息：

```typescript
if (!tool) {
  // 工具不存在
  yield {
    message: createUserMessage({
      content: [{
        type: 'tool_result',
        content: `<tool_use_error>Error: No such tool available: ${toolName}</tool_use_error>`,
        is_error: true,
        tool_use_id: toolUse.id,
      }],
    }),
  }
  return
}
```

在这里加一行关键日志：

```typescript
console.log("[TRACE] Tool lookup:", toolName, tool ? "FOUND" : "NOT FOUND")
console.log("[TRACE] Available tools:", toolUseContext.options.tools.map(t => t.name))
```

现在运行程序，重现用户报告的问题。当 AI 尝试使用那个"找不到"的工具时，你会看到：

```
[TRACE] Tool lookup: SomeTool NOT FOUND
[TRACE] Available tools: ["Read", "Write", "Bash", "Glob", "Grep", "Edit", ...]
```

线索出现了。`SomeTool` 确实不在可用工具列表里。但为什么？是工具没有被注册，还是注册了但被过滤掉了？

这就是追踪的价值：你不需要理解整个系统，你只需要在关键位置停下来，看看数据的实际状态。

---

## 第六站：权限检查

在工具被执行之前，还有一道关卡：权限。

打开 `src/utils/permissions/permissions.ts`，跳到第 473 行：

```typescript
export const hasPermissionsToUseTool: CanUseToolFn = async (
```

这个函数检查"当前用户是否允许执行这个工具"。有些工具需要用户明确授权，有些只需要一次授权后就记住决定，有些则完全禁止。

在我们的场景里，如果工具根本没被加载，权限检查就不会被触发——因为代码在找到工具之后才会走到权限检查。但如果你想追踪的是一个"工具被找到了但没执行"的问题，权限检查就是必看的地方。

加一行日志：

```typescript
console.log("[TRACE] Permission check for:", toolName, "result:", allowed)
```

如果这行日志显示 `result: false`，你就知道问题出在权限，而不是工具注册。

---

## 第七站：工具执行

假设工具被找到了，权限也通过了。接下来就是真正的执行。

以 Bash 工具为例，打开 `src/tools/BashTool/BashTool.tsx`，跳到第 420 行：

```typescript
export const BashTool = buildTool({
```

这是 Bash 工具的定义。`buildTool` 是一个工厂函数，它接收一个配置对象，返回一个完整的 `Tool` 实例。配置对象里最重要的字段是 `call`——这就是工具的执行逻辑。

如果你想追踪命令是怎么被执行的，找到 `call` 函数的实现，在它启动子进程的地方加一行日志：

```typescript
console.log("[TRACE] BashTool executing:", command)
```

当 AI 决定运行 `npm test` 时，你会看到这行日志被触发。然后子进程启动，命令的输出被逐行收集，最终作为工具结果返回。

---

## 第八站：压缩

如果你的追踪会话很长——你反复发送消息、AI 反复回复、工具反复执行——对话的 token 数会不断增长。在某个时刻，压缩会被触发。

打开 `src/services/compact/compact.ts`，跳到第 387 行：

```typescript
export async function compactConversation(
```

压缩函数被调用时，意味着对话已经很长了。如果你想确认压缩是否被触发，可以在 `shouldAutoCompact` 里加日志：

```typescript
console.log("[TRACE] Auto-compact check:", tokenCount, "vs threshold:", threshold)
```

这行日志会告诉你当前的 token 数和阈值。当前者超过后者时，压缩就开始了。

---

## 第九站：回到屏幕

一切处理完毕。AI 的回答、工具执行的结果、可能的压缩——所有这些最终都要显示在你的终端上。

回到 `src/screens/REPL.tsx`，第 572 行。REPL 组件不只是一个输入框，它也是输出区域。AI 的每一段文字、每一个工具调用的状态、每一条错误信息，都在这里被渲染成终端里的文字和颜色。

如果屏幕上显示的内容不对——比如工具结果没有显示，或者显示的内容和预期不符——问题很可能出在 REPL 的渲染逻辑里。

## 定位问题：为什么工具没被加载？

让我们回到追踪场景的核心问题：为什么某个工具没有被加载？

通过前面几站的日志，你已经知道了：

1. 工具确实不在可用列表里（第五站的日志告诉你的）。
2. 不是权限问题（因为工具根本没进入权限检查环节）。

那问题就出在更早的地方：工具的注册阶段。

工具是在程序启动时被注册到列表里的。回到 `src/main.tsx` 或者工具初始化的代码，搜索工具注册相关的逻辑。你可能会发现工具的注册受到某个配置项的控制——比如一个功能开关（feature flag），或者一个允许/禁止工具列表。

找到那个配置项，检查它的值。可能用户的配置文件里把某个工具禁用了，或者功能开关没有打开。修改配置，重启程序，再次追踪——这次第五站的日志应该显示 `FOUND` 而不是 `NOT FOUND`。

问题定位完毕。修复方法可能只是一行配置的改动。

这就是追踪的全过程。

## 你刚刚做了什么

让我们回顾一下你的追踪过程：

1. 你从程序入口 `main()` 开始，确认程序正常启动。
2. 你检查 REPL 组件，确认用户消息被正确捕获。
3. 你查看消息封装函数，确认消息被正确打包。
4. 你检查 API 调用，确认请求被正确发送。
5. 你在工具分发处找到线索——目标工具不在可用列表里。
6. 你检查权限系统，排除了权限问题。
7. 你回溯到工具注册阶段，找到了根本原因：配置项把工具禁用了。

整个过程不需要调试器，不需要复杂的开发环境，只需要几个 `console.log` 和对消息链路的理解。

你刚刚完成了一次真正的 bug 追踪。不是读教科书，不是看教程视频——你打开真实的源码，在真实的代码里加了真实的日志，找到了真实的问题。

## 追踪的艺术

你在这次追踪中用到的技巧，适用于任何大型代码库：

**从已知点出发。** 你知道消息从 `main()` 开始，所以从那里出发。你不知道问题出在哪，但你知道消息的路径，所以沿着路径一步步走。

**在岔路口停下来。** 每次消息从一个模块传递到另一个模块，就是一个"岔路口"——消息可能走对了路，也可能走错了。在岔路口加日志，看看消息的实际状态。

**排除法。** 你先排除了"工具不存在"（第五站确认了），然后排除了"权限拒绝"（第六站确认了），最终锁定了"注册阶段"（回溯找到的）。每排除一个可能性，搜索范围就缩小一圈。

**看数据，不看猜测。** 你没有靠猜——"我觉得可能是权限问题"——你用日志看到了实际的数据：工具列表里没有目标工具。数据驱动的调试比直觉驱动的调试高效得多。

这些不是理论。这是你刚刚亲手做过的事情。

## 卷一：你学到了什么

十一章的故事，加上一次实战追踪。现在停下来，看看你手里多了哪些能力。

**你能追踪一条消息的完整旅程。** 从你在终端里敲下回车键，到 AI 的回答出现在屏幕上，中间经过的每一个步骤你都知道：REPL 捕获输入、消息被封装、API 调用发起、流式数据返回、工具被识别和分发、权限被检查、命令被执行、结果被送回、对话被压缩、界面被更新。这些不再是黑箱。

**你能读懂 Claude Code 的源码结构。** 你知道了消息相关的代码在 `src/services/api/` 里，工具相关的代码在 `src/services/tools/` 和 `src/tools/` 里，UI 相关的代码在 `src/screens/` 里，压缩相关的代码在 `src/services/compact/` 里。当你需要找某个功能时，你知道去哪个目录翻。

**你能在源码里定位问题。** 就像你刚才做的那样——在关键位置加日志，沿着消息路径排查，用排除法缩小范围。你不需要理解每一行代码，你只需要知道在哪个位置停下来观察。

**你能修复简单的问题。** 配置错误、拼写错误、简单的条件判断失误——这些问题你都能找到并修复。你可能还没法重构整个工具注册系统或重新设计压缩算法，但你已经能在系统的表层发现问题、修复问题。

**你理解了编程的核心概念在真实项目里长什么样。** 函数、数组、对象、条件逻辑、异步操作、类型系统——这些你可能在教程里见过的概念，你在 Claude Code 的源码里看到了它们的真实应用。它们不是抽象的知识点，而是解决实际问题的工具。

这些能力不会只停留在 Claude Code 这一个项目里。追踪消息链路的思路适用于任何消息驱动的系统——Web 服务器、消息队列、微服务架构。读懂大型源码结构的能力适用于任何开源项目。定位和修复 bug 的能力适用于你写的任何代码。

## 但你还没看到引擎室

你跟着一条消息走完了它的旅程。你知道了它从哪里来、经过了哪些站点、最终去了哪里。这是一条完整的观光路线。

但观光路线不会带你进入引擎室。

想想这些问题：

消息的旅程中，每一个站点都是由什么支撑的？REPL 组件是怎么设计的，才能同时处理输入、输出、状态管理和界面更新？工具注册表是怎么组织的，才能让新工具随时被添加进来而不用修改任何已有代码？压缩算法是怎么设计的，才能保证摘要既简洁又不丢失关键信息？权限系统是怎么实现的，才能兼顾安全性和用户友好？

这些问题有一个共同特点：它们问的不是"发生了什么"，而是"为什么这样设计"。

你已经看到了"发生了什么"。卷二要打开引擎盖，看看这些系统内部是怎么设计的。

那些精巧的接口、灵活的注册表、聪明的压缩算法、多层防护的权限系统……它们是怎么被设计出来的？设计者在做决策时面临了哪些权衡？为什么选择了 A 方案而不是 B 方案？

这些问题的答案，藏在代码的结构里，藏在一个个设计模式的运用里，藏在接口的定义和实现的关系里。

你在卷一学会了看消息的旅程。卷二，你要学会看代码的骨架。
