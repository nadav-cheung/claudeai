# 第10章：调试的艺术

上一章，你学会了写测试。测试告诉你"出错了"——但它通常不会告诉你"为什么出错"。从"测试失败了"到"找到 bug 的根因"，中间有一段路要走。这段路，就是调试。

调试是一门手艺。好的调试不是靠运气瞎猜，而是系统性地缩小问题范围。这一章，我们学习 Claude Code 内置的调试工具，以及如何运用它们追踪问题。

---

## 目标

完成这一章后，你将能够：

1. 理解 Claude Code 内置的 debug 日志系统及其多个层次
2. 使用 `--debug`、`--debug=pattern`、`--debug-to-stderr` 启动调试
3. 利用 `logForDebugging()` 在源码中添加自定义调试日志
4. 使用性能分析器定位启动和查询中的慢操作
5. 配置 VS Code 调试器进行断点调试

---

## 动手

### 第一步：认识内置的 debug 日志系统

Claude Code 有一个精心设计的调试日志系统，核心在 `src/utils/debug.ts`。它不是一个简单的 `console.log` 包装器——它有日志级别、过滤机制、缓冲写入、文件轮转。

先看最核心的函数：

```typescript
// 文件：src/utils/debug.ts
export function logForDebugging(
  message: string,
  { level }: { level: DebugLogLevel } = { level: 'debug' },
): void {
  // 检查日志级别
  if (LEVEL_ORDER[level] < LEVEL_ORDER[getMinDebugLogLevel()]) {
    return
  }
  // 检查是否应该记录这条消息
  if (!shouldLogDebugMessage(message)) {
    return
  }
  // 格式化并写入
  const timestamp = new Date().toISOString()
  const output = `${timestamp} [${level.toUpperCase()}] ${message.trim()}\n`
  if (isDebugToStderr()) {
    writeToStderr(output)
    return
  }
  getDebugWriter().write(output)
}
```

这个函数做了三件事：

1. **级别过滤**——低于最低级别的消息直接丢弃。日志级别从低到高是：`verbose` < `debug` < `info` < `warn` < `error`
2. **消息过滤**——根据 debug 过滤器决定是否记录这条消息
3. **输出路由**——要么写到 stderr（实时），要么写到缓冲写入器（后台异步写入文件）

日志写到哪里？默认位置是：

```
~/.claude/debug/<session-id>.txt
```

同时维护一个 `latest` 符号链接，指向当前会话的日志文件：

```
~/.claude/debug/latest → ~/.claude/debug/abc123.txt
```

这意味着你可以随时用 `tail -f ~/.claude/debug/latest` 实时查看日志。

### 第二步：启动调试模式

有几种方式启用调试日志：

**`--debug` 或 `-d`**——最简单的方式。启用调试日志并写入文件：

```bash
claude --debug
```

**`--debug=pattern`**——带过滤器的调试。只记录匹配特定分类的消息：

```bash
claude --debug=api,mcp       # 只看 api 和 mcp 相关的日志
claude --debug=!1p,!file     # 排除 1p 和 file 类别的日志
```

过滤器的实现很有意思。`src/utils/debugFilter.ts` 定义了分类提取逻辑：

```typescript
// 文件：src/utils/debugFilter.ts
export function extractDebugCategories(message: string): string[] {
  const categories: string[] = []
  // "category: message" → 提取 category
  const prefixMatch = message.match(/^([^:[]+):/)
  if (prefixMatch) categories.push(prefixMatch[1].trim().toLowerCase())
  // "[CATEGORY] message" → 提取 CATEGORY
  const bracketMatch = message.match(/^\[([^\]]+)]/)
  if (bracketMatch) categories.push(bracketMatch[1].trim().toLowerCase())
  // "MCP server \"name\"" → 提取 mcp 和 name
  const mcpMatch = message.match(/^MCP server ["']([^"']+)["']/)
  if (mcpMatch) { categories.push('mcp'); categories.push(mcpMatch[1].toLowerCase()) }
  return Array.from(new Set(categories))
}
```

日志消息的分类是根据消息格式自动提取的。比如 `MCP server "github": connection established` 会被分类为 `mcp` 和 `github`，如果你用 `--debug=mcp` 过滤，这条消息就会出现。

**`--debug-to-stderr` 或 `-d2e`**——把日志直接写到标准错误输出，而不是文件。适合在终端里实时看日志：

```bash
claude --debug-to-stderr 2>&1 | tee debug-output.log
```

**环境变量 `DEBUG`**——经典的环境变量开关：

```bash
DEBUG=1 claude
```

### 第三步：用 `logForDebugging` 添加自定义日志

当你在开发自己的工具或插件时，可以导入并使用这个日志系统：

```typescript
import { logForDebugging } from '../utils/debug.js'

// 在你的工具逻辑中
async call(input) {
  logForDebugging(`MyTool called with input: ${JSON.stringify(input)}`)

  // ... 核心逻辑 ...

  logForDebugging(`MyTool result: ${result}`, { level: 'info' })

  // 出错时
  logForDebugging(`MyTool error: ${error.message}`, { level: 'error' })

  return { data: result }
}
```

注意几个要点：

- **不要在非 debug 模式下依赖日志**——`shouldLogDebugMessage` 在非 debug 模式下会返回 `false`，日志不会被写入。这意味着 `logForDebugging` 不会影响生产性能。
- **使用合适的级别**——`verbose` 用于高频诊断信息（可能每秒几十条），`debug` 用于常规调试，`info` 用于重要事件，`warn` 用于异常但可恢复的情况，`error` 用于真正的错误。
- **用 `CLAUDE_CODE_DEBUG_LOG_LEVEL=verbose` 启用最高级别**——默认级别是 `debug`，`verbose` 级别的消息会被过滤掉。只有设置了这个环境变量，你才能看到所有消息。

### 第四步：使用内置的 `/debug` skill

Claude Code 有一个内建的 `/debug` skill，用于调试当前会话的问题：

```
/debug [问题描述]
```

这个 skill 做了以下事情：

1. 如果你之前没有启用 debug 日志，它会**立即启用**（但之前的日志已经丢失了——它只能记录启用之后的活动）
2. 读取当前会话的 debug 日志的最后 20 行
3. 分析日志中的 `[ERROR]` 和 `[WARN]` 条目
4. 给出诊断结论和修复建议

它的源码在 `src/skills/bundled/debug.ts`：

```typescript
// 文件：src/skills/bundled/debug.ts
export function registerDebugSkill(): void {
  registerBundledSkill({
    name: 'debug',
    description: 'Enable debug logging for this session and help diagnose issues',
    allowedTools: ['Read', 'Grep', 'Glob'],
    // ...
    async getPromptForCommand(args) {
      const wasAlreadyLogging = enableDebugLogging()
      const debugLogPath = getDebugLogPath()

      // 读取日志文件的最后 64KB
      const stats = await stat(debugLogPath)
      const readSize = Math.min(stats.size, TAIL_READ_BYTES)
      // ... 读取并格式化最后 20 行 ...

      return [{
        type: 'text',
        text: `# Debug Skill\n\n日志路径: ${debugLogPath}\n\n${logInfo}\n\n## 问题\n${args || '请描述你遇到的问题'}`
      }]
    },
  })
}
```

这是一个很好的调试流程参考：**先启用日志，让用户重现问题，然后分析日志**。

### 第五步：性能分析——启动性能

当你觉得 Claude Code 启动太慢时，可以使用内置的启动性能分析器。

设置环境变量：

```bash
CLAUDE_CODE_PROFILE_STARTUP=1 claude
```

分析器会在 `src/utils/startupProfiler.ts` 中记录一系列检查点：

```typescript
// 文件：src/utils/startupProfiler.ts
const PHASE_DEFINITIONS = {
  import_time: ['cli_entry', 'main_tsx_imports_loaded'],
  init_time: ['init_function_start', 'init_function_end'],
  settings_time: ['eagerLoadSettings_start', 'eagerLoadSettings_end'],
  total_time: ['cli_entry', 'main_after_run'],
}
```

每个阶段记录了开始和结束的检查点。分析器使用 Node.js 的 `performance.mark()` API 记录精确时间戳，还会捕捉每个检查点的内存快照。

分析结果输出到：

```
~/.claude/startup-perf/<session-id>.txt
```

报告长这样：

```
================================================================================
STARTUP PROFILING REPORT
================================================================================

     0.0ms   +0.0ms  cli_entry                heap: 12.3MB
    45.2ms  +45.2ms  cli_dump_system_prompt_path
    89.7ms  +44.5ms  main_tsx_imports_loaded   heap: 28.1MB
   ...
   312.5ms  +12.3ms  main_after_run            heap: 45.6MB

Total startup time: 312.5ms
================================================================================
```

每一行显示了：相对起始时间、与上一个检查点的差值、检查点名称、堆内存使用量。如果某个步骤的耗时异常高，你一眼就能看到。

### 第六步：性能分析——查询性能

启动性能是一回事，运行时的查询性能是另一回事。Claude Code 有一个专门的查询分析器，追踪从用户输入到 AI 回复的完整管线。

设置环境变量：

```bash
CLAUDE_CODE_PROFILE_QUERY=1 claude
```

这个分析器在 `src/utils/queryProfiler.ts` 中，追踪了完整的查询生命周期：

```
query_user_input_received          # 用户输入开始
query_context_loading_start/end    # 系统提示词加载
query_microcompact_start/end       # 消息微压缩
query_autocompact_start/end        # 自动压缩检查
query_setup_start/end              # 流式执行器设置
query_tool_schema_build_start/end  # 工具 schema 构建
query_message_normalization_start/end  # 消息格式化
query_client_creation_start/end    # Anthropic 客户端创建
query_api_request_sent             # HTTP 请求发出
query_response_headers_received    # 收到响应头
query_first_chunk_received         # 第一个流式数据块（TTFT）
query_api_streaming_end            # 流式传输完成
query_tool_execution_start/end     # 工具执行
```

报告会计算关键指标：

```

  - Network latency: 1000ms (81.0%)

```

这些数据告诉你时间花在了哪里。如果 "Tool schemas" 占了很大比例，可能是工具数量太多或者 schema 构建效率有问题。如果 "Network TTFB" 占主导，瓶颈在 API 调用。

### 第七步：慢操作检测

除了主动的性能分析，Claude Code 还有一个被动的慢操作检测系统。它在 `src/utils/slowOperations.ts` 中，包装了常见的耗时操作：

```typescript
// 文件：src/utils/slowOperations.ts
export function jsonStringify(value, replacer?, space?) {
  using _ = slowLogging`JSON.stringify(${value})`
  return JSON.stringify(value, replacer, space)
}
```

`using _ = slowLogging\`...\`` 是一个精巧的 JavaScript 模式——`using` 是 ECMAScript 的资源管理语法（类似 Python 的 `with`），`slowLogging` 返回一个 `Disposable` 对象，它的 `[Symbol.dispose]()` 方法在代码块结束时被调用，计算耗时并决定是否记录。

```typescript
class AntSlowLogger {
  constructor(args) {
    this.startTime = performance.now()
    this.err = new Error()  // 捕获调用栈
  }
  [Symbol.dispose]() {
    const duration = performance.now() - this.startTime
    if (duration > SLOW_OPERATION_THRESHOLD_MS && !isLogging) {
      logForDebugging(
        `[SLOW OPERATION DETECTED] ${description} (${duration.toFixed(1)}ms)`
      )
    }
  }
}
```

阈值可以通过环境变量控制：

```bash
# 开发环境默认 20ms
# 内部用户默认 300ms
# 外部用户默认 Infinity（不检测）
CLAUDE_CODE_SLOW_OPERATION_THRESHOLD_MS=50 claude --debug
```

这个系统帮你捕捉到你可能根本不知道存在的性能问题。比如某次 `JSON.stringify` 突然花了 200ms，日志里就会出现 `[SLOW OPERATION DETECTED]`，带上调用栈帮你定位。

### 第九步：调试策略——系统化缩小范围

工具千千万，思路只一条：**系统化地缩小问题范围**。

**第一步：复现。** 你必须能稳定地复现问题。如果不能复现，先解决复现问题。用 `--debug-to-stderr` 启动，记录完整的会话日志。

**第二步：定位层级。** 问题发生在哪一层？

- **输入层**——AI 传过来的参数不对？检查 `inputSchema.parse()` 的输出
- **权限层**——操作被拒绝了？检查 `checkPermissions()` 的返回值
- **执行层**——`call()` 内部出错了？在 `call()` 里加日志
- **输出层**——结果格式不对？检查 `mapToolResultToToolResultBlockParam()`

**第三步：加日志。** 在问题层的入口和出口各加一行 `logForDebugging`：

```typescript
async call(input) {
  logForDebugging(`[MyTool] enter call, input=${JSON.stringify(input)}`)
  // ... 核心逻辑 ...
  logForDebugging(`[MyTool] exit call, result=${JSON.stringify(result)}`)
  return result
}
```

不要小看这两行日志。如果 enter 出现了但 exit 没有，说明中间抛了异常。如果 exit 的 result 和你期望的不一样，说明逻辑有 bug。

**第四步：二分查找。** 如果问题在一段长逻辑中，用二分法缩小范围：在中间加日志，看前半段还是后半段有问题，然后继续二分。

**第五步：固定和验证。** 找到问题后，先写一个测试复现它（防止回归），然后修复，最后确认测试通过。

## 遇到问题？

### 问题 1：debug 日志文件太大

**症状**：`~/.claude/debug/` 目录下有巨大的日志文件，占满了磁盘。

**原因**：debug 模式下日志是不限量写入的，长时间会话可能积累几十 MB 甚至几百 MB 的日志。

**解决方案**：定期清理旧的日志文件。日志文件按 session ID 命名，可以安全删除旧会话的日志：

```bash
# 删除 7 天前的日志
find ~/.claude/debug/ -name "*.txt" -mtime +7 -delete
```

### 问题 2：source map 断点不生效

**症状**：在 `src/` 下的 `.ts` 文件里设断点，但调试器不停。

**原因**：VS Code 的 source map 支持需要正确配置。有些版本的 Node.js 调试器对内联 source map 的处理有问题。

**解决方案**：确认 `cli.js.map` 和 `cli.js` 在同一目录。尝试在 VS Code 设置中添加：

```json
{
  "debug.javascript.sourceMapRenames": true,
  "debug.javascript.usePreview": true
}
```

如果仍然不生效，直接在 `cli.js` 中搜索目标函数设断点。虽然代码压缩后可读性差，但搜索函数名或关键字符串通常能定位到。

### 问题 3：`--debug` 模式下性能明显下降

**症状**：加了 `--debug` 之后，Claude Code 变慢了。

**原因**：debug 模式下写入器从"缓冲异步"切换到"立即同步"——每条日志都直接 `appendFileSync`，不再缓冲。高频日志会严重影响性能。

**解决方案**：如果你只需要看特定类别的日志，用 `--debug=pattern` 过滤：

```bash
claude --debug=api  # 只看 API 相关日志
```

这样非匹配的消息不会触发写入，性能影响小得多。

### 问题 4：慢操作日志没出现

**症状**：你设了 `CLAUDE_CODE_SLOW_OPERATION_THRESHOLD_MS=10`，但没有看到慢操作日志。

**原因**：慢操作日志只在 debug 模式下可见。`slowLogging` 调用了 `logForDebugging`，后者在非 debug 模式下不会写入。

**解决方案**：同时启用 debug 和阈值设置：

```bash
CLAUDE_CODE_SLOW_OPERATION_THRESHOLD_MS=10 claude --debug
```

## 验证

让我们确认你的调试技能到位了。

**练习 1：启用并查看日志。** 用 `claude --debug` 启动一个会话，执行几条命令，然后检查 `~/.claude/debug/latest` 文件。你应该能看到带时间戳的日志条目。

**练习 2：过滤日志。** 用 `claude --debug=mcp` 启动，触发一个 MCP 工具调用。日志里应该只包含 MCP 相关的消息。用 `--debug=api` 重复，确认只看到 API 相关的日志。

**练习 3：查询性能分析。** 用 `CLAUDE_CODE_PROFILE_QUERY=1 claude --debug` 启动，发送一条查询，然后在 debug 日志中找到 `QUERY PROFILING REPORT`。确认你看到了 TTFT 分解和阶段耗时。

**练习 4：添加自定义日志。** 在你之前创建的工具里加一行 `logForDebugging`，用 `--debug` 模式运行，确认你的日志出现在输出中。

如果这四个练习都完成了，你的调试工具箱就齐备了。

## 回顾

这一章，我们深入了 Claude Code 的调试体系：

1. **日志系统**——`logForDebugging` 是核心入口，支持五个级别、分类过滤、缓冲写入
2. **启动方式**——`--debug`、`--debug=pattern`、`--debug-to-stderr`、`DEBUG=1` 四种方式控制日志行为
3. **日志过滤**——`--debug=pattern` 支持正向和反向过滤，分类从消息格式自动提取
4. **内置 skill**——`/debug` 命令可以中途启用日志并自动分析问题
5. **启动性能**——`CLAUDE_CODE_PROFILE_STARTUP=1` 记录从入口到就绪的完整时间线
6. **查询性能**——`CLAUDE_CODE_PROFILE_QUERY=1` 记录从输入到首字返回的每个阶段
7. **慢操作检测**——`slowLogging` 包装常见操作，超过阈值自动报告
8. **断点调试**——VS Code + `cli.js.map` 实现源码级断点
9. **调试策略**——复现、定位层级、加日志、二分、写测试、修复

调试的核心不是工具，是思维方式：**不要猜，要观察。不要一次改多处，要一次只改一处。每一步都要有验证。**
