# 第02章：第一次修改

上一章你搭好了工坊，源码可以跑起来了。这一章，你要亲手改点什么——哪怕只是改一行文字。

别小看"改一行文字"。这意味着你理解了代码结构，找到了目标位置，做了修改，构建成功，并且看到了效果。这是 Contributor 的第一步。

---

## 目标

修改 FileReadTool 的工具描述（description），重新构建 Claude Code，然后验证 AI 确实使用了你修改后的描述。

完成后你会获得三样东西：

1. 知道工具的 prompt/description 在哪个文件定义
2. 知道怎么构建和测试修改
3. 拥有你的第一个 git commit

---

## 动手

### 第一步：找到目标

Claude Code 有三十多个工具。每个工具是一个目录，放在 `src/tools/` 下面。你可以浏览一下：

```bash
ls src/tools/
```

你会看到 `FileReadTool/`、`BashTool/`、`FileEditTool/` 等等。每个目录里都有该工具的全部代码。

我们要改的是 `FileReadTool`——它负责读取文件，是 AI 最常用的工具之一。

打开 `src/tools/FileReadTool/`，看看里面有什么：

```bash
ls src/tools/FileReadTool/
```

你会看到四个文件：

- `FileReadTool.ts` —— 主文件，定义工具的行为
- `prompt.ts` —— prompt 模板，定义 AI 看到的工具说明
- `UI.tsx` —— UI 渲染，定义用户看到的界面
- `imageProcessor.ts` —— 图片处理辅助
- `limits.ts` —— 文件大小限制配置

我们要改的就是 `prompt.ts`。

### 第二步：读懂结构

打开 `src/tools/FileReadTool/prompt.ts`。这个文件不长，但结构清晰。你会看到：

```typescript
export const FILE_READ_TOOL_NAME = 'Read'

export const DESCRIPTION = 'Read a file from the local filesystem.'

export const MAX_LINES_TO_READ = 2000

export const LINE_FORMAT_INSTRUCTION =
  '- Results are returned using cat -n format, with line numbers starting at 1'
```

这里有三个关键概念：

**`DESCRIPTION`** —— 工具的一句话描述。这个值会被送到 AI 那里，作为工具列表中每个工具的简介。当你输入一条消息后，AI 在决定使用哪个工具时，首先看到的就是这段文字。

**`renderPromptTemplate()`** —— 工具的详细说明模板。当 AI 决定使用 Read 工具时，这段文字会被完整注入到上下文中，告诉 AI 怎么正确使用这个工具。

**常量指令片段** —— `LINE_FORMAT_INSTRUCTION`、`OFFSET_INSTRUCTION_DEFAULT` 等，是详细说明中的可配置段落，可以根据运行时条件组合出不同的 prompt。

这种"常量 + 函数模板"的模式在 Claude Code 的工具系统中很常见。它把 prompt 拆成小块，方便单独修改和测试。

### 第三步：做出修改

我们要改的是 `DESCRIPTION` 常量——那句话的简介。把它改成更有个性一点的文字。

找到这一行（大约在第 12 行）：

```typescript
export const DESCRIPTION = 'Read a file from the local filesystem.'
```

把它改成：

```typescript
export const DESCRIPTION = 'Read a file from the local filesystem. Your trusty companion for exploring code.'
```

就是加了一句俏皮话。这不会影响工具的功能，但能让你在验证时一眼确认修改生效了。

保存文件。

### 第四步：理解修改怎么生效

你改了一行字符串常量。那这行常量是怎么跑到 AI 那里的？

打开 `src/tools/FileReadTool/FileReadTool.ts`，找到工具注册的部分（大约在第 337 行）：

```typescript
export const FileReadTool = buildTool({
  name: FILE_READ_TOOL_NAME,
  // ...
  async description() {
    return DESCRIPTION
  },
  async prompt() {
    const limits = getDefaultFileReadingLimits()
    // ...
    return renderPromptTemplate(
      pickLineFormatInstruction(),
      maxSizeInstruction,
      offsetInstruction,
    )
  },
  // ...
})
```

看到了吗？`description()` 方法返回的就是你刚才改的 `DESCRIPTION` 常量。而 `buildTool()` 函数（定义在 `src/Tool.ts` 里）把这个方法注册到工具对象上。

当 Claude Code 启动时，它会收集所有工具的 `description()`，打包进发给 AI 的系统消息里。AI 在决定"该用哪个工具"时，看到的就是这些描述文字。

数据流是这样的：

```
DESCRIPTION 常量
  → FileReadTool 的 description() 方法
    → buildTool() 注册到工具对象
      → 启动时收集所有工具描述
        → 发送给 AI 的系统消息
          → AI 读到你的修改
```

一行修改，经过了四五层传递，最终到达 AI 的"眼前"。这就是工具 prompt 的生命周期。

### 第五步：构建并测试

现在你需要构建项目。Claude Code 使用 Bun 作为运行时和构建工具。在项目根目录下运行：

```bash
bun run build
```

如果没有 build 脚本（这个项目可能直接用 Bun 运行 TypeScript），试试直接启动：

```bash
bun run dev
```

或者：

```bash
bun run start
```

具体命令取决于你的环境配置。如果上一章你已经成功启动过 Claude Code，用同样的方式启动就行。

启动后，随便找一个文件让 AI 去读。比如你可以说：

```
请帮我读一下 package.json 的前 10 行
```

AI 会使用 Read 工具。此时它内部看到的就是你修改后的描述。

但你怎么确认 AI 真的看到了你的修改呢？因为 description 是 AI 端的"内心独白"，不会直接显示在你的终端里。

### 第六步：验证修改生效

有几种方法可以验证：

**方法一：看日志。** 如果你开启了 debug 模式（通常通过环境变量 `DEBUG=1` 或类似的标志），系统消息会被打印出来，你可以在其中搜索 "Your trusty companion"。

**方法二：加一行 console.log。** 在 `FileReadTool.ts` 的 `description()` 方法里加一行：

```typescript
async description() {
  console.log('[MY_CHANGE] FileReadTool description:', DESCRIPTION)
  return DESCRIPTION
},
```

当你让 AI 读文件时，如果这行日志出现在终端里，说明你的修改路径是通的。

**方法三：让 AI "看到"自己的工具描述。** 你可以对 AI 说：

```
请告诉我你有哪些工具可用，特别是 Read 工具的描述是什么？
```

AI 有时能回溯自己的系统提示并告诉你它看到的工具描述。不过这种方法不太可靠，因为 AI 不一定会原样复述。

推荐使用方法二——加 `console.log` 最直接、最确定。

### 第七步：你的第一个 commit

验证成功了？现在把它提交到 git。这是你的第一个贡献。

先看看改了什么：

```bash
git diff
```

你应该看到类似这样的输出：

```diff
- export const DESCRIPTION = 'Read a file from the local filesystem.'
+ export const DESCRIPTION = 'Read a file from the local filesystem. Your trusty companion for exploring code.'
```

如果日志验证代码也加了，你可以选择保留它（作为学习痕迹），也可以先还原掉（保持代码干净）。

提交：

```bash
git add src/tools/FileReadTool/prompt.ts
git commit -m "chore: customize FileReadTool description for learning"
```

恭喜，这是你在 Claude Code 源码上的第一个 commit。

## 遇到问题？

### 构建报错了

如果你看到 TypeScript 类型错误，先确认修改没有引入语法问题。你改的只是一个字符串常量，不应该触发类型检查。如果类型错误来自其他地方，可能是你的环境配置问题，回顾上一章的搭建步骤。

### 找不到 bun 命令

确认 Bun 已安装：

```bash
bun --version
```

如果没装，去 [bun.sh](https://bun.sh) 安装。

### 构建缓存问题

有时修改了文件但构建产物没有更新。可以清理后重新构建：

```bash
rm -rf dist/
bun run build
```

或者如果你用的是开发模式（直接运行 TypeScript），缓存通常不是问题。

### console.log 没有输出

Claude Code 的日志可能被重定向或过滤了。检查：

1. 你是不是在正确的位置加了日志？（应该在 `description()` 方法内部）
2. 你是不是真的触发了 Read 工具？（让 AI 读一个文件试试）
3. 日志是否被重定向到文件？查看项目根目录下是否有日志文件。

### 改了但看不到效果

记住：`description` 是给 AI 看的，不是给你看的。你不会在终端界面上直接看到工具描述的变化。用上面提到的验证方法来确认。

如果你改的是 `renderPromptTemplate()` 里的详细说明，效果会更明显——因为那段文字会直接影响 AI 的行为。但作为第一次修改，改 `DESCRIPTION` 已经足够了。

## 验证

完成这一章后，你应该能回答这些问题：

1. **FileReadTool 的 prompt 定义在哪个文件？** —— `src/tools/FileReadTool/prompt.ts`

2. **`DESCRIPTION` 常量和 `renderPromptTemplate()` 函数各起什么作用？** —— `DESCRIPTION` 是工具的一句话简介，出现在工具列表中。`renderPromptTemplate()` 是详细的使用说明，当 AI 决定使用这个工具时才注入。

3. **工具的 description 是怎么到达 AI 的？** —— `buildTool()` 注册工具时收集 description 方法，启动时所有工具描述被写入系统消息。

4. **你的修改确实生效了吗？** —— 如果 console.log 输出了你修改后的字符串，说明生效了。

如果你能回答这四个问题，说明你真正理解了工具 prompt 的结构和数据流。这比改了多少代码都重要。
