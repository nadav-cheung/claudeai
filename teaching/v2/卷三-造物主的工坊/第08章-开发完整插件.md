# 第08章：开发完整插件

前面几章，我们学了工具的输入验证、权限规则、MCP 服务器接入和多 Agent 协作。这些是"零件"。现在，是时候把这些零件组装成一个完整的产品了。

Claude Code 的插件系统是零件的容器。一个插件可以包含：

- **Skills（技能）**——可被 AI 调用的命令
- **Agents（代理）**——特定类型的工作单元
- **Hooks（钩子）**——在特定事件发生时执行的脚本
- **MCP Servers**——外部工具服务器
- **Commands（命令）**——用户可用的斜杠命令

这一章，我们从零开始开发一个完整的插件，覆盖从目录结构到验证分发的全流程。

---

## 目标

完成这一章后，你将能够：

1. 理解插件的目录结构和 `plugin.json` manifest
2. 创建包含 skills、hooks 和 MCP 服务器的完整插件
3. 理解插件的加载和生命周期管理
4. 使用 `claude plugin validate` 验证插件质量
5. 理解插件的分发机制（marketplace）

## 动手

### 第一步：创建插件目录结构

一个标准的插件目录看起来像这样：

```
my-plugin/
├── .claude-plugin/
│   └── plugin.json          # 插件 manifest
├── skills/                   # 技能定义
│   └── my-skill/
│       └── SKILL.md          # 技能的 Markdown 文件
├── agents/                   # Agent 定义
│   └── my-agent.md           # Agent 的 Markdown 文件
├── commands/                 # 斜杠命令
│   └── my-command.md         # 命令的 Markdown 文件
└── hooks/
    └── hooks.json            # 钩子配置
```

注意几个关键点：

- `plugin.json` 必须放在 `.claude-plugin/` 目录下——这是插件系统查找 manifest 的标准位置
- Skills 必须是 `skills/<name>/SKILL.md` 的格式——每个技能是一个目录，目录下有 `SKILL.md` 文件
- Agents 和 Commands 是平铺的 `.md` 文件——不需要子目录

### 第二步：编写 plugin.json manifest

`plugin.json` 是插件的身份证。它告诉 Claude Code 这个插件叫什么、做什么、包含什么组件：

```json
{
  "name": "my-db-tools",
  "version": "1.0.0",
  "description": "Database query and management tools for Claude Code",
  "author": {
    "name": "Your Name",
    "email": "you@example.com"
  },
  "skills": ["skills/query-database", "skills/migrate-schema"],
  "agents": ["agents/db-inspector"],
  "hooks": {
    "hooks": "hooks/hooks.json"
  }
}
```

源码中，manifest 的 schema 定义在 `src/utils/plugins/schemas.ts` 中。它由多个子 schema 组合而成：

```typescript
// 文件：src/utils/plugins/schemas.ts
export const PluginManifestSchema = lazySchema(() =>
  z.object({
    ...PluginManifestMetadataSchema().shape,    // name, version, description, author
    ...PluginManifestHooksSchema().partial().shape,    // hooks 路径
    ...PluginManifestCommandsSchema().partial().shape, // commands 路径
    ...PluginManifestAgentsSchema().partial().shape,   // agents 路径
    ...PluginManifestSkillsSchema().partial().shape,   // skills 路径
    ...PluginManifestMcpServerSchema().partial().shape, // MCP 服务器配置
    ...PluginManifestSettingsSchema().partial().shape,  // 插件设置
  }),
)
```

每个子 schema 都是 `.partial()` 的——意味着 manifest 中所有的组件都是可选的。一个插件可以只提供 skills，也可以同时提供 skills、agents、hooks 和 MCP 服务器。

**name 字段的命名规则**：推荐使用 kebab-case（小写字母、数字、连字符），比如 `my-db-tools`。虽然 Claude Code 接受其他格式，但 Claude.ai 的 marketplace 同步要求 kebab-case。

### 第三步：创建 Skill

Skill 是 AI 可以调用的能力，定义在 Markdown 文件中。每个 Skill 由 YAML frontmatter（元数据）和 Markdown 正文（提示词）组成。

创建 `skills/query-database/SKILL.md`：

```markdown
---
description: "Execute a SQL query against the configured database and return results"
allowed-tools:
  - Bash
  - Read
---

You are a database query expert. When the user asks you to query data:

1. Analyze the user's request to determine what data they need
2. Construct a safe SQL query (only SELECT statements)
3. Use the Bash tool to execute: `psql $DATABASE_URL -c "<query>" -t -A`
4. Format the results in a readable table
5. If the query fails, explain the error and suggest a fix

Important rules:
- NEVER execute DROP, DELETE, or TRUNCATE statements
- Always use parameterized queries when possible
- Limit results to 100 rows unless the user specifies otherwise
```

frontmatter 中的字段：

- **`description`**——告诉 AI 什么时候应该使用这个 skill。好的描述是简短且具体的
- **`allowed-tools`**——这个 skill 可以使用哪些工具。限制工具范围可以防止 AI 做出超出 skill 范围的事情

Markdown 正文是给 AI 的系统提示词——当 skill 被调用时，这段文字会被注入到 AI 的上下文中。

#### Skill 的四大来源

Claude Code 的 skill 有四种来源，每种有不同的加载方式和适用场景：

| 来源 | 加载方式 | 典型场景 |
|------|----------|----------|
| **Bundled（内建）** | 编译时打包进 Claude Code 二进制 | 核心命令如 `/help`、`/init` |
| **skills/ 目录** | 扫描用户项目或全局配置的 `skills/` 目录 | 项目级自定义提示词 |
| **MCP（远程）** | 通过 MCP 服务器动态注册 | 第三方工具提供的命令 |
| **Plugin（插件）** | 从插件的 `skills/` 目录加载 | 插件分发的可复用技能 |

这四种来源统一由 skill 注册系统管理。加载顺序是 bundled > skills/ > MCP > plugin，同名 skill 后加载的不会覆盖先加载的——也就是说，内建 skill 拥有最高优先级。

### 第四步：创建 Agent

Agent 是更重量级的组件，它有独立的对话上下文和工具集。创建 `agents/db-inspector.md`：

```markdown
---
description: "Inspect database schema, indexes, and performance"
tools:
  - Bash
  - Read
  - Grep
max_turns: 15
---

You are a database inspector agent. Your job is to analyze database schema and performance.

Available commands:
- `psql $DATABASE_URL -c "\dt"` — list all tables
- `psql $DATABASE_URL -c "\d table_name"` — describe a table
- `psql $DATABASE_URL -c "\di"` — list all indexes

When asked to inspect a database:
1. Start by listing all tables
2. Describe the relevant tables
3. Check indexes on frequently queried columns
4. Report findings in a structured format

Keep your analysis under 500 words.
```

Agent 的 frontmatter 字段和我们在上一章看到的 `AgentDefinition` 是对应的：

- **`tools`**——Agent 可以使用的工具列表
- **`max_turns`**——最大对话轮数
- **`description`**——什么时候使用这个 Agent

### 第五步：创建 Hook

Hooks 是在特定事件发生时自动执行的脚本。创建 `hooks/hooks.json`：

```json
{
  "PreToolUse": [
    {
      "matcher": "Bash",
      "hooks": [
        {
          "type": "command",
          "command": "python3 validate_sql.py"
        }
      ]
    }
  ],
  "PostToolUse": [
    {
      "matcher": "Bash",
      "hooks": [
        {
          "type": "command",
          "command": "python3 log_query.py"
        }
      ]
    }
  ]
}
```

这个 hooks 配置做了两件事：

- **PreToolUse**——在每次调用 Bash 工具之前，运行 `validate_sql.py` 验证命令安全性
- **PostToolUse**——在每次调用 Bash 工具之后，运行 `log_query.py` 记录操作日志

Hooks 的 matcher 支持通配符。比如 `"matcher": "Bash(psql *)"` 只匹配以 `psql` 开头的 Bash 命令。

#### HookCommand 的四种类型

每个 hook 条目通过 `type` 字段指定执行方式，Claude Code 支持四种 HookCommand 类型：

| 类型 | 说明 | 关键字段 | 适用场景 |
|------|------|----------|----------|
| **`command`** | 执行 Shell 命令 | `command`, `shell`, `timeout` | 运行脚本、调用 CLI 工具 |
| **`prompt`** | 注入一段 AI 提示词 | `prompt`, `model`, `timeout` | 修改 AI 行为，注入上下文 |
| **`agent`** | 启动一个子 Agent | `agent` | 需要独立工具集的复杂处理 |
| **`http`** | 发送 HTTP 请求 | `url`, `headers`, `timeout` | 调用远程 API、通知外部系统 |

示例——四种类型的完整配置：

```json
{
  "PreToolUse": [
    {
      "matcher": "Bash",
      "hooks": [
        { "type": "command", "command": "python3 validate.py" },
        { "type": "prompt", "prompt": "Always confirm before running destructive commands" },
        { "type": "agent", "agent": "security-reviewer" },
        { "type": "http", "url": "https://audit.example.com/check", "headers": { "Authorization": "Bearer $TOKEN" } }
      ]
    }
  ]
}
```

`command` 类型最常用——它直接执行 Shell 命令，适合做前置检查和后置处理。`prompt` 类型不执行代码，而是在 AI 上下文中注入额外指令，用于引导 AI 行为。`agent` 类型最重，会启动一个完整的子 Agent。`http` 类型适合和外部系统集成。

#### inline 与 fork 执行模式

`command` 类型的 hook 有两种执行模式，决定了它和主进程的关系：

| 模式 | 工作方式 | 性能影响 | 失败影响 |
|------|----------|----------|----------|
| **inline** | 在主进程中同步执行 | 阻塞当前操作，等待完成 | 失败直接返回错误 |
| **fork** | fork 子进程执行 | 不阻塞主进程 | 失败只记录日志 |

inline 模式适合必须等待结果才能继续的场景——比如 PreToolUse 的安全检查。fork 模式适合"发后即忘"的操作——比如 PostToolUse 的日志记录和通知。

选择原则：**需要结果 → inline，只需执行 → fork**。

#### HookEvent 完整列表

前面我们只用了 `PreToolUse` 和 `PostToolUse` 两个事件。实际上 Claude Code 定义了 28 种 HookEvent，覆盖了会话、工具、权限、协作等各个阶段：

**工具相关事件：**

| 事件 | 触发时机 |
|------|----------|
| `PreToolUse` | 工具执行前 |
| `PostToolUse` | 工具执行成功后 |
| `PostToolUseFailure` | 工具执行失败后 |

**权限相关事件：**

| 事件 | 触发时机 |
|------|----------|
| `PermissionDenied` | 权限被拒绝时 |
| `PermissionRequest` | 请求权限时 |

**会话相关事件：**

| 事件 | 触发时机 |
|------|----------|
| `SessionStart` | 会话开始 |
| `SessionEnd` | 会话结束 |
| `Stop` | 会话正常停止 |
| `StopFailure` | 会话因错误停止 |

**子 Agent 事件：**

| 事件 | 触发时机 |
|------|----------|
| `SubagentStart` | 子 Agent 启动时 |
| `SubagentStop` | 子 Agent 停止时 |

**压缩相关事件：**

| 事件 | 触发时机 |
|------|----------|
| `PreCompact` | 上下文压缩前 |
| `PostCompact` | 上下文压缩后 |

**协作相关事件：**

| 事件 | 触发时机 |
|------|----------|
| `TeammateIdle` | 协作队友空闲时 |
| `TaskCreated` | 任务创建时 |
| `TaskCompleted` | 任务完成时 |

**交互相关事件：**

| 事件 | 触发时机 |
|------|----------|
| `Elicitation` | AI 请求用户输入时 |
| `ElicitationResult` | 用户输入返回时 |
| `UserPromptSubmit` | 用户提交提示词时 |

**环境和配置事件：**

| 事件 | 触发时机 |
|------|----------|
| `ConfigChange` | 配置变更时 |
| `WorktreeCreate` | 创建工作树时 |
| `WorktreeRemove` | 移除工作树时 |
| `InstructionsLoaded` | 指令加载完成时 |
| `CwdChanged` | 工作目录变更时 |
| `FileChanged` | 文件内容变更时 |
| `Notification` | 系统通知时 |

这些事件在 `src/schemas/hooks.ts` 中通过 `HookEvent` 类型定义。插件开发者可以根据需要选择监听哪些事件——绝大多数插件只需要 `PreToolUse` 和 `PostToolUse`，但高级场景（比如监听会话生命周期、跟踪子 Agent 状态）可以使用其他事件。

插件 hooks 的加载逻辑在 `src/utils/plugins/loadPluginHooks.ts` 中：

```typescript
// 文件：src/utils/plugins/loadPluginHooks.ts
export const loadPluginHooks = memoize(async (): Promise<void> => {
  const { enabled } = await loadAllPluginsCacheOnly()
  const allPluginHooks = { PreToolUse: [], PostToolUse: [], ... }

  for (const plugin of enabled) {
    if (!plugin.hooksConfig) continue
    const pluginMatchers = convertPluginHooksToMatchers(plugin)
    // 合并到全局 hooks 集合
    for (const event of Object.keys(pluginMatchers)) {
      allPluginHooks[event].push(...pluginMatchers[event])
    }
  }

  clearRegisteredPluginHooks()
  registerHookCallbacks(allPluginHooks)
})
```

每个插件的 hooks 会被转换成 `PluginHookMatcher`，带上 `pluginRoot` 和 `pluginName` 信息，这样在执行时可以正确定位脚本路径。

### 第六步：定义 MCP 服务器

插件还可以自带 MCP 服务器。在 `plugin.json` 中添加：

```json
{
  "name": "my-db-tools",
  "version": "1.0.0",
  "description": "Database tools plugin",
  "mcpServers": {
    "db-query": {
      "command": "node",
      "args": ["./mcp-servers/db-query-server.js"],
      "env": {
        "DATABASE_URL": "${DATABASE_URL}"
      }
    }
  }
}
```

插件 MCP 服务器的名字会被加上 `plugin:` 前缀。比如上面的 `db-query` 会变成 `plugin:my-db-tools:db-query`。这个前缀确保不同插件的服务器不会名字冲突。

插件 MCP 服务器还有去重机制——如果插件提供的服务器和用户手动配置的服务器实际上是同一个（相同的命令或 URL），插件版本会被抑制：

```typescript
// 文件：src/services/mcp/config.ts
export function dedupPluginMcpServers(pluginServers, manualServers) {
  const manualSigs = new Map()  // 签名 → 名字
  for (const [name, config] of Object.entries(manualServers)) {
    const sig = getMcpServerSignature(config)
    if (sig) manualSigs.set(sig, name)
  }

  const servers = {}
  for (const [name, config] of Object.entries(pluginServers)) {
    const sig = getMcpServerSignature(config)
    if (manualSigs.has(sig)) continue  // 手动配置优先
    servers[name] = config
  }
  return { servers }
}
```

**手动配置总是优先于插件配置。** 这是一个重要的设计原则——用户知道自己要什么。

### 第七步：理解插件的生命周期

一个插件从创建到运行，经历以下阶段：

**加载（Loading）。** `loadAllPluginsCacheOnly()` 读取所有启用插件的 manifest，验证结构，收集组件路径：

```typescript
// 文件：src/utils/plugins/pluginLoader.ts
export const loadAllPluginsCacheOnly = memoize(async (): Promise<PluginLoadResult> => {
  const result: PluginLoadResult = { enabled: [], disabled: [], errors: [] }
  // 加载 marketplace 插件
  // 加载内建插件
  // 加载 session 插件
  // 验证每个插件的 manifest
  // 返回 { enabled, disabled, errors }
})
```

**注册（Registration）。** 加载后，每个组件被注册到对应的系统：

- Skills 注册到命令系统
- Agents 注册到 AgentTool 的可用列表
- Hooks 注册到 hook 执行器
- MCP 服务器注册到连接管理器

**运行（Runtime）。** 注册完成后，插件就在后台工作了。AI 可以调用它的 skills，系统会执行它的 hooks，MCP 服务器提供额外的工具。

**热重载（Hot Reload）。** 当远程策略设置变更时，插件系统会检测到变化并重新加载：

```typescript
// 文件：src/utils/plugins/loadPluginHooks.ts
export function setupPluginHookHotReload(): void {
  settingsChangeDetector.subscribe(source => {
    if (source === 'policySettings') {
      const newSnapshot = getPluginAffectingSettingsSnapshot()
      if (newSnapshot === lastPluginSettingsSnapshot) return
      // 清除缓存，重新加载
      clearPluginCache(...)
      clearPluginHookCache()
      void loadPluginHooks()
    }
  })
}
```

### 第八步：验证插件

Claude Code 提供了内置的验证工具。在插件目录下运行：

```bash
claude plugin validate .
```

验证器会检查：

1. **JSON 语法**——`plugin.json` 是否是合法的 JSON
2. **Schema 合规**——是否符合 `PluginManifestSchema` 的要求
3. **路径安全**——组件路径是否包含 `..`（路径穿越攻击）
4. **命名规范**——`name` 是否是 kebab-case
5. **组件完整性**——引用的 skill/agent/command 文件是否存在
6. **hooks 格式**——`hooks.json` 是否符合 `PluginHooksSchema`

验证逻辑在 `src/utils/plugins/validatePlugin.ts` 中。它会针对每个组件文件检查 YAML frontmatter 的格式、`description` 字段是否存在、`allowed-tools` 是否是合法的工具名等等。

一个通过验证的插件应该零错误。如果验证器报告了警告（比如缺少 `description`），你可以决定是否修复——警告不会阻止加载，但会影响用户体验。

### 第九步：分发插件——Marketplace

插件通过 marketplace 分发。一个 marketplace 是一个 Git 仓库，包含一个 `marketplace.json` 文件，里面列出所有可用的插件：

```json
{
  "metadata": {
    "name": "my-marketplace",
    "description": "My collection of Claude Code plugins"
  },
  "plugins": [
    {
      "name": "my-db-tools",
      "source": "./plugins/my-db-tools",
      "version": "1.0.0",
      "description": "Database query and management tools"
    }
  ]
}
```

marketplace 文件必须放在仓库的 `.claude-plugin/` 目录下。

用户通过以下命令安装 marketplace 中的插件：

```bash
claude plugin add my-db-tools@my-marketplace
```

插件系统会：

1. 克隆或拉取 marketplace 仓库
2. 找到插件的源代码目录
3. 验证 manifest
4. 安装到本地缓存
5. 注册到用户的 `enabledPlugins` 设置中

让我们把所有组件打包成一个完整的插件。最终目录结构：

```
db-assistant/
├── .claude-plugin/
│   └── plugin.json
├── skills/
│   ├── query-database/
│   │   └── SKILL.md
│   └── migrate-schema/
│       └── SKILL.md
├── agents/
│   └── db-inspector.md
├── hooks/
│   └── hooks.json
└── mcp-servers/
    └── db-query-server.js
```

`plugin.json`：

```json
{
  "name": "db-assistant",
  "version": "1.0.0",
  "description": "Database assistant with query, inspection, and migration capabilities",
  "author": {
    "name": "Database Team"
  },
  "skills": ["skills/query-database", "skills/migrate-schema"],
  "agents": ["agents/db-inspector"],
  "hooks": "hooks/hooks.json"

```

这个插件提供了：

- 两个 skill：`query-database`（查询数据库）和 `migrate-schema`（执行迁移）
- 一个 agent：`db-inspector`（检查数据库结构）
- 一组 hooks：PreToolUse 验证 SQL 安全性，PostToolUse 记录查询日志

## 遇到问题？

### 问题 1：插件加载后 skills 不显示

**症状**：插件安装成功了，但 AI 看不到你的 skills。

**原因**：skills 的目录结构不对。Claude Code 要求每个 skill 必须是 `skills/<name>/SKILL.md` 格式——子目录下必须有 `SKILL.md` 文件。单独的 `.md` 文件（如 `skills/my-skill.md`）不会被加载。

**解决方案**：把 `skills/my-skill.md` 改为 `skills/my-skill/SKILL.md`。

### 问题 2：hooks.json 解析失败导致整个插件无法加载

**症状**：插件安装后完全不工作，日志显示 hooks.json 解析错误。

**原因**：`hooks.json` 使用的是 `.parse()`（不是 `.safeParse()`）进行验证。如果格式不正确，整个插件加载会失败。

**解决方案**：运行 `claude plugin validate .` 检查 hooks.json 的格式。确保每个 hook 都有 `type` 和 `command`（或 `type: "command"`），matcher 是合法的工具名。

### 问题 3：插件 MCP 服务器和手动配置冲突

**症状**：插件定义了一个 MCP 服务器，但它没有被连接。

**原因**：去重机制检测到用户已经手动配置了相同的服务器（相同的命令或 URL），插件版本被抑制了。

**解决方案**：这是预期行为——手动配置优先。如果你想使用插件版本，需要移除手动配置中的重复服务器。你可以用 `/mcp` 命令查看哪个版本生效了。

### 问题 4：插件在企业环境下被阻止

**症状**：安装插件时报策略错误。

**原因**：企业管理员可能配置了 `strictKnownMarketplaces`（只允许特定 marketplace）或 `blockedMarketplaces`（阻止特定 marketplace）。你的 marketplace 可能不在白名单中。

**解决方案**：联系管理员，把你的 marketplace 添加到允许列表中。

## 验证

让我们通过一个完整的流程来验证你的插件。

**测试 1：结构验证。** 创建插件目录，放入 `plugin.json`。运行 `claude plugin validate .`。输出应该显示零错误。

**测试 2：加载验证。** 用 `--plugin-dir ./db-assistant` 启动 Claude Code，或者把插件安装到 marketplace 中。用 `/plugins` 命令确认插件已加载。

**测试 3：Skill 验证。** 在对话中提及数据库查询。AI 应该能够识别并使用你的 `query-database` skill。

**测试 4：Hook 验证。** 让 AI 执行一个 Bash 命令（比如查询数据库）。PreToolUse hook 应该被触发，验证命令安全性。

**测试 5：Agent 验证。** 让 AI 启动 `db-inspector` Agent。Agent 应该能独立工作，检查数据库结构并返回报告。

如果这五个测试都通过了，你的插件就完整可用了。

## 插件设计四原则

在开发插件时，有四个工程原则值得牢记：

| 原则 | 说明 | 实践方式 |
|------|------|----------|
| **单一职责** | 每个插件只做一件事 | Git 插件专注 Git 操作，不要混入数据库功能 |
| **幂等性** | 多次安装结果一致 | 用 `settings.json` 记录状态，不依赖文件系统快照 |
| **错误隔离** | 插件崩溃不影响主程序 | 所有 hook 执行用 try/catch 包装，异常只记录不传播 |
| **版本兼容** | 考虑主程序版本升级 | 在 `plugin.json` 中指定兼容版本范围，安装时校验 |

单一职责让插件易于理解和维护。幂等性确保插件可以安全地重复安装和更新。错误隔离是稳定性保障——一个插件的 hook 脚本报错不应该导致 Claude Code 主进程崩溃。版本兼容是对未来的投资——Claude Code 还在快速迭代，今天能用的 API 明天可能改变。

**错误隔离的具体实现**：源码中，插件 hook 的执行都经过 `try/catch` 包装。如果 hook 脚本抛出异常，系统会捕获错误、记录日志，然后继续执行下一个 hook 或返回工具调用结果。这就是为什么前面提到的 `hooks.json` 解析失败会导致"整个插件无法加载"——因为解析发生在 try/catch 之外。修复方法是使用 `.safeParse()` 替代 `.parse()`，让解析错误也进入错误隔离层。

## 回顾

这一章，我们从头到尾开发了一个完整的 Claude Code 插件：

1. **目录结构**——`.claude-plugin/plugin.json` 是 manifest，`skills/`、`agents/`、`commands/`、`hooks/` 是组件
2. **plugin.json**——插件的身份证，声明包含哪些组件
3. **Skills**——Markdown 文件，frontmatter 是元数据，正文是 AI 提示词
4. **Agents**——独立的对话实体，有工具集和轮数限制
5. **Hooks**——事件驱动的自动化脚本，支持 PreToolUse、PostToolUse 等多种事件
6. **MCP Servers**——插件自带的外部工具服务器，自动去重
7. **生命周期**——加载 → 注册 → 运行 → 热重载
8. **验证**——`claude plugin validate` 检查插件的完整性和安全性
9. **分发**——通过 marketplace 仓库分发插件

插件系统的设计哲学是**组合优于继承**。每个插件是一个独立的模块，可以只包含一个 skill，也可以同时包含 skills、agents、hooks 和 MCP 服务器。这种灵活性让你可以从小处着手，逐步扩展。
