# 第09章：编写测试

上一章，你完成了一个完整的插件。功能跑通了，验证也通过了。但有一个问题始终悬在头上：**你怎么知道它下次修改后还能跑通？**

人类验证是好的——但人类会忘记、会偷懒、会在改了 A 之后忘了测 B。测试不会。好的测试是你留在代码里的保险：每次改动之后，它们自动跑一遍，替你确认一切还在正常工作。

这一章，我们讨论如何在 Claude Code 的代码库里编写测试。

---

完成这一章后，你将能够：

1. 理解 Claude Code 项目中的测试策略和工具选择
2. 为工具的 Zod schema 编写验证测试

4. 掌握模拟（mock）外部依赖的策略
5. 理解端到端测试模式——`TestingPermissionTool` 的启示

## 动手

### 第一步：认识项目的测试现状

先说一个事实：从 npm 包提取出来的源码里，**没有独立的测试文件**。

这听起来可能让人意外。但想一想就明白了——这个仓库不是 Anthropic 的内部 monorepo，而是从打包后的 `cli.js.map` 的 `sourcesContent` 里提取出来的。打包过程只包含运行时源码，不包含测试文件、测试配置、CI 脚本这些开发基础设施。

但你仍然能在源码中找到**测试的痕迹**：

**`TestingPermissionTool`**——`src/tools/testing/TestingPermissionTool.tsx` 是一个专门的测试工具：

```typescript
// 文件：src/tools/testing/TestingPermissionTool.tsx
export const TestingPermissionTool: Tool<InputSchema, string> = buildTool({
  name: 'TestingPermission',
  // ...
  isEnabled() {
    return "production" === 'test';  // 只有测试环境才启用
  },
  async checkPermissions() {
    return {
      behavior: 'ask' as const,
      message: 'Run test?'
    };
  },
  async call() {
    return { data: 'TestingPermission executed successfully' };
  },
})
```

注意 `isEnabled()` 的实现——`"production" === 'test'`。这串代码在正常构建里永远是 `false`（因为 `"production"` 不等于 `"test"`）。但在测试构建中，Bun 的 `feature()` 或构建替换会把 `"production"` 替换成 `"test"`，让这个工具启用。

这是一个经典的模式：**在生产代码中嵌入测试入口，通过构建时变量控制启用**。

**`setup.ts` 中的测试分支**：

```typescript
// 文件：src/setup.ts
if (process.env.NODE_ENV === 'test') {
  // 测试环境下的特殊行为
}
```

**`debug.ts` 中的测试过滤**：

```typescript
// 文件：src/utils/debug.ts
if (process.env.NODE_ENV === 'test' && !isDebugToStderr()) {
  return false;  // 测试时不写 debug 日志（除非显式要求）
}
```

这些痕迹告诉我们：项目内部确实有一套测试体系，只是它没有被打包进发布产物。

### 第二步：选择测试框架

既然源码里没有测试配置，我们需要自己选择。对于 TypeScript 项目，2026 年的主流选择有三个：

**Vitest**——与 Vite 生态无缝集成，原生支持 TypeScript，配置简单，速度极快。它的 API 和 Jest 几乎一样（`describe`、`it`、`expect`），迁移成本接近零。

**Jest**——最成熟的测试框架，生态最丰富，社区资源最多。但对 ESM 支持仍然偶尔有问题，配置相对繁琐。

**Bun 内置测试**——`bun test` 命令内置，零配置，速度最快。API 兼容 Jest。如果你用 Bun 运行项目（Claude Code 就是），这是最自然的选择。

我们的推荐：**Vitest** 或 **Bun test**。两者 API 几乎一样，选哪个取决于你更习惯哪个生态。下面的代码示例使用 Vitest 的 API，但换成 Bun test 只需要改 import。

### 第三步：安装和配置

在你的源码根目录下初始化测试环境：

```bash
# 安装 Vitest
npm install -D vitest
```

创建 `vitest.config.ts`：

```typescript
import { defineConfig } from 'vitest/config'

export default defineConfig({
  test: {
    // 测试文件位置
    include: ['src/**/*.test.ts'],
    // TypeScript 支持
    typecheck: {
      enabled: true,
    },
  },
})
```

在 `package.json` 里加上测试脚本：

```json
{
  "scripts": {
    "test": "vitest run",
    "test:watch": "vitest"
  }
}
```

### 第四步：测试 Zod Schema

你最应该测试的东西之一是**输入验证**。回忆一下：工具的 `inputSchema` 是 AI 和你的工具之间的契约。AI 传过来的 JSON 可能不符合预期——你的 schema 必须正确地接受合法输入、拒绝非法输入。

还记得第 03 章创建的 `TimestampTool` 吗？让我们为它的 schema 写测试。

创建 `src/tools/TimestampTool/TimestampTool.test.ts`：

```typescript
import { describe, it, expect } from 'vitest'
import { z } from 'zod/v4'

// 从工具模块导出 schema 用于测试
// 这里直接内联 schema 定义来演示
const inputSchema = z.strictObject({
  format: z
    .enum(['iso', 'unix', 'locale'])
    .optional()
    .describe('Output format'),
})

describe('TimestampTool inputSchema', () => {
  it('接受无参数调用', () => {
    const result = inputSchema.safeParse({})
    expect(result.success).toBe(true)
  })

  it('接受 iso 格式', () => {
    const result = inputSchema.safeParse({ format: 'iso' })
    expect(result.success).toBe(true)
    if (result.success) {
      expect(result.data.format).toBe('iso')
    }
  })

  it('接受 unix 格式', () => {
    const result = inputSchema.safeParse({ format: 'unix' })
    expect(result.success).toBe(true)
  })

  it('接受 locale 格式', () => {
    const result = inputSchema.safeParse({ format: 'locale' })
    expect(result.success).toBe(true)
  })

  it('拒绝非法格式', () => {
    const result = inputSchema.safeParse({ format: 'rfc2822' })
    expect(result.success).toBe(false)
  })

  it('拒绝额外字段（strictObject）', () => {
    const result = inputSchema.safeParse({ format: 'iso', extra: 'nope' })
    expect(result.success).toBe(false)
  })

  it('拒绝错误的类型', () => {
    const result = inputSchema.safeParse({ format: 123 })
    expect(result.success).toBe(false)
  })
})
```

运行测试：

```bash
npx vitest run src/tools/TimestampTool/TimestampTool.test.ts
```

你会看到所有测试通过。这个测试文件覆盖了 schema 的所有分支：合法值（三种格式）、缺失参数、非法值、额外字段、错误类型。

**为什么要测 schema？** 因为 schema 是你的工具和 AI 之间的接口。一个有漏洞的 schema（比如忘了 `strictObject`）会让 AI 传入你没想到的字段，引发下游 bug。测试确保你的防线是完整的。

### 第五步：测试 call() 逻辑

工具的核心是 `call()` 方法。测试它时，你需要关注的是：给定输入 X，输出是否正确？

```typescript
import { describe, it, expect, vi } from 'vitest'

// 模拟 call() 的核心逻辑（提取为纯函数便于测试）
function formatTimestamp(format?: string): { timestamp: string; format: string } {
  const actualFormat = format ?? 'iso'
  switch (actualFormat) {
    case 'unix':
      return { timestamp: String(Math.floor(Date.now() / 1000)), format: 'unix' }
    case 'locale':
      return { timestamp: new Date().toLocaleString(), format: 'locale' }
    case 'iso':
    default:
      return { timestamp: new Date().toISOString(), format: 'iso' }
  }
}

describe('TimestampTool call 逻辑', () => {
  it('默认返回 ISO 格式', () => {
    const result = formatTimestamp()
    expect(result.format).toBe('iso')
    expect(result.timestamp).toMatch(/^\d{4}-\d{2}-\d{2}T/)
  })

  it('返回 Unix 时间戳', () => {
    const result = formatTimestamp('unix')
    expect(result.format).toBe('unix')
    expect(result.timestamp).toMatch(/^\d+$/)
    // Unix 时间戳应该是合理的范围（2010 年之后）
    expect(Number(result.timestamp)).toBeGreaterThan(1262304000)
  })

  it('返回本地可读时间', () => {
    const result = formatTimestamp('locale')
    expect(result.format).toBe('locale')
    expect(result.timestamp.length).toBeGreaterThan(0)
  })

  it('使用固定时间来避免时区问题', () => {
    // 用 vi.useFakeTimers() 固定时间
    vi.useFakeTimers()
    vi.setSystemTime(new Date('2026-01-15T10:30:00.000Z'))

    const result = formatTimestamp('iso')
    expect(result.timestamp).toBe('2026-01-15T10:30:00.000Z')

    vi.useRealTimers()
  })
})
```

注意最后一个测试——`vi.useFakeTimers()`。这是一个重要的技巧：**涉及时间的测试必须固定时间**，否则测试结果取决于运行时的时刻，可能在不同时区或不同时间运行时失败。

### 第六步：模拟（Mock）外部依赖

在 Claude Code 的工具里，很多操作涉及外部依赖——文件系统、API 调用、子进程执行。测试时，你不想真的去读文件、调 API、跑命令。你需要**模拟**这些依赖。

**原则：模拟边界，不模拟核心。**

什么是边界？文件系统是边界。网络是边界。子进程是边界。你的核心逻辑（数据处理、决策逻辑、状态转换）不是边界，不应该被模拟。

举个例子：假设你有一个工具需要读取配置文件。核心逻辑是"解析配置并返回结构化数据"，边界是"从文件系统读取"。

```typescript
// 工具逻辑（伪代码）
async function loadConfig(filePath: string): Promise<Config> {
  const content = await fs.readFile(filePath, 'utf-8')  // 边界
  const parsed = JSON.parse(content)                      // 核心
  return validateConfig(parsed)                           // 核心
}
```

测试策略：

```typescript
import { describe, it, expect, vi } from 'vitest'
import { readFile } from 'fs/promises'

// 模拟 fs.readFile
vi.mock('fs/promises', () => ({
  readFile: vi.fn(),
}))

describe('loadConfig', () => {
  it('解析合法的配置文件', async () => {
    // 设置模拟返回值
    vi.mocked(readFile).mockResolvedValue(
      JSON.stringify({ name: 'test', version: '1.0.0' })
    )

    const result = await loadConfig('/fake/path/config.json')

    expect(result).toEqual({ name: 'test', version: '1.0.0' })
    expect(readFile).toHaveBeenCalledWith('/fake/path/config.json', 'utf-8')
  })

  it('文件不存在时抛出错误', async () => {
    vi.mocked(readFile).mockRejectedValue(
      new Error('ENOENT: no such file or directory')
    )

    await expect(loadConfig('/no/such/file')).rejects.toThrow('ENOENT')
  })

  it('非法 JSON 时抛出错误', async () => {
    vi.mocked(readFile).mockResolvedValue('not json at all')

    await expect(loadConfig('/bad/config')).rejects.toThrow()
  })
})
```

三种场景覆盖了：正常路径、文件缺失、数据损坏。你不需要真的创建文件——`vi.mock` 替你处理了文件系统的交互。

### 第七步：测试权限逻辑

第 05 章我们学了 `checkPermissions`。权限逻辑是安全关键路径，必须测试。

```typescript
describe('DBQueryTool checkPermissions', () => {
  const tool = new DBQueryTool()
  const mockContext = {} as ToolUseContext

  it('SELECT 查询自动放行', async () => {
    const result = await tool.checkPermissions(
      { query: 'SELECT * FROM users' },
      mockContext,
    )
    expect(result.behavior).toBe('allow')
  })

  it('DROP 操作直接拒绝', async () => {
    const result = await tool.checkPermissions(
      { query: 'DROP TABLE users' },
      mockContext,
    )
    expect(result.behavior).toBe('deny')
    expect(result.message).toContain('Destructive')
  })

  it('INSERT 操作需要确认', async () => {
    const result = await tool.checkPermissions(
      { query: 'INSERT INTO users VALUES (1, "test")' },
      mockContext,
    )
    expect(result.behavior).toBe('passthrough')
  })

  it('大小写不敏感', async () => {
    const result = await tool.checkPermissions(
      { query: 'select * from users' },
      mockContext,
    )
    expect(result.behavior).toBe('allow')
  })
})
```

权限测试的关键是**覆盖所有行为分支**。`allow`、`deny`、`passthrough`（最终变成 `ask`）——每种行为至少有一个测试。

### 第八步：集成测试——测试工具注册

单元测试验证单个函数的行为。集成测试验证组件之间的协作。

```typescript
import { describe, it, expect } from 'vitest'

describe('工具注册', () => {
  it('TimestampTool 出现在工具列表中', () => {
    const tools = getAllBaseTools()
    const names = tools.map(t => t.name)
    expect(names).toContain('Timestamp')
  })

  it('所有工具都有 name 属性', () => {
    const tools = getAllBaseTools()
    for (const tool of tools) {
      expect(tool.name).toBeTruthy()
      expect(typeof tool.name).toBe('string')
    }
  })

  it('所有工具都有 inputSchema', () => {
    const tools = getAllBaseTools()
    for (const tool of tools) {
      expect(tool.inputSchema).toBeDefined()
    }
  })

  it('工具名不重复', () => {
    const tools = getAllBaseTools()
    const names = tools.map(t => t.name)
    const uniqueNames = new Set(names)
    expect(uniqueNames.size).toBe(names.length)
  })
})
```

这类测试帮你捕捉"注册了但忘了加到列表"、"名字打错了"、"schema 忘了定义"这类错误。

## 遇到问题？

### 问题 1：导入源码时报路径错误

**症状**：`Cannot find module '../../Tool.js'`

**原因**：Claude Code 使用 `.js` 后缀的 import（ESM 约定），但实际文件是 `.ts`。Vitest 默认能处理这个转换，但需要正确配置。

**解决方案**：确保 `vitest.config.ts` 中的路径别名配置正确。如果仍然报错，检查 `tsconfig.json` 中的 `moduleResolution` 设置是否为 `bundler` 或 `node16`。

### 问题 2：`bun:bundle` 相关的导入报错

**症状**：`Cannot find module 'bun:bundle'`

**原因**：`bun:bundle` 是 Bun 运行时特有的模块，用于编译时的 feature flag。在 Vitest/Jest 环境下不可用。

**解决方案**：在测试中模拟这个模块：

```typescript
vi.mock('bun:bundle', () => ({
  feature: vi.fn((name: string) => {
    // 根据需要返回 true/false
    return false
  }),
}))
```

### 问题 3：涉及 `src/` 路径别名的导入

**症状**：`Cannot find module 'src/bootstrap/state.js'`

**原因**：Claude Code 内部使用了 `src/` 作为路径别名。你的测试环境可能没有配置这个别名。

**解决方案**：在 `vitest.config.ts` 中添加路径别名：

```typescript
import { defineConfig } from 'vitest/config'
import path from 'path'

export default defineConfig({
  resolve: {
    alias: {
      'src': path.resolve(__dirname, 'src'),
    },
  },
  test: {
    include: ['src/**/*.test.ts'],
  },
})
```

### 问题 4：测试异步生成器（async generator）

**症状**：工具返回的是 `AsyncGenerator`，不知道怎么在测试中消费。

**解决方案**：用 `for await...of` 收集所有 yield 的值：

```typescript
it('测试 async generator 工具', async () => {
  const results = []
  for await (const item of tool.call(input, context, canUseTool, message)) {
    results.push(item)
  }
  expect(results).toHaveLength(1)
  expect(results[0].data).toBeDefined()
})
```

## 验证

让我们确认你掌握了测试的核心技能。

**测试 1：为 Zod schema 写测试。** 给定以下 schema：

```typescript
const configSchema = z.strictObject({
  name: z.string().min(1),
  timeout: z.number().positive().default(30000),
  retries: z.number().int().min(0).max(5).default(3),
})
```

写至少四个测试：合法输入、缺失必需字段、值超出范围、额外字段被拒绝。如果你写的测试全部通过，你的 schema 测试技能就到位了。

**测试 2：时间敏感测试。** 写一个测试验证"ISO 格式的时间戳包含 T 分隔符"，使用 `vi.useFakeTimers()` 确保测试可重复。

**测试 3：模拟策略。** 假设你的工具需要调用外部 API。设计模拟策略时，你应该模拟什么、不模拟什么？

- 模拟：HTTP 请求（网络边界）
- 不模拟：响应数据的解析和验证逻辑（核心逻辑）

如果这三个测试你都理解了，说明你已经具备了为 Claude Code 工具编写测试的能力。

## 回顾

这一章，我们讨论了在 Claude Code 的代码库里如何编写测试：

1. **测试现状**——从 npm 包提取的源码没有独立测试文件，但源码中有 `TestingPermissionTool`、`NODE_ENV === 'test'` 分支等测试痕迹
2. **框架选择**——推荐 Vitest 或 Bun test，两者 API 兼容，选哪个取决于你的生态偏好
3. **Schema 测试**——最先测试的东西应该是 Zod schema，它是工具和 AI 之间的契约
4. **核心逻辑测试**——`call()` 的纯逻辑应该提取为可测试的纯函数，用 `vi.useFakeTimers()` 处理时间依赖
5. **模拟策略**——模拟边界（文件系统、网络、子进程），不模拟核心逻辑
6. **权限测试**——`checkPermissions` 的每个行为分支（allow/deny/passthrough）都需要测试
7. **集成测试**——验证工具注册、名字唯一性、schema 存在性等跨组件属性

测试不是负担，是投资。每多写一个测试，你就多了一个不会疲倦的守卫者，在你改代码的时候替你盯着旧功能是否还在正常工作。

下一章，我们转向调试——当代码的行为不如预期时，如何系统地找到问题根源。
