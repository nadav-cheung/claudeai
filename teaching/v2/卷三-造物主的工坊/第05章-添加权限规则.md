# 第05章：添加权限规则

上一章，你学会了用 Zod 验证输入。现在 AI 传过来的参数是合法的了——但你有没有想过另一个问题：**参数合法，就代表这个操作应该被执行吗？**

想象一下，AI 要执行 `rm -rf /`。参数格式完全合法——它就是一个字符串，Zod 不会拒绝。但这个命令显然不应该被默许执行。

这就是权限系统要解决的问题。在 Claude Code 里，权限检查发生在输入验证之后、工具执行之前。它回答的唯一问题是：**这个操作，是自动放行、直接拒绝、还是需要用户确认？**

这一章，我们从源码出发，理解 Claude Code 的权限决策流程，然后为你的工具添加自定义的权限规则。

---

## 目标

完成这一章后，你将能够：

1. 理解 Claude Code 权限系统的三态决策：`allow`、`deny`、`ask`
2. 掌握 `PermissionRule` 的结构和规则解析流程
3. 理解 `checkPermissions()` 在权限管线中的位置和职责
4. 学会实现工具级别的自定义权限逻辑
5. 了解 `hasPermissionsToUseTool` 的完整决策管线

## 动手

### 第一步：理解三态决策——allow、deny、ask

Claude Code 的权限系统不是简单的"允许或拒绝"二选一。它有三种行为，定义在 `PermissionRule.ts` 中：

```typescript
// 文件：src/utils/permissions/PermissionRule.ts
export const permissionBehaviorSchema = z.enum(['allow', 'deny', 'ask'])
```

- **`allow`**——自动放行，不需要用户确认
- **`deny`**——直接拒绝，不执行也不问用户
- **`ask`**——弹出确认对话框，等用户决定

这三种行为对应着权限规则的三个"桶"：`alwaysAllowRules`、`alwaysDenyRules`、`alwaysAskRules`。每条规则从配置中加载，被打上行为标签后进入对应的桶。

### 第二步：认识 PermissionRule 的结构

每条权限规则长这样：

```typescript
// 文件：src/types/permissions.ts
type PermissionRuleValue = {
  toolName: string           // 规则针对的工具名
  ruleContent?: string       // 可选的细粒度匹配内容
}

type PermissionRule = {
  source: PermissionRuleSource  // 规则来源：userSettings、projectSettings、cliArg、session 等
  ruleBehavior: 'allow' | 'deny' | 'ask'
  ruleValue: PermissionRuleValue
}
```

规则有两种粒度：

**工具级规则**——匹配整个工具。比如 `"Bash"` 表示"Bash 工具的所有操作"。

**内容级规则**——匹配工具的特定操作。比如 `"Bash(npm install)"` 表示"只有 npm install 这个命令"。

内容级规则的解析逻辑在 `permissionRuleParser.ts` 中。格式是 `ToolName(content)`，其中括号内的内容支持转义：

```typescript
// 文件：src/utils/permissions/permissionRuleParser.ts
export function permissionRuleValueFromString(ruleString: string): PermissionRuleValue {
  // "Bash" → { toolName: "Bash" }
  // "Bash(npm install)" → { toolName: "Bash", ruleContent: "npm install" }
  // "Bash(git commit -m \"fix\\(bug\\)\")" → { toolName: "Bash", ruleContent: "git commit -m \"fix(bug)\"" }
}
```

解析器会找到第一个未转义的 `(` 和最后一个未转义的 `)`，把中间的内容提取为 `ruleContent`。括号本身可以用 `\(` 和 `\)` 转义。

### 第三步：权限管线的完整流程

当 AI 要使用一个工具时，`hasPermissionsToUseTool` 函数被调用。这是整个权限管线的主入口，定义在 `src/utils/permissions/permissions.ts` 中。让我们按顺序走一遍这个管线的每一个步骤：

```
步骤 1a：检查 deny 规则 → 命中则直接拒绝
步骤 1b：检查 ask 规则 → 命中则要求用户确认
步骤 1c：调用 tool.checkPermissions() → 工具级自定义逻辑
步骤 1d：工具返回 deny → 直接拒绝
步骤 1e：工具需要用户交互 → 强制弹出确认
步骤 1f：内容级 ask 规则 → 即便 bypass 模式也要确认
步骤 1g：安全检查 → .git/ 等敏感路径必须确认
步骤 2a：检查 bypassPermissions 模式 → 全部放行
步骤 2b：检查 allow 规则 → 命中则自动放行
步骤 3：默认行为 → 转换为 ask（要求用户确认）
```

让我们看源码中的关键片段：

```typescript
// 文件：src/utils/permissions/permissions.ts
// 步骤 1a：整个工具被 deny 规则拒绝
const denyRule = getDenyRuleForTool(appState.toolPermissionContext, tool)
if (denyRule) {
  return {
    behavior: 'deny',
    decisionReason: { type: 'rule', rule: denyRule },
    message: `Permission to use ${tool.name} has been denied.`,
  }
}
```

deny 规则拥有最高优先级。如果一个工具被加入了 deny 列表，后面所有检查都不会执行。这是安全设计的基本原则：**拒绝优先于放行**。

```typescript
// 步骤 1c：调用工具自身的权限检查
const parsedInput = tool.inputSchema.parse(input)
toolPermissionResult = await tool.checkPermissions(parsedInput, context)
```

这里调用了工具的 `checkPermissions()` 方法。这是你作为工具开发者可以自定义的部分。我们稍后会详细讨论。

```typescript
// 步骤 2b：检查整个工具是否在 allow 列表中
const alwaysAllowedRule = toolAlwaysAllowedRule(
  appState.toolPermissionContext,
  tool,
)
if (alwaysAllowedRule) {
  return {
    behavior: 'allow',
    decisionReason: { type: 'rule', rule: alwaysAllowedRule },
  }
}
```

如果工具通过了所有 deny 和 ask 检查，并且被列在 allow 规则中，它会被自动放行。

```typescript
// 步骤 3：默认行为——转成 ask
const result = toolPermissionResult.behavior === 'passthrough'
  ? { ...toolPermissionResult, behavior: 'ask' as const }
  : toolPermissionResult
```

`passthrough` 是一个特殊值，意思是"工具自己没有意见，交给通用规则"。如果所有规则都没有命中，它会被转成 `ask`——要求用户确认。**默认安全**是这条管线的核心原则。

### 第四步：实现 checkPermissions

每个工具都可以通过实现 `checkPermissions` 方法来添加自己的权限逻辑。这个方法在 Tool 基类中的签名是：

```typescript
// 文件：src/Tool.ts，第500-503行
checkPermissions(
  input: z.infer<Input>,
  context: ToolUseContext,
): Promise<PermissionResult>
```

它接收已验证的输入和工具使用上下文，返回一个 `PermissionResult`：

```typescript
type PermissionResult =
  | { behavior: 'allow'; updatedInput?: Record<string, unknown> }
  | { behavior: 'deny'; message: string }
  | { behavior: 'ask'; message: string; suggestions?: PermissionUpdate[] }
  | { behavior: 'passthrough'; message: string }
```

- **`allow`**——工具自己决定放行，附带可选的修改后输入
- **`deny`**——工具自己决定拒绝
- **`ask`**——工具请求用户确认
- **`passthrough`**——工具没有意见，交给通用规则

大多数简单工具返回 `{ behavior: 'passthrough', message: '...' }`——它们自己不做权限判断，完全依赖规则系统。

但对于像 Bash 这样的工具，`checkPermissions` 是权限逻辑的核心。它会解析命令内容，检查每条子命令是否匹配 allow/deny 规则，然后返回汇总结果。

### 第五步：为你的工具添加权限逻辑

假设你正在开发一个操作数据库的工具 `DBQueryTool`。你想实现这样的权限策略：

- `SELECT` 查询自动放行
- `DROP` 和 `DELETE` 直接拒绝
- 其他语句需要用户确认

```typescript
async checkPermissions(
  input: { query: string },
  context: ToolUseContext,
): Promise<PermissionResult> {
  const sql = input.query.trim().toUpperCase()

  // SELECT 查询——只读操作，自动放行
  if (sql.startsWith('SELECT')) {
    return {
      behavior: 'allow',
      updatedInput: input,
    }
  }

  // DROP 和 DELETE——危险操作，直接拒绝
  if (sql.startsWith('DROP') || sql.startsWith('DELETE')) {
    return {
      behavior: 'deny',
      message: 'Destructive SQL operations are not allowed.',
    }
  }

  // 其他操作——交给用户决定
  return {
    behavior: 'passthrough',
    message: `DBQuery tool requires permission for: ${input.query}`,
  }
}
```

这段代码做了三件事：

1. **安全操作自动放行**——`SELECT` 是只读的，不需要确认
2. **危险操作直接拒绝**——`DROP` 和 `DELETE` 太危险，连问都不问
3. **不确定的操作交给通用规则**——`INSERT`、`UPDATE` 等操作返回 `passthrough`，最终变成 `ask`

### 第六步：auto mode 和分类器

Claude Code 还有一个特殊的权限模式：**auto mode**。在 auto mode 下，一个 AI 分类器（classifier）会代替用户做权限决定。分类器会看对话上下文和工具调用的内容，判断这个操作是否安全。

这个流程发生在 `hasPermissionsToUseTool` 的后半段：

```typescript
// 文件：src/utils/permissions/permissions.ts
if (appState.toolPermissionContext.mode === 'auto') {
  // 检查 acceptEdits 快速路径
  const acceptEditsResult = await tool.checkPermissions(parsedInput, {
    ...context,
    getAppState: () => ({
      ...context.getAppState(),
      toolPermissionContext: { ...state.toolPermissionContext, mode: 'acceptEdits' },
    }),
  })
  if (acceptEditsResult.behavior === 'allow') {
    return { behavior: 'allow', decisionReason: { type: 'mode', mode: 'auto' } }
  }

  // 检查安全工具白名单
  if (isAutoModeAllowlistedTool(tool.name)) {
    return { behavior: 'allow', decisionReason: { type: 'mode', mode: 'auto' } }
  }

  // 运行分类器
  const classifierResult = await classifyYoloAction(...)
  if (classifierResult.shouldBlock) {
    return { behavior: 'deny', message: '...' }
  }
  return { behavior: 'allow' }
}
```

auto mode 有三个层级的安全网：

1. **acceptEdits 快速路径**——如果这个操作在 acceptEdits 模式下会被允许，就直接放行，不调用分类器
2. **安全工具白名单**——像 `Read`、`Grep`、`Glob` 这种只读工具直接放行
3. **AI 分类器**——对于不确定的操作，调用分类器 API 做判断

白名单定义在 `classifierDecision.ts` 中，包含了所有"天然安全"的工具：

```typescript
// 文件：src/utils/permissions/classifierDecision.ts
const SAFE_YOLO_ALLOWLISTED_TOOLS = new Set([
  FILE_READ_TOOL_NAME,
  GREP_TOOL_NAME,
  GLOB_TOOL_NAME,
  LSP_TOOL_NAME,
  TOOL_SEARCH_TOOL_NAME,
  // ... 更多只读工具
])
```

### 第七步：决策原因——decisionReason

权限系统的每一个决定都附带一个 `decisionReason`，记录了**为什么**做出这个决定。这对于日志分析和用户提示非常重要：

```typescript
type PermissionDecisionReason =
  | { type: 'rule'; rule: PermissionRule }          // 命中了某条规则
  | { type: 'mode'; mode: PermissionMode }          // 当前权限模式
  | { type: 'classifier'; classifier: string; reason: string }  // AI 分类器的判断
  | { type: 'hook'; hookName: string }              // Hook 拦截
  | { type: 'safetyCheck' }                         // 安全检查
  | { type: 'asyncAgent'; reason: string }          // 异步 agent 自动拒绝
  | { type: 'subcommandResults'; reasons: Map<string, PermissionResult> }  // 子命令汇总
```

当权限请求被展示给用户时，`createPermissionRequestMessage` 会把 `decisionReason` 转换成人类可读的消息：

```
"Permission rule 'Bash(npm install)' from user settings requires approval for this Bash command"
```

## 遇到问题？

### 问题 1：我的工具在 bypassPermissions 模式下仍然要求确认

**症状**：用户启动了 `--dangerously-skip-permissions` 模式，但某些操作仍然弹出确认框。

**原因**：权限管线中有几个检查点是"bypass 免疫"的——即使在 bypassPermissions 模式下也会生效。具体包括：

- 步骤 1d：工具 `checkPermissions` 返回 `deny`
- 步骤 1f：内容级 ask 规则（比如 `Bash(npm publish:*)` 配置为 ask）
- 步骤 1g：安全检查（`.git/`、`.claude/` 等敏感路径）

**解决方案**：如果你确实想在 bypass 模式下跳过这些检查，你需要确保 `checkPermissions` 不返回 `deny` 或带有 `safetyCheck` 原因的 `ask`。

### 问题 2：MCP 工具的权限规则怎么写

**症状**：你想给一个 MCP 工具写权限规则，但不知道规则格式。

**原因**：MCP 工具的名字格式是 `mcp__serverName__toolName`。权限规则可以按两种粒度匹配：

**匹配整个 server**——`mcp__server1` 会匹配该 server 下的所有工具。

**匹配单个工具**——`mcp__server1__tool1` 精确匹配某个工具。

**匹配通配符**——`mcp__server1__*` 匹配该 server 下的所有工具（和 server 级匹配效果相同）。

### 问题 3：规则优先级是什么

**症状**：你同时配了 allow 和 deny 规则，不确定哪个生效。

**原因**：管线的执行顺序就是优先级。deny 检查在 allow 检查之前（步骤 1a 在步骤 2b 之前），所以 deny 永远优先于 allow。

**解决方案**：当你同时配了 `Bash(rm -rf /)` deny 和 `Bash(*)` allow 时，deny 会先命中，操作被拒绝。这是正确的安全行为。

### 问题 4：checkPermissions 里的 input 类型不对

**症状**：你在 `checkPermissions` 中访问 `input.command`，TypeScript 报类型错误。

**原因**：`checkPermissions` 的 `input` 参数类型是从工具的 `inputSchema` 推导出来的。如果你的 schema 还没有定义这个字段，类型系统自然不知道它的存在。

**解决方案**：确保 `inputSchema` 中定义了你在 `checkPermissions` 中需要访问的所有字段。权限检查发生在输入验证之后，所以 `input` 已经是验证后的数据。

## 验证

让我们验证你的理解。

**测试 1：理解管线顺序。** 下面的规则组合会产生什么效果？

- `Bash(rm *)` → deny
- `Bash(npm *)` → allow
- `Bash` → deny

当 AI 调用 `Bash(rm -rf /tmp)` 时，管线会依次检查 deny→ask→工具权限→allow。第一步 deny 检查命中 `Bash(rm *)`，直接拒绝。后面的 allow 规则和工具权限都不会被检查。

**测试 2：设计 checkPermissions。** 为一个文件操作工具设计权限逻辑，要求：

- 读取操作（`mode: 'read'`）自动放行
- 写入当前目录自动放行
- 写入当前目录之外需要确认
- 写入 `.env` 文件直接拒绝

```typescript
async checkPermissions(input, context) {
  if (input.mode === 'read') {
    return { behavior: 'allow', updatedInput: input }
  }
  if (input.file_path.endsWith('.env')) {
    return { behavior: 'deny', message: 'Cannot write to .env files' }
  }
  const cwd = getCwd()
  if (input.file_path.startsWith(cwd)) {
    return { behavior: 'allow', updatedInput: input }
  }
  return {
    behavior: 'passthrough',
    message: `Writing outside CWD requires permission: ${input.file_path}`,
  }
}
```

**测试 3：白名单判断。** 以下哪些工具在 auto mode 下会被安全白名单直接放行（不调用分类器）？

- FileReadTool → 是（只读操作）
- GrepTool → 是（只读搜索）
- FileWriteTool → 否（写操作，不在白名单中）
- GlobTool → 是（只读文件搜索）
- BashTool → 否（可能执行任何命令）

如果这三个测试你都理解了，说明你已经掌握了 Claude Code 权限系统的核心机制。

## 回顾

这一章，我们深入了 Claude Code 的权限决策流程：

1. **三态决策**——`allow`/`deny`/`ask` 不是非黑即白，`ask` 是一种尊重用户的安全默认
2. **PermissionRule**——规则的粒度从整个工具到特定内容，支持多层配置来源
3. **权限管线**——deny 优先于 allow，安全检查优先于 bypass，默认行为是 ask
4. **checkPermissions**——工具级自定义权限的入口，返回 allow/deny/ask/passthrough
5. **auto mode**——分类器替代用户做决定，但有多层安全网保护
6. **decisionReason**——每个决定都有原因追踪，保证可解释性

记住权限系统的设计原则：**默认安全，拒绝优先，工具可以自定义但通用规则兜底。**
