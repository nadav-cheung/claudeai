# 第11章：从代码到贡献

你已经能写工具、写测试、调试问题了。你的本地环境里可能已经有了几个能跑的改动。但代码停留在本地，就像文章留在草稿箱——只有发表出去，它才有价值。

这一章，我们讨论如何把你的本地改动变成对项目的贡献。从 Git 分支到代码审查，从 commit message 到 Pull Request，走完"从代码到贡献"的完整旅程。

---

## 目标

完成这一章后，你将能够：

1. 理解 Claude Code 项目的贡献流程和分支策略
2. 编写符合规范的 commit message
3. 创建高质量的 Pull Request
4. 应对代码审查（code review）中的反馈
5. 理解开源贡献的文化和礼仪

---

## 动手

### 第一步：理解项目的贡献入口

Claude Code 的源码仓库在 GitHub 上：`github.com/anthropics/claude-code`。这是我们贡献代码的入口。

在开始之前，先了解几个关键位置：

**Issue 列表**——项目的 bug 报告和功能请求都在 GitHub Issues 里。这是你找到贡献机会的地方。

**Pull Request 列表**——所有待合并的代码改动在这里。浏览已合并的 PR 可以帮你理解项目的贡献风格。

**README 和文档**——通常包含贡献指南、行为准则和联系方式。

**源码仓库的特殊性**——回忆第 01 章的内容：我们从 npm 包提取出来的源码仓库不是 Anthropic 的内部开发仓库。真正的贡献需要推送到 GitHub 上的官方仓库。这意味着你需要 fork 官方仓库，在 fork 上开发，然后向官方仓库提 PR。

### 第二步：Fork 和分支策略

**Fork** 是你自己的仓库副本。你在 fork 上有完整的写权限，可以自由地创建分支和推送代码。

```bash
# 1. 在 GitHub 上 fork 官方仓库
# 2. 克隆你的 fork
git clone https://github.com/your-username/claude-code.git
cd claude-code

# 3. 添加官方仓库作为上游（upstream）
git remote add upstream https://github.com/anthropics/claude-code.git

# 4. 确认远程仓库配置
git remote -v
# origin    https://github.com/your-username/claude-code.git (fetch)
# origin    https://github.com/your-username/claude-code.git (push)
# upstream  https://github.com/anthropics/claude-code.git (fetch)
# upstream  https://github.com/anthropics/claude-code.git (push)
```

**分支策略**：永远不要在 `main` 分支上直接开发。为每个贡献创建一个独立的分支：

```bash
# 从最新的 main 创建分支
git checkout main
git pull upstream main
git checkout -b fix/glob-tool-symlink-resolution

# 或者为功能开发
git checkout -b feat/add-timestamp-tool
```

分支命名建议：

- `fix/` 前缀：bug 修复（如 `fix/permission-deny-rule-override`）
- `feat/` 前缀：新功能（如 `feat/add-timestamp-tool`）
- `refactor/` 前缀：代码重构（如 `refactor/extract-schema-validation`）
- `docs/` 前缀：文档更新（如 `docs/update-tool-development-guide`）
- `test/` 前缀：测试补充（如 `test/add-permission-logic-tests`）

### 第三步：编写好的 Commit Message

Commit message 是你的改动的故事。好的 commit message 让审查者和未来的维护者能快速理解"改了什么"和"为什么改"。

Claude Code 项目使用的是 Conventional Commits 风格：

```
<type>(<scope>): <description>

[optional body]

[optional footer]
```

**type（类型）**：

- `feat`：新功能
- `fix`：bug 修复
- `refactor`：代码重构（不改变功能）
- `test`：测试相关
- `docs`：文档相关
- `chore`：构建、工具、依赖更新
- `perf`：性能优化

**scope（范围）**：可选，标识改动影响的模块。比如 `tools`、`permissions`、`api`、`mcp`。

**description（描述）**：简短的一句话，说明改了什么。用祈使句（"Add" 而不是 "Added"）。

举几个例子：

```
feat(tools): add Timestamp tool for ISO/unix/locale time formats

fix(permissions): prevent deny rule bypass in bypassPermissions mode

refactor(debug): extract debug filter logic into separate module

test(schemas): add validation tests for tool input schemas
```

**Body（正文）**——当描述一行写不下时，用正文补充上下文：

```
fix(permissions): prevent deny rule bypass in bypassPermissions mode

Previously, the permission pipeline checked bypass mode before
checking deny rules. This meant that if a user had --dangerously-skip-permissions
enabled, deny rules were ignored.

This commit reorders the pipeline to check deny rules first, ensuring
that explicitly denied operations are never executed regardless of mode.

Fixes #1234
```

好的 commit message 的标准：

1. **第一行不超过 72 个字符**——这样在 `git log --oneline` 和 GitHub 的 commit 列表里都能完整显示
2. **第一行是祈使句**——"Fix bug" 而不是 "Fixed bug"
3. **解释"为什么"而不是"什么"**——`git diff` 已经告诉读者改了什么，commit message 应该解释为什么这样改
4. **引用相关的 Issue**——`Fixes #1234` 或 `Related to #5678`

### 第四步：控制 PR 的范围

一个 PR 只做一件事。

这是最重要的贡献原则。大而全的 PR 很难审查——审查者面对 500 行改动时会犹豫从哪里开始看，可能遗漏关键问题。小而聚焦的 PR 审查起来轻松，合并起来快速。

**好的 PR 范围**：

- "为 TimestampTool 添加 unix 格式支持"——15 行改动，清晰明确
- "修复 BashTool 在 Windows 下的路径处理"——30 行改动，一个问题一个修复
- "为权限规则解析器添加单元测试"——100 行改动，全是新文件，不影响现有代码

**不好的 PR 范围**：

- "改进工具系统"——500 行改动，混合了重构、新功能、bug 修复，审查者不知道从哪里开始
- "修复所有 lint 警告"——200 行改动，虽然每行改动都小，但涉及几十个文件，难以验证每个改动是否安全

如果你发现自己在一个 PR 里做了多件不相关的事，把它拆分成多个 PR。每个 PR 独立可审查、独立可合并。

### 第五步：创建 Pull Request

代码准备好了，commit 也写好了。推送到你的 fork：

```bash
git push origin fix/glob-tool-symlink-resolution
```

然后在 GitHub 上创建 Pull Request。好的 PR 有以下要素：

**标题**——和 commit message 的第一行格式一样：`<type>(<scope>): <description>`

**描述模板**：

```markdown
## Summary

<!-- 一到三句话说明这个 PR 做了什么 -->

## Changes

<!-- 列出具体的改动点 -->

- Added `format` parameter to TimestampTool inputSchema
- Implemented unix timestamp format in call()
- Added validation tests for the new format

## Testing

<!-- 你怎么验证这些改动的 -->

- [x] Unit tests pass (`npx vitest run`)
- [x] Manual test: `claude` then "给我当前的 Unix 时间戳"
- [x] No type errors (`npx tsc --noEmit`)

## Related Issues

<!-- 关联的 Issue -->

Fixes #1234
```

**PR 描述是写给审查者看的**。审查者可能不熟悉你修改的代码区域——好的描述帮他们快速建立上下文，理解你的改动意图和验证方法。

### 第六步：理解代码审查（Code Review）

提交 PR 之后，项目维护者会审查你的代码。这是学习的好机会——不要把审查意见当成批评，把它当成对话。

代码审查通常关注以下几个方面：

**正确性**——代码是否做了它声称要做的事？有没有边界情况遗漏？有没有 off-by-one 错误？

**安全性**——改动是否引入了安全风险？比如路径穿越、注入攻击、敏感信息泄露。

**可读性**——代码是否容易理解？命名是否清晰？逻辑是否直观？是否需要注释？

**一致性**——代码风格是否和项目其他部分保持一致？有没有违反项目的编码规范？

**性能**——改动是否引入了不必要的性能开销？有没有 O(n^2) 算法可以优化为 O(n)？

**测试**——改动是否有相应的测试覆盖？测试是否测试了正确的东西？

### 第七步：回应审查反馈

收到审查意见后，你的回应方式很重要。

**不要急于修改**——先理解意见的意图。审查者说"这里用一个 Map 更好"，不要马上改成 Map。先想想为什么他这么说，是不是有性能原因？是不是数据结构更适合？

**如果不同意，说清楚**——好的审查是技术讨论。如果你认为你的方案更合理，解释你的理由。但要注意语气——是"我认为...因为..."，而不是"你不懂..."。

**区分"必须改"和"建议"**——有些意见是阻塞性的（必须改才能合并），有些是建议性的（改不改都行）。通常审查者会明确标注，比如 "nit:"（小问题，可选）或者 "blocking:"（必须修改）。

**逐条回复**——对每条审查意见都给出回应，即使是 "Done"、"Good point, fixed in abc123" 或者 "I respectfully disagree because..."。这让审查者知道你看了每一条意见。

**用新的 commit 回应**——不要 force push 覆盖旧的 commit。推一个新的 commit，说明你做了什么修改：

```bash
git add -A
git commit -m "refactor(permissions): use Map for rule lookup per review feedback"
git push origin fix/glob-tool-symlink-resolution
```

审查者可以在后续的 commit 中看到你的修改历史，这比一个被 force push 覆盖的 commit 更容易追踪。

### 第八步：保持 PR 更新

在你等待审查的过程中，`main` 分支可能在继续演进。你需要定期把 main 的最新改动合并到你的分支：

```bash
git checkout fix/glob-tool-symlink-resolution
git fetch upstream
git merge upstream/main

# 解决冲突（如果有的话）
git push origin fix/glob-tool-symlink-resolution
```

如果你的分支和 main 差距太大，审查者可能会要求你 rebase：

```bash
git fetch upstream
git rebase upstream/main

# 解决冲突后
git push origin fix/glob-tool-symlink-resolution --force-with-lease
```

注意 `--force-with-lease` 而不是 `--force`。前者更安全——如果远程分支有别人的改动，它会拒绝推送，而不是覆盖。

### 第九步：合并之后

PR 被合并了！恭喜。但故事没结束：

**清理分支**：

```bash
# 删除本地分支
git branch -d fix/glob-tool-symlink-resolution

# 删除远程分支
git push origin --delete fix/glob-tool-symlink-resolution
```

**跟进**——观察你的改动是否在后续版本中正常工作。如果有人报告了相关的问题，积极参与讨论。

**庆祝**——然后去找下一个贡献机会。

## 遇到问题？

### 问题 1：PR 好几周没有人审查

**症状**：你提交了 PR，但迟迟没有人审查。

**原因**：维护者可能很忙，或者你的 PR 没有引起注意。大型项目每天收到大量 PR，维护者需要按优先级排序。

**解决方案**：

- 在 PR 描述里提供充分的上下文，降低审查门槛
- 在相关的 Issue 里提及你的 PR
- 在项目讨论区（GitHub Discussions 或 Discord）提及你的贡献
- 如果等了两周还没有回复，礼貌地在 PR 里留言请求审查

### 问题 2：CI 测试失败

**症状**：PR 提交后，自动化的 CI 测试报错了。

**原因**：可能是你的改动引入了回归，也可能是 CI 环境和你的本地环境有差异。

**解决方案**：

- 仔细阅读 CI 的错误输出
- 在本地复现 CI 的测试命令
- 如果是环境问题（比如 Node 版本差异），在 PR 描述中说明

### 问题 3：审查者要求大范围重构

**症状**：你提交了一个小修复，审查者要求你重写整个模块。

**原因**：审查者可能看到了你没注意到的设计问题，或者他们希望借此机会改善代码质量。

**解决方案**：

- 如果重构确实有必要，但超出了当前 PR 的范围，提议把重构拆成单独的 PR
- 先处理当前 PR 的问题，重构留到后续
- 不要在一个 PR 里同时做修复和重构

### 问题 4：merge conflict 太多

**症状**：`git merge upstream/main` 产生了大量冲突。

**原因**：你的分支和 main 差距太大，或者你修改的文件也被其他人改了。

**解决方案**：

- 频繁合并 main（至少每周一次），减少差距
- 专注于小范围的 PR，减少冲突面
- 如果冲突太复杂，考虑基于最新的 main 重新实现你的改动

## 验证

让我们确认你理解了贡献流程。

**检查 1：分支策略。** 你要修复一个 bug。正确的流程是什么？

- Fork 仓库
- 从最新的 main 创建分支 `fix/bug-name`
- 在分支上开发和测试
- 提交 PR 到官方仓库

**检查 2：commit message。** 以下哪个是好的 commit message？

- ~~"fix stuff"~~——太模糊
- ~~"Fixed the bug where permissions were being bypassed"~~——用了过去时
- "fix(permissions): check deny rules before bypass mode"——好的。有类型、有范围、有具体描述

**检查 3：PR 描述。** 一个好的 PR 描述应该包含什么？

- Summary：一两句话说清楚做了什么
- Changes：具体的改动列表
- Testing：你怎么验证的
- Related Issues：关联的 Issue

**检查 4：回应审查。** 审查者说 "This should be a Map instead of an array"。你的回应？

- 先理解原因（查找性能？去重？顺序保证？）
- 如果同意，修改并回复 "Done in commit abc123"
- 如果不同意，解释原因："I used an array because the order matters for rule priority"

如果这四个检查你都能答对，你的贡献技能就准备好了。

## 回顾

这一章，我们走过了从代码到贡献的完整流程：

1. **Fork 和分支**——fork 官方仓库，从 main 创建功能分支，命名有规范
2. **Commit message**——Conventional Commits 格式，解释"为什么"而不是"什么"
3. **PR 范围**——一个 PR 只做一件事，小而聚焦
4. **PR 描述**——Summary、Changes、Testing、Related Issues 四要素
5. **代码审查**——正确性、安全性、可读性、一致性、性能、测试
6. **回应反馈**——先理解再修改，逐条回复，用新 commit 而不是 force push
7. **保持更新**——定期合并 main，处理冲突
8. **合并后**——清理分支，观察后续，找下一个机会

贡献不只是写代码。它是一整套社交流程——和项目维护者沟通、接受反馈、在技术讨论中保持尊重和专业。写代码是硬技能，贡献是软技能和硬技能的结合。
