# 第03章：工具系统的演进

你在卷二拆过引擎室。你知道 BashTool、FileReadTool、GrepTool 这些工具是怎么工作的——接收参数、校验输入、检查权限、执行操作、返回结果。你甚至自己写过工具定义。

但有一个问题我们一直没问：**为什么所有工具长得都一样？**

打开 `src/tools/` 目录，43 个子目录一字排开。BashTool 的目录里有 18 个文件，FileReadTool 有 5 个文件，GlobTool 有 3 个文件。它们做完全不同的事——一个执行命令、一个读文件、一个搜索文件名模式。但如果你只看它们的骨架，你会发现它们的形状一模一样：

```typescript
export const SomeTool = buildTool({
  name: '...',
  inputSchema: lazySchema(() => z.object({ ... })),
  async call(args, context, canUseTool, parentMessage, onProgress) { ... },
  async description() { ... },
  async prompt() { ... },
  // ...
})
```

这种一致性不是巧合。它来自一个精心设计的接口——`Tool<Input, Output, P>`——以及一个把所有工具串成一条管线的执行函数——`runToolUse`。

这一章我们讨论这个设计是怎么来的，还有什么别的选择，以及它是不是最好的选择。

---

## 现状：统一的工具接口

### Tool<Input, Output, P>：一个接口，三十多种形态

`src/Tool.ts` 定义了整个工具系统的核心类型：

```typescript
export type Tool<
  Input extends AnyObject = AnyObject,
  Output = unknown,
  P extends ToolProgressData = ToolProgressData,
> = {
  name: string
  inputSchema: Input
  outputSchema?: z.ZodType<unknown>
  call(
    args: z.infer<Input>,
    context: ToolUseContext,
    canUseTool: CanUseToolFn,
    parentMessage: AssistantMessage,
    onProgress?: ToolCallProgress<P>,
  ): Promise<ToolResult<Output>>
  // ... 还有几十个方法和属性
}
```

三个泛型参数：`Input` 是 Zod schema，定义工具接受的参数；`Output` 是工具返回数据的类型；`P` 是进度事件的类型。每个工具有自己具体的这三样东西——BashTool 的 `Input` 有 `command` 字段和 `timeout` 字段，FileReadTool 的 `Input` 有 `file_path` 字段和 `offset`/`limit` 字段——但它们共享同一个 `Tool` 接口形状。

这意味着什么？意味着在任何需要"一个工具"的地方，你不需要知道它是哪种工具。`Tools` 类型就是 `readonly Tool[]`——一组工具，不关心具体类型。调用方通过 `name` 找到工具，通过统一的 `call` 方法执行它，通过统一的 `mapToolResultToToolResultBlockParam` 把结果转成 API 格式。

### buildTool：默认值的聪明处理

不是每个工具都需要实现 `Tool` 接口的每一个方法。`Tool` 类型有二十多个方法和属性，但很多工具只关心其中十来个。剩下的——比如 `isConcurrencySafe`、`isReadOnly`、`checkPermissions`——大多数工具要么永远返回同一个值，要么委托给通用逻辑。

`buildTool` 函数解决了这个问题：

```typescript
export function buildTool<D extends AnyToolDef>(def: D): BuiltTool<D> {
  return {
    ...TOOL_DEFAULTS,
    userFacingName: () => def.name,
    ...def,
  } as BuiltTool<D>
}
```

`TOOL_DEFAULTS` 提供了一组安全默认值：`isEnabled` 默认 `true`，`isConcurrencySafe` 默认 `false`（假设不安全），`isReadOnly` 默认 `false`（假设会写），`checkPermissions` 默认放行。工具定义只需要覆盖自己关心的部分。GlobTool 声明 `isConcurrencySafe() { return true }` 和 `isReadOnly() { return true }`，因为搜索文件名不会修改任何东西。BashTool 不覆盖这两个默认值，因为执行命令确实可能不安全、确实可能修改文件。

这是一种"约定优于配置"的模式。默认值是保守的（假设最危险的情况），工具定义通过覆盖来声明自己更安全。

### 统一执行管线：runToolUse

所有工具调用都经过同一个函数：`src/services/tools/toolExecution.ts` 里的 `runToolUse`。这个函数是一条精心设计的管线：

```
找到工具 → Zod 校验输入 → validateInput → PreToolUse Hooks →
检查权限 → tool.call() → PostToolUse Hooks → 返回结果
```

每一步都有明确的职责。Zod 校验（`inputSchema.safeParse`）确保 AI 返回的 JSON 在结构上合法——字段类型对不对、必填字段有没有缺。`validateInput` 做语义校验——路径存不存在、命令合不合法。PreToolUse Hooks 让外部脚本在工具执行前介入。权限检查决定是否要问用户。`tool.call()` 是工具的核心逻辑。PostToolUse Hooks 让外部脚本在工具执行后介入。

这条管线不在乎它是执行 BashTool 还是 FileReadTool 还是 MCP 工具。它只依赖 `Tool` 接口定义的方法。`tool.inputSchema` 做校验，`tool.validateInput` 做语义检查，`tool.checkPermissions` 做权限判断，`tool.call()` 执行操作。每一个工具自己决定这些方法的具体实现，管线只负责按顺序调用它们。

### Zod：编译时和运行时的桥梁

工具的 `inputSchema` 是一个 Zod schema。在 Claude Code 里，Zod 不只是一个运行时校验库——它是类型系统的延伸。

`z.infer<typeof inputSchema>` 让 TypeScript 从 Zod schema 推断出输入数据的精确类型。这意味着 `tool.call()` 的第一个参数不是 `any` 或 `Record<string, unknown>`，而是这个工具特有的、类型精确的输入。BashTool 的 `call` 方法知道它收到的是 `{ command: string; timeout?: number; description?: string }`，FileReadTool 的 `call` 方法知道它收到的是 `{ file_path: string; offset?: number; limit?: number }`。

同时，`inputSchema.safeParse(input)` 在运行时校验 AI 返回的原始 JSON。AI 可能返回 `{ command: 123 }`——一个数字而不是字符串。Zod 会拒绝它，管线会返回一个清晰的错误消息，AI 下次可以修正。

一份 Zod schema 定义，两种用途：编译时的类型推断和运行时的数据校验。这种模式你在第一章见过，在工具系统里它发挥到了极致。

## 当时还有什么选择

工具系统不是必须长这样的。让我们看看其他可能的设计。

### 硬编码 switch-case

最直接的方式：一个大 switch 语句，根据工具名字分发到不同的处理逻辑。

```typescript
function executeTool(name: string, input: Record<string, unknown>) {
  switch (name) {
    case 'Bash':
      return executeBash(input.command, input.timeout)
    case 'Read':
      return readFile(input.file_path, input.offset, input.limit)
    case 'Edit':
      return editFile(input.file_path, input.old_string, input.new_string)
    // ... 30 个 case
    default:
      throw new Error(`Unknown tool: ${name}`)
  }
}
```

优点是简单、直接、容易理解。没有抽象层、没有泛型、没有接口。对于原型阶段，这可能是最快的实现方式。

但它的缺点在规模化之后会致命。每加一个工具，你得改这个 switch。校验逻辑、权限逻辑、UI 渲染逻辑全部散落在各个 case 分支里，没有统一的结构。没有类型安全——`input` 是一个松散的 `Record<string, unknown>`，每个 case 分支得自己做类型断言。没有统一的生命周期——某个工具忘了做权限检查，编译器不会告诉你。

### 插件系统（类似 webpack loader）

webpack 的 loader 是一个插件链：每种文件类型经过一串 loader 处理，每个 loader 接收上一个的输出，产生下一个的输入。如果工具系统也设计成这样：

```typescript
const toolChain = [
  inputValidator,
  permissionChecker,
  hookRunner,
  toolExecutor,
  outputFormatter,
]
```

每个阶段是一个独立的"插件"，工具通过注册自己的插件来定义行为。这种设计更灵活——你可以动态插入新的阶段（比如加一个缓存层），也可以让不同的工具走不同的管线。

但灵活性本身是成本。插件系统需要一个注册机制、一个管线调度器、一套插件间通信的协议。调试一个 5 层插件链比调试一个 switch 语句难得多。而且 Claude Code 的工具系统并不需要那种程度的灵活性——所有工具都走同一条管线，管线阶段从来没有需要动态改变过。

### 事件驱动的工具分发

工具调用作为一种事件，监听器根据事件类型做出反应：

```typescript
eventBus.on('tool:call', async (event) => {
  const handler = handlers[event.toolName]
  if (!handler) throw new Error(`Unknown tool: ${event.toolName}`)
  await handler(event.input)
})
```

这种模式在微服务架构里很常见——事件的发送者不关心谁来处理，处理者也不关心谁发了事件。解耦彻底。

但在 Claude Code 里，工具调用不是一种可以解耦的事件。它是一个同步的、有序的、需要返回结果的请求-响应流程。AI 说"执行 Bash 命令 `ls`"，你需要按顺序完成校验、权限、执行，然后把结果原封不动地返回给 AI。事件总线的异步性和解耦性在这里反而是障碍——你需要确保事件处理的顺序，你需要等待处理完成，你需要把结果传回发送方。用事件总线做这些，等于把简单的事情做复杂了。

### 纯函数 Map

没有类、没有接口，只有一堆函数存在一个 Map 里：

```typescript
const tools = new Map<string, {
  schema: ZodSchema
  execute: (input: unknown) => Promise<unknown>
  render: (output: unknown) => ReactNode
}>()
```

这比 switch-case 整洁一点——至少新工具只需要 `tools.set(name, ...)` 而不用改 switch。但类型安全的问题依然存在。`input` 是 `unknown`，`output` 是 `unknown`，每个工具自己负责类型转换。没有编译器帮你检查 `executeBash` 的返回值是不是符合 `renderBash` 的输入期望。

在一个 30 多个工具、每个工具都有特定输入输出类型的项目里，这种"松散 Map + 手动类型转换"的方式会在某个时刻出错，而且编译器帮不了你。

## 为什么选了这个

### 理由一：类型安全不是奢侈品

Claude Code 有 43 个工具目录。BashTool 的输入是 `{ command: string; timeout?: number }`，输出是 `{ stdout: string; stderr: string; exitCode: number }`。FileReadTool 的输入是 `{ file_path: string; offset?: number; limit?: number }`，输出是 `{ content: string; lineNumbers: boolean }`。每个工具的输入输出都不一样。

`Tool<Input, Output, P>` 的泛型设计让每个工具有自己精确的类型，同时保持接口的统一。当你写 `FileReadTool.call(args, ...)` 时，TypeScript 知道 `args` 的类型是 `z.infer<typeof fileReadInputSchema>`——不是 `any`，不是 `Record<string, unknown>`，是精确到每个字段类型的结构。

在一个有 30 多种输入格式的系统里，这种类型安全不是锦上添花。它是防止你在 FileEditTool 里用了 BashTool 的参数类型的唯一保障。纯函数 Map 做不到这一点——它的 `input` 永远是 `unknown`。switch-case 也做不到——每个 case 分支里的 `input` 类型没有区别。

### 理由二：统一的生命周期

校验 → 语义检查 → 权限 → 执行 → 后处理。这个顺序不是随意的。校验必须在执行之前，权限必须在执行之前，hooks 在权限前后都需要运行。如果这个顺序由每个工具自己实现，迟早会有工具忘记某一步。

统一的 `runToolUse` 管线确保了每一步都不遗漏。不管你是内置工具还是 MCP 工具，不管你是只读操作还是破坏性操作，管线都会走完每一步。`Tool` 接口里的每个方法——`validateInput`、`checkPermissions`、`call`——被管线在正确的时机调用，工具不需要操心调用顺序。

这种"框架控制流程、工具填充细节"的模式，比"工具自己控制一切"安全得多。它把容易出错的流程编排从工具开发者手里拿走，放进一个经过充分测试的公共函数里。

### 理由三：扩展不需要碰核心代码

加一个新工具，你需要做什么？在 `src/tools/` 下建一个目录，写一个 `buildTool({ ... })` 定义，然后在 `src/tools.ts` 的 `getAllBaseTools()` 数组里加上它。不需要改 `runToolUse`，不需要改权限管线，不需要改任何核心代码。

MCP 工具更极端——它们甚至不需要在 `tools.ts` 里注册。MCP 服务器启动时发送的工具列表会自动被包装成 `Tool` 接口的实现，无缝插入同一条管线。内置工具和 MCP 工具使用完全相同的执行路径，调用方不需要区分它们。

这种扩展性不是插件系统那种"理论上可以加任何东西"的灵活性。它是一种受控的扩展——你可以加新工具，但不能改变管线本身。管线是稳定的，工具是可变的。这种分界线在 43 个工具、多个外部贡献者的项目里至关重要。

### 理由四：Zod 的双重价值

AI 返回的工具调用参数是不可信的。它可能把 `timeout` 传成字符串 `"5000"` 而不是数字 `5000`，可能忘了传必填的 `command` 字段，可能传了根本不存在的字段。你需要一个强壮的校验层。

Zod 在工具系统里的角色不只是"校验库"。它同时提供了：

1. **Schema 定义**：`inputSchema` 是工具输入的单一真相来源。API 发给模型的工具描述（JSON Schema）从它生成，管线运行时的校验用它执行，TypeScript 的类型从它推断。一份定义，三种用途。
2. **运行时守卫**：`inputSchema.safeParse(input)` 在 AI 返回参数的第一时间校验。如果 AI 发了格式错误的数据，管线会返回一个精确的错误消息，告诉 AI 哪个字段错了、期望什么类型、实际收到什么。
3. **`lazySchema` 延迟初始化**：Zod schema 的构建不是免费的。在一个启动时就要初始化 30 多个工具的 CLI 里，延迟 schema 构建到第一次访问可以加快启动速度。`lazySchema` 就是一个简单的延迟缓存：

```typescript
export function lazySchema<T>(factory: () => T): () => T {
  let cached: T | undefined
  return () => (cached ??= factory())
}
```

三行代码，换来更快的冷启动。这种优化只有在"所有工具都用同一个 schema 模式"的前提下才值得做——如果每个工具有自己的 schema 初始化方式，你很难统一优化。

## 如果重新设计

假设今天从零重写工具系统。同样的需求——30 多个工具、AI 驱动的参数、权限检查、MCP 扩展。核心设计大概率不变。但有些地方可以做得不同。

### 更好的工具组合

当前的 `Tool` 接口是扁平的。一个工具要么支持搜索（`isSearchOrReadCommand`），要么不支持。要么是 MCP 工具（`isMcp`），要么不是。这些能力标记散落在接口的各个属性里。

如果用组合模式替代扁平标记：

```typescript
interface Tool {
  capabilities: Set<'search' | 'read' | 'destructive' | 'mcp' | 'lsp'>
  // ...
}
```

或者更进一步，用 mixin 模式让工具组合不同的能力包。一个"可搜索的工具"自动获得搜索相关的 UI 渲染和权限逻辑。这比在每个工具里重复实现 `isSearchOrReadCommand` 更 DRY。

### 声明式工具定义

当前的工具定义是命令式的——你写一个 JavaScript 对象，里面填满方法。如果工具的核心逻辑足够简单（比如 MCP 工具只是一个代理），一个声明式的定义方式可能更清晰：

```yaml
name: ReadFile
input:
  file_path: { type: string, required: true }
  offset: { type: number }
  limit: { type: number }
permissions: read-only
concurrency: safe
```

用 YAML 或 JSON 定义工具的骨架，框架自动生成校验、权限、UI 渲染的默认行为。只有特殊逻辑（比如 BashTool 的安全沙箱）才需要写命令式代码。

这会让工具定义更紧凑，但也更受限。声明式系统总会在某个地方撞到表达能力的天花板。BashTool 那种复杂的命令语义分析（判断一个管道命令是只读还是破坏性的）很难用声明式表达。

### 工具链（Tool Chaining）

当前的工具执行是独立的——一个工具调用完了，结果返回给 AI，AI 决定下一步。没有"工具 A 的输出自动变成工具 B 的输入"这种链式操作。

如果支持工具链，某些操作会更高效。比如 `Glob → Read` 链：搜索文件名，自动读取找到的文件。或者 `Grep → Edit` 链：搜索匹配行，自动编辑它们。AI 不需要两轮往返，一轮就能完成。

但工具链也带来复杂性。错误怎么传播？权限怎么检查——每个工具独立检查还是整个链一起检查？中间结果怎么缓存？在一个已经 43 个工具的系统里，工具链的组合爆炸可能会带来更多问题而不是解决问题。

## 你怎么看

这一章没有标准答案。几个开放的问题，留给你思考。

**`Tool` 接口是不是太大了？** 它有二十多个方法和属性。有些工具（比如 MCP 工具）只用到其中五六个。接口的庞大意味着工具定义要处理很多不相关的细节。如果把 `Tool` 拆成几个小接口——`Executable`、`Renderable`、`Permissible`——用组合替代继承，会不会更清晰？还是会更零碎？

**`buildTool` 的默认值策略合理吗？** `isConcurrencySafe` 默认 `false`，`isReadOnly` 默认 `false`——这是"假设最危险"的保守策略。但如果某个工具忘了覆盖 `isConcurrencySafe`，它永远不会被并发执行，性能受影响但不会出错。反过来，如果默认值是 `true`（乐观策略），忘了覆盖的工具可能在并发执行时产生竞态条件。哪种策略更合适？有没有更好的方式确保工具定义者显式声明安全属性？

**MCP 工具和内置工具用同一个接口是最优选择吗？** 它们共享 `Tool` 接口和 `runToolUse` 管线，但 MCP 工具有很多特殊处理——`toolOrchestration.ts` 里的并行调度、`mcpInfo` 属性、`inputJSONSchema` 的直接 JSON Schema 支持。这种"表面统一、内部特殊"的设计在 30 个工具时还能管理，如果 MCP 生态爆发到几百个工具呢？

**`runToolUse` 管线是不是过于复杂了？** 它有 1700 多行代码，处理了 Zod 校验、输入校验、hook 执行、权限决策、工具调用、结果映射、错误处理、遥测日志——几乎所有工具系统关注点都在这一个函数里。这是"所有逻辑在一个地方"的好处（容易理解全局流程），还是"函数过于庞大"的坏处（难以理解局部细节）？

这些问题的答案在你读过的源码里。你追踪过 `runToolUse` 的每一行，你看过 BashTool 和 FileReadTool 的实现，你知道管线怎么把它们串起来。你有足够的信息形成自己的判断。

下一章，我们讨论工具系统里最敏感的部分：安全和便利的平衡。权限检查的设计——什么时候问用户、什么时候自动放行、什么时候直接拒绝——是整个工具系统里最需要"工程判断"的地方。
