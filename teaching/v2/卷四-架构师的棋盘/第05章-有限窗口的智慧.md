# 第05章：有限窗口的智慧

你在卷二第八章追踪过压缩的完整流程——从 `shouldAutoCompact` 判断是否触发，到 `compactConversation` 生成摘要，再到 `microcompactMessages` 做渐进清理。你看到了每一步怎么做。但有一个问题我们从未触及：**这么做，值不值？**

上下文压缩的本质，是用信息损失换取空间。你不可能把一段五万 token 的对话无损地塞进两千 token 的摘要里。每做一次压缩，都有东西永远消失。问题在于：消失的是什么？消失的东西重要吗？我们怎么知道？

这一章不谈代码流程。这一章谈选择。

---

## 现状：三层压缩的防御体系

Claude Code 的上下文管理不是一道防线，而是三道。

### 第一层：Microcompact——静默的清道夫

`microcompactMessages` 是最早行动的机制。它不做摘要，不做总结，只是悄悄地把旧的工具结果清掉。当你读了一个文件、执行了一条命令，这些结果占着上下文空间。时间久了，它们变得陈旧而冗余。

时间触发的 microcompact 逻辑很直白：如果距离上一次 assistant 消息已经超过了阈值（`gapThresholdMinutes`），那么服务端缓存已经过期了，反正要重写整个前缀，不如先把旧内容清掉，缩小重写范围。清理方式是把旧的 `tool_result` 内容替换成一个标记：

```typescript
export const TIME_BASED_MC_CLEARED_MESSAGE = '[Old tool result content cleared]'
```

保留最近 N 个工具结果不动，其余全部替换。这个 N 的值由远程配置控制，默认是 `keepRecent` 个。没有 AI 参与，没有 API 调用，纯粹的客户端操作。

### 第二层：Session Memory Compact——结构化的记忆

当 autocompact 触发时，系统先尝试 `trySessionMemoryCompaction`。这不是把对话喂给 AI 做摘要，而是把结构化的 session memory（会话记忆）当作压缩手段——如果 session memory 已经记录了关键信息，就直接裁剪消息，用 memory 的内容替代。

它的配置有一组精心选择的参数：

```typescript
export const DEFAULT_SM_COMPACT_CONFIG: SessionMemoryCompactConfig = {
  minTokens: 10_000,          // 压缩后最少保留的 token 数
  minTextBlockMessages: 5,    // 最少保留的消息条数
  maxTokens: 40_000,          // 压缩后的硬上限
}
```

为什么是 10,000 和 40,000？太小了模型丢失太多上下文，太大了压缩没意义。这两个数字是工程直觉加上大量实验数据的结果。

### 第三层：Full Compact——AI 做摘要

如果 session memory 不可用或不足以释放足够空间，系统才启动完整的 AI 摘要压缩。这是代价最高但也最灵活的方式。它把对话历史喂给一个专门的压缩 agent，让 AI 生成一段结构化的摘要。

压缩提示词要求 AI 输出九个部分：主要请求与意图、关键技术概念、文件与代码段、错误与修复、问题解决、所有用户消息、待办任务、当前工作、可选的下一步。每个部分都有详细的指引。这不是随便写写，而是一份精心设计的模板。

## 当时还有什么选择

在设计上下文压缩时，有几条路可以走。

### 选择一：不压缩，直接截断

最简单的方案。上下文满了，把最老的消息删掉，只保留最近的。不需要 AI，不需要摘要，零额外 API 成本。

这是很多早期聊天系统的做法。问题显而易见：截断是无脑的。如果用户在第一轮说"帮我重构认证模块"，然后进行了五十轮对话，截断会把最关键的指令删掉。模型记得第五十轮的某个 bug 细节，但不记得用户最初要做什么。

### 选择二：滑动窗口 + 向量检索

把旧对话存进向量数据库，每轮开始时用当前输入检索相关的历史片段。理论上很优雅——不丢失信息，只在需要时召回。RAG（检索增强生成）就是这个思路。

问题在于延迟和精度。每次检索需要额外的网络调用或本地计算，而且向量检索不是精确的。在编程助手的场景里，你需要的往往是精确的文件名、具体的错误消息、逐字的用户指令，而不是"语义相近"的模糊匹配。一句话里差一个字，可能就是一个 bug。

### 选择三：AI 摘要压缩

这就是 Claude Code 选择的路。让 AI 读完对话，生成结构化摘要，然后用摘要替代原始对话。代价是一次额外的 API 调用，好处是摘要能保留语义层面的关键信息。

---

## 为什么选了这个

选择 AI 摘要压缩，是基于几个关键的约束。

### 约束一：上下文窗口是硬限制

不管你的模型多聪明，200K token 就是 200K token。超了就是超了，API 会返回 `prompt_too_long` 错误。这是一个物理限制，不是可以优化的东西。你必须在窗口内工作。

### 约束二：编程助手需要精确信息

"大概记得"在聊天机器人里可以接受，在编程助手里不行。模型需要知道确切的文件名、准确的函数签名、具体的错误栈。这排除了截断方案，也对摘要质量提出了极高要求。

### 约束三：延迟必须可控

编程助手是交互式工具。用户敲一个命令，等的是秒级响应。如果每次压缩需要十秒钟的向量检索，用户体验会崩。AI 摘要虽然需要一次 API 调用，但它只在上下文快满的时候触发，不是每轮都做。

### 为什么是三层而不是一层

单靠 AI 摘要，每次都要消耗一次完整的 API 调用，成本高、延迟大。Microcompact 是免费的——它只是本地文本替换。Session memory compact 也是几乎免费的——它利用已有的结构化数据。三层设计让系统在大多数情况下用廉价方案解决问题，只在必要时才动用昂贵的 AI 摘要。

压缩触发的阈值设计也体现了这个哲学。`AUTOCOMPACT_BUFFER_TOKENS` 设为 13,000，意味着系统在离窗口边界还有 13K token 的时候就开始压缩。这个缓冲区给系统留了足够的时间，不会在最后一刻手忙脚乱。

## 如果重新设计

回头看这套设计，有几个值得反思的地方。

### 摘要的单调损失

每次压缩都是不可逆的。你从五万 token 压缩到两千 token，信息损失是永久的。如果用户在压缩后问了一个需要早期对话细节的问题，模型只能从摘要里找，而摘要不可能包含所有细节。

`prompt.ts` 里的摘要模板尝试缓解这个问题——它要求 AI 特别注意"文件名、完整代码片段、函数签名、文件编辑"。但一份两千 token 的摘要不可能装下一万 token 的代码。

一个改进方向是分层摘要：第一次压缩生成详细摘要，后续压缩基于前一次摘要生成，但保留一个"关键事实"的精简列表，穿越所有压缩层次。这会增加摘要的 token 成本，但能减缓信息衰减。

### 摘要质量的不确定性

AI 生成的摘要质量参差不齐。有时候它会遗漏关键信息，有时候它会过度关注不重要的事情。`prompt.ts` 里的 `NO_TOOLS_PREAMBLE` 反复强调"不要调用工具，只输出文本"：

```
CRITICAL: Respond with TEXT ONLY. Do NOT call any tools.
Tool calls will be REJECTED and will waste your only turn
```

这段话之所以这么强调，是因为在某些模型上（注释提到了 Sonnet 4.6），模型有时会在压缩请求中尝试调用工具。这会导致摘要失败——`maxTurns` 设为 1，工具调用被拒绝后，模型没有第二次机会。这不是边缘情况：注释说这在 4.6 上有 2.79% 的发生率。

如果重新设计，可以考虑用一个专门的、更小的模型来做摘要，而不是用主模型。摘要需要的不是创造力，是准确性和完整性。一个小模型可能更适合这种结构化的信息提取任务。

### 缓存与压缩的冲突

压缩会破坏 prompt cache。这是一对矛盾：缓存要求请求前缀保持不变，而压缩的本质是替换前缀。

代码里有一个精巧的设计来缓解这个冲突。`streamCompactSummary` 函数使用 `runForkedAgent` 来执行压缩，这允许压缩请求共享主对话的缓存前缀：

```typescript
const promptCacheSharingEnabled = getFeatureValue_CACHED_MAY_BE_STALE(
  'tengu_compact_cache_prefix',
  true,
)
```

实验数据（注释里提到）证实了这个选择：禁用缓存共享会导致 98% 的缓存未命中，增加约 0.76% 的全舰队缓存创建成本。默认开启是正确的。

如果重新设计，可以探索更激进的缓存友好策略——比如只压缩后缀，保留前缀不变。这正是 `partialCompactConversation` 的 `'up_to'` 方向在做的事情。但部分压缩带来了新的复杂性：哪些消息属于"前缀"，哪些属于"后缀"？用户的对话不是线性叙事，前后之间有复杂的引用关系。

## 你怎么看

上下文压缩不是一个可以"解决"的问题。它是有限资源下的永恒权衡。

200K token 的窗口看起来很大，但在一个深度编程会话里，它很快就会被填满——系统提示、工具定义、文件内容、命令输出、模型的思考过程，每一项都在蚕食空间。压缩不是锦上添花，是呼吸。

Claude Code 的三层设计是一个务实的方案。它用最廉价的手段解决大部分问题，把最昂贵的方案留给最需要的时刻。但它也有代价——信息的单调损失、摘要质量的不确定性、缓存与压缩的内在冲突。

如果你要做一个自己的编程助手，这些问题你也需要面对。窗口永远有限，信息永远在增长。你能做的，不是消除压缩，而是让压缩的损失落在最不重要的地方。

这需要判断力。而判断力，恰恰是最难编码的东西。
