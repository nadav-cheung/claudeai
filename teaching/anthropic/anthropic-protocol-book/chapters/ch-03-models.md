## 3.1 概念全景

### 模型选择的工程哲学

在 2026 年的 LLM 生态中，模型选择已不再是简单的"选最强的那个"。Anthropic 的 Claude 模型家族呈现出一个精心设计的能力阶梯 —— 每一级台阶都在特定维度上做出了有意义的权衡。理解这些权衡的本质，是构建高性价比 AI 应用的基础。

模型选择的三个核心维度是：

1. **能力（Capability）**：模型解决复杂问题的上限。Opus 系列在复杂推理、agentic coding 和多步规划上占据绝对优势；Sonnet 在大多数生产任务中表现接近 Opus 但成本显著更低；Haiku 则在简单分类、摘要和实时交互场景中提供了压倒性的速度优势。

2. **成本（Cost）**：按每百万 token 计价。输入 token 和输出 token 的价差通常为 3-5 倍，这意味着生成密集型任务（如长文写作、代码生成）的成本主要由输出驱动，而理解密集型任务（如文档分析、RAG 检索）的成本主要由输入驱动。

3. **延迟（Latency）**：从发送请求到完成响应的端到端时间。Haiku 的延迟通常只有 Opus 的 1/3 到 1/2，这使得它成为实时聊天、代码补全等交互场景的首选。

这三个维度构成一个不可能三角 —— 没有模型在所有维度上同时最优。工程上的任务是在特定的预算和延迟约束下，找到恰好足够完成任务的最经济模型。

### 动态模型选择的工程价值

在生产系统中，模型不应该是硬编码的常量。一个成熟的 AI 系统应该具备"模型路由"能力：

- 简单问候、FAQ 匹配 → Haiku（$1/$5 per MTok）
- 中等复杂度的客服对话、内容润色 → Sonnet（$3/$15 per MTok）
- 复杂代码重构、多步推理、架构设计 → Opus（$5/$25 per MTok）

一个合理的路由策略能将整体 API 成本降低 40-60%，同时保持最终用户体验不劣化。

### 3.2.3 Token 机制深度解析

#### Tokenizer 原理

Tokenizer 是 LLM 与人类文本之间的桥梁。它将自然语言文本转换为模型可处理的 token 序列。Anthropic 使用 BPE（Byte-Pair Encoding）类 tokenizer，其核心原理是：

1. **训练阶段**：在海量文本上统计字符/字节对的出现频率，高频组合合并为新 token，重复直到词汇表达到目标大小。
2. **编码阶段**：将输入文本从字符级别开始，贪心地应用词汇表中最长的匹配 token。
3. **解码阶段**：将 token ID 序列反向映射回文本。

Claude Opus 4.7 引入了新一代 tokenizer，与旧模型不兼容。重要影响：

- 相同文本在 Opus 4.7 上可能产生多至 35% 的 token。
- 这意味着即使单价相同（$5/$25），使用 Opus 4.7 的实际美元成本可能高于 Opus 4.6。
- **但**：更多 token 意味着模型对文本有更细粒度的理解，这可能是其性能提升的部分原因。

#### 经验性 Token 估算

在实际编程中，没有 Ananthropic 官方 tokenizer 的情况下，可以使用经验规则估算 token 数：

| 语言 | 每 token 约含字符数 | 每 token 约含单词数 |
|------|-------------------|-------------------|
| 英语 | ~4 字符 | ~0.75 词 |
| 中文 | ~1.5-2 字符 | ~0.5-0.8 词 |
| 代码（Python/JS）| ~3.5 字符 | — |
| JSON | ~3 字符 | — |

粗略公式（适用于英语/代码，Opus 4.7 之前模型）：

```
tokens_estimate = len(text) / 4
```

对于 Opus 4.7（新 tokenizer）：

```
tokens_estimate = len(text) / 4 * 1.2  # 留 20% 余量
```

**请求 token 计算**：一次 API 调用的总 input tokens 包括：

```
input_tokens = system_prompt_tokens + messages_tokens + tools_schema_tokens + tool_results_tokens + overhead_tokens
```

其中 overhead 主要来自：
- 每条消息的角色和格式标记（~3-5 tokens / 消息）
- 工具定义的系统提示（使用工具时固定 346 tokens，`any`/`tool` 时为 313 tokens）
- 图片编码 token（根据图片尺寸动态计算）

#### 上下文窗口（Context Window）

上下文窗口是模型在一次请求中能"看到"的总 token 数上限。当前分布：

- **1M tokens**：Opus 4.7、Opus 4.6、Sonnet 4.6 —— 约等于 75 万英文单词或 340 万 Unicode 字符。足以容纳《三体》三部曲的全部内容。
- **200k tokens**：Haiku 4.5、Sonnet 4.5 及更早模型 —— 约等于 15 万英文单词或一部中篇小说。

关键约束：
- 上下文窗口 = 输入 token 上限。输出 token 不计入上下文窗口但受 `max_tokens` 参数限制。
- 超出上下文窗口的请求会返回 `400` 错误。
- Prompt caching 的缓存内容也在上下文窗口内计算。

### 3.2.4 推理参数数学

Claude API 提供三个核心推理参数来控制输出的随机性和确定性。理解它们的精确数学定义和交互关系，是精准调控模型输出的关键。

#### Temperature（温度）

**数学定义**：在 softmax 之前，将 logits 除以 temperature 值 T。

$$P(token_i) = \frac{\exp(z_i / T)}{\sum_j \exp(z_j / T)}$$

其中 z_i 是 token i 的原始 logit（模型最后一层输出的未归一化分数）。

**取值范围**：0 到 1（Claude API 限定）。

**行为分析**：

| T 值 | 效果 | 适用场景 |
|------|------|---------|
| T = 0 | 完全确定性。每次输出相同（给定相同输入） | 代码生成、数学计算、分类任务 |
| T = 0.3 | 低随机性。输出基本一致，偶有措辞变化 | 客服回复、内容摘要、翻译 |
| T = 0.7 | 中等随机性。输出有明显变化但保持连贯 | 创意写作、头脑风暴 |
| T = 1.0 | 最高随机性。logits 原始分布直接用于采样 | 开放式创意生成 |

**与 top_p 的区别**：Temperature 改变的是整个概率分布的"平坦程度"——它直接影响每个 token 的相对概率。而 top_p 和 top_k 是通过截断来限制候选集。

#### Top-p（Nucleus Sampling）

**数学定义**：从概率最高的 token 开始累加，直到累积概率 >= p。仅从这个"核"中采样。

给定概率分布 P = {p_1, p_2, ..., p_V}（已降序排列），选择最小索引 k 使得：

$$\sum_{i=1}^{k} p_i \geq p$$

然后从 {token_1, ..., token_k} 中按比例重新归一化概率后采样。

**p 值含义**：

| p 值 | 效果 |
|------|------|
| p = 0.1 | 仅从最高概率的极少数 token 中采样（非常保守） |
| p = 0.5 | 从覆盖一半概率质量的 token 中采样 |
| p = 0.9 | 从覆盖 90% 概率质量的 token 中采样（广度） |
| p = 1.0 | 无截断（等价于只使用 temperature） |

#### Top-k

**数学定义**：仅保留概率最高的 k 个 token，其余 token 的概率置零，重新归一化后采样。

这是最简单的截断策略：按概率降序排列所有 token，直接取前 k 个。

**典型值**：

- k = 1 → 等价于贪心解码（greedy decoding）
- k = 5-10 → 强确定性，几乎总是选择最可能的 token
- k = 40-50 → 中等随机性
- k = 大值 → 接近无截断

#### 三参数交互关系

三个参数按以下顺序作用于采样过程：

```
原始 logits → Temperature 缩放 → Top-k 截断 → Top-p 截断 → 重新归一化 → 采样
```

**实用建议**：

1. **同时设置 temperature 和 top_p 可能造成冗余**。通常选择以下组合之一：
   - 仅 temperature（最常用）
   - temperature + top_p（精细控制）
   - temperature + top_k（简单截断）

2. **推荐默认值**：temperature = 0.7, top_p 不设置。这是 Claude API 的默认行为，适用于大多数场景。

3. **需要确定性输出时**：设置 temperature = 0。这将使模型始终选择概率最高的 token。

4. **防止退化**：如果输出重复或无意义，降低 temperature 或设置 top_p = 0.9 可以增加输出的多样性。

#### Prompt Caching 盈亏平衡分析

Prompt caching 的核心数学问题是：在多少次缓存读取后，缓存方案的总成本低于不使用缓存的方案。

**场景设置**：假设你有一段 100,000 token 的系统提示/文档需要在 N 次 API 调用中重复使用。

**5 分钟缓存**（写入倍率 1.25x，读取倍率 0.1x）：

| 模型 | 无缓存 N 次成本 | 缓存成本（1 写 + N 读） | 盈亏平衡点 |
|------|----------------|----------------------|-----------|
| Opus 4.7 | N × $0.50 | $0.625 + N × $0.05 | N >= 2 |
| Sonnet 4.6 | N × $0.30 | $0.375 + N × $0.03 | N >= 2 |
| Haiku 4.5 | N × $0.10 | $0.125 + N × $0.01 | N >= 2 |

**推导**：

无缓存成本 = N × base_input_price × 100k / 1M

缓存成本 = cache_write_price × 100k / 1M + N × cache_read_price × 100k / 1M

盈亏平衡条件：缓存成本 < 无缓存成本

→ write_price + N × read_price < N × base_price

→ write_price < N × (base_price - read_price)

→ N > write_price / (base_price - read_price)

以 Opus 4.7 5 分钟缓存为例：

N > 6.25 / (5 - 0.50) = 6.25 / 4.50 ≈ 1.39

结论：**缓存读取 2 次以上即盈利**（实际数学上约 1.39 次，取整为 2 次）。

**1 小时缓存**（写入倍率 2x，读取倍率 0.1x）：

N > 10 / (5 - 0.50) = 10 / 4.50 ≈ 2.22

结论：**缓存读取 3 次以上才盈利**。

**缓存策略建议**：

| 场景 | 推荐方案 |
|------|---------|
| 短时间突发请求（< 5 分钟间隔） | 5 分钟缓存，立即盈利 |
| 周期性请求（每小时几次） | 1 小时缓存 |
| 一次性请求 | 不使用缓存（写入成本无法摊销） |
| 超高频率（每分钟数十次） | 5 分钟缓存 + 持续刷新 |

#### Batch API 折扣

Batch API 提供 50% 的输入和输出折扣，适用于非实时场景：

- 提交后 24 小时内完成处理
- 不支持流式响应
- 可以叠加 prompt caching 折扣

**组合折扣示例**（Opus 4.7 + Batch + Cache Read）：

- 标准输入：$5.00 / MTok
- Batch 输入：$2.50 / MTok（50% off）
- Batch + Cache Read：$0.25 / MTok（Batch 基础上再 0.1x）——仅为标准价格的 **5%**！

这就是 Anthropic 定价模型的精妙之处：通过合理组合缓存和批处理，即使使用最强模型，也能将成本控制在极低水平。

#### Claude Credit Unit (CCU)

CCU 是 Anthropic 在 AWS Marketplace 上的计价单位。

- **换算关系**：1 CCU = $0.01 USD（固定汇率）
- **计价方式**：先按标准美元费率计算 token 费用，再转换为 CCU
- **折扣处理**：折扣通过减少 CCU 计量数量来实现，而非改变 CCU 的美元价值
- **适用范围**：仅用于通过 AWS Marketplace 接入的 Claude Platform on AWS 用户

对于直接使用 Anthropic API 的用户，不需要关心 CCU —— 费用直接以美元计。

#### 实际成本计算示例

**场景 1**：使用 Sonnet 4.6 分析一份 50k token 的代码库，生成 5k token 的分析报告。

```
成本 = 50,000 / 1,000,000 × $3.00  +  5,000 / 1,000,000 × $15.00
     = $0.15 + $0.075
     = $0.225
```

**场景 2**：使用 Opus 4.7 + 缓存处理 1,000 条客服对话。每条 3k 输入 + 0.5k 输出，系统提示 20k token（缓存）。

```
无缓存总成本 = 1,000 × (3,000/1M × $5 + 500/1M × $25)
              = 1,000 × ($0.015 + $0.0125)
              = $27.50

缓存写入 = 20,000/1M × $6.25 = $0.125
缓存读取 = 1,000 × 20,000/1M × $0.50 = $10.00
其余输入 = 1,000 × 3,000/1M × $5 = $15.00
输出     = 1,000 × 500/1M × $25 = $12.50

缓存总成本 = $0.125 + $10.00 + $15.00 + $12.50 = $37.625
```

注意：这个例子中缓存反而增加了成本，因为每条输入的 3k token 相对于 20k 的缓存内容较小，且只有 1,000 条请求。重新计算：

```
无缓存：每条 = 23k tokens 输入 + 0.5k 输出 = $0.115 + $0.0125 = $0.1275/条
缓存：每条 = 3k tokens 非缓存输入($0.015) + 20k 缓存读取($0.01) + 输出($0.0125) = $0.0375/条
加上一次性写入 $0.125
总缓存成本 = $0.125 + 1,000 × $0.0375 = $37.625
总无缓存成本 = 1,000 × $0.1275 = $127.50
```

实际上缓存节省了 $89.875（70% 节省）！上述计算错误已修正。

## 3.5 最佳实践

### 3.5.1 不同场景的模型选择

#### 编码助手 / IDE 补全

**需求**：低延迟（< 500ms 感知时间），单行/多行代码补全。

**推荐**：Haiku 4.5。它的速度优势在此场景中压倒一切。配合 prompt caching 缓存当前文件上下文，可将延迟降至最低。

**例外**：当用户明确需要复杂的多文件重构解释时，路由至 Sonnet 4.6 或 Opus 4.7。

#### 客服机器人

**需求**：中低延迟，稳定的回答质量，成本敏感（每天数万次调用）。

**推荐**：多层路由策略

1. 意图分类：Haiku 4.5（简单分类，T=0，成本极低）
2. FAQ 匹配：Haiku 4.5（检索增强，只需生成简短回答）
3. 复杂问题：Sonnet 4.6（需要推理和多轮对话）
4. 升级/投诉：Opus 4.7（需要高情商和精确表达）

**成本分解**：假设 80% 简单 + 15% 中等 + 5% 复杂，加权成本远低于全部使用 Sonnet。

#### 文档分析与 RAG

**需求**：大上下文窗口，精确的信息提取。

**推荐**：Sonnet 4.6。1M 上下文窗口在此场景中是关键差异因素。Opus 4.7 虽然推理更强，但在大多数文档分析任务上，Sonnet 4.6 的性价比更高。

**缓存策略**：将文档语料预写入 1 小时缓存。对每个用户查询，仅发送查询+缓存指针。

#### 批量数据标注

**需求**：大规模（百万级），非实时，成本极敏感。

**推荐**：Batch API + Haiku 4.5 或 Sonnet 4.6（取决于标注复杂度）。

**成本对比**：
- 标准 API Sonnet 4.6：100 万条 × 2k tokens × $3/MTok = $6,000
- Batch API Sonnet 4.6：$3,000（50% 节省）
- Batch API Haiku 4.5：$1,000（如果标注任务足够简单）

### 3.5.2 成本优化检查清单

1. **先分类，后路由**：用最便宜的模型（Haiku 4.5, T=0）做任务分类，再根据分类结果路由到合适的模型。
2. **缓存一切可以缓存的**：系统提示、示例、文档、对话前缀——任何在多轮请求中重复的内容都应该缓存。
3. **优先使用 5 分钟缓存**：它的盈亏平衡点最低（只需 2 次读取），适合大多数 Web 应用场景。
4. **批量处理离线任务**：任何不需要实时响应的任务都应该走 Batch API，节省 50%。
5. **控制输出长度**：设置合理的 `max_tokens`，不要给模型无限的输出空间。输出 token 价格是输入的 3-5 倍。
6. **监控 token 使用**：在生产环境中记录每次调用的 `usage.input_tokens` 和 `usage.output_tokens`，建立成本仪表板。
7. **警惕 Opus 4.7 新 tokenizer**：如果你的系统 prompt 在 4.6 上刚好合适，在 4.7 上可能超出上下文窗口。升级前务必测试。

### 3.5.3 常见反模式

1. **"所有请求都用 Opus"**：大多数生产任务不需要旗舰模型。Opus 比 Sonnet 贵 67%，比 Haiku 贵 500%。
2. **"缓存反正便宜，随便写"**：每次缓存写入都有成本。只缓存确实会被重复读取的内容。
3. **"先上线，后优化成本"**：模型的成本差异可能是数量级的。上线第一天的成本结构如果不对，后续迁移可能需要大量 prompt 重构。
4. **"temperature 设为 0 就是 100% 确定性的"**：即使 T=0，由于浮点精度和硬件差异，不同运行之间可能存在微小的输出差异。对于需要法律/金融级别确定性的场景，考虑后处理验证。
